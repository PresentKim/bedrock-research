# Ore UI 개요

:::caution[26.64부터 막힘]
리소스팩으로 Ore UI 파일(HTML·JS·CSS)을 바꾸는 길, 곧 서버가 암호화해 보낸 팩과 빈 `content.zipe`를 둔 팩은 26.63까지 동작했다. 26.64에서 Mojang이 보안 문제로 리소스팩의 Ore UI 접근을 막아, 지금은 이 방법으로 Ore UI 페이지를 바꿀 수 없다(출처: 비공개 조사). 이 섹션의 실측은 그 전 판(Windows 1.26.52)의 기록이다. 버튼 스타일 다리와 `pack://` 텍스처는 신뢰 판정을 거치지 않는 통로이고, 26.64에서 다시 시험하지 않았다.
:::

분석 대상은 Windows 1.26.52(`Microsoft.MinecraftUWP 1.26.5203.0`) 설치 폴더, Android 1.26.52.3 네이티브 클라이언트 라이브러리의 엔진 동작 분석, 2026-10-23에 Windows 1.26.52 클라이언트로 Dragonfly 시험 서버가 탐침 리소스팩(평문과 암호화)을 보낸 실측이다. (출처: repo-ore-ui-loading)

## 엔진과 이름

Ore UI를 그리는 엔진은 Coherent Labs의 Gameface다. 예전 이름이 Hummingbird라서 설치 폴더가 `hbui`(HummingBird UI)다. Mojang 개발자가 Q&A에서 "Hummingbird는 GameFace의 옛 이름이고, 새 Bedrock UI를 만들려고 쓰는 UI 기술"이라고 답했다(출처: bedrock-wiki, GameTest Q&A). Gameface는 브라우저가 아니라 게임용 HTML·CSS 엔진이므로 웹 표준 가운데 빠진 것이 있다. 확인한 것은 다음과 같다.

- 일반 `div`에 `click`이 오지 않는다. `mousedown`을 쓴다.
- 여러 값을 받는 단축 속성 안의 `calc()`와 `inset` 그림자는 무시된다.
- `@media`를 쓰지 않는다.
- `min-width: 0`이 듣지 않는다.
- 스크롤 막대를 그리지 않는다.
- `fetch`가 없다.

자세한 목록은 [페이지 환경](./page-environment.mdx)과 [UI 스타일](./style.mdx)에 있다. Bedrock Wiki는 "JSON UI는 Ore UI로 대체되는 중이며, Ore UI는 하드코딩되어 리소스팩으로 바꿀 수 없다"고 적는다(출처: bedrock-wiki, json-ui-intro). 이 섹션의 실측은 26.63까지 그 문장이 평문 팩에는 맞고 암호화 팩에는 맞지 않았음을 보인다. 26.64부터는 암호화 팩도 막혀 Ore UI 파일에 대해서는 그 문장이 맞다.

## 평문 팩이 Ore UI에 닿는 세 통로

1. **버튼 스타일 다리 `vanilla.resourcePackOverrides`**: 엔진이 JSON UI 정의 `common_buttons.light_text_button`·`common_buttons.focus_border`의 변수를 팩 스택에서 풀어 게임 중 Ore UI에 넘긴다. 서버 리소스팩으로 Ore UI 사망 화면 버튼의 배경 텍스처와 글자색이 바뀌는 것을 확인했다 `{실측}`.
2. **`pack://` 텍스처**: Ore UI가 `pack://textures/...png`로 요청한 텍스처는 신뢰하지 않는 서버 팩에서도 풀렸다 `{실측}`.
3. **DDUI 레이아웃 `ddui/root`, `ddui/composition`**: 레이아웃 JSON은 리소스팩 폴더에서 읽는다. 엔진이 게임 내장 팩만 읽도록 걸러서 사용자 팩은 지금 막혀 있다 `{코드}`. 프런트엔드는 "출처 팩이 바닐라가 아닌 레이아웃"을 처리할 준비가 되어 있다 `{코드}`.

Ore UI 파일 요청(`ui://...`)은 설치 폴더로 가기 전에 팩 스택을 먼저 뒤진다. 다만 **신뢰된(trusted) 팩만** 본다 `{코드}`. 평문 서버 팩에 넣은 `hbui/*.css`는 적용되지 않았고, 같은 팩을 암호화해 보내자 적용되었다 `{실측, 1.26.52}`. 암호화 팩의 신뢰 판정은 [로딩 경로](./loading-paths.mdx)에서 다룬다. 26.64부터는 암호화 팩도 Ore UI 파일을 바꾸지 못한다.

## 빈 `content.zipe` (26.63까지)

26.63까지는 로컬 리소스팩 폴더에 빈 파일 `content.zipe`(0바이트)를 넣으면, 키가 없어도 암호화 접근 전략으로 열려 신뢰되었다 `{실측}`. 서버가 보낸 평문 팩에 빈 `content.zipe`를 넣어도 게임 중 Ore UI 페이지가 쓰였다 `{실측}`([리소스팩 전달](../server/resource-pack-delivery.mdx)). 26.64부터는 두 경우 모두 막혔다. 시험 기록은 [Ore UI 페이지 바꾸기](./modifying-pages.mdx)에 있다.

`gameplay.html`의 라우트(`routes.json`): `/gameplay/death`(기본), `/gameplay/bedtime`, `/gameplay/inventory`, `/gameplay/data-driven`(DDUI), `/gameplay/trade`, `/gameplay/block-actors/:id` 등.

`routes.json`의 한 항목은 `fileName`(예: `/hbui/index.html`), `scope`(`in-game`, `out-of-game`), `defaultRoute`, `supportedRoutes[]`(route, regexp, params, transition)를 가진다(출처: ore-ui-customizer-app). 어떤 화면이 Ore UI로 넘어갔는지 확인하려면 설치본의 `routes.json`과 `gameplay-*.js`가 쓰는 facet을 본다.

## 엔진과 통신하는 방식 `{코드}`

Ore UI 페이지는 전역 `engine` 객체의 이벤트로 게임과 대화한다(출처: repo-ore-ui-customizer, 8Crafter 코드 분석).

- facet 구독: `engine.trigger("facet:request", 이름)`을 보내고 `engine.on("facet:updated:" + 이름, cb)`로 받는다. 오류는 `facet:error:이름`, 해제는 `facet:discard`다.
- 쿼리: `query:subscribe/이름`을 보내면 `query:subscribed/id`, `query:updated/id`가 온다. 해제는 `query:unsubscribe`다.
- 라우터: `core:router:push`, `replace`, `go`, `back`, 변경 알림 `core:router:changed`, 현재 상태 `core:router:requestState`.
- facet 이름공간: `core.*`(입력·로케일·라우터·사운드·안전 영역), `vanilla.*`(월드 목록·옵션·리소스팩·렐름), `vanilla.gameplay.*`(화로 진행도, 컨테이너 아이템·크기 쿼리, 사망 정보, 리스폰, 침대, 좌표 HUD 등 13개), `debug.*`, `dev.*`, `test.*`. 전체 162개 이름은 [Customizer 분석](./customizer-tool.mdx)에 있다.
- 게임 중 번들은 아이템·블록 아이콘을 엔진 프로토콜 `geo-item://`로 그린다. 엔진이 그 아이템을 직접 렌더링한다 `{실측}`([아이콘과 컨테이너](./geo-item-and-containers.mdx)). `pack://textures/...png`는 그와 다른 일반 텍스처 경로다. Customizer 앱이 테스트용으로 흉내 낸 쿼리 응답에서는 아이템 이미지가 `pack://textures/items/stick.png` 형식이다. 화로는 `burnProgress`·`litProgress`(0~1), 컨테이너 아이템은 `amount`·`name`·`damageValue`·`maxDamage`·`image` 필드를 가진다.
- 화면마다 JSON UI와 Ore UI 중 무엇을 쓸지 고르는 facet `vanilla.screenTechStack`이 있다(`getTechStackForScreen`, `getPreferredTechStackForScreen`, `selectTechStackForScreen`). 값은 `JsonUI=0`, `OreUI=1`이다. 두 구현이 공존하는 화면에서는 JSON UI 수정이 JSON UI 쪽이 선택됐을 때만 보인다고 본다 `{추론}`. 수정이 보이지 않으면 먼저 그 화면이 어느 쪽으로 열렸는지 확인한다.

## 화면 선택과 문자열 `{코드, 추론}`

- `vanilla.screenTechStack`의 대상 화면 열거는 `PlayScreen="/play"`, `EditWorldScreen="/edit-world"`다. 바이너리에 `OreUI_PlayScreen_OptIn`, `OreUI_EditWorldScreen_OptIn`, `OreUI_PlayScreen_Servers_OptIn` 같은 이름이 있다. 서버 "treatment"로 켜고 끄는 것으로 보인다.
- Windows 1.26.65.1 클라이언트에는 화면 선택기 초기화 객체(`UIScreenTechStackSelectorInitializerAnon`)의 등록 함수가 12개 있다(RTTI 이름 문자열 확인): `registerPlayScreen`, `registerMainMenuScreen`, `registerPreStartScreen`, `registerStartFromTemplateScreen`, `registerEditWorldScreen`, `registerPlayerPermissionsScreen`, `registerSendInvitesScreen`, `registerBedScreen`, `registerSettingsScreen`, `registerSafeZoneScreen`, `registerWishlistScreen`, `registerSearchScreen`. 열거에 적힌 두 화면 말고도 이 화면들이 Ore UI 쪽으로 열릴 수 있는 후보다 `{코드}`.
- 선택기가 실제로 기록하는 경로는 14개다. 위 12개 이름 가운데 RTTI 이름이 없는 화면(`/create-new-world`, `/gameplay/death`)이 더 있다. 경로마다 조건 함수 A와 B가 있다. 조회 핸들러는 사용자 재정의 옵션이 있고 값이 0이 아니면 그 값이 1일 때 참을 돌려주고, 그 밖에는 `A 그리고 B`를 돌려준다. 옵션 열거에는 `DEV_NEW_*_SCREEN_OVERRIDE` 계열 이름이 있지만 이 클라이언트에는 등록 코드가 없어서 기본 결과는 `A 그리고 B`일 가능성이 크다 `{코드, 추론}`. 참을 Ore UI로 보는 것은 `/create-new-world`, `/gameplay/death`, `/gameplay/bedtime`이 두 조건 모두 상수 참이고 Ore UI 화면으로 알려져 있어서 하는 추정이다 `{추론}`. `p3`, `p4`는 기기나 입력 상태에서 오는 값으로 보이나 무엇인지는 모른다.

| 경로 | A | B | 기본 결과 |
|---|---|---|---|
| `/play` | 참 | not(p3 또는 p4) | not(p3 또는 p4) |
| `/main-menu`, `/pre-start` | 서비스 질의 | not(p3 또는 p4) | 서비스 질의 그리고 not(p3 또는 p4) |
| `/create-new-world`, `/gameplay/death`, `/gameplay/bedtime` | 참 | 참 | 참 |
| `/start-from-template`, `/safezone` | 참 | not(p3 또는 p4) | not(p3 또는 p4) |
| `/edit-world`, `/oreui-marketplace/wishlist` | 참 | not(불리언 하나, p4로 보임) | 같음 |
| `/player-permissions` | 참 | 서비스 질의의 부정 | 서비스 질의의 부정 |
| `/send-invites` | 거짓 | 거짓 | 거짓 |
| `/oreui-marketplace/search` | 서비스 질의(원격 기능 플래그 `mc-oreui-search-screen`일 가능성) | not(불리언 하나, p4로 보임) | 서비스 질의 그리고 not(그 불리언) |
| `/settings` 계열 | 경로가 `/settings`일 때만 조건이 달라지고 나머지 분기는 읽지 않았다 | | |

서비스 질의는 `mc-` 접두 원격 기능 플래그와 같은 계열의 서비스로 보인다 `{추론}`. 이 조건 함수들은 리소스팩 정보를 읽지 않는다. 팩이 JSON UI 정의를 바꾸는 것과 별개로, 이 선택이 Ore UI로 나온 화면에서는 JSON UI 정의가 쓰이지 않는다는 것이 코드가 말하는 전부다 `{코드}`.
- 경로 문자열은 `/oreui-settings`, `/oreui-settings/gamma`, `/oreui-marketplace`, `/oreui-marketplace/wishlist`, `/oreui-marketplace/search`, `/oreui-marketplace/redeem`이 있다.
- 세 opt-in 이름(`OreUI_PlayScreen_OptIn`, `OreUI_PlayScreen_Servers_OptIn`, `OreUI_EditWorldScreen_OptIn`)은 각각 이름 문자열 하나를 만들어 서비스 객체의 가상 함수에 넘긴다. 앞의 둘은 이어서 값 0(Play)과 2(Play 서버)를 처리 함수에 넘기고, 셋째는 인자가 2일 때만 `/edit-world` 경로를 만든다. 이름이 서버 쪽 실험 이름으로 쓰인다는 추정은 이 모양과 맞고, 팩이나 월드가 바꿀 수 있는 값이 아니다 `{코드, 추론}`.
- 옵션 이름 `mc-oreui-search-screen`, `mc-oreui-entry-flow`와 개발자 옵션 `DEV_ORE_UI_GAMEPLAY_UI`, `options.dev_enableOreUIEditWorldPreviewButton`이 있다. `options.dev_enableOreUIEditWorldPreviewButton`은 옵션 id 553이 이 문자열을 저장 키 칸에 넣어 등록하고, `DEV_ORE_UI_GAMEPLAY_UI`는 열거 이름만 있고 등록 코드가 없다 `{코드}`. 클라이언트가 켜는 원격 기능 플래그가 `mc-` 접두 이름으로 100개 넘게 한 함수에서 등록된다. 이름만 확인했다.
- 화면 선택 facet(`vanilla.screenTechStack`)을 등록하는 함수가 `selectTechStackForScreen`, `getTechStackForScreen`, `getPreferredTechStackForScreen` 세 이벤트 핸들러를 건다 `{코드}`.
- 내장 팩 목록에는 `resource_packs/oreui` 말고도 `script_ui`("DDUI Built-in Pack")와 `platform_gdk_pc`(texts만)가 있다. 이 둘이 팩 스택에서 일반 리소스팩보다 아래인지 위인지는 모른다 `{코드}`.
- Ore UI 문자열은 내장 `oreui` 팩의 `.lang`에 있다. 엔진이 이 팩을 어디서 여는지는 코드로 찾지 못했다.
- Ore UI 정식 변경 기록에도 "Ore UI 시스템의 여러 줄 글에서 서식 코드 수정" 같은 항목이 나온다(출처: ms-learn 1.26.30 업데이트 노트). Ore UI는 계속 개발 중이라 판마다 바뀐다.

## 남은 것과 한계

- DDUI 레이아웃이 사용자 팩에서 막히는지는 **실측하지 않았다.** `@minecraft/server-ui`의 `CustomForm`을 띄우는 동작 팩과 `ddui/root/custom_form.json`을 넣은 리소스팩으로 시험할 수 있다. DDUI의 팩 필터는 Ore UI 파일 조회의 신뢰 판정과 다른 값을 보므로 암호화해도 열리지 않을 수 있다.
- 메뉴(`index.html`)를 서버 팩으로 바꿀 수 있는지, 서버 접속이 끝난 뒤 언제 원래대로 돌아오는지 시험하지 않았다. 커뮤니티 보고(2026-10-30~11-05)로는 26.63까지 로컬 전역 리소스 팩의 `/hbui/index.html` 교체가 동작했고 게임을 재시작해야 적용되었다(LAN 월드 숨기기, World Filter 등). 26.64부터는 이것도 막혔다.
- 주입 JS에서 facet 읽기와 엔진 호출이 되는지는 시험하지 않았다(DDUI query와 명령은 된다).
- 26.64에서 Mojang이 리소스팩의 Ore UI 접근을 막았다. [로딩 경로](./loading-paths.mdx)의 접근 전략 표는 그 전 판(Android 1.26.52.3)의 분석이다. 26.64 이후 판의 판정 방식은 분석하지 않았다.
- DDUI 팩 필터가 보는 두 표시가 정확히 무엇인지는 확인하지 못했다.
- 분석한 바이너리는 Android 판이고 실측은 Windows 판이다. 엔진 코드는 같다고 보지만 보장하지는 않는다.
