Ore UI는 Coherent Gameface 위에서 도는 React 기반 웹 UI다. 설정, 월드 목록, 로딩, 사망 화면, 게임 중 일부 화면과 스크립트 폼(DDUI)이 이쪽이다. JSON UI와 달리 리소스팩의 JSON으로 배치를 바꾸지 못하므로 "리소스팩으로 정말 못 바꾸나"가 오래된 질문이었다. 이 페이지는 클라이언트 바이너리를 읽어 **파일 요청이 팩을 어떻게 조회하는지**, **어떤 팩이 신뢰되는지**, **JSON UI 버튼 정의가 Ore UI로 넘어가는 다리**, **DDUI 데이터 통로**, **`geo-item://` 아이콘 해석**을 확인한 결과다.


검증 수준은 모두 `코드`다. 컴파일 결과를 읽은 것이라 게임 동작까지 보장하지 않으며, 게임 실측과 다르면 실측을 따른다. 분석 대상은 Android 1.26.52.3 arm64 빌드다. 주소와 내부 함수·클래스 이름 같은 바이너리 세부는 사이트에 싣지 않고 저장소의 `native-notes/`에 따로 둔다. 분석한 코드는 싣지 않고 동작만 한국어로 다시 썼다.

각 발견은 서버·Dragonfly로 탐침 팩을 보내 Windows 1.26.52에서 확인한 실측(`OL`, Ore UI 로딩 조사)과 짝을 이룬다. 바이너리는 "왜 그렇게 되는가"를, 실측은 "실제로 그렇게 되는가"를 답한다.

:::caution[26.64부터 막힘]
NB-17과 NB-20이 설명하는 길(암호화 팩과 `content.zipe` 팩이 Ore UI 파일을 바꾸는 것)은 26.63까지 동작했다. 26.64에서 Mojang이 보안 문제로 리소스팩의 Ore UI 접근을 막았다(출처: 비공개 조사). 이 페이지의 분석은 그 전 판의 기록이고, 26.64 이후 판은 분석하지 않았다.
:::

## 0. 한눈에

- Ore UI 파일 요청(`ui://…`)은 설치 폴더보다 **팩 스택을 먼저** 보지만 신뢰된 팩만 본다. 일반·서버 리소스팩의 `hbui/…`는 쓰이지 않는다(NB-17).
- 암호화 팩 접근 전략은 **언제나 신뢰된다**. 그래서 서버가 아무 콘텐츠 키로 암호화해 보낸 팩, 또는 로컬 팩 루트에 0바이트 `content.zipe`만 둔 팩은 Ore UI 파일을 대체했다(NB-20). 이 길은 26.63까지 동작했고 26.64부터 막혔다.
- 게임 중 Ore UI 버튼의 모양은 `vanilla.resourcePackOverrides`로 JSON UI의 두 정의(`common_buttons.light_text_button`, `common_buttons.focus_border`)에서 넘어온다(NB-18).
- DDUI 레이아웃(`ddui/root`, `ddui/composition`)은 내장 팩 표시가 있는 팩에서만 읽힌다(NB-19).
- 아이템 아이콘 `geo-item://<이름>?width=&height=&id=&bag=`은 JSON UI 아이템 렌더러가 쓰는 `#item_id_aux` 속성 묶음을 받는다(NB-22).

## 1. 파일 요청과 팩 조회

### NB-17 Ore UI 파일 요청은 신뢰된 팩을 먼저 보고, 없으면 설치 폴더에서 연다

질문은 "Ore UI를 리소스팩으로 정말 못 바꾸나"였다(2026-10-23 분석). 실측까지 한 조사 전체는 (`OL`)에 있다.

- 엔진은 요청 경로를 `ui://…`로 맞춘 뒤 파일을 찾는다. `../`·`..\`는 거부한다.
- 팩 스택을 돌며, 팩 접근 전략의 신뢰 검사가 참인 팩에서만 파일이 있는지 본다(이 검사를 신뢰 판정으로 보는 것은 추론). 없으면 `gui/dist/` 아래를 앱 패키지 파일 시스템에서 연다.
- `hbui/routes.json`과 `gui/dist/hbui/fonts`는 설치 폴더에서만 읽는다.
- 서버 팩에 넣은 `hbui/…css`는 적용되지 않았다(`OL` 실측).


## 2. 팩 접근 전략과 신뢰

"팩이 신뢰되는가"는 팩을 읽는 **접근 전략 클래스**가 정한다. 팩 UUID나 manifest는 보지 않는다.

### NB-20 암호화 팩 접근 전략은 언제나 신뢰된다

NB-17의 신뢰 검사를 접근 전략 종류마다 확인했다.

- Zip 팩 접근 전략은 팩이 앱 패키지 안에 있거나 생성 플래그 하나가 켜졌을 때, 폴더 팩 접근 전략은 팩이 앱 패키지 안에 있을 때만 참이다.
- 암호화 파일 접근 전략, 압축 암호화 파일 접근 전략, 암호화 폴더 팩 접근 전략은 **언제나 참**을 돌려준다.
- 팩 UUID나 manifest는 보지 않는다. 서버가 아무 콘텐츠 키로 암호화해 보낸 팩도 신뢰되어 Ore UI 파일을 대체한다(`OL` 7장 실측).
- 폴더 팩은 팩을 만들 때 키 공급자가 있으면 `content.zipe`를 찾고, 있으면 암호화 폴더 팩 접근 전략으로 연다. 로컬 팩 루트에 0바이트 `content.zipe`만 두어도 신뢰되어 Ore UI 파일을 대체했다(`OL` 7장 실측). 이 검사는 파일이 있는지만 보는 것으로 보인다. 팩 파일 종류 판정은 256바이트 미만을 암호화 파일로 보지 않는데, 빈 파일이 통했기 때문이다(추론).
- Zip 팩의 그 플래그는 팩을 만들 때 인자로 정해진다. Zip 팩을 만드는 네 곳이 모두 이 값에 0을 넣으므로, 이 플래그로 신뢰되는 팩은 없다.
- 클라이언트는 콘텐츠 키를 서버가 보낸 키, 엔타이틀먼트, 내장 표에서만 찾는다. 팩 옆 키 파일이나 월드 db는 보지 않는다.


## 3. JSON UI에서 Ore UI로 넘어가는 버튼 정의

### NB-18 `vanilla.resourcePackOverrides`: JSON UI 버튼 정의 두 개가 Ore UI로 넘어간다

- facet은 `definitions`·`lastUpdated`를 낸다. 정의는 `identifier`, `control`, `propertyData[]`(`name`, `value`), `textureData[]`(`identifier`, `path`, `sliceSize`, `uvSize`, `uvScale`)다.
- 엔진이 푸는 정의는 하드코딩된 두 개다: `common_buttons.light_text_button`(텍스처 `$new_ui_button_texture`, 속성 `$text_color`·`$border_color`)과 `common_buttons.focus_border`(텍스처 `texture`).
- 게임 중 번들이 이것을 primary·secondary 버튼의 상태별 `border-image`(`pack://<path>.png?filtering=point`), `color`, `filter`로 바꾼다. 서버 팩으로 Ore UI 사망 화면 버튼이 바뀌는 것을 확인했다(`OL` 실측).


## 4. DDUI

DDUI(`@minecraft/server-ui`의 `CustomForm` 계열)는 스크립트가 만든 폼을 Ore UI가 그리는 방식이다. 레이아웃 로더와 데이터 통로는 다음과 같다.

### NB-19 DDUI 레이아웃은 내장 팩에서만 읽는다

- 엔진은 팩 스택의 `ddui/root`(`minecraft:ui-root`)와 `ddui/composition`(`minecraft:ui-composition`)을 읽고 팩 UUID를 `sourcePackId`로 남긴다.
- 팩 객체의 두 bool 표시 중 하나가 참인 팩만 읽는다. 같은 두 표시가 POI 로더에서 `minecraft:` 이름공간 허용을 가른다(둘 다 거짓이면 `Cannot use minecraft namespace found %s`). 그래서 이 값은 내장 팩 표시로 본다(추론). 사용자 팩의 DDUI 레이아웃은 읽히지 않는다. 실측하지 않았다.

### NB-21 DDUI 데이터 통로와 게임 중 Ore UI 스위치

- 게임 중 번들은 DDUI 데이터를 엔진 query `vanilla.ddui.string/number/bool/object/objectArray`(인자: 저장소, 속성, 경로)로 읽는다. 쓰기는 명령 그룹 `vanillaDduiDataStoreSetCommandGroup`(`setDataStorePathString/Number/Bool`, `dataStoreButtonPress`, `dataStoreCloseButtonPress`)이다. 주입 JS도 `engine.trigger("query:subscribe/<이름>", id, …)`와 `window.__commands__`로 같은 것을 쓸 수 있다(`OL` 9장 실측).
- 바이너리에는 이 query와 명령 그룹, 데이터 저장소의 클라이언트·서버 동기화에 대응하는 타입이 있다. 패킷 `ClientboundDataStorePacket`은 cereal 스키마로 정의되고, 내용은 갱신·변경·삭제 세 종류 중 하나다.
- 아이템 아이콘은 `geo-item://<이름>?width=&height=`이다(`OL` 10장 실측). 해석은 NB-22.
- `vanilla.screenSpecificOptions`의 속성 `devOreUIGameplayUI`는 클라이언트 옵션 하나가 정수 1이면 참이다(1 켬, 2 끔). 이 옵션을 읽는 다른 두 곳은 먼저 전역 설정 객체를 확인하고, 옵션이 1인지 본다. 그중 하나는 인자로 받은 화면 번호가 비트 마스크에 드는지까지 본다(화면 종류별 허용 표로 보인다, 추론). 옵션을 등록하는 곳은 읽지 못했다.
- 기능 토글 표는 (번호, 플라이팅 키, 이름, 기본값)을 등록한다. `mc-enable-sdl-inventory`/`enableSDLInventoryPage`가 그중 하나이고 기본 꺼짐이다.


## 5. 아이템 아이콘 `geo-item://`

### NB-22 `geo-item://`은 JSON UI 아이템 렌더러의 속성 묶음을 받는다

- `geo-item://` 스킴은 `https://`, `paperdoll://`과 함께 등록되고, `geo-item://`과 `paperdoll://`은 같은 처리기를 플래그 하나로 나눠 쓴다.
- 처리기는 요청의 URL 문자열을 아이템 리소스 해석 단계에 넘긴다.
- 해석 단계는 URL의 호스트를 아이템 이름으로 둔다. 쿼리 키로는 `width`, `height`, `id`(정수), `bag`(URL 디코드 후 JSON 값)을 읽는다. 기본 크기는 50이다.
- 아이템 핸들을 만드는 단계는 이름을 아이템 레지스트리에서 찾고, 없으면 빈 핸들을 돌려준다. 있으면 아이템 인스턴스를 만들어 그 id·aux 값을 속성 묶음의 `#item_id_aux`에 넣는다. 다만 **속성 묶음에 `#item_id_aux`가 이미 있으면 넣지 않는다**. 그래서 `bag`으로 준 `#item_id_aux`가 그려질 아이템이 된다. 커스텀 아이템·블록도 그려진다(`OL` 10장 실측).
