이 페이지는 `scripts/gen-rules.mjs`가 `rules/*.json`에서 만든다. 직접 고치지 않고 JSON을 고친 뒤 `npm run gen-rules`를 실행한다. 주제 페이지의 규칙 글머리(`- **[ID]**`)도 같은 원본에서 채워진다.

설명과 예제는 주제 페이지 [바닐라 화면 수정](../../json-ui/modifying-vanilla.mdx)에 있다.

| MOD-01 | `modifications`는 `array_name`, `operation`, `value`(넣을 항목 배열), `where`(지울 항목을 찾는 조건)로 쓴다. 이 프로젝트 출처에서 확인된 `operation`은 `insert_back`, `insert_front`, `remove`다. 바닐라 자신은 `modifications`를 한 번도 쓰지 않는다(팩 전용 기능). 엔진의 연산 이름표는 11가지이고(MOD-23), 나머지 8가지도 Windows 1.26.65.1 실측에서 동작했다(MOD-14). | 작동팩, 코드(바이너리), 바닐라, 실측 | Windows 1.26.65.1 | AP-samples hud_screen.json, BA 2장, BC 4.1, VN 0회, NB-01, 2026-11-18 Windows 1.26.65.1 |
| MOD-02 | `modifications`는 **파일 경로 단위**로 해석된다. 바닐라 파일과 같은 경로의 사본에 쓴 것만 바닐라 정의에 적용되고, 여러 팩의 것이 팩 순서대로 쌓인다. 다른 경로 파일에 쓰면, 팩 자신의 namespace 정의는 새 정의로 읽혀 원래 정의를 대체하고(`Type not specified`, `Unknown property [modifications]`), 바닐라 정의는 조용히 무시된다(FILE-22). Cinnabar 재구성은 이 구분 없이 namespace와 이름만으로 합치지만, 실측을 따른다(충돌 C-46). | 실측 | 모름 | BC-facts, 충돌 C-46 |
| MOD-03 | 게임에서 `modifications`가 닿은 배열은 `controls`와 `bindings`이고, `variables`를 지정하면 무시되었다(BC-facts). 그런데 Windows 1.26.65.1 실측에서는 자기 `variables` 배열이 없는 `thanks_for_testing`의 `text_panel`에 `array_name: "variables"`로 `insert_back`을 하자 `$description_text_line_2`가 `FROM_VARIABLES`로 바뀌었다([주장 실측](../../design/json-ui-claims.mdx)). 두 실측이 어긋나고, 자기 `variables` 배열이 있는 정의는 재지 않았다. 엔진은 `array_name`을 고정 목록으로 거르지 않으므로(MOD-25) `button_mappings` 같은 다른 배열도 해석은 되지만 효과는 실측되지 않았다(충돌 C-64). `target_control` 키는 엔진이 실제로 읽는다(MOD-24). | 실측, 코드(바이너리), 충돌 | Windows 1.26.65.1 | BC-facts, NB-02, NB-03, 충돌 C-10, 충돌 C-64, 2026-11-18 Windows 1.26.65.1 |
| MOD-04 | 대상이 **직접 선언하지 않고 상속만 받은 배열**에 insert하면 새 배열이 생겨 상속받은 내용을 가린다(바닐라 내용이 통째로 사라짐). 그래서 배열을 직접 선언한 정의에 넣는다. 상속받은 배열이 원래 없는 정의(예: 바인딩이 없는 `hud_title_text`의 `bindings`)에 넣는 것은 문제없다. Windows 1.26.65.1에서도 `controls`를 상속만 받은 `server_form`의 `long_form`에 `insert_front`하자 폼 본문이 통째로 사라졌고, `controls`를 직접 선언한 `long_form_scrolling_content`에 넣자 남았다([실측 기록](../../design/json-ui-claims.mdx#62-hud-타이틀)). | 실측, 작동팩 | Windows 1.26.65.1 | BC-facts, AP-samples hud_screen.json, 2026-11-18 Windows 1.26.65.1 |
| MOD-05 | 파생 정의에서 **상속받은 자식 컨트롤**을 `remove`하면 로그도 없이 그 파일의 수정 전체가 적용되지 않는다. 반면 정의가 직접 가진 **바인딩 항목**을 `where`로 지정해 `remove`하는 것은 동작한다. 설정·인벤토리 화면에는 지우면 안 되는 필수 토글도 있다(MOD-16). Cinnabar 재구성은 진단만 남기고 나머지를 적용하지만, 실측을 따른다(충돌 C-47). | 실측, 작동팩 | 모름 | BC-facts, AP 4.4, BW-doc, 충돌 C-47 |
| MOD-06 | 바닐라 컨트롤은 지우지 말고 **바인딩으로 숨긴다.** 숨김 조건을 `#visible` view 바인딩으로 덧붙이거나, 감싼 패널의 가시성으로 가린다. 설정·인벤토리 화면의 필수 토글은 빼면 개발 빌드에서 assert가 나므로 숨기더라도 남긴다(MOD-16). | 실측, 작동팩 | 모름 | BC 6.3-7, BA 2장, AP 4.4, BW-doc |
| MOD-07 | 바닐라 `#visible` 바인딩을 내 조건과 AND로 묶으려면 원래 바인딩을 `remove`(`where`로 지정)한 뒤 `insert_front`로 원래 값과 내 값을 다시 읽어 합친다. | 작동팩 | - | AP 4.4, AP-samples chat_screen.json |
| MOD-08 | 원래 `#visible` 바인딩이 없는 정의라면 `insert_back`으로 view 바인딩만 덧붙여도 숨길 수 있다(바닐라 `long_form`·`custom_form`에 제목 접두사 검사를 붙이는 방식). | 코드(소스) | - | BC 4.1-(1), BW-form, BW-intro |
| MOD-09 | 바닐라 정의를 직접 고치지 않고 **감싼다.** `"래퍼": { "controls": [ { "long_form@server_form.long_form": {} } ] }`는 다른 UI 팩이 `long_form`을 통째로 바꿔도 최종 병합 결과를 참조하므로, 래퍼에 건 가시성 조건이 살아남는다. BA는 2.0.2에서 이 구조로 "UI 팩과 함께 쓰면 화면이 뒤섞이는" 문제를 팩 순서와 무관하게 고쳤다. | 작동팩 | - | BA 2장 |
| MOD-10 | 바닐라 템플릿에 기능을 더할 때는 **기본값이 꺼진 슬롯**으로 넣는다. 예: `common_buttons.focus_border`에 `"$show_hover_content\|default": false`와 `ignored`로 감싼 자식을 추가하면, 그 변수를 켠 버튼에만 영향이 간다. | 작동팩 | - | AP 4.8 |
| MOD-11 | 화면의 내용을 통째로 바꾸려면 화면 정의를 같은 경로 파일에서 재선언해 `$screen_content`를 바꾼다. 바닐라도 `shulker_box_screen@chest.small_chest_screen`, `barrel_screen@chest.small_chest_screen`처럼 같은 방식으로 화면을 만든다. | 바닐라, 실측 | 모름 | VN chest_screen.json:240·258, BC 4.3-(2), BC-facts |
| MOD-12 | 화면 정의를 재선언하면 같은 화면을 재선언하는 다른 팩과는 한쪽만 남는다. 일반 NPC 대화 같은 바닐라 기능도 재선언한 속성(`render_game_behind` 등)을 함께 받는다. 꼭 필요할 때만 쓰고, 바닐라 내용을 감싸 두어 원래 기능이 계속 동작하게 한다. | 작동팩, 추론 | - | AP 4.2 |
| MOD-13 | 여러 애드온이 같은 바닐라 화면에 붙어야 하면 **아무 정의도 하지 않는 `modifications`만** 쓴다. 바닐라 파일에 정의(속성 덮어쓰기 포함)를 쓰면 다른 팩의 같은 정의와 덮어쓰기 경쟁을 한다. Windows 1.26.65.1 실측에서 세 팩이 같은 `main_screen_content`에 건 `insert_back`은 셋 다 들어갔다([주장 실측](../../design/json-ui-claims.mdx)). | 실측, 추론 | Windows 1.26.65.1 | BC 6.3-9, BC-facts, BW-best, 2026-11-18 Windows 1.26.65.1 |
| MOD-14 | 위키가 문서화한 `operation`은 11가지다: `insert_back`, `insert_front`, `insert_after`, `insert_before`, `move_back`, `move_front`, `move_after`, `move_before`, `swap`, `replace`, `remove`. 기준 항목은 `controls`에서는 `"control_name": "이름"`, `bindings`에서는 `"where": { "binding_name": "#x" }`로 찾고, 두 번째 기준이 필요한 `move_after`·`move_before`·`swap`은 `"target": { … }`을 쓴다. `replace`는 `where`로 찾은 항목을 `value`로 바꾼다. 엔진의 연산 이름표도 정확히 이 11가지이고(MOD-23), 두 번째 기준은 `target_control`을 먼저, 없으면 `target`을 읽는다(MOD-24). Windows 1.26.65.1 실측에서 `insert_after`, `insert_before`, `move_front`, `move_back`, `move_after`, `move_before`, `swap`, `replace`가 모두 동작했다. 같은 경로 파일로 `thanks_for_testing`의 `text_panel` 자식을 옮겨 쟀고, 결과 순서는 [주장 실측](../../design/json-ui-claims.mdx)에 있다. `move_before`는 `target`으로, `swap`과 `move_after`는 `target_control`로 동작했고, `insert_back`의 `value`는 객체 하나여도 들어갔다. | 코드(바이너리), 실측 | Windows 1.26.65.1 | NB-01, NB-02, 충돌 C-39, 2026-11-18 Windows 1.26.65.1 |
| MOD-15 | 바닐라 화면에 붙는 지점(진입점)은 **한 곳**으로 모은다. 여러 하위 컨트롤에 각각 `insert`하면 그중 하나의 이름만 바뀌어도 일부가 깨지고, 디버깅할 곳이 늘어난다. 내 컨트롤은 진입점 하나에 넣은 래퍼 패널 안에 둔다. | 추론 | - | BW-best, BW-hud |
| MOD-16 | 설정 화면과 인벤토리 화면에는 엔진이 반드시 있다고 가정하는 토글이 있다(설정의 접근성 탭, 인벤토리의 construction·equipment·items·nature 탭 등). 화면을 통째로 바꾸면서 이 토글을 빼면 개발 빌드에서 assert가 난다. 숨기더라도 남겨 둔다(MOD-06). | 미검증 | - | BW-doc "HardCoded Toggles" |
| MOD-17 | `modifications`는 같은 항목의 일반 속성 병합이 끝난 **뒤에** 적용된다. 한 번의 `modifications` 안에서 뒤 연산은 원래 원소만 고를 수 있어, 앞에서 넣은 원소를 같은 목록에서 다시 옮기거나 지울 수 없다. | 코드(소스) | - | CN |
| MOD-18 | `where`가 객체면 **멤버 하나라도 같은** 첫 원소를 고른다(전부 같을 필요 없음). `where: {}`는 아무것도 고르지 않고, 조건이 없으면 첫 원소를 고른다. 지울 바인딩은 고유한 멤버(`binding_name`)로 지정한다. | 코드(소스) | - | CN |
| MOD-19 | 같은 경로 재선언에서 기존과 **다른 `@base`**를 적으면 기존 정의(타입, 팩토리, 바인딩)가 버려지고 새 정의가 된다. 바닐라 정의의 속성만 바꿀 때는 `@`를 적지 않는다. | 코드(소스) | - | CN |
| MOD-23 | 엔진의 `operation` 이름표는 MOD-14의 11개가 전부다(번호 1~11). 이름은 정확히 같아야 하고, 그 밖의 연산은 없다. 11개 모두 게임에서 동작했고, 나머지 8개는 Windows 1.26.65.1에서 쟀다(MOD-14). | 코드(바이너리), 실측 | Windows 1.26.65.1 | NB-01, 2026-11-18 Windows 1.26.65.1 |
| MOD-24 | 연산 항목의 두 번째 기준은 **`target_control`(문자열)을 먼저** 읽고, 없을 때만 `target`을 읽는다. 엔진이 읽는 항목 키는 `array_name`, `control_name`, `operation`, `where`, `target_control`, `target`, `value`다. | 코드(바이너리) | 모름 | NB-02 |
| MOD-25 | `array_name`은 고정 목록과 비교하지 않고 정의에서 **같은 이름의 멤버**를 찾아 배열이면 대상으로 쓴다. `array_name`이 비어 있고 `control_name`이 문자열이면 `"controls"`로 채우므로, 컨트롤 연산은 `array_name`을 생략해도 된다. 그래서 해석 단계에서는 `controls`·`bindings` 밖의 배열도 대상이 될 수 있다. Windows 1.26.65.1 실측에서 자기 `variables` 배열이 없는 정의의 `variables` 수정은 효과가 있어 이 해석과 맞았고, `variables`가 무시됐다는 이전 실측(MOD-03)과는 어긋난다. | 코드(바이너리), 실측, 충돌 | Windows 1.26.65.1 | NB-03, 충돌 C-64, 2026-11-18 Windows 1.26.65.1 |

## 제안 규칙

아직 본문 규칙으로 합치지 않은 제안이다. 쓰기 전에 근거를 확인한다.

| ID | 규칙 | 수준 | [근거 환경](../rules.mdx#근거-환경) | [출처](../source-abbreviations.mdx) |
| --- | --- | --- | --- | --- |
| MOD-20 | Marketplace 협력형 애드온 공식 지침은 `ui/`와 `font/` 파일 덮어쓰기를 금지한다(여러 애드온이 같은 자산을 함께 고칠 수 없어서). 협력형으로 낼 팩은 MOD-13의 `modifications`조차 피하고 JSON UI 밖의 우회를 먼저 고른다. 근거는 실측이 아니라 정책 문서다. 확인하지 않은 것: 실제 심사에서 `modifications`만 쓴 팩도 거부되는지. | 추론 | - | ms-learn, Guidelines for Building Cooperative Add-Ons |
| MOD-21 | 같은 경로에서 `server_form.long_form`의 `controls`를 바꾸는 서버 폼 팩(Chest-UI, upgrader)은 서로 공존하지 못한다. 두 팩 모두 `long_form`을 같은 경로에서 `@` 없이 재선언하고(`type: panel`, `controls` 두 개) 제목 접두사 검사식으로 바닐라 모양과 자기 화면을 가른다. 팩 순서상 나중 것의 `controls`만 남는다(FILE-21). 공존이 필요하면 MOD-09 감싸기나 MOD-13 `modifications`만 쓰기로 바꾼다. | 작동팩, 추론 | - | CU, UP |
| MOD-22 | 여러 바닐라 컨트롤이 함께 쓰는 텍스처를 교체할 때는 원본을 `_original` 같은 다른 이름으로 복사하고, 바꾸지 않을 컨트롤은 같은 경로 UI 파일의 경로 키(`"부모/자식": {"texture": "textures/ui/text_label_box_original"}`)로 사본에 다시 연결한다. | 작동팩 | - | SP |
