## 개념: 틱과 예산

서버 월드는 1초에 20번(50ms마다) 한 틱씩 세계를 진행한다. **틱 값은 한 틱을 처리하는 데 걸린 시간**이고 50ms가 예산이다. 틱이 50ms를 넘으면 다음 틱이 밀리고 TPS가 20 아래로 떨어진다. 부하율은 대략 틱 / 50ms다(6ms는 약 12%). 대략 25ms(50%) 아래는 여유, 25~40ms는 다른 일(저장, 청크 전송)이 겹치면 가끔 튀고, 40ms를 넘으면 TPS 하락이 보이기 시작한다. (출처: 비공개 조사)

MS Learn의 `server.properties`에서 성능에 직접 닿는 키는 `max-players`(높으면 영향), `view-distance`(기본 32, 높으면 영향), `tick-distance`(기본 4, 범위 4~12), `max-threads`(기본 8, 0이면 가능한 만큼), `compression-threshold`, `compression-algorithm`이다(출처: ms-learn).

## BDS 성능과 스케일링 (커뮤니티)

- **CPU**: 월드 틱은 사실상 단일 스레드라 단일 코어 성능이 핵심이다(EPYC 같은 서버 CPU보다 소비자용 CPU가 낫다). 네트워크와 청크 작업은 다른 스레드에서 돌아서, 사람이 많으면 스레드 5개 이상을 권한다. `max-threads`로 다른 프로세스 몫을 남긴다(예: 4스레드 VPS에서 2). 스크립트 처리 루프도 단일 스레드다. *(확인됨)*
- **수용 인원 보고**
  - "성능을 신경 쓰면" 40~50명. 50~60명이 최선이고 75명은 위험선.
  - 약 $7 OVH VPS에서 80명(모두 약 20청크 안에 모여 있고 스크립트 포함)이라는 주장, 고성능 CPU에서 생성 포함 약 120명이라는 주장.
  - 공유 호스트(Ryzen 9 9900X)에서 35명 넘으면 렉, MSPT는 44명까지 괜찮았다.
  - OVH VPS에서 25명, 7000청크, 19~20 TPS.
  - Endstone에서 엔티티 300개를 한곳에 모아 $4.90 VPS로 약 19 TPS.
  - 병목: 단일 코어, 호스트의 과잉 판매, 애드온/스크립트, 청크 생성, 엔티티 수.
- **최적화 체크리스트**
  - 청크를 미리 생성한다.
  - view distance를 16 이하로 둔다(기본 32).
  - 엔티티/아이템 상한(400~500 정도): 주변 몹을 스택하고 아이템을 병합하는 스크립트, 약 5분 뒤 despawn.
  - SMP는 tick distance 약 4.
  - 스크립트 결과를 캐시하고, VS Code 디버거로 무거운 부분을 찾는다.
  - 플레이어당 RAM 약 250MB.
  - 상시로 도는 `system.run` 루프가 많으면 모든 코어가 튄다. 폴링 방식을 개선한다.
- **로드되는 청크**: render distance가 아니라 simulation distance가 정한다. 한 회원의 측정으로는 sim distance 4가 6보다 CPU를 더 썼다. *(단일 보고)*
- **압축**
  - 기본 `compression-threshold`가 낮다. snappy + 512/1024/2048, 또는 zlib + 약 8192~10240(한 회원은 zlib + 65535)을 권한다. 압축 레벨은 1로 둔다.
  - 접속 패킷과 스킨은 2KB를 넘으므로 이득을 본다.
  - snappy는 일부 기기나 아주 옛 클라이언트에서 접속 실패를 일으킬 수 있다(지금은 드물고, 콘솔은 괜찮다는 보고).
  - snappy가 크래시 봇을 막는다는 효과는 snappy를 구현하지 않은 단순한 봇을 걸러낼 뿐이다.
- **메모리**: 보통 Java 서버의 1/4~1/10이고, 솔로 월드는 1GB 미만이다. 몇 시간에 걸쳐 메모리가 늘면 대개 BP/스크립트 누수다. 정기 재시작(.bat + 작업 스케줄러)으로 우회한다. 호퍼와 경로 탐색이 CPU 핫스팟이다.
- **애드온 하나 때문에 30~60초 멈춤**: 거의 언제나 애드온 탓이니 하나씩 빼 본다. 손상된 청크가 계속 CPU를 잡아먹을 수도 있으니 백업을 복원하고 로컬에서 테스트한다. 큰 애드온 하나를 여러 개로 쪼개면 팩마다 스크립트 컨텍스트가 생겨 오히려 무거워진다(subpack이 낫다).
- **장기 운영 사례**: 1.16부터 돌린 바닐라 월드가 28.8GB, .ldb 16k+개, 540만 청크인데 1.26.21에서도 렉이 없었다. 높은 지연의 rubberbanding에는 클라이언트 권한 이동 설정을 썼다. Starlink CGNAT는 playit.gg 터널로 해결했다.
- **Windows 콘솔 Quick Edit**: 콘솔 창을 클릭하면 서버가 멈추고 입력할 때까지 로그도 멈춘다. Quick Edit을 끈다.
- **기타 관찰**: phantom 스폰 버그 이력(기본 simulation distance를 10으로 바꾸자 플레이어당 약 200마리). `/listd`가 Windows에서 다른 플레이어가 있으면 월드를 크래시시킨다는 보고. 1.26.14.1 Linux의 원인 모를 크래시.

## Dragonfly(v0.11, 패치본)의 스레딩

(출처: 비공개 조사)

- **월드 하나 = 논리 고루틴 하나.** 월드 상태는 `handleTransactions`(world/world.go) 한 고루틴이 큐(`queue`, 버퍼 128)에서 트랜잭션을 하나씩 실행할 때만 바뀐다. `w.Do`/`w.Exec`, 패킷 처리, 틱 모두 이 큐에 들어간다.
  - 틱도 트랜잭션이다: `tickLoop` 가 50ms 티커마다 `<-w.exec(t.tick)` 을 부른다(world/tick.go). 틱이 50ms 를 넘기면 놓친 틱은 건너뛰고(따라잡지 않음) TPS 가 떨어진다.
  - 한 틱: 엔티티 틱(보는 사람이 있는 청크), 예약 틱, 무작위 틱, **틱 범위 안 모든 청크의 블록 엔티티 `Tick` 을 매 틱**(world/tick.go `tickBlocksRandomly`), 이웃 갱신, 레드스톤.
  - 틱 범위: 뷰어(플레이어·로더)마다 `tickRange` 청크 반경(world/world.go). 이 서버는 인스턴스마다 `SetTickRange(LoadRadius)`(기본 4청크, platform/instance/instance.go)를 쓰고, 섬 중심 `NopViewer` 로더와 산 청크마다 1청크 로더(`KeepLoaded`)가 뷰어로 쳐서 **섬은 사람이 없어도 계속 돈다**. 산 청크마다 로더가 있으니 섬 전체(최대 반경 12청크)가 틱 범위다.
- **청크 읽기·생성**은 청크 작업자 고루틴(기본 1개, `ChunkLoadWorkers`, world/chunk_request.go)이 하고, 결과 반영·조명은 월드 고루틴이 한다. **저장은 월드 고루틴에서 동기로 한다**(LevelDB 쓰기, world/world.go `save`).
- **접속**: 세션마다 고루틴 3개(쓰기, 패킷 읽기, 20Hz 백그라운드). 패킷 처리는 결국 그 플레이어가 있는 **월드 트랜잭션 안**에서 한다(session/session.go `handlePackets`). 보내는 패킷은 채널(256)로 넘기고 gophertunnel 이 50ms 마다 묶어 보낸다.
- **월드끼리는 병렬**: 월드마다 큐·고루틴이 따로라 Go 스케줄러가 여러 코어에 나눈다. GOMAXPROCS 를 따로 정하지 않아 모든 코어를 쓴다. 블록 레지스트리 잠금은 등록 때만 잡는다.
- **이 서버**: 로비 1 + 활성 세이브마다 월드 1(`MaxActive` 까지). 인스턴스마다 `run()` 고루틴이 0.2초(`Session.Fast`: WAILA 같은 게이지)·1초(시계, 기간제, `Session.Second`, 자동 저장) 작업을 월드 큐에 넣는다.

### 정리
- **섬 하나의 모든 일은 CPU 코어 하나**에서 돈다. 섬이 여러 개면 코어가 여러 개 쓰인다.
- 한 섬의 비용은 대체로 **틱 범위 안 블록 엔티티 수 × 20회/초**(기계·서랍·호퍼·상자 등)와 그 섬 플레이어의 패킷·청크 전송이다.
- 한 Dragonfly 기반 서버 `Game.sessionOf` 는 `sync.Map` 으로 월드의 세션을 찾으므로 기계·서랍의 `Tick` 마다 불려도 섬끼리 잠금을 다투지 않는다.
- 틱 시간(`World.TickStats`, world/tick_stats.go)은 큐 대기 + 틱 실행 시간이다.

## 부하 시험(`/sgdebug factory`)

모듈 하나(19×11 블록 바닥):
- 채굴 줄: 자동 자원 채굴기(조약돌 기반), 분쇄기 → 호퍼 → 서랍
- 체 줄: 자갈 한 상자 → 호퍼 → 자동 체 → 옆·아래 상자

## 부하 시험과 측정

모듈 하나(19x11 블록 바닥)로 채굴 줄, 체 줄, 9x9 농장을 짓는 시험 명령으로 쟀다. 개발 컨테이너 4코어, 플레이어 1명이 가운데, 짓고 30~35초 뒤 사이드바 값이다.

| 4 | 4 | 20 | 50 | 1.4ms | 2.1ms | 20.0 |
| 25 | 25 | 125 | 330 | 4.2ms | 8.4ms | 19.6 |
| 50 | 37 | 250 | 650 | 7.2ms | 13.7ms | 18.8 |
| 64 | 48 | 320 | 830 | 7.1ms | 13.0ms | 18.4 |

- 틱 범위 안 모듈 하나당 평균 틱은 약 **0.13~0.17ms** 다. 틱 예산 50ms 를 다 쓰기 전(평균 25ms, 절반 여유)이면 이 모듈 기준 **섬 하나에 150개 안팎**(기계 750, 블록 엔티티 2,000)이 한계로 보인다.
- 다만 50개부터 평균 틱이 낮아도 TPS 가 18 대로 내려갔다: 틱 사이에 다른 트랜잭션(0.2초 WAILA, 청크 전송, 자동 저장)과 봇·서버가 같은 4코어를 나눠 쓰는 흔들림이 섞인 것으로 보인다.

- 짓는 순간(블록 수만 개 + 청크 로드)은 틱 최대값이 크게 튄다. 실제 플레이에서는 조금씩 지어서 이런 튐은 없다.
- 실서버 측정: `/sgdebug factory 100` 을 지어도 TPS 20.0, 틱 5.1ms(최대 9.7ms)로 괜찮았다. 더 빽빽한 시험은 `/sgdebug dense <개수>`(2×1 칸 셀, 채굴기·분쇄기·호퍼·서랍)로 한다.
- 실서버 측정: `/sgdebug dense 1000`(채굴기 1000, 분쇄기 1000, 호퍼 1000, 서랍 1000, 블록 엔티티 약 5000)에서 TPS 20, 틱 평균 6ms·최대 9ms. 틱 예산 50ms 의 12~18% 로 서버는 여유가 크다. 대신 **클라이언트에 렉**이 걸린다: 서랍 표시 엔티티 1000개와 커스텀 블록 모델 수천 개를 그리는 렌더링 부담으로 보인다. 섬 크기 한도에는 서버보다 클라이언트 쪽이 먼저 닿는다.

### "틱" 읽는 법
- 월드는 1초에 20번(50ms 마다) 한 틱씩 세계를 진행한다. **틱 값 = 한 틱을 처리하는 데 걸린 시간**(틱 예정 시각부터 끝날 때까지, 최근 5초 평균과 최대).
- 50ms 가 예산이다. 틱이 50ms 를 넘으면 다음 틱이 밀리고 놓친 틱은 건너뛰어 TPS 가 20 아래로 떨어진다.

- 블록 엔티티는 아직 서브청크 요청마다 인코딩한다.

## 접속 시간 기록

플레이어가 접속해 로딩 화면이 닫히면 INFO 줄 하나를 남긴다: `join timing player=... total_ms=... connect_to_packs_ms=... to_start_game_ms=... client_load_ms=...`. 표시는 Login 처리, 리소스팩 완료, StartGame 보냄, 클라이언트의 SetLocalPlayerAsInitialised 네 곳이다. `client_load_ms`(StartGame 보낸 뒤 로딩이 끝날 때까지)는 블록 상태와 퍼뮤테이션 수에 따라 커진다. 팩 내려받기는 라이브러리 안에서 처리돼 따로 보이지 않아 `connect_to_packs_ms`에 로그인부터 팩 완료까지가 합쳐진다. 비교하려면 같은 클라이언트와 기기로 여러 번 접속해 두 번째 접속 값을 쓰거나 클라이언트 팩 캐시를 비운다.

도관을 블록으로 그리는 비용을 잰 값: 엔티티로 그릴 때 `client_load_ms` 4,005, 블록 2개(블록마다 상태 37,249개, 합 74,498)로 그릴 때 9,019(+5.0초). 채운 칸 12,083개에서 FPS는 엔티티 7~20, 블록 184(1% low 60). 블록 상태가 많은 커스텀 블록은 접속 로딩을 늘린다.

## 클라이언트가 먼저 무거워진다

서랍 표시 엔티티 1000개와 커스텀 블록 모델 수천 개가 있는 섬에서 서버는 틱 평균 6ms, 최대 9ms로 여유가 있었지만 클라이언트가 렉을 일으켰다. 섬 크기 한도에는 서버보다 클라이언트 쪽이 먼저 닿는다(출처: 비공개 조사).
