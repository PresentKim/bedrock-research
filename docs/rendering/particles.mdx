# 파티클

## 개념

파티클 시스템은 작은 스프라이트를 많이 띄워 연기, 불, 눈 같은 효과를 낸다. **입자**(particle)는 3D 공간에 놓인 스프라이트 하나이고 자기만의 이동·모양 규칙을 가진다. **방출기**(emitter)는 입자를 한꺼번에(폭발) 또는 시간에 걸쳐(steady) 만들어 내는 장치다. 파티클 파일은 리소스 팩 `particles/` 폴더의 JSON이며, 하위 폴더 어디에 두든 파일 안의 식별자(예: `sample:colored_smoke`, `minecraft:` 네임스페이스는 바닐라 전용)로 참조한다. 모든 단위는 블록(미터)과 초이고 각도는 도(degree)다. 삼각함수도 도 단위다(출처: ms-learn, Particles Introduction; bedrock-wiki `particles/particles`).

## 예제: 횃불 불꽃 파티클

<Excerpt src="ms-learn" title="Introduction to Particles (flame example)" path="creator/Reference/Content/ParticlesReference/ParticlesIntroduction.md">

```json
{
  "format_version": "1.10.0",
  "particle_effect": {
    "description": {
      "identifier": "minecraft:basic_flame_particle",
      "basic_render_parameters": {
        "material": "particles_alpha",
        "texture": "textures/particle/particles"
      }
    },
    "components": {
      "minecraft:emitter_rate_instant": { "num_particles": 1 },
      "minecraft:emitter_lifetime_expression": { "activation_expression": 1, "expiration_expression": 0 },
      "minecraft:emitter_shape_sphere": { "radius": 0.025, "direction": [0, 0, 0] },
      "minecraft:particle_lifetime_expression": { "max_lifetime": "Math.random(0.6, 2.0)" },
      "minecraft:particle_appearance_billboard": {
        "size": [
          "(0.1 + variable.ParticleRandom1*0.1) - (0.1 * variable.ParticleAge)",
          "(0.1 + variable.ParticleRandom1*0.1) - (0.1 * variable.ParticleAge)"
        ],
        "facing_camera_mode": "lookat_xyz",
        "uv": { "texture_width": 128, "texture_height": 128, "uv": [0, 24], "uv_size": [8, 8] }
      }
    }
  }
}
```

</Excerpt>

`basic_render_parameters`가 머티리얼과 텍스처를 정하고, 컴포넌트는 순서와 상관없이 놓는다. 컴포넌트는 방출기용과 입자용으로 나뉜다.

| 종류 | 컴포넌트 (모두 `minecraft:` 접두사) |
| --- | --- |
| 방출기 초기 상태 | `emitter_local_space`, `emitter_initialization` |
| 방출 속도 | `emitter_rate_instant`, `emitter_rate_steady`, `emitter_rate_manual` |
| 방출기 수명 | `emitter_lifetime_looping`, `emitter_lifetime_once`, `emitter_lifetime_expression`, `emitter_lifetime_events` |
| 방출기 모양 | `emitter_shape_point`, `emitter_shape_sphere`, `emitter_shape_box`, `emitter_shape_custom`, `emitter_shape_entity_aabb`, `emitter_shape_disc` |
| 입자 초기 상태 | `particle_initialization`, `particle_initial_speed`, `particle_initial_spin` |
| 입자 움직임 | `particle_motion_dynamic`, `particle_motion_parametric`, `particle_motion_collision` |
| 입자 모양 | `particle_appearance_billboard`, `particle_appearance_tinting`, `particle_appearance_lighting` |
| 입자 수명 | `particle_lifetime_expression`, `particle_lifetime_events`, `particle_expire_if_in_blocks`, `particle_expire_if_not_in_blocks`, `particle_kill_plane` |

## 이벤트

이벤트는 JSON 다른 곳에서 불러 새 파티클이나 사운드를 낸다. 형식은 `emitter`(이벤트 위치에 fire-and-forget으로 방출기를 만든다), `emitter_bound`(생성한 방출기가 액터·로케이터에 묶여 있으면 같은 곳에 묶는다), `particle`(이벤트 위치의 `effect` 방출기에 입자를 수동으로 낸다. 방출기가 없으면 만든다. 대상은 `emitter_rate_manual`이어야 한다), `particle_with_velocity`(생성한 입자의 속도를 이어받는다)다. 사운드는 "level sound event" 이름을 지정한다. 이벤트는 `sequence`(배열을 순서대로, 발동 시 모두 실행)와 `randomize`(가중치 `weight`로 하나 선택)를 중첩할 수 있다(출처: ms-learn, Particle Effect Events).

```json
"event_name": {
  "sequence": [
    { },
    { "randomize": [ { "weight": 1.0 }, { "weight": 3.0 } ] }
  ]
}
```

위는 게임에서 확인하지 않은 예제다. MS Learn 문서의 구조(노드 트리 안에 `sequence`와 `randomize`를 임의로 중첩)를 줄인 골격이며, 각 노드에 들어가는 이펙트·사운드 키는 대상 버전의 레퍼런스로 확인해야 한다 `{실측 필요}`.

## 시계는 넷이다 (Particle Jester 정리)

(출처: particle-jester, MIT. 저장소는 게임 실측을 하지 않았다.)

- 방출기 방출 속도, 방출기 수명, 입자 수명, 애니메이션 수명은 서로 다른 시계다. `emitter_lifetime_once.active_time: 2`에 입자 `max_lifetime: 3`이면 마지막 입자는 생성 뒤 약 5초까지 남는다. `active_time`의 단위는 초다.
- 방출 속도 컴포넌트는 하나만 쓴다. 한 번에 뿌리기는 `rate_instant`, 계속 뿌리기는 `rate_steady`, 이벤트가 입자를 요청하는 대상은 `rate_manual`이다. 이벤트 종류 `particle`과 `particle_with_velocity`는 manual 방출기를 대상으로 한다.
- 이벤트 노드를 순서대로 나열해도 지연이 생기지 않고 한꺼번에 실행된다. 단계 사이 시간은 타임라인 항목이나 스크립트·애니메이션 시계로 만든다.
- 자식 이펙트는 부모 방출기의 변수를 이어받지 않는다. 자식에 기본값을 주거나 두 이펙트를 같이 초기화하는 쪽에서 넘긴다.

## 크기, 좌표, UV 계산

- 빌보드 `size`는 **반 크기**다. `[0.5, 0.5]`가 한 블록이다. 텍스처 안의 투명 여백까지 생각해야 눈에 보이는 크기가 맞는다. `emitter_shape_box`의 크기도 반 크기라 `[12,7,12]`는 24x14x24 블록이다.
- 모델 로케이터는 모델 단위(16이 1블록), 파티클은 블록·초 단위, Molang 삼각함수는 도 단위다.
- 원판 위 균일 분포는 반지름에 `R * math.sqrt(random)`, 구 표면 균일 방향은 `y=2u-1, rho=sqrt(1-y*y)`처럼 무작위 값을 변환해 쓴다. 갱신 식에서 `math.random`을 매번 부르면 떨리므로 입자마다 고정되는 `variable.particle_random_1`~`4`를 쓴다.
- UV의 `texture_width`와 `texture_height`는 좌표계일 뿐 PNG 픽셀 수와 같을 필요가 없다. 픽셀로 바꿀 때 가로는 `PNG 너비 / 선언 너비`, 세로는 `PNG 높이 / 선언 높이`를 곱한다.
- 직선 `step_UV`는 다음 줄로 넘어가지 않는다. 격자 아틀라스는 식으로 칸을 고르거나 띠를 여러 개 쓴다. 칸 번호 `i`에서 `u = (i % 열수) * 칸너비`, `v = floor(i / 열수) * 칸높이`다.
- 틴트는 텍스처 RGB에 곱해진다. 빨간 그림에 파란 틴트를 주면 거의 검게 된다. 색을 바꿔 쓸 텍스처는 흰색으로 그린다.
- 재질: `particles_alpha`는 투명을 잘라 내고(컷아웃), 부드러운 반투명은 `particles_blend`, 빛나는 겹침은 가산 재질(`particles_add`)이다. 왜곡 효과에는 블렌드 모드 "exclusion"이 있다. 파티클 머티리얼은 매우 제한적이고 평평한(언릿) 파티클 머티리얼이 없다. 필요하면 엔티티를 쓰거나, fog가 고르게 적용되도록 큐브 대신 파티클 구를 만든다. `particles_add`는 `entity_beam_additive`의 파티클판이다. 글로우는 가산 머티리얼에서 나오고 주변을 밝히지 않으며, 반투명 텍스처에서는 스프라이트 안에서만 빛난다. 파티클 커스텀 머티리얼은 블렌드 모드와 컬링만 부분적으로 먹는다.
- 양면 파티클: 머티리얼 파일 이름은 정확히 `particles.material`이어야 하고(아니면 "material invalid"), `"particles_twoface_alpha:particles_alpha": {"+states":["DisableCulling"]}`처럼 정의해 `basic_render_parameters.material`에서 참조한다. `particles_blend`도 같은 방식이다. `emitter_transform_xz` 파티클이 아래에서 안 보인 원인도 뒷면 컬링이었다.
- 예제 충격파는 링을 텍스처 반지름의 0.85 지점에 그렸기 때문에 크기 식을 `0.85`로 나눴다. 나누지 않으면 8블록이어야 할 링이 6.8블록으로 보였다.

## 문서끼리 어긋나는 곳 (Particle Jester 대조)

| 주제 | 어긋남 | 저장소가 따른 쪽 |
| --- | --- | --- |
| `max_frame` | 빌보드 레퍼런스는 첫 프레임이 1이고 `max_frame`이 최대 프레임 번호라고 한다. 튜토리얼은 0부터 세서 8칸에 7을 쓴다. 바닐라 `basic_smoke.json`은 8칸에 8을 쓴다. Wintersky 1.3.3은 0부터 센 내부 프레임이 `max_frame`에 닿으면 처음으로 돌아간다 | 8칸 불꽃에 `max_frame: 8`. 옛 튜토리얼 문구만 보고 기존 팩의 값을 틀렸다고 고치지 않는다 |
| 방향 모드 이름 | 레퍼런스 본문은 모드 값으로 `custom_direction`을 쓴다. 고정한 Mojang 메타데이터와 실제 정의는 `mode: "custom"`에 벡터를 `custom_direction`에 둔다 | `mode: "custom"` |
| 카메라 모드 키 | 문서 주석의 `face_camera_mode`는 오타이고 실제 키는 `facing_camera_mode` | `facing_camera_mode` |
| 파티클 `format_version` | 바닐라 예제에 `"1.10.0"`이 그대로 있다. 게임 버전으로 바꾸지 않는다 | `"1.10.0"` |

이 표는 저장소가 문서와 바닐라(bedrock-samples 46ba6ea)를 대조한 결과다 `{레포 주장}`.

## 형식과 텍스처 규칙 (커뮤니티 조사)

(출처: 비공개 조사)

- 빛나는 VFX에는 `particles_alpha`나 `particles_add`, 고품질 PNG 텍스처, 크기·페이드 곡선을 쓴다. `particles_alpha`는 알파 테스트라 반투명에는 `particles_blend`를 쓴다. 원점이 블록 안일 때의 어두움은 fog 때문일 가능성이 크다. 파티클 effect `format_version: 1.26.0`이 허용된다.
- 파티클 텍스처는 2의 거듭제곱(4~16 px)이어야 하고, 아니면 Snowstorm·Blockbench에서는 괜찮아도 게임에서 깨진다. 분홍-검정 사각형은 잘못된 텍스처 이름이나 `uv`다. `particle_appearance_billboard`의 `uv`는 `texture_width`, `texture_height`, `uv`, `uv_size`를 쓰고, 텍스처 없음 표시는 최근 분홍과 검정으로 바뀌었다. 폴더의 중복 파티클 파일은 로그 경고 없이 텍스처를 빠뜨렸고, offset이 있는데도 요구한다는 오류는 파티클 식별자 중복일 가능성이 크다. 파티클은 텍스처를 반복할 수 없으니 1024x1 점선 텍스처를 쓴다. `texture_width`와 `texture_height`가 실제 시트 크기와 같아야 한다는 커뮤니티 보고는 위 "크기, 좌표, UV 계산" 절의 설명(좌표계일 뿐)과 어긋난다(`conflicting`). `uv_size`가 맞지 않으면 늘어난다. 텍스처 밖을 샘플링하거나 조건에 따라 텍스처를 바꿀 수 없으니 UV 오프셋을 쓴다. 바닐라 시트 `textures/particle/particles`는 경로로 참조하고 UV로 칸을 고른다. `particle_appearance_tinting`에는 `[r,g,b,a]` 단색도 쓸 수 있다.
- 방향: 빌보드 `direction`의 유효한 모드는 `"custom"`(`custom_direction: [x,y,z]`)이다. 모드로 `"custom_direction"`을 쓰면 "The 'direction' sub section is not using a valid mode!"가 난다. `direction`은 `particle_appearance_billboard` 안에 있어야 한다. `custom_direction`의 `direction_z`는 정규화된 y의 절댓값이 0.999보다 크면(약 2.5625도) 수평면으로 스냅된다. 플레이어 움직임에 따라 파티클이 회전하지 않게 하려면 `facing_camera_mode`를 `lookat_*`에서 `direction_x`, `direction_y`, `direction_z`로 바꾼다. `facing_camera_mode: direction_x` 단일 빔이 안 보인 예시(JSON 1.10.0, `particles_alpha`)는 미해결이다.
- 수명과 단위: 충돌 시 사라지는 파티클은 `particle_motion_collision`의 `expire_on_contact`, 또는 공기를 지정한 `expire_if_not_in_blocks`다. 로컬 공간은 `"minecraft:emitter_local_space": {"position": true}`다(Snowstorm 토글). 로케이터 지오메트리에 남은 16x16 평면이 파티클을 깨뜨린 사례가 있다.
- 궤도와 구: `particle_motion_parametric`(방출기 기준 Molang 오프셋)으로 궤도를 돌리고, 구 방출기는 `emitter_shape_sphere`를 쓴다. 바닐라 파티클은 bedrock-samples `resource_pack/particles`에 있다(TNT: `large_explosion_level`, `huge_explosion_level`). TNT·폭발 파티클 정의는 samples에 없다는 보고(하드코딩일 수 있음, 스크립트 API로 생성 가능)도 있다. 잔류 포션 구름은 `minecraft:mobspell_lingering`이다.
- 바닐라 파티클 id에는 네임스페이스가 필요하다(`minecraft:basic_smoke_particle`). 예: `minecraft:water_splash_particle_manual`, `water_evaporation_manual`, `magical_critical_hit_emitter`, `heart_particle`(번식 하트와 구분할 수 없음). 바닐라 파티클은 덮어쓸 수 있고 `num_particles` 0으로 끌 수 있다(폭발, 토템). 거품처럼 동작을 바꾸려면 같은 모양의 커스텀 파티클을 만든다.
- 블록 파괴 파티클 템플릿: `emitter_rate_instant`에 `Math.random(15,30)`, `emitter_lifetime_once`, `particle_motion_dynamic`(가속 -9.8과 drag), `particle_motion_collision`, 16x16 안의 무작위 UV, `particle_appearance_lighting`.
- 이벤트 타이밍: `minecraft:emitter_lifetime_events`의 `creation_event`가 불안정했고 `minecraft:particle_lifetime_events`의 `"timeline": {"0.0": "ring"}`으로 해결했다. 팩 설정 토글은 `"num_particles": "(1) * q.is_pack_setting_enabled('hooked:ding')"`와 manifest `settings`로 만든다. `sound_effect.event_name`은 individual_event_sounds에 있는 이름이어야 한다.

## 엔티티와 파티클 연결

**개념**: 엔티티에 붙는 파티클은 (1) 지오메트리의 로케이터, (2) 애니메이션 또는 컨트롤러의 파티클 키프레임, (3) 클라이언트 엔티티 `particle_effects`의 짧은 이름, (4) 실제 파티클 식별자 순서로 이어진다. 키프레임은 별칭을 쓰고 `/particle`과 스크립트는 식별자를 쓴다. 파일 이름은 식별자가 아니다.

```json
"particle_effects": { "tank_particle": "particle:tank_firing" }
```

```json
"particle_effects": { "0.0": { "effect": "tank_particle", "locator": "muzzle" } }
```

첫 블록은 클라이언트 엔티티, 둘째 블록은 애니메이션 파일의 키프레임이다(출처: bedrock-wiki `visuals/animation-effects`와 private-research). 루프 플래그가 계속 방출하게 한다. 엔티티를 따라가되 복제되지 않게 하려면 파티클에 `emitter_local_space`의 `position`과 `rotation`을 true로 준다. 이미터는 엔티티의 애니메이션에서 생성돼야 한다. 계속 도는 효과는 컨트롤러 상태가 맡게 하고, 반복 애니메이션에 무한 루프 방출기를 걸면 방출기가 쌓인다 `{레포 주장}`. 사슬 전체는 BP 트리거, 클라이언트 애니메이션 별칭 또는 컨트롤러, 상태·애니메이션, 파티클 키프레임, `particle_effects` 별칭, 식별자, 텍스처 순이다.

- 1인칭·페이퍼돌 중복: 애니메이션·컨트롤러에 `!q.is_in_ui && !v.is_paperdoll`(또는 `!(v.is_paper_doll || q.is_in_ui)`) 조건을 준다. VV에서는 플레이어 그림자에서도 파티클이 재생될 수 있다. `q.is_first_person`, `v.is_first_person`으로 1인칭에서 파티클을 숨기는 것은 동작하지 않는다는 보고(모든 카메라에서 1.0)가 있고, 페이퍼돌을 켜면 1인칭과 3인칭 파티클이 둘 다 생긴다. 이미터 생성식도 중복 이미터를 만들었다. 대안은 스크립트로 설정한 BP property를 리소스 팩에서 읽는 것이다.
- 변수 전달: 파티클은 플레이어·엔티티의 사용자 변수를 읽을 수 없다. 엔티티에서 파티클로 Molang 변수를 넘길 수 없게 됐고 `q.self`와 `q.get_nearby_entities`가 제거됐다. 파티클은 주로 서버 측 쿼리(`q.property`, `q.position`, `q.variant`)는 읽지만 클라이언트 전용은 못 읽는다. 커스텀 엔티티 property를 파티클에서 조회한다(BP `player.json` 필요). 플레이어에 붙은 파티클은 액터 property(엔티티당 32개, 각 float 하나)를 조회할 수 있고, 로컬 위치를 끄고 parametric motion을 월드 좌표로 쓰면 자유롭게 움직이며 1인칭에서도 렌더링된다.
- 위치·로케이터 쿼리: 파티클 자신의 위치는 알 수 없다(`q.position`은 0). `query.bone_orientation_trs`는 클라이언트 엔티티에 `queryable_geometry`가 필요하고, `query.get_locator_offset`과 `get_root_locator_offset`은 있지만 로케이터 쪽은 불안정하다. 파티클 `pre_effect_script`에서 `query.bone_orientation_trs('leftarm')`은 첫 등장 때 "called without an animation component set"을 낸다. `query.bone_orientation_trs('x').rotation.z`는 "found multiple operations without a combining operation"을 내니 변수에 저장한 뒤 `.r.z`를 읽는다. 두 엔티티 로케이터 사이의 선은 월드 공간 수식이 필요하다. 파티클에서는 스텐실, TRS 쿼리, 카메라 쿼리를 쓸 수 없다.
- 엔티티에 붙인 parametric: 엔티티에 붙은 이미터의 `particle_motion_parametric`은 월드 좌표를 써서 원점에 생기니 상대 위치를 켜거나 `q.position`을 쓴다. 파티클은 월드보다 1프레임 늦게 렌더링되므로(한 프레임에 평가, 다음 프레임에 렌더) 빠른 엔티티·카메라를 늦게 따라간다.
- 두 엔티티 연결 불가: 리드·가디언 빔처럼 두 엔티티에 붙일 수는 없고 스크립팅으로 근접할 뿐이다. 승객 엔티티에 붙은 파티클은 1인칭에서 렌더링되지 않는다. 플레이어에 탑승하는 커스텀 엔티티는 `parrot_tame` 패밀리로(앵무새 자리를 차지) 가능하다.

## Script API로 파티클 띄우기

- `Dimension.spawnParticle(id, location, MolangVariableMap)`은 **고정된 월드 위치**에 방출기를 만든다. 핸들을 돌려주지 않고 엔티티에 붙지도 않는다. 엔티티를 따라가는 효과는 클라이언트 엔티티의 애니메이션 로케이터나 컨트롤러 상태로 만든다(출처: particle-jester).
- `MolangVariableMap`의 펼침 규칙: `setVector3`는 `.x/.y/.z`, `setColorRGBA`는 `.r/.g/.b/.a`, `setSpeedAndDirection`은 `.speed/.direction_x/.direction_y/.direction_z`다. `new MolangVariableMap().setFloat("name", v)`로 설정한 변수는 파티클 JSON에서 `v.name`이나 `variable.name`으로 쓴다. `emitter_initialization.creation_expression`에서 다시 대입하면 0으로 리셋되니 하지 않는다. 파티클 초기화가 Molang 초기화 뒤에 실행되므로 MolangVariableMap 변수는 파티클 안에서 정의할 수 없다.
- 예제 BP는 `/scriptevent pm:vfx` 뒤에 `portal`, `blizzard`, `explosion`, `boss` 중 하나를 받아 시작 위치를 복사해 두고, 단계마다 `system.runTimeout`을 건 다음 실행 직전에 엔티티 유효성·차원·`isChunkLoaded`를 다시 확인한다. 플레이어가 나가거나 엔티티가 죽으면 남은 예약을 지운다. 이미 뿌린 입자는 자기 수명대로 사라진다.
- 품질 입력 `variable.quality`(0.4~1.5)를 `setFloat`로 넘기고 파티클 JSON은 `rate * (variable.quality ?? 1)`로 받는다. `/particle`로 띄우면 값이 없어서 1이 된다. `??` 연산자를 엔진이 받는지는 저장소도 대상 버전에서 확인하라고만 적는다 `{실측 필요}`.
- 이벤트로 변수 전달("temp leaking"): `event: { sequence: [ {expression: "t.a=v.some_var;"}, {particle_effect: {..., pre_effect_script: "v.some_var=t.a;"}} ] }`. 이것은 의도치 않은 버그라 깨질 수 있다. 반면 파티클 수 쿼리로 방출 후 파티클을 제어하는 것은 안정적이고 의도된 기능이다(veka). 파티클 수 쿼리는 데이터 사이드 채널로 쓸 수 있다.
- 하위 이미터로 변수 넘기기: 부모의 expression 이벤트로 `variable`을 `temp`에 담고, 자식의 `pre_effect_expression`에서 `t.x`를 `v.x`로 옮긴다. `t.vec1.x` 같은 점 이름은 "temp variables only on their own" 오류를 내니 `t.vec1x`를 쓴다. 자식 변수도 자식 안에서 초기화하고, 변수는 이미터별 지역 변수다.
- Molang JIT: 무거운 파티클은 처음 생성될 때 멈칫한다. temp 변수로 구조체를 만들 수 없어서 16항목 temp 변수 256개와 삼항식 이진 탐색으로 배열을 흉내 낸 사례가 있다. `single report`
- `t.`와 `v.`: 프레임을 넘어 유지돼야 하는 데이터에 `t.`를 쓰지 않는다. `t.last_offset_index`를 `v.`로 바꾸자 `spawnParticle`과 `MolangVariableMap`으로 그린 다중 파티클 블록 외곽선이 고쳐졌다.
- 파티클별 값: 방출기 하나에서 파티클마다 다른 값(크기)은 파티클 수명에 데이터를 인코딩한다(veka 제안). 오프셋 트릭: `emitter_initialization.creation_expression "v.i = 0;"`과 `v.i`를 증가시키는 `emitter_shape_point.offset` 식. `creation_expression` 카운터나 `particle_initialization.per_render_expression`으로 `emitter_shape_point.offset`을 파티클별로 주는 것은 예상대로 되지 않았다(미해결).
- 강제 만료: `particle_lifetime_expression.expiration_expression`에서 수를 비교한다. 예: `MolangVariableMap`으로 `variable.particle_count = 2`를 주고 생성하면 `q.effect_emitter_count < q.effect_particle_count`가 참이 된다. 같은 조건으로 `emitter_lifetime_expression.expiration_expression`도 추가해야 이미터가 파티클과 함께 끝난다. 플레이어별 파티클(`player.spawnParticle`)이면 만료가 단순하다. `query.any_tag`는 엔티티 `/tag`가 아니라 아이템·블록 태그를 조회하므로 만료 트리거로 쓸 수 없다.
- 카메라·LOD 쿼리: 파티클에서 `q.distance_to_camera`는 되지만 `q.rotation_to_camera(...)`는 안 된다. 만료식으로 `q.lod_index(10,20) == 1`은 됐지만 `q.lod_index(10) >= 1`은 안 됐고 `q.distance_from_camera > 50`은 즉시 만료됐다. 파티클의 `query.position`은 FPS와 관계없이 40 Hz로 갱신되고 `query.log`는 개발 빌드 전용이다. `q.camera_rotation`이 1인칭에서 0이라는 보고도 있다(결론 없음).
- **메모리 누수**: `emitter_rate_manual`에 `max_particles`가 없으면 크게 새서 FPS가 회복되지 않으니 항상 지정한다(최대 1000). 커스텀 트레일 파티클이 RAM을 새게 한 것처럼 보인 사례(이미터 미삭제 의심)는 미해결이다.
- 사운드: 파티클 이벤트는 바닐라 사운드 이벤트만 쓸 수 있고, 파티클에서 새(커스텀) 사운드를 재생하는 것은 지원되지 않는다(MCPE-101714). 커스텀 사운드가 필요하면 스크립트로 재생한다. 클라이언트 측 틱당 생성 확률, 변수로 정하는 파티클 수명 질문은 답이 없었다.

## 렌더링 특성과 기법

- 깊이: `particles_blend` 파티클은 뒤 파티클이 앞 파티클 위에 그려질 수 있다. 깊이는 한 방출기(또는 그것이 생성한 방출기) 안에서만 동작하고 별개 방출기 사이에서는 안 된다. alpha_test 파티클은 이 문제가 없지만 블렌딩이 없다. 복셀·3D 큐브 파티클에서 알파 테스트는 단면이니 블렌드 머티리얼을 쓴다. blend(fog)와 add(반딧불이) 파티클 사이의 깜빡임은 미해결이다. 같은 위치에 겹친 파티클의 그리기 순서는 지정할 수 없으니 Molang으로 위치를 조금 어긋나게 한다.
- 한계: 파티클은 벽 너머로 보일 수 없고, 시뮬레이션 거리 밖에서 렌더링되지 않으며, 텍스트를 넣을 수 없다(이름이 있는 엔티티나 떠 있는 텍스트를 쓴다). 카메라를 향하지 않는 떠 있는 텍스트·빌보드는 미해결이다. 파티클 머티리얼에서 `"-defines": ["ENABLE_FOG"]`로 fog를 없애는 것은 안 됐고 fog는 파티클도 물들인다. 파티클 렌더 거리는 엔티티의 약 두 배다. 파티클은 월드에 영향을 줄 수 없으니 로직은 엔티티가 맡는다. 벽 너머로 보여야 하면 엔티티를 쓴다(Mojang 맵도 같은 방식).
- 3D 모양 파티클: 파티클은 3D 지오메트리를 쓸 수 없어 면마다 파티클 하나가 필요하다는 답(2026-03, 2026-06)이 있었고, 2026-10에는 Molang 변수로 회전·크기가 바뀌는 큐브를 파티클 하나로 그려 먼 3D 모델에 쓰는 시연이 나왔다. Molang만으로 블록 텍스처 파티클(엔티티 1개, 한 면)을 그린 예도 있고 성능은 이미터 수에 좌우된다. 엔티티를 로케이터 없이 로컬 위치와 수식으로 따라가게 할 수도 있다.
- 비와 날씨: 비는 파티클이고 바닐라 비 파티클은 samples에 없으며 감지할 수 없다. 커스텀 비는 충돌로 땅 높이에서 튀길 수 있다(엔티티 위는 제외). 빗줄기와 튀김을 두 파티클로 나누거나 바닐라 튀김 이벤트로 물결을 만든다. Wildlifecraft의 비 렉은 8틱마다 650개와 이중 땅 검사(클라이언트) 때문이었다. 가짜 날씨는 스크립트로 플레이어 근처에 바이옴별 큰 파티클을 띄운다.
- VV: 디퍼드 렌더링 비용은 [VV 설정 파일](./vv-settings.mdx)의 성능 절을 본다. VV에서 파티클은 조명을 무시할 수 없고 조명 컴포넌트를 빼거나 발광 PBR 텍스처를 쓰면 부분적으로 해결된다. "빛 강화" 파티클 머티리얼은 VV에서 반대로 동작한다. 파티클 텍스처에 MER 파일을 주면 VV에서 빛난다(2026-03). VV의 바닐라 파티클 글로우(불꽃 등)는 하드코딩이고 커스텀 파티클용 문서화된 방법이 없다고 했다. 발광 파티클은 VV에서 빛을 내지 않고 블룸만 낸다. `particle_appearance_tinting`에 `query.spellcolor`를 쓰면 색상이 틀어진다(빨강이 자홍, 답 없음). VV에서 커스텀 파티클 머티리얼이 가까이서만 보였다는 보고와, 로케이터에서 생성한 파티클이 VV에서 Fancy와 다른 위치에 나온다는 보고가 있다(미해결, `single report`).
- 빔: 텍스처가 긴 아주 긴 2D 파티클 하나, +45/-45도로 돌리고 늘린 교차 파티클 두 개, 또는 모델을 쓴다. 방향 있는 빔 파티클은 `v.dir_x/y/z`로 `emitter_shape_point` 오프셋을 주고 `facing_camera_mode: direction_z`, `custom_direction [v.dir_z, 0, -v.dir_x]`를 쓴다. `emitter_local_space` rotation true는 빔을 비틀고, 스크립트로 생성하면서 MolangVariableMap으로 회전을 넘길 수도 있다. x와 z에 같은 랜덤 값을 쓰자 3중 빔 아티팩트가 사라졌다. 블록 외곽선 같은 단일 파티클 선 렌더러로는 `gfx:line`이 있다.
- 트레일: 초당 파티클을 더 많이 만들고 더 천천히 줄여 틈을 메우거나(성능 비용) 애니메이션 루프에서 프레임마다 생성한다.
- 가짜 그림자: 아래로 아주 빠르게 움직이고 충돌을 켠 파티클로 땅에 붙는 클라이언트 그림자를 흉내 낸다(가장자리가 어색하다).
- 파티클 하늘·천문(리소스 팩만으로): 플레이어 엔티티에 (큐브 없이 로케이터만 있는) 지오메트리를 붙여 약 6개 파티클을 방출하고, 자체 렌더 컨트롤러와 애니메이션 컨트롤러로 본을 태양계 모형처럼 회전한다. 지오메트리는 몸 회전을 상쇄하는 루트의 자식이고 VV에서만 동작한다(VV에서는 지오메트리를 몸에 고정하고 몸 회전을 상쇄할 수 있지만 non-VV에서는 머리에만 붙는다). 리소스 팩만으로 혜성, 행성, 일식을 그린 시연(2026-11)과 Better Clouds를 파티클만으로 옮기는 작업이 있다. 클라이언트 파티클은 생성 지점 근처에서만 로드되므로 서버 측에서 천체 파티클을 내는 우회도 쓰인다. `query.time_of_day`, `query.day`를 쓰고, Realms에서 낮 주기가 끊기면 `query.delta_time`과 lerp를 쓴다. 파티클 파일의 오프셋은 블록 단위이고 지오메트리 로케이터 오프셋이 아니다. 하늘 물체를 파티클로 그릴 때 오프셋 256은 렌더 거리에 따라 블록 앞에 그려지고, 1024는 항상 뒤에 그려지지만 불투명도·색이 깨지며, 512는 색이 나쁘다. 바이옴 강수는 바꿀 수 있지만 Nether식 파티클로만 가능하고 1인칭 그림자가 이상해진다.
- 오픈소스 예: 입김 파티클(Apache 2.0, whynotoss/cold-breath).
- Snowstorm: 표준 파티클 편집기다(snowstorm.app). 미리보기는 게임이 거부하는 것도 받아들이고, 스크립트로 정의한 변수는 해석하지 못하며, JSON에 주석이 있으면 로드에 실패할 수 있다. 3.3(2026-11-04)에서 blend·additive 그리기 순서와 update expression 평가 순서가 고쳐졌다. 일부 Blockbench 버전에서는 Snowstorm 파티클이 깨지고 로케이터 방향이 뒤집혔다. Blockbench는 파티클을 미리 보여 줄 뿐 파티클 편집기가 아니다. 편집기 목록은 [모델링과 텍스처 도구](../tools/modeling.mdx)를 본다.
- 블록 파티클: 블록은 바닐라가 이미 내는 것 외의 파티클을 리소스 팩만으로 낼 수 없다. 생존 모드에서 방벽을 보이게 하려면 방벽 블록 안에서만 보이는 파티클로 흉내 낸다.

## Particle Jester 저장소 (도구와 검증)

(출처: particle-jester, 커밋 b91df84, MIT, 2026-10-09 하루 만든 커밋 2개. 이 위키는 저장소 도구를 실행하지 않았다.)

Particle Jester는 AI(OpenAI Codex)가 배드락 파티클을 만들고 고치고 미리 보게 하는 스킬 하나와 Node 도구 묶음, 직접 만든 예제 파티클 18개로 이루어져 있다. JSON UI 자료가 아니다. 구조는 mcbejsonuimasterAI에서 가져와 지식 층(스킬·문서)과 결정적 도구 층을 나누고 검증 수준을 따로 보고한다. 실행 환경은 Node.js 22 이상이고, 예제 팩은 `min_engine_version [1,26,50]`, 스크립트는 `@minecraft/server` 2.9.0(안정판)이다. 게임 실측은 하지 않았다.

**검증 수준 다섯 단계**: `structurallyValid`(직접 쓴 스키마 통과), `referencesResolved`(파티클·텍스처·트리거 연결이 풀림), `staticChecksPassed`(지원하는 Molang 문법, 상수 UV 범위, 변수 생산자, 성능 입력 범위 통과), `previewVerified`(실제 캡처와 사람이 본 검수 기록이 현재 파일 해시에 묶임), `minecraftRuntimeVerified`(대상 클라이언트 실측, 모든 예제가 false).

| 명령 | 하는 일 | 한계 |
| --- | --- | --- |
| `scan` | 전체 목록, PNG 디코딩, 경로, 의존 그래프, 변수·UV 진단 | 스크립트는 Acorn으로 파싱만 하고 실행하지 않는다. 파일 50,000개와 512 MiB 한도 |
| `validate file.json --texture png` | 스키마와 의미 검사 | 엔진 파서와 같다는 보장 없음 |
| `texture png` | 크기, 알파 히스토그램, 보이는 영역, 해시 | 아틀라스 칸을 짐작하지 않음 |
| `molang "식"` | 지원하는 문법과 수학 함수 이름 검사 | 반복문, 배열, `->`, `this`는 지원 안 함 |
| `repair`, `optimize` | 명시한 PNG로 바꾸기, 방출 수·상한을 비율로 줄인 사본 | 화면이 같다는 주장은 아님 |
| `preview`, `studio` | Wintersky 1.3.3과 Three.js r134로 브라우저 렌더 | 블록 충돌, locator, 엔티티 query, 그래픽 모드, 멀티플레이는 재현 못 함 |
| `mcp` | stdio MCP 도구 5개 | 지정 폴더 밖 경로 금지 |

스키마가 받는 컴포넌트는 위 표의 29개다. 예제 팩은 네임스페이스 `pm:`, 파티클 18개(`shockwave`, `portal_ring`, `portal_core`, `portal_motes`, `blizzard_snow`, `blizzard_gust`, `explosion_sparks`, `explosion_smoke`, `debris`, `cinematic`, `vortex`, `beam`, `lightning`, `trail`, `slash`, `flame`, `water`, `dust`)와 텍스처 8장(`arc`, `flame`, `ring`, `rune`, `slash`, `snow`, `soft`, `streak`)이다. 파티클 텍스처는 아이템·지형 아틀라스 등록이 필요 없다. 시퀀스 4개는 portal(3겹 동시), blizzard(2겹), explosion(0~0.15초에 4겹), boss(0~1.85초에 7단계)다. `pm:cinematic`은 입자를 직접 뿌리지 않는 루트 방출기의 타임라인 이벤트로 단계를 만든다. 빔·번개·베기는 평면 그림 예제일 뿐 임의 끝점 조준이나 칼에 붙는 효과가 아니다. 사용자 파티클 모음(정의 856개) 분석 카탈로그는 출처·라이선스가 불분명해 공개판에서 빠졌다.

한계: 저장소가 게임 실측을 하지 않았으므로 위 파티클 사실과 예제는 게임에서 확인하지 않았고 `{실측 필요}`다. 미리보기는 브라우저 재구현이라 Bedrock 렌더러와 같다는 보장이 없다. 이후 갱신 여부는 알 수 없다.
