# 함수(mcfunction)와 명령 패턴

함수는 여러 줄의 명령을 담은 `.mcfunction` 파일이고 게임 안에서 `/function` 명령으로 실행한다. 함수 팩은 함수 파일만으로 시스템을 만든 팩이다. 함수는 명령 블록을 오가며 디버깅하는 시간을 줄이고 여러 월드로 시스템을 옮기기 쉽게 한다. 근거는 Bedrock Wiki(0930b39) 명령 문서(BedrockCommands 커뮤니티 제공), MS Learn의 FunctionsIntroduction(a9fd1c0), 커뮤니티 조사다.

## 1. 파일 구조

함수는 행동 팩의 `functions/` 폴더에 둔다.

```text
BP/functions/this_code.mcfunction
BP/functions/tick.json
BP/functions/wiki/teleport/zone/hell.mcfunction
```

권장 규칙(출처: bedrock-wiki):

1. 모든 `.mcfunction` 파일은 `functions` 아래의 네임스페이스 루트 폴더에 둔다(`BP/functions/wiki/random_number.mcfunction`은 좋고 루트에 바로 두는 것은 나쁘다).
2. 폴더와 파일 이름은 snake_case(소문자, 숫자, 밑줄)로 쓴다.
3. 올바르게 중첩한다(`wiki/teleport/zone/hell`이 `wiki/teleport_hellzone`보다 낫다).
4. 이름은 동사가 먼저인 `action_object` 구조를 따른다(`add_all`, `shuffle_position`).
5. 경로 전체 길이는 80자를 넘기지 않는다(콘솔 제한).
6. 내용 폴더는 단수나 복수 중 하나로 통일한다.

함수 파일에는 한 줄에 명령 하나를 쓴다. 슬래시는 생략하고 `#`으로 시작하는 줄은 주석이다.

```mcfunction
# BP/functions/wiki/ability/ice_blast.mcfunction
effect @e[r=5,type=!player] slowness 5 3
particle minecraft:snowflake_particle ~ ~1 ~
playsound random.glass @a ~ ~ ~
```

`tick.json`은 매 틱 실행할 함수를 나열한다.

```json
{ "values": [ "wiki/main_loop" ] }
```

## 2. 호출 방법

- 게임 안: `/function wiki/ability/ice_blast`.
- 엔티티 이벤트에서: `queue_command`의 `command`에 `function wiki/ability/ice_blast` 또는 `scriptevent ns:id`를 둔다. 엔티티는 `/place`와 op 전용 명령을 실행할 수 없으므로 이런 명령은 `/scriptevent`로 스크립트에 넘겨 `placeFeature` 등으로 우회한다(출처: 비공개 조사).
- 플레이어 컨트롤러에서: BP 애니메이션 컨트롤러의 상태 `on_entry: "/function ..."`으로 우클릭 같은 입력을 감지해 함수를 실행한다(전환 쿼리 예: `query.is_item_name_any('slot.weapon.mainhand','ns:item') && query.is_using_item`).
- 스크립트에서: `source.runCommand`, `system.run(...)`으로 감싸 호출한다. `dimension.runCommand('... @s')`는 `@s`가 차원이 되어 실패한다. Realms에서는 제거된 `runCommandAsync` 대신 `runCommand`를 쓴다.

## 3. 자주 쓰는 명령 패턴

- 점수판 타이머, 이동 감지, 플레이어 접속/사망/리스폰 감지, 엔티티 카운터는 위키 commands 섹션이 다룬다(mcfunctions, scoreboard-timers, on-player-death 등).
- `/playanimation @p <anim> <next_state> <blend_out_time> "<stop_expression>" <controller>`로 애니메이션을 재생하고 stop expression으로 변수를 설정한다(예: `playanimation @s animation.first_person.attack_rotation_item x 900 "v.attack_time=1;"`).
- 어그로 강제: `damage @s 0 entity_attack entity <target>`(근거리만).
- 이동 제한: `/inputpermission set <player> movement disabled`. 말 체력 바 숨기기: `/hud @s hide horse_health`(되돌리기 `/hud @s reset horse_health`).
- 장비 지급: `replaceitem entity @s slot.armor.feet 1 id`, `/loot replace entity @s slot.armor.chest 0 loot "..."`. 아이템 잠금은 `item_lock` 모드 `lock_in_slot`이다.
- 소환과 이벤트: `/summon minecraft:camel_husk ~ ~ ~ ~ ~ minecraft:spawn_with_rider`, `/summon custom:mob ~~~ minecraft:promote_to_illager_captain`, `/event entity @s name`.
- `/gamerule domobspawning false`로 자연 스폰을 끄고 커스텀 몹을 명령/스크립트로 스폰할 수 있다.
- 피처 배치: `/place feature`, `/place featurerule`, `/place jigsaw <pool> <target> <depth> ~~~ true`는 명령 블록이나 함수에서 실행할 수 없다. 구조물은 `/structure load ns:name`, 삭제는 `/structure delete <name>`이다.
- 시야를 확인하는 명령 조건 예: `if block ^ ^ ^0.25 air`로 장애물을 확인하며 facing 텔레포트로 조종할 수 있다.
- 명령 블록에서의 `/event entity` 여러 개는 각각 이벤트를 발동한다.

## 4. 사례: 데미지 숫자를 파티클로 그리기

명령/함수가 아니라 스크립트 + 파티클로 피격 숫자를 띄우는 애드온 분석이다(출처: repo-damage-indicator). 그 애드온은 JSON UI를 전혀 쓰지 않고 BP 스크립트와 RP 파티클 하나와 PNG 한 장으로 이뤄진다. 핵심 기법은 다음과 같다.

- 글리프 아틀라스: 가로 1024, 세로 64의 PNG에 64px 정사각 셀 16칸을 두고 `0`~`9`, `-`, `.` 12칸에 검은 외곽선의 흰 글자를 그린다. 흰색으로 그려 두고 색은 틴트로 입힌다. 파티클의 UV는 `"uv": ["variable.glyph * 64", 0]`, `"uv_size": [64, 64]`이며 `variable.glyph`로 셀을 고른다.
- 스크립트는 글자마다 파티클 하나를 `attacker.spawnParticle("pdi:damage_glyph", pos, vars)`로 띄운다. `Player.spawnParticle`은 해당 플레이어에게만 보이고 `Dimension.spawnParticle`은 주변 모두에게 보인다.

```javascript
const vars = new MolangVariableMap();
vars.setFloat("variable.glyph", glyph);
vars.setFloat("variable.scale", scale);
vars.setColorRGBA("variable.tint", color);
attacker.spawnParticle("pdi:damage_glyph", pos, vars);
```

- `setColorRGBA("variable.x", ...)`는 `variable.x.r/.g/.b/.a` 네 개로 풀린다. 틴트 그라디언트에서 RGB는 변수, 알파만 키프레임(0 → 1 → 1 → 0)으로 주면 색과 페이드를 분리할 수 있다. 반투명은 `particles_blend`, 컷아웃은 `particles_alpha`다.
- 글자 배치: 공격자 시선을 XZ 평면으로 정규화한 `view`에서 `right = (-view.z, 0, view.x)`를 구하고 간격 0.155 x `(i - (len-1)/2)`만큼 민다. `facing_camera_mode: lookat_xyz`와 함께 쓰면 어느 각도에서도 읽힌다. 연속 표시는 후보 오프셋 중 최근 5개와 가장 먼 것을 고른다.
- 치명타는 `isFalling`이고 물속·수영·등반이 아니며 실명·느린 낙하가 없을 때로 추정하는 휴리스틱이다. 근접과 철퇴 강타만 표시한다. 월드에 붙은 표시(머리 위 숫자 등)는 JSON UI가 아니라 파티클이나 엔티티로 만들어야 한다.

## 5. 함수 규칙 상세 (커뮤니티 조사 packs-versions 병합)

- 줄바꿈은 LF(CRLF 아님)이고 명령은 `/`로 시작하지 않는다. 어기면 함수가 조용히 나타나지 않는다. bridge.로 만들거나 기존 함수를 복사하면 피할 수 있다. (confirmed)
- BP manifest/format이 1.17.0을 넘으면 `#` 주석이 동작하지 않으며 로드에 실패한 함수는 목록에 나오지 않는다. (본문 1절의 주석 예는 위키 관례이고, 이 보고와 충돌하면 주석을 지운다.)
- `Unexpected @a / @e` 오류나 `execute` 파싱 실패는 manifest가 1.19.50 이전 문법으로 파싱되기 때문이다. `"format_version": 2` + `"min_engine_version": [1,19,50]` 이상으로 고치거나 옛 문법을 쓴다. 변환: `execute @a ~ ~ ~ <cmd>` = `execute as @a at @s positioned ~ ~ ~ run <cmd>`, `detect ~ ~ ~ air` = `if block ~ ~ ~ air`.
- `tick.json`은 `functions/`에 두고 매 틱 실행할 함수를 나열한다. 여러 애드온의 tick.json 함수는 동시에 실행된다. 점수 보유자 플래그로 다른 함수를 조건부 호출하는 `main.mcfunction` 하나를 두는 구성이 권장된다(`execute if score map_1 wiki:q.is_active matches 1 run function maps/map_1/on`). tick.json 대 엔티티 `environment_sensor` 러너의 성능은 보고가 엇갈린다. tick.json 폴링은 이벤트 기반 스크립트보다 느리다.
- 조건부 체인은 없으니 `execute if/unless`나 스코어보드로 대신한다. `/schedule`은 함수 안에서 쓸 수 있고 `/schedule on_area_loaded`는 청크 로드를 기다린다.
- 스크립트에서 함수 호출은 `player.runCommand('function name')`이다. 스크립트에서 허용되지 않는 명령(`/place`)을 담은 함수는 스크립트로 실행해도 돌지 않는다. `/op`, `/connect`는 스크립트 엔진에서 실패한다.
- NPC/대화 JSON의 명령 문자열은 내부 따옴표를 이스케이프한다: `"on_open_commands": ["/tellraw @a {\"rawtext\":[{\"text\":\"hi\"}]}"]`. 2026-01에 NPC 대화 텍스트의 `selector` `@initiator`/`score` rawtext가 동작하지 않는다는 보고가 있다. 아이템 사용 트리거 함수가 조용히 실패한 원인은 잘못된 `execute` 문법이었다.
- 권한 수준: 함수는 권한 레벨 1로 파싱되고 `/place`는 레벨 2라서 명령 블록·함수·tick.json에서 `/place`(jigsaw, feature)를 실행할 수 없다. 스크립트의 `runCommand`로 우회한다. `/reload`도 명령 블록/함수/NPC에서 불가하다.
- 함수는 호출자의 실행 컨텍스트를 상속한다. 채팅에서 부르면 플레이어 위치/회전/실행자, 명령 블록에서는 블록 위치에 실행자 없음(`execute as` 전까지 `@s` 정의 안 됨), tick.json에서는 0,0,0에서 실행되어 위치 셀렉터(`y=0,dy=-600`)가 0,0,0 기준으로 조용히 검사된다. 해결 예: `execute in the_end as @a[rm=0] at @s if entity @s[tag=eternal,y=0,dy=-600] run function eternal_void`(`in`은 뒤따르는 하위 명령의 디멘션만 바꾸므로 `as @a[rm=0]` 또는 `r=999999999`로 디멘션별 필터). (confirmed)
- 셀렉터: `r`/`rm`은 엔티티 발 위치 기준이고 볼륨 `x,y,z,dx,dy,dz`는 히트박스 접촉 검사다(웅크리면 히트박스가 작아져 웅크림 감지 가능). 볼륨 셀렉터는 `~` 상대 좌표를 받고 최소 1x1x1이다. 링 검사: `execute as @a at @s if entity @e[type=!player,r=6,rm=5]`, `rm=0.001`(또는 0.01)로 자신을 제외한다.
- 타이머는 체인 지연이나 레드스톤보다 스코어보드 타이머를 권장한다. `tp`의 `^^^`는 실행 위치 기준이므로 각 대상을 옮기려면 `execute as <targets> at @s run tp @s ^..`를 쓴다. `/execute facing`은 텔레포트 전, `tp ... facing`은 후 회전한다. 뒤로 10블록은 `execute as @a at @s rotated ~ 0 run tp @s ^^^-10`이다. 블록 비교는 `execute if blocks <ref> <ref> <target> all|masked`(`all`은 공기 포함, `masked`는 무시)이며 오프셋은 목적지 모서리 기준이고 서명된 책·이름까지 비교해 불안정할 수 있다. 물 잠김은 블록 상태로 검사할 수 없다.
- 커스텀 명령(`namespace:name`, 이름이 유일하면 네임스페이스 없이 호출 가능)을 선호하는 합의가 있다. `/scriptevent`는 명령 이름을 소비하지 않고 사용자에게 숨겨지며 재로드 없이 바뀌어 팩 내부/팩 간 호출에 적합하지만 사용자가 실행할 수 있으니 deop이나 권한 제한이 필요하다. 커스텀 명령은 Realms에서 동작하고(beta `chatSend`보다 이식성 높음) `runCommand`로 실행할 수 있으나 결과 텍스트는 반환되지 않는다. 커스텀 명령 실행은 채팅창을 닫으므로 그 직후 폼을 띄우기 좋다.

## 6. 스크립트·도구 관련 요약 (scripting / tooling-server 병합)

- before 이벤트, 명령 콜백, startup은 restricted(early) execution이라 `runCommand`, `setItem`, `spawnParticle`, `addTag`, 폼 `show` 등이 `Native function [...] cannot be used in restricted execution`으로 실패한다. `system.run(() => ...)`으로 감싼다. 2.x 마이그레이션에서 `runCommandAsync`가 제거돼 `runCommand`를 쓴다.
- `system.afterEvents.scriptEventReceive`(world가 아님)는 `{id, message, sourceType, initiator, sourceEntity, sourceBlock}`를 주고 `ScriptEventSource`는 Block, Entity, NPCDialogue, Server다. `/scriptevent ns:id msg` 또는 `system.sendScriptEvent(id, message)`로 보낸다. 엔티티 JSON `queue_command`로 스크립트에 신호를 보낸다. 애드온 간 통신(IPC)은 모두 scriptevent를 전송 수단으로 쓴다(MCBE-IPC가 사실상 표준).
- 블록에는 `runCommand`가 없으므로 `block.dimension.runCommand("execute positioned x y z run function ...")`을 쓴다(`/setblock ... destroy`는 드롭, `block.below().setType("minecraft:air")`는 드롭 없음). `player.kick` API는 없어 `system.run` 안에서 `runCommand`로 `kick @s "reason"`을 쓴다. `Player.stopSound`는 beta이고 stable은 `runCommand("stopsound ...")`다.
- 몹 장비 쓰기는 `entity.runCommand("replaceitem entity @s slot.armor.head 0 diamond_helmet")`(RP 엔티티에 `"enable_attachables": true`), 읽기는 `testfor @s[hasitem={item=...}]`로 한다. 구조물 로드는 비동기라 고정 틱 대기가 필요하고 큰 구조물(96x96)은 네이티브 호출을 크래시시킬 수 있어 jigsaw 조각으로 나눈다. `dimension.placeFeature(feature, location, true)`와 `Dimension.placeFeatureRule()`은 대량 사용이 비싸다. 엔티티는 `/place`를 실행할 수 없으니 `/scriptevent`로 스크립트에 요청한다.
- `/connect` 또는 `/wsserver host:port`는 클라이언트가 실행하는 명령이라 스크립트의 `runCommand`로 실행할 수 없고 `successCount`가 항상 0이다. 스크립트에서 WebSocket/HTTP는 불가하다. server-net/server-admin은 BDS 전용이다.
- 도구: bridge.(웹 편집기)는 mcfunction 생성을 지원하고, VS Code 확장 MCBE Command Checker가 mcfunction을 검증하며, `MCDevKit.jsonte-vscode`는 .mcfunction 안의 injection을 지원한다. 위키의 긴 `/execute` 체인 글은 스크립팅이 있는 Bedrock에서는 쓸모가 제한적이라는 평이 있다. AI 답변은 Bedrock 명령과 Script API에서 믿기 어렵다.
- 멀티플레이 동기화: 많은 엔티티에 계속 `tp`를 쓰면 호스트가 아닌 플레이어에게 렉으로 보인다. 셀렉터와 fork는 플레이어 수만큼 늘어나므로 명령 비용이 커진다.
- BP 애니메이션 컨트롤러는 트리거 기반이라 싸고 스크립트는 상한이 높고 조합이 쉽다. 우클릭 함수 실행은 player.json 컨트롤러(`query.is_using_item && query.is_item_name_any('slot.weapon.mainhand', 'ns:item')` → `on_entry` `/function`)로도 가능하다.

## 7. 전체 레퍼런스

명령 목록과 소개 문서는 [명령 목록](./reference/commands-1.mdx)에 MS Learn 원문 발췌로 실었다.
