# 함수(mcfunction)와 명령 패턴

함수는 여러 줄의 명령을 담은 `.mcfunction` 파일이고 게임 안에서 `/function` 명령으로 실행한다. 함수 팩은 함수 파일만으로 시스템을 만든 팩이다. 함수는 명령 블록을 오가며 디버깅하는 시간을 줄이고 여러 월드로 시스템을 옮기기 쉽게 한다. 근거는 Bedrock Wiki(0930b39) 명령 문서(BedrockCommands 커뮤니티 제공), MS Learn의 FunctionsIntroduction(a9fd1c0), 커뮤니티 조사다.

## 1. 파일 구조

함수는 행동 팩의 `functions/` 폴더에 둔다.

```text
BP/functions/this_code.mcfunction
BP/functions/tick.json
BP/functions/wiki/teleport/zone/hell.mcfunction
```

권장 규칙(출처: bedrock-wiki):

1. 모든 `.mcfunction` 파일은 `functions` 아래의 네임스페이스 루트 폴더에 둔다(`BP/functions/wiki/random_number.mcfunction`은 좋고 루트에 바로 두는 것은 나쁘다).
2. 폴더와 파일 이름은 snake_case(소문자, 숫자, 밑줄)로 쓴다.
3. 올바르게 중첩한다(`wiki/teleport/zone/hell`이 `wiki/teleport_hellzone`보다 낫다).
4. 이름은 동사가 먼저인 `action_object` 구조를 따른다(`add_all`, `shuffle_position`).
5. 경로 전체 길이는 80자를 넘기지 않는다(콘솔 제한).
6. 내용 폴더는 단수나 복수 중 하나로 통일한다.

함수 파일에는 한 줄에 명령 하나를 쓴다. 슬래시는 생략하고 `#`으로 시작하는 줄은 주석이다.

```mcfunction
# BP/functions/wiki/ability/ice_blast.mcfunction
effect @e[r=5,type=!player] slowness 5 3
particle minecraft:snowflake_particle ~ ~1 ~
playsound random.glass @a ~ ~ ~
```

`tick.json`은 매 틱 실행할 함수를 나열한다.

```json
{ "values": [ "wiki/main_loop" ] }
```

## 2. 호출 방법

- 게임 안: `/function wiki/ability/ice_blast`.
- 엔티티 이벤트에서: `queue_command`의 `command`에 `function wiki/ability/ice_blast` 또는 `scriptevent ns:id`를 둔다. 엔티티는 `/place`와 op 전용 명령을 실행할 수 없으므로 이런 명령은 `/scriptevent`로 스크립트에 넘겨 `placeFeature` 등으로 우회한다(출처: 비공개 조사).
- 플레이어 컨트롤러에서: BP 애니메이션 컨트롤러의 상태 `on_entry: "/function ..."`으로 우클릭 같은 입력을 감지해 함수를 실행한다(전환 쿼리 예: `query.is_item_name_any('slot.weapon.mainhand','ns:item') && query.is_using_item`).
- 스크립트에서: `source.runCommand`, `system.run(...)`으로 감싸 호출한다. `dimension.runCommand('... @s')`는 `@s`가 차원이 되어 실패한다. Realms에서는 제거된 `runCommandAsync` 대신 `runCommand`를 쓴다.

## 3. 자주 쓰는 명령 패턴

- 점수판 타이머, 이동 감지, 플레이어 접속/사망/리스폰 감지, 엔티티 카운터는 위키 commands 섹션이 다룬다(mcfunctions, scoreboard-timers, on-player-death 등).
- `/playanimation @p <anim> <next_state> <blend_out_time> "<stop_expression>" <controller>`로 애니메이션을 재생하고 stop expression으로 변수를 설정한다(예: `playanimation @s animation.first_person.attack_rotation_item x 900 "v.attack_time=1;"`).
- 어그로 강제: `damage @s 0 entity_attack entity <target>`(근거리만).
- 이동 제한: `/inputpermission set <player> movement disabled`. 말 체력 바 숨기기: `/hud @s hide horse_health`(되돌리기 `/hud @s reset horse_health`).
- 장비 지급: `replaceitem entity @s slot.armor.feet 1 id`, `/loot replace entity @s slot.armor.chest 0 loot "..."`. 아이템 잠금은 `item_lock` 모드 `lock_in_slot`이다. `/replaceitem entity @a slot.weapon.mainhand 0 keep air`는 손이 비어 있을 때만 성공하므로 빈 주손 감지에 쓸 수 있다. 표식 아이템을 `keep`으로 넣고 성공한 플레이어에게 태그를 붙인 뒤 표식을 지우는 방식이 제안됐다(unverified).
- 플레이어의 블록 설치 거리를 늘리는 공식 방법은 없다.
- 소환과 이벤트: `/summon minecraft:camel_husk ~ ~ ~ ~ ~ minecraft:spawn_with_rider`, `/summon custom:mob ~~~ minecraft:promote_to_illager_captain`, `/event entity @s name`.
- `/gamerule domobspawning false`로 자연 스폰을 끄고 커스텀 몹을 명령/스크립트로 스폰할 수 있다.
- 피처 배치: `/place feature`, `/place featurerule`, `/place jigsaw <pool> <target> <depth> ~~~ true`는 명령 블록이나 함수에서 실행할 수 없다. 구조물은 `/structure load ns:name`, 삭제는 `/structure delete <name>`이다.
- 시야를 확인하는 명령 조건 예: `if block ^ ^ ^0.25 air`로 장애물을 확인하며 facing 텔레포트로 조종할 수 있다.
- 명령 블록에서의 `/event entity` 여러 개는 각각 이벤트를 발동한다.
- 블록 중앙 정렬은 `execute align xz positioned ~0.5 ~0.5 ~0.5 run ...`, 디멘션 이동은 `/execute in nether run tp <target> ~ ~ ~`다. `/tp @e ^^^+3 true`의 마지막 `true`는 이동 경로의 블록을 검사한다.
- `/fill`이 "world not loaded"로 실패하면 시뮬레이션 거리가 낮아 fill 영역 전체가 틱킹 영역 안에 들어오지 않은 것이다.
- `/camera @s fade ...`로 화면을 단색으로 덮을 수 있다. 매 틱 `/camera`를 갱신하면 호스트가 아닌 플레이어에게 끊겨 보이고, 곡선 이동은 spline 모드뿐이다. `camera ... facing @s`를 `execute at @s`와 함께 쓰면 화면이 깜빡인 사례가 있다(미해결).
- 게임룰 사실: `dofiretick`을 끄면 번개가 만드는 불도 막고, `showtags`를 끄면 잠긴 아이템 표시가 숨겨진다. 하루는 24000틱이다.
- `/spreadplayers`로 안전한 무작위 텔레포트를 만든다. `/place feature minecraft:coal_ore_feature`로 놓은 결과는 월드를 다시 열기 전까지 보이지 않는 경우가 있다. 명령만으로는 플레이어별로 다르게 보이는 파티클을 만들 수 없다.

## 4. 사례: 데미지 숫자를 파티클로 그리기

명령/함수가 아니라 스크립트 + 파티클로 피격 숫자를 띄우는 애드온 분석이다(출처: repo-damage-indicator). 그 애드온은 JSON UI를 전혀 쓰지 않고 BP 스크립트와 RP 파티클 하나와 PNG 한 장으로 이뤄진다. 핵심 기법은 다음과 같다.

- 글리프 아틀라스: 가로 1024, 세로 64의 PNG에 64px 정사각 셀 16칸을 두고 `0`~`9`, `-`, `.` 12칸에 검은 외곽선의 흰 글자를 그린다. 흰색으로 그려 두고 색은 틴트로 입힌다. 파티클의 UV는 `"uv": ["variable.glyph * 64", 0]`, `"uv_size": [64, 64]`이며 `variable.glyph`로 셀을 고른다.
- 스크립트는 글자마다 파티클 하나를 `attacker.spawnParticle("pdi:damage_glyph", pos, vars)`로 띄운다. `Player.spawnParticle`은 해당 플레이어에게만 보이고 `Dimension.spawnParticle`은 주변 모두에게 보인다.

```javascript
const vars = new MolangVariableMap();
vars.setFloat("variable.glyph", glyph);
vars.setFloat("variable.scale", scale);
vars.setColorRGBA("variable.tint", color);
attacker.spawnParticle("pdi:damage_glyph", pos, vars);
```

- `setColorRGBA("variable.x", ...)`는 `variable.x.r/.g/.b/.a` 네 개로 풀린다. 틴트 그라디언트에서 RGB는 변수, 알파만 키프레임(0 → 1 → 1 → 0)으로 주면 색과 페이드를 분리할 수 있다. 반투명은 `particles_blend`, 컷아웃은 `particles_alpha`다.
- 글자 배치: 공격자 시선을 XZ 평면으로 정규화한 `view`에서 `right = (-view.z, 0, view.x)`를 구하고 간격 0.155 x `(i - (len-1)/2)`만큼 민다. `facing_camera_mode: lookat_xyz`와 함께 쓰면 어느 각도에서도 읽힌다. 연속 표시는 후보 오프셋 중 최근 5개와 가장 먼 것을 고른다.
- 치명타는 `isFalling`이고 물속·수영·등반이 아니며 실명·느린 낙하가 없을 때로 추정하는 휴리스틱이다. 근접과 철퇴 강타만 표시한다. 월드에 붙은 표시(머리 위 숫자 등)는 JSON UI가 아니라 파티클이나 엔티티로 만들어야 한다.

## 5. 함수 규칙 상세 (커뮤니티 조사 packs-versions 병합)

- 줄바꿈은 LF(CRLF 아님)이고 명령은 `/`로 시작하지 않는다. 어기면 함수가 조용히 나타나지 않는다. bridge.로 만들거나 기존 함수를 복사하면 피할 수 있다. (confirmed)
- BP manifest/format이 1.17.0을 넘으면 `#` 주석이 동작하지 않으며 로드에 실패한 함수는 목록에 나오지 않는다. (본문 1절의 주석 예는 위키 관례이고, 이 보고와 충돌하면 주석을 지운다.)
- `Unexpected @a / @e` 오류나 `execute` 파싱 실패는 manifest가 1.19.50 이전 문법으로 파싱되기 때문이다. `"format_version": 2` + `"min_engine_version": [1,19,50]` 이상으로 고치거나 옛 문법을 쓴다. 변환: `execute @a ~ ~ ~ <cmd>` = `execute as @a at @s positioned ~ ~ ~ run <cmd>`, `detect ~ ~ ~ air` = `if block ~ ~ ~ air`.
- `tick.json`은 `functions/`에 두고 매 틱 실행할 함수를 나열한다. 여러 애드온의 tick.json 함수는 동시에 실행된다. 점수 보유자 플래그로 다른 함수를 조건부 호출하는 `main.mcfunction` 하나를 두는 구성이 권장된다(`execute if score map_1 wiki:q.is_active matches 1 run function maps/map_1/on`). tick.json 대 엔티티 `environment_sensor` 러너의 성능은 보고가 엇갈린다. tick.json 폴링은 이벤트 기반 스크립트보다 느리다.
- 조건부 체인은 없으니 `execute if/unless`나 스코어보드로 대신한다. `/schedule`은 함수 안에서 쓸 수 있고 `/schedule on_area_loaded`는 청크 로드를 기다린다. 다만 tick 함수에서 부른 mcfunction 안의 `/schedule delay add <function> 60`이 실행되지 않고 같은 명령이 커맨드 블록에서는 동작한 사례가 있다(원인 미확인, 2026-11). `/schedule delay add`로 예약한 함수는 실행자 컨텍스트를 잃어 `@s`가 아무도 가리키지 않는다. 예약 전에 플레이어에게 태그를 붙이고 함수 안에서 `@a[tag=book]`처럼 태그로 대상을 고른다.
- 스크립트에서 함수 호출은 `player.runCommand('function name')`이다. 스크립트에서 허용되지 않는 명령(`/place`)을 담은 함수는 스크립트로 실행해도 돌지 않는다. `/op`, `/connect`는 스크립트 엔진에서 실패한다.
- NPC/대화 JSON의 명령 문자열은 내부 따옴표를 이스케이프한다: `"on_open_commands": ["/tellraw @a {\"rawtext\":[{\"text\":\"hi\"}]}"]`. 2026-01에 NPC 대화 텍스트의 `selector` `@initiator`/`score` rawtext가 동작하지 않는다는 보고가 있다. 아이템 사용 트리거 함수가 조용히 실패한 원인은 잘못된 `execute` 문법이었다.
- 권한 수준: 함수는 권한 레벨 1로 파싱되고 `/place`는 레벨 2라서 명령 블록·함수·tick.json에서 `/place`(jigsaw, feature)를 실행할 수 없다. 스크립트의 `runCommand`로 우회한다. `/reload`도 명령 블록/함수/NPC에서 불가하다. NPC는 `/dialogue`로 열 수 있고 높은 권한으로 명령을 실행한다는 언급이 있다. (single report)
- 함수는 호출자의 실행 컨텍스트를 상속한다. 채팅에서 부르면 플레이어 위치/회전/실행자, 명령 블록에서는 블록 위치에 실행자 없음(`execute as` 전까지 `@s` 정의 안 됨), tick.json에서는 0,0,0에서 실행되어 위치 셀렉터(`y=0,dy=-600`)가 0,0,0 기준으로 조용히 검사된다. 해결 예: `execute in the_end as @a[rm=0] at @s if entity @s[tag=eternal,y=0,dy=-600] run function eternal_void`(`in`은 뒤따르는 하위 명령의 디멘션만 바꾸므로 `as @a[rm=0]` 또는 `r=999999999`로 디멘션별 필터). (confirmed)
- 셀렉터: `r`/`rm`은 엔티티 발 위치 기준이고 볼륨 `x,y,z,dx,dy,dz`는 히트박스 접촉 검사다(웅크리면 히트박스가 작아져 웅크림 감지 가능). 볼륨 셀렉터는 `~` 상대 좌표를 받고 최소 1x1x1이다. 링 검사: `execute as @a at @s if entity @e[type=!player,r=6,rm=5]`, `rm=0.001`(또는 0.01)로 자신을 제외한다. 높이와 상관없이 x=0, z=0 주변 반경 안의 플레이어를 고르려면 실행 위치의 Y를 각 플레이어의 Y로 맞춘다: `execute as @a positioned as @s positioned 0 ~ 0 run effect @s[r=20] regeneration 10 0 true`. 상자 영역은 `x,z,dx,dz`로 고른다.
- 체커보드 격자: 2블록 간격, 2x2 오프셋으로 실행을 포크하는 명령 네 개(둘은 검정, 둘은 흰색 fill)로 칠한 뒤 가장자리를 덮어쓴다.
- 타이머는 체인 지연이나 레드스톤보다 스코어보드 타이머를 권장한다. `tp`의 `^^^`는 실행 위치 기준이므로 각 대상을 옮기려면 `execute as <targets> at @s run tp @s ^..`를 쓴다. `/execute facing`은 텔레포트 전, `tp ... facing`은 후 회전한다. 뒤로 10블록은 `execute as @a at @s rotated ~ 0 run tp @s ^^^-10`이다. 블록 비교는 `execute if blocks <ref> <ref> <target> all|masked`(`all`은 공기 포함, `masked`는 무시)이며 오프셋은 목적지 모서리 기준이고 서명된 책·이름까지 비교해 불안정할 수 있다. 물 잠김은 블록 상태로 검사할 수 없다.
- 커스텀 명령(`namespace:name`, 이름이 유일하면 네임스페이스 없이 호출 가능)을 선호하는 합의가 있다. `/scriptevent`는 명령 이름을 소비하지 않고 사용자에게 숨겨지며 재로드 없이 바뀌어 팩 내부/팩 간 호출에 적합하지만 사용자가 실행할 수 있으니 deop이나 권한 제한이 필요하다. 커스텀 명령은 Realms에서 동작하고(beta `chatSend`보다 이식성 높음) `runCommand`로 실행할 수 있으나 결과 텍스트는 반환되지 않는다. 커스텀 명령 실행은 채팅창을 닫으므로 그 직후 폼을 띄우기 좋다.
- 커스텀 명령의 권한 수준: 커맨드 블록에서는 쓰이지만 채팅에서는 op가 필요한 명령(예: `/effect`)은 낮은 단계의 권한 수준을 준다. 기준은 [Bedrock Wiki custom-commands](https://wiki.bedrock.dev/scripting/custom-commands#command-permission-level)에 있다. 스크립트 커스텀 명령이 커맨드 블록에서 실행되지 않았다는 보고는 해결되지 않았다.

## 6. 스크립트·도구 관련 요약 (scripting / tooling-server 병합)

- before 이벤트, 명령 콜백, startup은 restricted(early) execution이라 `runCommand`, `setItem`, `spawnParticle`, `addTag`, 폼 `show` 등이 `Native function [...] cannot be used in restricted execution`으로 실패한다. `system.run(() => ...)`으로 감싼다. 2.x 마이그레이션에서 `runCommandAsync`가 제거돼 `runCommand`를 쓴다.
- `system.afterEvents.scriptEventReceive`(world가 아님)는 `{id, message, sourceType, initiator, sourceEntity, sourceBlock}`를 주고 `ScriptEventSource`는 Block, Entity, NPCDialogue, Server다. `/scriptevent ns:id msg` 또는 `system.sendScriptEvent(id, message)`로 보낸다. 엔티티 JSON `queue_command`로 스크립트에 신호를 보낸다. 애드온 간 통신(IPC)은 모두 scriptevent를 전송 수단으로 쓴다(MCBE-IPC가 사실상 표준).
- 블록에는 `runCommand`가 없으므로 `block.dimension.runCommand("execute positioned x y z run function ...")`을 쓴다(`/setblock ... destroy`는 드롭, `block.below().setType("minecraft:air")`는 드롭 없음). `player.kick` API는 없어 `system.run` 안에서 `runCommand`로 `kick @s "reason"`을 쓴다. `Player.stopSound`는 beta이고 stable은 `runCommand("stopsound ...")`다.
- 몹 장비 쓰기는 `entity.runCommand("replaceitem entity @s slot.armor.head 0 diamond_helmet")`(RP 엔티티에 `"enable_attachables": true`), 읽기는 `testfor @s[hasitem={item=...}]`로 한다. 구조물 로드는 비동기라 고정 틱 대기가 필요하고 큰 구조물(96x96)은 네이티브 호출을 크래시시킬 수 있어 jigsaw 조각으로 나눈다. `dimension.placeFeature(feature, location, true)`와 `Dimension.placeFeatureRule()`은 대량 사용이 비싸다. 엔티티는 `/place`를 실행할 수 없으니 `/scriptevent`로 스크립트에 요청한다.
- `/connect` 또는 `/wsserver host:port`는 클라이언트가 실행하는 명령이라 스크립트의 `runCommand`로 실행할 수 없고 `successCount`가 항상 0이다. 스크립트에서 WebSocket/HTTP는 불가하다. server-net/server-admin은 BDS 전용이다.
- 도구: bridge.(웹 편집기)는 mcfunction 생성을 지원하고, VS Code 확장 MCBE Command Checker가 mcfunction을 검증하며, `MCDevKit.jsonte-vscode`는 .mcfunction 안의 injection을 지원한다. 위키의 긴 `/execute` 체인 글은 스크립팅이 있는 Bedrock에서는 쓸모가 제한적이라는 평이 있다. AI 답변은 Bedrock 명령과 Script API에서 믿기 어렵다.
- 멀티플레이 동기화: 많은 엔티티에 계속 `tp`를 쓰면 호스트가 아닌 플레이어에게 렉으로 보인다. 셀렉터와 fork는 플레이어 수만큼 늘어나므로 명령 비용이 커진다.
- BP 애니메이션 컨트롤러는 트리거 기반이라 싸고 스크립트는 상한이 높고 조합이 쉽다. 우클릭 함수 실행은 player.json 컨트롤러(`query.is_using_item && query.is_item_name_any('slot.weapon.mainhand', 'ns:item')` → `on_entry` `/function`)로도 가능하다.

### Molang 사용 규칙

- Molang은 왼쪽에서 오른쪽으로 단락 평가한다. `!q.is_in_ui && ...`처럼 검사를 앞에 두면 "called on an entity with no actor" 오류를 피한다. 불리언 쿼리는 `q.is_sprinting == true` 대신 `q.is_sprinting`, `!q.is_sprinting`으로 쓴다.
- `q.scoreboard`는 BP에서만, `q.is_local_player`는 RP에서만 쓸 수 있다.
- `math.clamp(value, min, max)`는 인자가 3개다. 삼항 안에서 대입하는 대신 `q.in_range(v, lo, hi)`를 쓴다.
- RP만으로는 플레이어 사이의 거리를 얻을 수 없다.

## 7. 클라이언트에 등록된 명령 (Windows 1.26.65.1)

클라이언트 코드의 명령 등록 함수와 게임 안 실행 결과를 공식 `mojang-commands.json`(1.26.50.4)과 비교한 것이다. 게임 안 실행은 치트를 켠 크리에이티브 월드에서 했고 응답은 CommandOutput 패킷의 메시지 키로 읽었다. 치트를 끈 월드에서는 몇 명령만 따로 쳐 보았다(7.2).

### 7.1 권한과 플래그

등록 함수는 명령 이름, 설명 키, 권한 바이트, 16비트 플래그 두 개를 받는다. 두 플래그는 OR로 합쳐 명령 기록의 16비트 값이 된다 `{코드}`.

- 플래그의 `0x80` 비트는 치트가 필요 없다는 뜻이다. 이름이 풀리고 `mojang-commands.json`에 있는 74개 명령에서 `requires_cheats`는 이 비트가 꺼져 있다는 것과 74건 모두 일치했다. 같은 74개의 권한 바이트도 `permission_level`과 모두 일치하므로 0에서 4까지의 숫자는 공식 문서의 체계와 같다(0은 `help`, `list`, `me`, `tell`, `packstack`, 2는 `op`, `deop`, `permission`, `place`, `reload`, `script`, `wsserver`, 3은 `setmaxplayers`, 4는 `allowlist` 계열, `stop`, `transfer`, 나머지 대부분은 1) `{코드}`.
- `gamerule`은 권한 1에 `0x80`이다. 문자열 `commands.gamerule.type.nocheatsenabled`가 있어, 명령은 치트 없이 열리고 규칙별로 치트 필요 여부를 따로 막는 구조로 보인다 `{코드, 추론}`.
- 명령 열거형 값은 소문자여야 한다. 등록되지 않은 키워드는 `Keywords in commands need to be lower case. '%s' was not registered.`로 거부된다 `{코드}`.
- 서버가 보낸 명령 목록(AvailableCommands)을 받아 등록하는 경로도 같은 등록 함수를 쓰고 권한과 플래그를 패킷 항목 그대로 넘긴다. 클라이언트 쪽 플래그는 서버가 정하고 해석은 같다는 뜻이다 `{코드}`.

| 플래그 | 명령 | 뜻 |
|---|---|---|
| `0x80` | `gamerule`, `list`, `packstack`, `kick`, `project`, `party`, `tell`, `tellraw`, `me`, `say`, `op`, `deop`, `permission`, `help` | 공식 JSON에 있는 명령에서는 치트 없이 사용 가능과 일치. `party`는 공식 JSON에 없고, 치트를 끈 월드에서 쓸 수 있는 것은 확인하지 못했다(7.2) |
| `0x40` | `tell`, `tellraw`, `me`, `say`, `title`, `titleraw` | 채팅 메시지 형식 명령 묶음으로 보인다. 공통점만 확인했다 `{추론}` |
| `0x10` | `help` | 로컬 처리로 보인다 `{추론}` |
| `0x20` | `script`, `wsserver` | 디버거와 웹소켓 계열이라는 공통점만 확인했다 `{추론}` |
| `0x400` | `op`, `deop`, `permission` | 편집기 객체가 있고 이 비트가 켜져 있으면 `commands.generic.disabled.editorLocked` 오류로 간다 |
| `0x2`, `0x4`, `0x8` | 아래 7.2 표의 `0x6` 명령, `lesson`(`0x4`), `codebuilder`(`0x4`) | 실행 주체 종류별 "차단" 비트다. 명령 기록에 비트가 켜져 있고 실행 주체가 그 종류이면 권한 수준과 상관없이 `commands.generic.error.permissions`로 거부된다. 플레이어는 `0x4`, 명령 블록과 명령 블록 마인카트는 `0x2`, 자동화 플레이어 계열은 `0x8`이다. 코드로 확정한 것은 종류 숫자(0은 `0x4`, 1과 2는 `0x2`, 5와 6은 `0x8`)이고 종류 이름은 `{추론}`이다 `{코드}` |

실행 직전 검사는 이 순서다 `{코드}`. 실행 주체의 권한 수준이 명령 권한보다 작으면 거부한다. 권한이 충분하면 실행 주체 종류를 위 비트로 바꿔 명령 플래그에 그 비트가 켜져 있는지 본다. 켜져 있으면 거부하고, 꺼져 있으면 실행한다. 종류 3, 4와 7 이상은 비트가 없어 이 검사를 건너뛴다. 거부 문구는 일반 클라이언트에서 항상 `commands.generic.error.permissions`이고, 교육판 차단 목록이 있는 플레이어만 `commands.generic.blocked_edu`가 나올 수 있다. 구문 분석이 이 검사보다 앞서므로 인자 없는 `/gettopsolidblock`은 `commands.generic.syntax`다. 등록 때 전역 불리언이 참이면 세 비트가 모두 지워져 어느 출처에서도 쓸 수 있다. 그 불리언이 어느 설정인지는 읽지 못했다. 자동완성에서 명령을 숨기는 비트는 찾지 못했다 `{코드}`.

치트를 켠 일반 크리에이티브 월드의 실측은 이렇다 `{실측}`.

- 서버가 보낸 명령 목록에 `gettopsolidblock`, `querytarget`, `listd`, `agent`는 있었고, 위 표의 나머지 명령(`closechat`, `closewebsocket`, `enableencryption`, `getchunkdata`, `getchunks`, `getspawnpoint`, `resourceuri`, `takepicture`, `ability`, `codebuilder`, `lesson`, `classroommode`, `worldbuilder`, `immutableworld`)은 이름이 없었고 실행하면 `commands.generic.unknown`이었다. 이 월드에서는 등록되지 않았거나 숨겨진 것이다. `geteduclientinfo`, `getlocalplayername`, `gametips`, `globalpause`는 응답으로 구분하지 못했다(목록에는 없었다).
- `/gettopsolidblock`은 `commands.generic.syntax`, `/gettopsolidblock ~ ~ ~`는 `commands.generic.error.permissions`였다. `/querytarget @s`와 `/listd`도 `commands.generic.error.permissions`였다. 세 명령은 명령으로 존재하고 이 월드의 플레이어 채팅으로는 거부된다. 이유는 권한 수준이 아니라 플래그 `0x6`의 `0x4`(플레이어 출처 차단)다. 호스트 권한 수준을 올려도 플레이어 채팅에서는 풀리지 않는다 `{코드}`. 출력 내용은 거부 때문에 재지 못했다. `/agent`는 `commands.generic.syntax`(구문 안내)였다.
- 플래그 `0x6`이 붙은 명령 중 어떤 것은 목록에 있고 어떤 것은 없었다. 이 플래그는 실행 직전 검사에서만 읽히고 목록 전송을 막는 곳은 코드에서 찾지 못했다. 목록에 나오는지는 서버 쪽 등록이 정하는 것으로 보인다 `{코드, 추론}`.
- `gettopsolidblock`, `querytarget`, `listd`를 실제로 돌릴 수 있는 출처는 플레이어(`0x4`)와 명령 블록(`0x2`)이 아닌 쪽, 곧 웹소켓 접속 같은 자동화 출처로 추정한다. 출처 종류의 이름과 이 가정은 측정하지 않았다 `{추론}`.

치트를 끈 단일 플레이어 월드(Windows 1.26.65.1)에서 채팅으로 입력한 결과는 이렇다 `{실측}`.

- `/party hello`는 `CommandRequest` 패킷이 나가지 않고 로컬 메시지 "이 세계에서는 치트를 사용할 수 없습니다."만 나왔다. 없는 명령 `/zzzfoo`와 같은 결과이고, 자동완성에서 `/p`는 `packstack`, `permission`, `deop`, `help`, `op`만 나왔다. 이 월드에서는 `party`가 등록되지 않았거나 숨겨져 있다. 권한 0과 플래그 `0x80`만으로는 쓸 수 있다고 할 수 없다. 등록이 파티 서비스 조건 뒤에 있다는 코드 읽기와 맞는다 `{코드}`.
- `/listd`, `/gametips`, `/querytarget @s`, `/gettopsolidblock ~ ~ ~`, `/agent`, `/getchunks`, `/getlocalplayername`, `/closechat`, `/closewebsocket`, `/ability @s mayfly true`도 모두 패킷 없이 같은 로컬 메시지였다. `/listd`를 입력줄에 끝까지 입력해도 자동완성 항목이 나오지 않았다. 이 월드에서는 보이지 않고 쓸 수 없다.
- 대조로 `/list`는 패킷이 나가고 `commands.players.list`(파라미터 `["1","8"]`)와 이름 목록이 돌아왔다.
- 치트를 끈 상태에서 `listd`와 `gametips`가 거부된 원인은 권한 수준이 아니다. `listd`는 플래그 `0x6`이라 플레이어 출처에서는 막힌다. `op-permission-level=4`에서 게임 안에서 `listd`가 보인다는 서술은 원격 서버 조건이고 이 측정에서는 확인되지 않았다.

### 7.3 공식 JSON에 없는 명령의 문법

클라이언트의 등록 함수에서 오버로드 등록 호출과 인자 이름, 인자 형식 객체를 읽어 짝지은 것이다. 인자가 둘 이상이면 순서와 선택 여부를 확정하지 못했다. 서버가 보내는 AvailableCommands 패킷을 덤프하면 확정된다 `{코드}`.

| 명령 | 문법 |
|---|---|
| `gettopsolidblock` | `<position: x y z>`. 출력 키 `position`, `blockName`. 오류 `commands.gettopsolidblock.notfound`, `commands.generic.invalidcontext` |
| `querytarget` | `<target: target>`. 대상마다 `uniqueId`, `id`, `yRot`, `position`, `dimension`, `details`를 낸다. 성공 키 `commands.querytarget.success`, 대상 없음 `commands.generic.noTargetMatch` |

### 7.4 별개 명령이 아닌 이름 정정

`spawnParticleEmitter`, `screenshake`, `transferserver`는 별개 명령이 아니라 `particle`, `camerashake`, `transfer`의 설명 키 이름이다. 등록 함수의 이름 값을 풀면 각각 `particle`, `camerashake`, `transfer`이고 설명 키만 `commands.spawnParticleEmitter.description`, `commands.screenshake.description`, `commands.transferserver.description`이다 `{코드}`. 그래서 바닐라 lang의 `commands.spawnParticleEmitter.description=Creates a particle emitter`는 `particle` 명령의 설명이다. 권한은 `particle` 1, `camerashake` 1, `transfer` 4로 공식 JSON과 같다.

실측에서 `/spawnParticleEmitter`, `/screenshake`, `/transferserver`는 모두 `commands.generic.unknown`이었다. `/particle minecraft:villager_happy ~ ~2 ~`의 성공 키가 `commands.spawnParticleEmitter.success`, `/camerashake add @s 1 2`의 성공 키가 `commands.screenshake.success`였다. `/transfer KimPresent 127.0.0.1 19999`는 `commands.generic.error.permissions`로 거부돼 월드를 떠나지 않았다. `transfer`의 인자는 `owner`, `server`, `port`(정수, 선택)이고 구문이 틀리면 `commands.generic.syntax`다 `{실측}`.

### 7.5 게임규칙

클라이언트의 `gamerule` 등록은 열거형 `BoolGameRule`, `IntGameRule`, `FloatGameRule` 셋을 만든다. 공식 JSON에는 `FloatGameRule`이 없다(`BoolGameRule`, `IntGameRule`, `playerwaypointsRule`, `playerwaypointsValues`뿐). 게임규칙 레지스트리는 규칙 39개를 만든다. 실수형 규칙은 하나도 없고 값 읽기와 쓰기 코드만 구현돼 있어서 `FloatGameRule`은 빈 열거형으로 읽힌다(자동완성에 항목이 없을 것, 측정하지 않았다 `{추론}`). 공식 JSON(1.26.50.4)의 38개 이름은 모두 있고, JSON에 없는 규칙은 `locatorbar` 하나다. `locatorbar`는 예전 세이브의 키 이름이다. 월드 데이터를 읽을 때 이 키가 `playerWaypoints`의 초기값으로 바뀐다(키가 없거나 true이면 1, false이면 0). `locatorbar`가 `/gamerule` 자동완성에 나오는지는 열거형 등록 코드가 이 규칙을 빼지 않는 것으로 보여 나올 가능성이 높지만 측정하지 않았다 `{코드, 추론}`.

규칙 순서와 이름, 형식, 기본값, 치트 필요 여부를 클라이언트 레지스트리에서 읽은 것이다. 이름은 레지스트리의 표기이고 명령에는 소문자로 노출된다(열거형 값은 소문자여야 한다는 검사와 맞는다 `{코드, 추론}`). 치트 필요가 "필요"인 규칙은 치트를 끈 월드에서 `/gamerule`이 `commands.gamerule.type.nocheatsenabled`로 막는다 `{코드}`.
