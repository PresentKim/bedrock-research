애드온을 BP/RP 소스에서 게임용 팩으로 만드는 빌드 도구와 템플릿 언어, 배포 경로를 다룬다. 작은 애드온은 도구 없이 `development_behavior_packs`에 직접 넣어도 되지만, 필터로 JSON을 생성하거나 TypeScript를 번들하거나 여러 환경에 내보내려면 컴파일러가 필요하다.

| 도구 | 하는 일 | 라이선스 |
|---|---|---|
| Regolith | 프로젝트 폴더를 복사하고 필터를 돌려 com.mojang으로 내보내는 애드온 컴파일러(Go) | MIT |
| jsonte | JSON 템플릿 엔진과 질의 언어(Go, Regolith 필터) | MIT |
| bedrock-boost | Script API용 유틸리티 라이브러리(npm) | MIT |
| `@minecraft/core-build-tasks` | Mojang 공식 just-scripts 배포 작업 | Microsoft 패키지 |

## Regolith

**하는 일.** `bridge. v2`처럼 "프로젝트 폴더"(RP, BP, 모델, 텍스처, 설정을 한 폴더에)를 쓰고, 가장 단순한 경우 RP와 BP를 com.mojang 폴더로 "컴파일"(복사)한다. 복사 중에 필터(프로그램)를 순서대로 돌려 파일을 변환한다. 가치는 여러 언어로 만든 도구를 하나의 컴파일 흐름에 묶는 데 있다(출처: tool-regolith, `README.md`, MIT, Copyright 2021 Bedrock-OSS, 조사 커밋 `eeaf064`). 필터는 프로그램이므로 믿을 수 있는 것만 실행한다.

**설치.** 사용자용 설치 안내는 문서의 Installation 절이고(winget, MSI, Homebrew 등 채널 차이는 아래 노트), 소스에서 받으려면 Go가 필요하다.

```bash
go install github.com/Bedrock-OSS/regolith@latest
```

**기본 명령.**

```bash
regolith init                 # config.json이 있는 프로젝트 만들기
regolith install jsonte       # 필터 레지스트리에서 필터 설치
regolith install-all          # config의 모든 필터 설치
regolith run dev              # profile 하나 실행 후 export
regolith watch dev            # 파일이 바뀔 때마다 다시 실행
regolith apply-filter <필터>   # 필터 결과를 소스에 반영
```

게임에서는 `reload all`로 다시 불러온다(스크립트와 함수만이면 `reload`).

**config.json.** 프로젝트 루트의 `config.json`은 팩 경로, profile, 필터 정의, export 대상을 적는다. 저장소 테스트 프로젝트에서 가져온 최소 예다.

```json
{
  "$schema": "https://raw.githubusercontent.com/Bedrock-OSS/regolith-schemas/main/config/v1.2.json",
  "name": "my_project",
  "author": "me",
  "packs": { "behaviorPack": "./packs/BP", "resourcePack": "./packs/RP" },
  "regolith": {
    "profiles": {
      "dev": {
        "filters": [ { "filter": "test_exe_filter" } ],
        "export": { "target": "development", "readOnly": false }
      }
    },
    "filterDefinitions": {
      "test_exe_filter": { "runWith": "exe", "exe": "./executables/test_exe_filter" }
    },
    "dataPath": "./packs/data"
  }
}
```

`runWith`는 필터 실행 방식(`python`, `nodejs`, `deno`, `bun`, `shell`, `exe`, `dotnet` 등)이고 `data` 폴더에는 필터별 데이터를 둔다. export 대상은 `development`(com.mojang의 development 폴더), `local`, `exact`(경로 직접 지정) 등이다. com.mojang 경로는 사용자 환경변수 `COM_MOJANG`으로 지정하는 것이 권장이다.

**한계.**
- 프로젝트당 BP와 RP가 하나씩이고 임시 폴더 이름은 `BP`, `RP`, `data`로 고정이다.
- `regolith watch`는 필터가 소스를 수정하면 무한 루프가 돈다.
- 큰 프로젝트에서는 필터 입출력이 시간을 대부분 쓴다(jsonte가 자주 범인).
- 릴리스 바이너리가 일부 백신에 오탐된다.

세부(1.6~1.8 릴리스별 기능, 러너, 필터 개발, 다중 팩)는 아래 노트에 있다.

## jsonte (JSON Templating Engine)

**하는 일.** Minecraft 애드온처럼 반복되는 대량 JSON을 적은 스크립트로 생성하는 JSON 전용 템플릿 엔진이다. 자체 질의 언어를 가진다. 온라인 데모와 인터랙티브 튜토리얼이 `mcdevkit.com`에 있다(출처: tool-jsonte, `README.md`, MIT, Copyright 2021 MCDevKit, 커밋 `73a3c3b`).

**설치.**

```powershell
regolith install jsonte                       # Regolith 필터로
go install github.com/MCDevKit/jsonte@latest  # 독립 실행 (Go 1.18 이상)
```

소스 개발은 `go mod vendor` 후 `scripts` 폴더의 ANTLR 설정과 문법 컴파일 스크립트를 실행하고 `go build`한다. VS Code 확장은 `MCDevKit.jsonte-vscode`다. 한계는 위 Regolith와 같은 성능 문제(Deno만 쓰는 구성이 5000파일을 1초 안에 컴파일하는 데 jsonte를 더하면 약 10초)와 문법 학습 비용이다.

## bedrock-boost

**하는 일.** Script API 개발 보조 라이브러리로 `Vec3` 벡터, 차원 조회와 블록 permutation을 캐시하는 `Cache`(네이티브 호출 감소), 플레이어 폴리필(`applyImpulse`, `clearVelocity`), `console.log`를 채팅으로 보내는 폴리필, 프로파일링 보조(`addIdleDummy`), `Timings`, 레벨·태그·필터가 있는 `Logger`, `ChatColor`, `ColorJSON`, 작업을 틱에 나누는 `PulseScheduler` 계열(`PlayerPulseScheduler` 등), `BlockUtils`, `CommandUtils`, `EntitySaver`, `JobUtils`를 제공한다(출처: tool-bedrock-boost, `README.md`, MIT, Copyright 2023 Bedrock-OSS, 커밋 `1314f85`).

```bash
npm install @bedrock-oss/bedrock-boost
```

```typescript
import { Vec3 } from "@bedrock-oss/bedrock-boost";
import { world } from "@minecraft/server";

world.beforeEvents.itemUse.subscribe((event) => {
  event.source.applyImpulse(Vec3.from(event.source.getViewDirection()).setY(0).normalize().multiply(2));
});
```

로거는 `Logger.getLogger("main", "tag1")`로 얻고 `scriptevent logging:level <레벨>`로 레벨을 바꾼다. 번들러(esbuild 등)가 필요하고 [Script API 개요](../scripting/overview-and-modules.mdx)의 번들링 규칙을 따른다.

## 커뮤니티 노트

아래는 커뮤니티 조사로 모은 GDK 경로 이동, Regolith 릴리스와 버그, 필터 생태계, 그 밖의 빌드 도구, TypeScript 개발 도구, 커뮤니티 라이브러리와 Molang 도구다.

`(confirmed)`, `(single report)`, `(conflicting)` 같은 말은 보고의 신뢰도 표시다.

### GDK 경로 이동과 배포

- **경로**: 1.21.120(2025-10)부터 `%AppData%\Minecraft Bedrock\Users\Shared\games\com.mojang`(공유)와 `...\Users\<개인별 숫자>\games\com.mojang`(사용자별)를 쓴다. 예전 UWP LocalState 경로는 쓰지 않는다. 이동 과정에서 dev 팩이 지워진 것처럼 보이는 사례가 있었다. 개발 팩은 Shared에 둔다. 이주 문서: `https://learn.microsoft.com/en-us/minecraft/creator/documents/gdkpcprojectfolder?view=minecraft-bedrock-stable` , `https://jaylydev.github.io/posts/bedrock-gdk/#restore-your-data` (confirmed)
- **중복 dev 팩**: 이주 중에 숫자 폴더에 dev 팩이 중복으로 생겨 `/reload all`이 새 파일을 못 보는 것처럼 보인 사례가 있다. 중복 팩(오래된 사본)이 있으면 변경이 반영되지 않는다.
- **멀티플레이 텍스처 캐시**: GDK 이후에는 `%temp%/Minecraft Bedrock` 아래에 있다. 리소스 팩 캐시가 `%LOCALAPPDATA%\Temp\minecraftpe\packcache\resource`에 있고 `AppData\Roaming\Minecraft Bedrock\premium_cache`에는 스킨 데이터만 있다는 다른 보고도 있다(**conflicting**). OneDrive가 폴더를 리디렉션할 수도 있다. content log는 `AppData/Roaming/Minecraft Bedrock/logs`에 쌓이는데, 켜 두면 수십 GB까지 커질 수 있다. 바닐라 게임 파일은 `C:\XboxGames` 아래에 있다.
- **`@minecraft/core-build-tasks` local-deploy**: ^5.5.0(또는 latest)으로 올리고 `.env`의 product를 `MINECRAFT_PRODUCT="BedrockGDK"`로 바꾼 뒤(이전 값은 MinecraftW8P/UMP) `npm run local-deploy -- --watch`를 실행한다. 새 starter 프로젝트를 만드는 방법도 있다.
- **Junction 스크립트**: LuckedCoronet의 PowerShell `mc-link.ps1` gist로 com.mojang에 junction을 만든다. Linux/macOS는 minecraft-linux.github.io를 참고한다.
- **GDK 전환 뒤 지원 상태**: MCPE-tool(jeanmajid)이 GDK 경로를 지원한다. bridge. 컴파일 대상 설정은 `https://wiki.bedrock.dev/guide/project-setup#windows` 를 따른다. Haze(월드 파일 이동 도구)는 경로가 바뀐 뒤 동작하지 않는다.
- **UWP 서버**: UWP는 사라지는 중이지만, 2025-11 당시 많은 서버가 여전히 1.21.94 UWP를 썼다.
- **플랫폼 간 블록 불일치**: GDK 전환 뒤 플랫폼 사이에 "blocks between client and server do not match"가 날 수 있다. 양쪽 버전을 맞춘다. (single report)
- **loopback 예외**: BDS 문서의 loopback 예외/UPnP loopback은 UWP 제약이었고 GDK에서는 필요 없다. 예전 방식은 `CheckNetIsolation.exe LoopbackExempt -a -p=<SID>`다.
- **여러 인스턴스 실행**: GDK에서는 설치를 복제해야 한다(복제한 exe는 시작 화면을 건너뛴다).
  - gdk-version-archiver(`gdkva`, github.com/conmaster2112/gdk-version-archiver, npm, Bun 필요): `gdkva archive --tag=stable`, `gdkva archive *windowsbeta* --tag=preview`, `gdkva list`, `gdkva run --tag=stable`.
  - 2026-03 프리뷰에서는 다중 인스턴스가 깨졌다. 계정 전환은 Xbox 로그인에 묶여 있다.
  - 같은 계정으로 한 월드를 두 인스턴스에서 열 수는 없다(Blaze 오류).
  - 설치된 GDK 파일은 패키지 컨텍스트 안에서 복사한다. 예: `Invoke-CommandInDesktopPackage -PackageFamilyName "Microsoft.MinecraftUWP_8wekyb3d8bbwe" -App Game -Command "powershell" -Args "-Command Copy-Item 'C:\XboxGames\Minecraft for Windows\Content' -Destination 'C:\MinecraftBedrockInstances' -Recurse"`. Preview는 `Microsoft.MinecraftWindowsBeta_8wekyb3d8bbwe`와 `C:\XboxGames\Minecraft Preview for Windows\Content`를 쓴다. 복사한 폴더의 exe로 로그인하려면 GDK 도구 `wdapp`으로 폴더를 등록한다.
  - MCLauncher(`https://github.com/MCMrARM/mc-w10-version-launcher`)는 PR #359로 GDK 빌드를 지원한다.
- **버전 보관**: GdkLinks의 `urls.json`(`https://raw.githubusercontent.com/MinecraftBedrockArchiver/GdkLinks/refs/heads/master/urls.json`)이 버전별 다운로드 URL을 모으고, Archiver(`https://github.com/MinecraftBedrockArchiver/Archiver`)가 빌드를 보관한다(Viewer는 메타데이터만 보여 주고 보관본은 약 1TB다). 옛 preview 빌드는 몇 주 뒤 받을 수 없게 된다. Xbox 앱은 assets2.xboxlive.com의 `.msixvc`를 받는다.
- **사용자 폴더 이름**: `Users\<숫자>` 폴더 이름은 XUID 10진 문자열의 UTF-8 바이트를 FNV-1 64(FNV-1a가 아님)로 해시한 값이다. 게임은 팔레트 블록 정렬에 fnv1_64, 블록 해시에 fnv1a_32를 쓴다는 설명이 있다.
- **dev 팩 위치**: `development_*_packs`를 `Minecraft.Windows.exe`와 같은 폴더에 두어도 인식된다는 보고가 있다(월드는 com.mojang에 있다). (single report)
- **MCBE 프로토콜 URI**: 2025-10 말 GDK 릴리스에서 Editor를 빼고는 대부분 동작하지 않다가 나중에 복구됐다.
- **Linux 경로**: Wine/GDK에서는 com.mojang 안의 `development_*_pack`이 동작하지 않는다(원인 미상). mcpelauncher는 네이티브와 flatpak 두 위치를 쓴다.

### 다른 OS에서 개발하기

- **WineGDK** (`https://github.com/Weather-OS/WineGDK`): GDK 빌드를 Wine으로 돌린다.
  - vkd3d가 wineD3D보다 빠르고 Vibrant Visuals가 동작한다. 약 40청크를 넘으면 크래시한다는 보고가 있다.
  - AMD에서 Vulkan을 강제하면 크래시하고 NVIDIA는 동작했다. GE-Proton으로 preview에 로그인한 사례가 있다(2026-04).
  - 파일 대화상자 문제로 구조물 export가 실패한다.
  - 새 prefix에서 설정이 초기화되므로 `options.txt`를 백업하거나 읽기 전용으로 둔다.
  - 같은 기기에서 Android 빌드가 AMD에서 약 두 배 빠르다는 보고가 있다. (single report)
- **Linux 런처**: BedrockOnLinux(`https://github.com/Wyze3306/BedrockOnLinux`), umu/WineGDK GE-Proton 런처, mcpelauncher-linux(`https://github.com/minecraft-linux/mcpelauncher-manifest`), mcarm.
- **macOS**: macrock(`https://github.com/vincenzopio/macrock`), blockintosh.multision.dev, nyx 래퍼가 있다. Apple Silicon의 PlayCover는 iOS판을 돌리지만 로그인할 수 없다. 개발은 Windows VM으로 하는 경우가 많은데, Parallels에서는 Store 설치가 막히고 arm64 빌드가 없다.
- **Windows와 Android 런처**: Amethyst, LeviLaunchroid(`docs.levimc.org/LeviLaunchroid/`, Android 모드 로더는 없다), Bedrock Launcher(UWP 시절 이전 버전 고정). LeviLauncher(GPL-3.0)는 버전 격리와 .zip/.dll 모드를 지원하고, LeviLamina 통합은 GDK 빌드에서만 된다.

### Regolith

#### 기본
- **동작 방식**: `regolith run`/`regolith watch`는 프로젝트를 복사하고 필터를 돌린 뒤 `development_behavior_packs`/`development_resource_packs`로 export한다. 게임에서는 `reload all`(스크립트와 함수만이면 `reload`)로 다시 불러온다. 필터는 프로그램이므로 믿을 수 있는 것만 실행한다. 문서: `https://regolith-docs.readthedocs.io/en/stable/introduction/introduction/`
- **Python 필터**: `python` 명령을 쓴다(Windows는 `python` 다음 `python3`, Linux는 반대 순서). 외부 모듈이 없으면 기본 인터프리터로 돌기 때문에 `.regolith/cache/venvs`가 비어 있다. 버전을 고르려면 PATH 맨 앞에 둔다.
  - bump_manifest는 Python 3.9+가 필요하다(1.1.1이 새 manifest를 지원한다).
  - Python 3.15의 install manager는 `Scripts`를 PATH에 넣지 않으므로 `python -m pip`를 쓴다.
  - PATH 항목 끝에 `\`가 있으면 "Python version check failed"가 난다.
- **설정 위치**: Regolith는 `.env`를 읽지 않는다(1.7.0부터 지원). config.json은 프로젝트 단위 설정이므로 머신별 경로는 환경변수에 둔다.
- **업데이트 채널**: winget 업데이트는 UnownBot PR로 처리되어 약 1주 늦을 수 있다. 빨리 받으려면 MSI를 쓴다. 릴리스 바이너리는 Malwarebytes에 오탐된다. Homebrew(goreleaser `brews`, PR #362)는 2026-07-17 develop에 머지됐고 다음 릴리스부터 나온다.
- **스튜디오 사용**: XP Games는 모든 프로젝트에 Regolith를 쓴다. 필터 몇 개를 한 언어로만 쓰면 이득이 적다는 의견이 있다. 필터는 컴파일 언어로도 쓸 수 있다. Windows ARM 지원 질문에는 답이 없었다.
- **기여 규칙**: fork해서 `develop` 브랜치를 대상으로 한다(`main`은 릴리스용이라 뒤처져 있다). 새 기능은 문서(docs 저장소, Bedrock-OSS/regolith-schemas)를 갖춘 뒤에 릴리스한다. 로고와 에셋: `https://github.com/Bedrock-OSS/regolith-docs/tree/main/docs/_static`

#### GDK 경로와 export target
- **권장 방법**: 사용자 환경변수 `COM_MOJANG`을 `development_behavior_packs`와 `development_resource_packs`가 있는 폴더로 설정한다. 다른 방법은 config.json에 `exact` target으로 경로를 적는 것인데, 머신마다 달라서 팀에서는 환경변수가 낫다. (confirmed)
- **환경변수 적용 시점**: 환경변수는 설정 이후에 시작한 프로세스에만 보인다. 통합 터미널만이 아니라 VS Code 창을 전부 닫는다. "여전히 예전 경로로 export된다"는 보고 대부분이 이 경우였다.
- **안 되는 방법**: profile `export` 블록 안의 `"COM_MOJANG": "..."`는 `"target": "development"`에서 동작하지 않는다. 환경변수를 쓰거나 `"target": "local"`/`exact`를 쓴다.
- **환경변수 목록**: `COM_MOJANG`, `COM_MOJANG_PREVIEW`, 그리고 각 문맥에서 우선하는 `COM_MOJANG_PACKS`, `COM_MOJANG_WORLDS`, `COM_MOJANG_PACKS_PREVIEW`, `COM_MOJANG_WORLDS_PREVIEW`가 있다. 보통은 아무것도 설정하지 않는다. export 경로 안에서는 `%var%`와 함께 `${var}`, `$var`도 쓸 수 있다(1.6.0). 문서: `https://regolith-docs.readthedocs.io/en/stable/project-configuration/export-targets/#export-target-environment-variables` , 경로 결정 방식: `https://regolith-docs.readthedocs.io/en/1.6.0/project-configuration/export-targets/#how-does-regolith-determine-the-com-mojang-path`
- **UWP 폴백 없음**: 1.6.0부터 GDK 경로가 기본이고 UWP로 폴백하지 않는다. UWP 사용자는 환경변수를 설정해야 한다. 다른 도구에서는 `output: "stable"|"preview"|"stable_uwp"|"preview_uwp"` 같은 방식도 논의됐다.
- **다중 export target(1.8.0)**: 프로필당 여러 target을 리스트로 지정할 수 있다. `https://regolith-docs.readthedocs.io/en/stable/project-configuration/export-targets/#single-or-multiple-export-targets`

#### watch 모드와 알려진 버그
- **필터가 소스를 수정하면 무한 루프**: 같은 내용으로 다시 써도 루프가 돈다. 예를 들어 gametests 필터가 `package.json`의 modules를 고치면 루프가 돌므로 필터 settings로 설정한다. `node_modules`를 지울 때까지 루프가 돈 사례도 있다. `runWith: shell` 필터(예: prettier)로 소스를 포맷해도 루프가 돈다. 소스에 반영하려면 `regolith apply-filter`를 쓴다.
- **`"when": "initial == true"` 반복 실행(2026-03~04)**: 필터가 pack/data 폴더에 쓰면 중단된 빌드가 `initial`이 true인 채로 다시 시작해 계속 반복된다. 필터는 `initial`을 직접 읽을 수 없다. 제안: `when` 스코프를 JSON 환경변수로 넘기거나 `data`에 `regolith-meta.json`을 쓰는 것.
- **RP/BP 디렉터리가 없을 때**: `regolith watch`는 "Could not start watching" 오류를 내고, `run`은 경고만 낸다. 빈 문자열 경로는 건너뛴다. BP만 정의해도 `development_resource_packs`에 빈 RP 폴더를 만드는 버그가 있다(`regolith/profile.go`).
- **재귀 파일 감시**: fsnotify는 공식적으로 Windows만 지원한다. regolith는 arexon의 포크로 Linux에서 강제로 쓴다. 2026-10-30 기준 `regolith watch`는 macOS에서 동작하지 않고, 이를 고치는 PR(`https://github.com/Bedrock-OSS/regolith/pull/349`)은 Windows 버그 때문에 머지되지 않았다. macOS는 FSEvents로 재귀 감시를 지원하고 트리를 직접 훑어야 하는 쪽은 Linux(inotify)라는 설명이 있다. macOS에서는 수동 `regolith run`이나 아래 rgl 브랜치를 쓴다.
- **빠른 편집 누락**: 아주 빠르게 연속 편집하면 watch가 dev 폴더를 갱신하지 못할 때가 있다(원인 미확인).
- **병렬 필터의 효과**: 대부분의 필터가 앞 필터의 출력에 의존해서 속도 이득이 드물다. 오류가 나면 필터 하나의 오류만 보고된다.

#### 러너 (Node, Deno, Bun)
- **Deno와 Bun**: Deno는 `require()`/`import()`를 쓰는 필터(비 CJS 스코프의 `require()`)에서 실패한다. `require("node:os")`는 Deno에서 동작한다. gametests 필터는 bun에서 동작하지 않을 수 있다. Node에는 regolith가 플래그를 넘기지 못하므로 `exe` 필터를 우회로로 쓴다(`"bun": {"runWith":"exe","exe":"filters/bun/bun.exe"}`). Node 24는 기본으로 TS 타입을 벗겨낸다. Regolith는 Deno 필터를 모든 권한으로 실행한다.
- **성능**: 전부 Deno인 필터 구성은 5000파일 프로젝트를 1초 안에 컴파일한다. jsonte를 더하면 약 10초가 된다.
- **TS watch 병행**: `concurrently`로 regolith와 함께 돌리거나, 필터로 트랜스파일하는 편이 낫다(gametests 필터가 esbuild로 번들한다).

#### 필터 개발
- **입력 받기 금지**: Python `input()`은 stdin이 연결돼 있지 않아 EOFError가 난다. 오류를 던지거나 profile settings를 쓴다. 필터가 오류를 던지면 전체 실행이 멈춘다.
- **`data` 폴더**: `data/<filtername>`은 기본으로 읽기 전용이다. `exportData: true`이면 소스에 다시 쓴다. 바깥에 쓰려면 환경변수 `ROOT_DIR`(프로젝트 루트)을 쓰는 편이 낫다. 필터의 `test` 폴더는 캐시 다운로드에서 빠진다.
- **설정 설계**: 필터는 profile/필터 이름으로 의도를 추측하지 말고 profile별 settings를 받는다. 필터 settings에는 JSON 스키마를 붙일 수 없으니 config 전체용 스키마를 직접 만든다. 필터 config에서 PascalCase와 snake_case 키를 섞지 않는다.
- **배포**: 필터 저장소에 `node_modules`를 커밋하지 않는다(`regolith install`/`install-all`이 설치한다). 버전은 git 태그 `<filter-name>-<semver>`(예: `git tag loot_tabler-1.0.0`)로 붙인다. 문서: `https://regolith-docs.readthedocs.io/en/stable/developing-filters/publishing-filters/#versioning-your-filter`
- **필터 레지스트리**: Bedrock-OSS/regolith-filter-resolver(`https://github.com/Bedrock-OSS/regolith-filter-resolver`)에 PR로 항목을 추가해야 `regolith install <name>`이 동작한다. 커스텀 resolver를 붙일 수도 있다(예: `regolith config resolvers --append github.com/Alien-Edds/Regolith-Filters/resolver.json`). brarchive 필터처럼 표준 저장소에서 거절된 필터는 자기 저장소에 호스팅한다.
- **filter-manifest PR #323**: 릴리스 zip URL로 실행 파일 필터를 배포하자는 PR인데, 비공개 저장소 인증 문제로 정체 중이다.
- **`regolith install --profile`**: 설치한 필터를 그 profile에 추가할 뿐이다.
- **다른 starter 필터를 쓰는 profile**: `{ "filter": "starter_filter", "settings": {...}}, {"profile": "main_profile"}`로 만든다. go-simple-eval의 `profile` 변수는 중첩된 경우에도 현재 profile을 담는다.
- **git 버전 얻기**: `ROOT_DIR`에서 `git describe --tags --always --abbrev=0`을 실행한다(태그가 없으면 커밋 id가 나온다).

#### 프로젝트 구조와 다중 팩
- **BP/RP 한 쌍**: 프로젝트당 BP와 RP가 하나씩이고, tmp 폴더 이름은 반드시 `BP`, `RP`, `data`다(project-config-standard의 일부이고 bridge.도 쓴다).
  - 우회법: 추가 팩을 `data`에 두고 필터로 복사하거나, profile이나 프로젝트를 나눈다.
  - 제안(Draft PR #363): `filters`에 `{"bpOrder":[0,1],"rpOrder":[1,0]}` 같은 설정 단계를 넣어 tmp의 팩 디렉터리 이름을 바꾸는 방식.
- **Project Config Standard**: `https://github.com/Bedrock-OSS/project-config-standard/` 의 공유 `config.json`에 `name`, `packs: {behaviorPack, resourcePack}`, `targetVersion`을 두고, 각 도구가 자기 네임스페이스 섹션(예: `"bedrock-cli": {...}`)을 더한다.
- **대형 프로젝트 불만**: 컴파일이 30초를 넘고, 병렬 profile이 없다(`regolith run profile1 profile2` 제안).
  - 시간 대부분은 필터 IO에 들고, jsonte가 자주 범인이다. json_cleaner를 Rust로 다시 쓰니 150ms에서 16~20ms가 됐는데, 대부분 단일 패스 알고리즘 덕분이었다.
  - 대안으로 rgl(`https://github.com/ink0rr/rgl`, Rust 재작성)이 있다. `port-missing-features` 브랜치(`https://github.com/ink0rr/rgl/tree/port-missing-features`)에 Regolith를 대체할 기능이 다 있다는 말이 있지만 2026-10-30 기준 main에 머지되지 않았다.
  - Molang 한 줄 제한은 프로젝트 컴파일러로 해결한다.

### Regolith 필터 생태계와 템플릿 언어

#### JSONTE (stirante, `https://github.com/MCDevKit/jsonte`)
- **설계 원칙**: 템플릿(`.templ`, 모듈 `.modl`)은 그 자체로 유효한 JSON이어야 한다. VS Code에서는 `"files.associations": {"*.templ": "jsonc", "*.modl": "jsonc"}`로 연결한다.
- **2.16.0 (2026-05-28)**
  - 문법: backtick 템플릿 문자열 `` `$&#123;a&#125; + $&#123;b&#125;` ``, `+=`, block lambda, 일급 lambda
  - `.molang` 파일: `#{expr}` 보간, `# ` 주석 제거, minify(`query.foo` → `q.foo`)
  - `.jsonte` scope 스크립트: `$scope.key = value` 형태로 scope를 수정한다.
  - 함수: `loadText(path)`, 구분자 없는 `join()`
  - CLI: `--workers N`(0이면 CPU 코어 수), `jsonte help`, `--scope '{"debug":true}'`, symlink 디렉터리 순환 감지
  - 벤치마크: 2.4배 빠르고 메모리 9.5배 적음. 한 사용자 비교에서 컴파일이 18s에서 3s가 됐다.
- **2026-09 변경**
  - `$molang:` 필드 접두사(예: `$molang:pre_animation`)로 Molang을 minify하고 검증한다.
  - `loadMolang(file, scope)`: 예를 들어 `variable.i = #{test};`에 `{test: 5}`를 주면 `v.i=5;`가 나온다.
  - `brarchive` 지원
  - object shorthand, computed key, 배열 slicing, `in`, else 없는 삼항식, compound assignment, `++`/`--`, 16진수와 과학 표기 리터럴
  - Claude의 도움으로 최적화해 약 80% 빨라졌다고 주장했다.
- **`$scope` 함정**: 같은 scope 안의 값끼리는 `{{=floor(x/y)}}`로 서로 참조할 수 없다(앞 항목이 문자열이나 NaN으로 들어온다). JS로 생성하는 것이 권장 우회법이다.
- **릴리스에서 dev 전용 templ 빼기**: 기본 기능이 없으므로 `dev` 폴더를 지우는 작은 필터나 스크립트를 쓴다.
- **VS Code 확장**: `MCDevKit.jsonte-vscode`. templ/modl 스키마, 자동완성, .molang/.lang/.mcfunction 안의 injection을 지원한다.
- **jsonte 작성자의 "fast json" 파서(Go)**: 전체 파싱과 순회가 91.5µs로 표준 라이브러리 146.8µs보다 빠르다. 키 하나만 읽을 때는 가장 느리다.

#### ModularMC (nusiq, System Template 2)
- **위치**: `https://github.com/Nusiq/regolith-filters` (`modular_mc`), 문서 `https://modular-mc-docs.readthedocs.io` (llms.txt: `https://modular-mc-docs.readthedocs.io/llms.txt`). Deno와 esbuild 기반이다.
- **`{ts: ... :}` 블록은 실제로는 JS다**(`new Function()`): 타입 주석을 넣으면 "Unexpected token ':'"가 난다. 타입 있는 헬퍼는 `.ts`에 두고 `_map.ts`에서 import해 scope로 넘긴다. `_map.ts`를 `.js`로 바꿀 수는 없다.
- **scope JSON 주석**: `import x from "./_scope.json" with { type: "json" }`은 주석을 허용하지 않으므로 `_scope.ts`를 쓴다.
- **기본 `onConflict` 없음**: `terrain_texture.json`, `sounds.json` 등에는 플러그인 함수(예: `defaults([...])`)로 `onConflict: "merge"`를 채운다. `_map.ts`에서 `Deno.writeTextFile(...)`로 파일을 직접 만들 수도 있다.
- **빌드 전용 npm 패키지**: `deno.json`에 넣는다(게임 스크립트가 import하지 않으면 번들에 들어가지 않는다).
- **실행 순서**: 컴파일은 알파벳 순서다. `executionOrder` MAP 속성(1.3.0, 2026-09-14)이 `prioritized_systems`를 대체한다.
- **버전 이력**: 1.1.1(2026-06-05, 병렬 읽기, 약 15% 빠름), 1.2.0(Deno 2.6+에서 `deno.json` 상대 import 수정), 1.3.0(`executionOrder`). config에 `"version": "<commit sha>"`로 고정할 수 있다.
- **예시**: git 버전을 scope에 넣는 `Deno.Command("git", {args:["describe","--tags","--always","--abbrev=0"], cwd: Deno.env.get("ROOT_DIR")})`. `**/*.lang`을 `RP/texts/`에 `onConflict: "appendEnd"`로 붙인다. `__unpack__`과 `::` 표현식으로 terrain_texture 변형을 만든다. map 화살표 안의 `{i}`는 `({i})`로 쓴다.

#### 커뮤니티 기술 토론 (빌드/코드 생성)
- **feature 생성기 패턴(TS)**: `scatterFeature({identifier, feature: singleBlockFeature({block})})` 같은 헬퍼를 둔다. 자식 id는 `__<n>`으로 이어 붙이고(`__1__1` 식 연쇄는 피한다), 속성명은 snake_case로 하고, 클래스보다 인터페이스를 쓴다. arexon의 `https://github.com/arexon/mcbe-types` (`FeatureRule`, `AggregateFeature`, `ScatterDistribution`; features 브랜치)가 있다. 공개된 feature-rule 생성기로는 MachineBuilder 것만 언급됐다. 정의를 BDS 데이터에서 일부 생성할 수는 있다.
- **자주 바뀌는 포맷의 라이브러리 버전 정책**(예: material.bin): 유지보수 여력에 맞춰 정한다. 프로토콜 프로젝트는 최근 3~4개 버전을 지원한다.
- **git 기반 의존성 도구 논의**: `destination`은 실제 clone 위치로 정하는 쪽으로 합의됐다.
- **oxc 툴체인**(oxlint, oxfmt, tsgo, Rolldown): CI의 lint/format/typecheck가 30s에서 10s로 줄었다. VS Code oxc 확장은 불안정하다. IR에서 JS를 내보낼 때는 AST보다 문자열 버퍼 writer를 권한다.
- **스크립트 번들 가이드**: esbuild는 `https://jaylydev.github.io/posts/bundle-minecraft-scripts-esbuild/#project-setup` 을 따르고, rolldown은 약 10줄 설정으로 충분하다는 추천이 있다.
- **TypeScript 컴파일러의 Go 네이티브화**: typescript-go가 2026-08-20 microsoft/TypeScript 본 저장소로 옮겨졌다.
- **런타임 소식**: Bun이 2026-05-14에 Rust 포트를 머지했다. Deno PR `https://github.com/denoland/deno/pull/36194` , `https://github.com/littledivy/v8x` .
