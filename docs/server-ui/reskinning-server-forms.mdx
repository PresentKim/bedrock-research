서버 폼의 글과 버튼은 서버가 정하지만 모양은 클라이언트의 `server_form.json`이 정한다. 서버가 리소스팩을 함께 보내 이 파일을 고치면 같은 폼 데이터로 전혀 다른 화면(상자, 표, 발전과제 트리, 상점)을 그릴 수 있다. 이 페이지는 그 방법을 개념, 구조 예제, 규칙과 실측 순서로 정리한다. 바닐라 폼 구조는 [서버 폼 API와 폼 종류](./modal-forms.mdx)의 8절에 있다.

## 1. 개념: 폼 데이터는 채널이다

JSON UI는 서버가 보낸 폼에서 읽을 수 있는 값이 정해져 있다. 액션 폼에서는 제목(`#title_text`), 본문(`#form_text`), 버튼마다 글(`#form_button_text`)과 아이콘 경로(`#form_button_texture`)다. 이 네 가지가 서버에서 팩으로 가는 데이터 채널이다.

- **화면 고르기**: 제목에 표식 글자를 넣고, 팩이 `#title_text`에 표식이 들어 있는지 검사해 레이아웃을 보이거나 숨긴다.
- **칸 고르기**: 버튼 글 앞에 표식(`§0§X§r`처럼)을 넣어 칸 종류를 고른다.
- **값 싣기**: 버튼 글·본문을 고정 폭 레코드로 만들어 팩이 `'%.Ns'` 슬라이스와 뺄셈(`-`)으로 잘라 읽는다.
- **그림 싣기**: 버튼 아이콘 경로에 `textures/...` 경로 또는 숫자 문자열을 넣는다.

연구 서버 서버는 액션 폼 하나로 메뉴·상점·표·인벤토리 같은 칸·연구 화면(격자 + 상세)·발전과제 트리·도감(레시피 뷰어)·목록 분할 화면·로비 메인 메뉴를 모두 그린다. 화면 종류는 제목 앞 표식(`§d§f§c§r` 등)으로, 칸 종류는 버튼 글 앞 표식으로 고른다 (출처: 비공개 조사).

## 2. 진입 구조: 바닐라 `long_form`을 감싸기

팩이 `server_form.json`을 같은 경로에 두면 바닐라 파일 위에 병합된다. 바닐라의 진입은 `main_screen_content`의 `server_form_factory` 팩토리가 `control_ids`로 `long_form`과 `custom_form`을 잇는 구조다.

### 2.1 하지 말 것: `long_form` 통째로 다시 정의

Chest-UI는 `long_form`을 같은 경로에서 `@` 없이 다시 선언해 `type: panel`과 `controls`를 바꾼다. `controls`는 배열이라 통째로 교체된다. 다른 서버 폼 팩(upgrader 등)도 똑같이 하므로 두 팩을 함께 켜면 팩 순서상 나중 것의 `controls`만 남아 다른 쪽 UI가 사라진다 `{추론}` (출처: repo-chest-ui). Chest-UI의 저장소 구성은 `RP/ui/server_form.json`(재선언), `chest_server_form.json`, `chest_inventory_system.json`, `furnace_server_form.json`, `_global_variables.json`이다 (출처: chest-ui-pack, CC BY 4.0).

### 2.2 감싸기 + 팩토리 추가

BedrockAdvancements 애드온은 `long_form`을 고치지 않고 감싼다. 아래는 원본 구조의 요약이며, 모양만 옮긴 것이다 (출처: 비공개 조사).

```jsonc
{
  "namespace": "server_form",
  // 1. 내 화면: 제목에 'CUSTOMUI:BA'가 포함되면 보임
  "ba_long_form": {
    "type": "panel", "size": ["100%", "100%"],
    "bindings": [
      { "binding_name": "#title_text" },
      { "binding_type": "view",
        "source_property_name": "(not ((#title_text - 'CUSTOMUI:BA') = #title_text))",
        "target_property_name": "#visible" }
    ],
    "controls": [{ "ba_screen@ba_adv.root": {} }]
  },
  // 2. 바닐라(또는 다른 팩이 바꾼) long_form을 감싸서 내 화면일 때만 숨김
  "ba_hideable_long_form": {
    "type": "panel", "size": ["100%", "100%"],
    "bindings": [ /* 1번의 반대 조건 */ ],
    "controls": [{ "long_form@server_form.long_form": {} }]
  },
  // 3. 기존 팩토리의 control_ids만 경로 키로 덮어쓰기
  "main_screen_content/server_form_factory": {
    "control_ids": {
      "long_form": "@server_form.ba_hideable_long_form",
      "custom_form": "@server_form.custom_form"
    }
  },
  // 4. 내 화면용 팩토리를 하나 더 추가
  "main_screen_content": {
    "size": ["100%", "100%"],
    "modifications": [{ "array_name": "controls", "operation": "insert_back",
      "value": [{ "ba_server_form_factory": { "type": "panel", "size": ["100%", "100%"],
        "factory": { "name": "server_form_factory",
                     "control_ids": { "long_form": "@server_form.ba_long_form" } } } }] }]
  }
}
```

왜 이 구조가 안전한가.

- `long_form@server_form.long_form`은 **최종적으로 병합된** `long_form`을 참조한다. 다른 UI 팩이 `long_form`을 통째로 바꿔도 감싼 패널의 가시성 조건이 유지된다. 이 애드온의 2.0.2 변경 내역("UI 팩을 쓰면 화면 뒤에 텍스트·버튼이 뒤죽박죽 보이던 문제, 팩 순서와 무관하게 수정")이 이 구조다. 거꾸로 이전 판이 수정 방식이어서 UI 팩 호환이 깨졌던 실패 사례이기도 하다.
- `"부모/자식": {...}` 경로 키로 바닐라 컨트롤의 속성(`control_ids`)만 부분 덮어쓴다.
- 같은 이름(`server_form_factory`)의 팩토리를 둘 둔다. 하나는 감싼 바닐라, 하나는 내 화면을 만들고, 가시성으로 하나만 보인다.
- 제목 판별을 접두 검사(`'%.Ns'`)가 아니라 **포함 검사**(`(#s - 'X') = #s`의 부정)로 하면 제목 뒤에 메타데이터(개수 등)를 붙일 수 있다. 예: `CUSTOMUI:BAT0153L0000`(트리 레코드 153개, 리스트 0개).
- `custom_form`은 바닐라에 그대로 넘긴다(이 애드온은 액션 폼만 재스킨한다).

### 2.3 다른 방식: 접두 일치와 `modifications`

bedrock-core 계열 팩은 `server_form_factory`를 교체하고 제목 앞 13바이트 일치(`'%.13s' * #title_text = 'corev0009core'`)로 판별하며, 바닐라 `long_form`·`custom_form`에는 바인딩 `modifications`를 붙인다. 판별이 접두라 제목 뒤에 데이터를 붙일 수 없는 대신 구조가 단순하다. 두 방식 모두 팩 순서에 민감한 `controls` 통째 교체보다 안전하다(MOD-09 감싸기, MOD-13 `modifications`만 쓰기).

### 2.4 제목 표식을 길고 고유하게

표식은 다른 팩·서버와 겹치지 않게 길고 고유하게 만든다(`CUSTOMUI:BA`, `CUSTOMHUD:ba_toast:`). 글자마다 `§`를 붙인 표식(`§c§h§e§s§t§5§4§r`, Chest-UI `HOST-34`)은 모든 글자가 서식 코드로 소비되므로, 리소스팩이 없는 클라이언트나 바닐라 모양에서도 제목에 표식이 보이지 않는다. UI 쪽은 `(#title_text - '§c§h§e§s§t')` 포함 검사로 찾는다. 끝의 `§r`은 뒤 제목의 서식을 되돌린다 (출처: repo-chest-ui, chest-ui-pack).

## 3. 하나의 폼을 여러 화면으로: 레이아웃 게이트 `{실측}`

연구 서버는 `server_form.json`의 `long_form` 아래에 레이아웃 13개를 두고 제목 표식으로 하나만 보인다 (출처: 비공개 조사).

- **게이트 조건**: 레이아웃마다 `"visible": false`로 시작하고 `#title_text`(전역) 포함 검사를 `"binding_condition": "always"`로 `#visible`에 넣는다. `once`면 폼이 다음 폼으로 바뀌는 사이 잠깐 맞았던 레이아웃이 다음 폼 위에 남았다.
- **팩토리·격자 길이의 조건**: 레이아웃 안 팩토리 길이(`#form_button_contents` → `#collection_length`)를 `"binding_condition": "visible"`로 두면 숨은 레이아웃은 버튼 칸을 만들지 않았다. 처음부터 보이는 레이아웃에 `visible`을 쓰면 숨은 레이아웃도 첫 프레임에 칸을 만들어 렉이 났다. `always_when_visible`·생략(기본)은 첫 프레임에 만든 칸의 바인딩이 갱신되지 않아 표식·글자가 비었다(창을 바꾸거나 눌러야 정상).
- **식 안의 변수**: 표식을 `$변수`로 받아 `source_property_name` 식 안에 끼우면 치환되지 않았다(탭·뒤로 버튼이 안 보임, 검사기도 못 잡음). 표식은 식마다 글자로 적는 `vis_*` 템플릿으로 나눈다.
- **글자 비교**: `(not ((A - B) = 'z'))`처럼 식 안에서 바로 비교하면 참·거짓이 뒤집혔다. 먼저 `#변수`에 담고 `(not (#변수 = 'z'))`로 비교하니 맞았다.

### 3.1 사전 조회 라우팅(팩토리 게이트)

`stack_panel`에 `property_bag`로 레이아웃 후보 값을 두고 `factory`의 `control_ids`가 그 값으로 레이아웃을 고르는 방식이다.

```json
{
  "type": "stack_panel",
  "property_bag": { "#df_layout_1": [ "on" ], "#df_layout_0": [] },
  "factory": { "name": "layout", "control_ids": { "on": "…@df_form.split_form" } },
  "bindings": [
    { "binding_type": "view",
      "source_property_name": "(('#df_layout_' + (조건 * 1)))",
      "target_property_name": "#collection_length" }
  ]
}
```

- 이 방식은 동작한다. 조건이 맞을 때만 레이아웃이 만들어졌다(멈춤·종료 없음).
- **게이트 안에서는 폼 데이터가 비었다**: 팩토리가 만든 레이아웃 안에서 격자(`grid` + `collection_name`)의 칸은 버튼 글·아이콘을 읽었다. 고정 `collection_index` 칸(탭, 상세, 동작 버튼)은 비었다. 레이아웃 안의 `#form_button_contents` 팩토리(목록, 런처)는 아무것도 만들지 않았다. `collection_panel`(+`collection_name` 유무), `stack_panel`, `control_name`, `control_ids` 조합 모두 같았고, 고정 인덱스 칸의 바인딩에 `always`를 줘도 그대로였다. `panel` + `factory`는 아무것도 만들지 않았다(창이 보이지 않은 채 폼이 열림).
- 그래서 레이아웃 13개를 모두 `visible`로만 바꿔 둔다. 게이트를 쓰려면 레이아웃이 버튼을 격자로만 읽어야 한다. 2026-10 초 기록(`collection_panel` 게이트 안에서 팩토리·격자가 버튼을 못 읽고 고정 칸만 읽음)은 이번 결과와 반대인데, 무엇이 달랐는지 분리하지 못했다.

## 4. 버튼 수와 격자 크기 `{실측}`

- **`#form_button_length`가 남는다**: 클라이언트는 이 값을 지금까지 본 가장 큰 폼의 버튼 수로 붙잡고 있었다(디버그 라벨로 93, 재접속 뒤에도 93). 이 값으로 `#maximum_grid_items`를 정하면 작은 폼에서 빈 칸이 끝없이 이어지고 도감 아래에 빈 스크롤이 생겼다. `always_when_visible`로도 바뀌지 않았다.
- **본문 앞에 개수 싣기**: 서버가 격자 칸 수를 본문 맨 앞 12바이트에 쓰고 팩이 읽는다.
  - 처음: 16진수 숫자 글자(`'3'`)를 `=`로 비교하면 맞지 않았다(글자는 `3`인데 값은 0). 6진수 a~f 글자 셋(`§a§b§d§r`)으로 바꾸니 맞았다.
  - 지금: 서버가 `§r§r§r042`를 보내고 팩이 `((('%.12s' * #form_text) - '§r') - 0)`을 `#maximum_grid_items`에 바로 넣는다. 격자마다 바인딩이 6개에서 1개가 됐다.
  - `042§r§r§r`처럼 숫자를 앞에 두면 `('%.12s' * #form_text)`가 숫자 42로 읽혀(EXP-30) 본문 자르기 `(#form_text - ('%.12s' * #form_text))`가 깨져 본문이 사라졌다.
- **격자에 칸이 아닌 버튼**: 줄바꿈 격자는 숨은 버튼도 칸을 차지한다. 탭·뒤로·쪽 버튼까지 칸 수에 넣으면 빈 줄이 한 줄 더 생겨 도감이 몇 픽셀 스크롤됐다. 칸 버튼 수만 보내 해결했다. 표식 버튼은 칸 **뒤에** 둔다(앞에 두면 칸이 오른쪽으로 밀려 시작).
- **식으로 계산한 길이**: 팩토리·격자 길이를 `#form_button_contents`·`#form_button_length`의 식(`* 1`, `* (표식 일치)`)으로 만들면 팩토리는 버튼을 만들지 않았고 격자는 식 자체가 됐다.

## 5. 고정 인덱스와 성능 `{실측}`

- **줄마다 팩토리는 느리다**: 연구 화면(48칸 격자 + 재료·보상 줄)을 줄마다 버튼 전체를 걷는 스택으로 만들었더니 여는 데 4~5초 걸렸다. 칸마다 `collection_index`로 버튼 하나만 읽는 고정 배치로 바꾸니 1초쯤이 됐다.
- **`collection_index`의 자리**: `collection_name`을 가진 `stack_panel`의 바로 아래 자식에서만 먹는다. 쪽 화살표 줄을 `panel`에 두니 콘텐츠 로그에 `Unknown property [collection_index]`, `[collection_name]`이 찍히고 비었다. 상자 화면도 같아서 `stack_panel` 자체에 `"collection_name": "container_items"`를 준다.
- **누를 수 없는 버튼**: 서버 폼 버튼은 끌 수 없다. `$pressed_button_name`을 엔진이 모르는 이름(`button.df_noop`)으로 두면 눌러도 폼에 답하지 않고 호버 툴팁은 그대로 떴다. 칸마다 버튼은 하나만 둔다. 누르는 버튼과 안 누르는 버튼을 둘 다 두면 컨트롤이 두 배라 연구 화면이 몇 초 걸렸다.
- **`%` 연산자**: 아이템 아이콘 식 `(#t - (#t % 65536))`이 오래 들어 있었는데 아이콘은 그려졌고 콘텐츠 로그에 `Invalid expression`도 없었다. `(#t - 0)`으로 바꾼 뒤 폼이 눈에 띄게 빨라졌다는 사용자 보고가 있었다(재지 않음).
- BedrockAdvancements는 노드 하나당 수백 개의 컨트롤이 생겨 "모든 탭의 노드를 보내면 여는 데 몇 초 걸렸다". 그래서 선택된 탭의 노드만 보내고 탭을 누르면 폼을 제출한 뒤 그 탭으로 다시 연다 (출처: 비공개 조사).

## 6. 레이아웃 `{실측}`

- **두 열**: 가로 `stack_panel`에 두 세로 열을 넣으면 높이가 0이 됐다. `panel`(높이 `100%cm`) 안에 왼쪽·오른쪽으로 붙인 두 세로 스택을 둔다.
- **분할 화면**: 왼쪽 판·오른쪽 상세를 가로 스택에 두면 `100%c`가 높이를 더하고 `100%cm`은 오른쪽 상세를 접었다. `panel` 안에 왼쪽 위 기준(오른쪽은 offset)으로 둔다.
- **창 크기**: 창 높이를 `100%c`로 내용에 맞추면 창과 내용이 서로를 참조해 무너졌고(버튼이 창 밖으로), 화면 비율 크기는 짧은 목록에서 빈 공간을 남겼다. 모든 창을 고정 픽셀(최대 바닐라 인벤토리 326×166)로 둔다. 휴대폰은 UI를 크게 그려 이보다 큰 창은 화면에 들어가지 않는다. BedrockAdvancements는 반응형으로 `size: [314, "100% - 64px"]`, `max_size: [314, 236]`을 쓴다.
- **목록 칸**: 목록을 내용 높이(`100%c + 8px`)로 두면 빈 목록이 얇은 막대가 되고 긴 목록이 창 밖으로 나간다. 목록 칸은 창 높이로 고정하고 안에 `common.scrolling_panel`을 둔다.
- **동작 칸 높이**: 고정 높이(94)의 동작 칸 위에 본문 두 줄이 오면 오른쪽 칸에 스크롤바가 생겼다. 동작 칸을 `stack_panel` `100%c`로 버튼 높이만큼만 차지하게 하고, 짧은 정보는 버튼 글에 넣는다.
- **격자 높이**: 격자 높이를 `#form_button_contents`나 `default`로 두면 버튼이 하나도 생기지 않았다. `100%c`로 둔다(LAY-30) `{기록}`.
- **가로 스택의 `100%c`**: 자식 높이를 모두 더해 탭 줄 아래에 큰 공백이 생겼다. 가장 큰 자식을 따르는 `100%cm`을 쓴다 `{기록}`.
- **크기 배열 안의 숫자 변수**: `"size": [ "$w", "100%c" ]`처럼 배열 안에 숫자 변수를 두면 "Dangling number" 오류가 났다. 크기는 배열 전체를 변수로 준다(`"size": "$window_size"`) `{기록}`.

## 7. 글·툴팁·그림 `{실측}`

- **엔진 툴팁**: 칸 옆에 직접 그린 호버 상자는 스크롤 창에 잘렸다. 바닐라 `common.hover_text`(`hover_text_renderer`)를 호버 상태의 자식으로 두고 `#hover_text`에 버튼 글을 넣으면 포인터 옆에 잘리지 않고 뜬다. `$hover_text_max_width`가 0이면 글의 `\n`에서만 줄을 바꾸고, 150이면 한글이 다섯 글자쯤에서 꺾였다. Chest-UI는 이 렌더러를 hover 컨트롤 안에 둔다(`type: custom`, `renderer: hover_text_renderer`, `allow_clipping: false`, `layer: 30`, `#hover_text` 바인딩). hover 상태에서만 만들어지므로 칸이 많아도 하나만 생긴다(INP-25).
- **포커스**: 바닐라 `common.button`·`common.toggle`은 `focus_enabled`가 켜져 있어, 휴대폰에서 폼을 열면 첫 버튼(제목 막대의 "?")이 호버 상태로 그려졌다. 폼의 모든 버튼에 `$focus_enabled: false`, 라디오 토글에 `$toggle_group_default_selected: -1`, `$toggle_focus_enabled: false`.
- **라디오 토글 그룹**: 라디오 토글은 형제 컨트롤끼리만 한 그룹이다. 격자 칸은 칸마다 부모가 따로라 배타적이지 않았다(누르는 대로 상자가 쌓임).
- **흑백 PNG**: 클라이언트는 grayscale PNG를 반투명하게 그렸다(회색 노드 틀과 창이 비침). 최적화 도구가 회색 그림을 grayscale로 바꾸므로 팩의 PNG는 RGB·RGBA로 둔다(99개 변환). 최적화 뒤에 `file`로 grayscale이 없는지 본다.
- **`%`가 든 라벨**: 스코어보드 줄 라벨이 번역을 거치면 `%`가 사라졌다. `localize: false`.
- **숫자만 든 글** `{기록}`: 숫자로 읽히는 값(`" 219"`, `"1,532/4,096"`)은 라벨에 보이지 않았다. 색 코드로 시작하는 글로 보내거나 변수 식 안에서 `'§r' + 값`으로 문자열로 만든다(EXP-15). 숫자 한 글자 플래그도 숫자가 되어 글자 비교가 맞지 않으므로 플래그는 글자(`a`~`k`)로 쓴다. Chest-UI는 알 수 없는 서식 코드 `§z`를 접두로 써 결과를 문자열로 유지한다: `(('§z') + (('%.8s' * T) - ('%.6s' * T)))`(TXT-18).
- **변수 블록의 식** `{기록}`: 개수 식은 라벨 자신의 `variables` 블록에 두어야 계산됐다. 부모 패널 `variables`의 식이나 `text` 안의 `('§r' + $변수)`는 계산되지 않았다. 변수 블록의 식을 다른 식 안에서 쓴 것도 계산되지 않았다.
- **입력 폼 글자** `{기록}`: 바닐라 입력 칸의 글자는 흰색이라 밝은 카드 위에서는 보이지 않는다.

## 8. 화면 호스트 `{실측}`

- **폼 화면 애니메이션**: `third_party_server_screen`에 `"$screen_animations": []`, `"$background_animations": []`를 준다. 창이 움직이는 동안 다음 폼이 오면 두 창이 겹쳐 보였고, 닫고 다시 여는 메인 메뉴 폼이 깜빡였다.
- **폼 뒤 배경**: `third_party_server_screen`의 `$screen_bg_content`(안전 영역 밖, 화면 전환 때 밀리지 않음)를 바꿔 로비 틀을 폼 뒤에 그린다. 거기의 `#title_text` 바인딩을 `once`로 두면 폼 내용이 오기 전에 평가돼 보이지 않았다.
- **HUD는 폼 뒤에서 그려지지 않는다**: 폼이 열려 있는 동안 HUD는 그려지지 않는다. 폼 뒤에도 같은 틀을 보이려면 폼 배경에도 그린다. 바닐라는 폼 뒤를 `screen_background` 투명도 0.4로 어둡게 한다 `{기록}`.

## 9. 고정 폭 레코드 프로토콜 (BedrockAdvancements)

숫자·플래그를 많이 보내야 할 때 버튼 글을 고정 폭 레코드로 쓴다. 아래는 원본의 구조를 다시 쓴 것이다 (출처: 비공개 조사).

```text
[KIND 4][TAB 2][FRAME 24][TOKENS 160][PROGRESS 16][PCT 4][TITLE 120][DESC ...]
 0       4      6          30          190          206    210         330
```

| 필드 | 용도 |
| --- | --- |
| KIND | 레코드 종류(`BAN\|` 노드, `BAT\|` 탭, `BAL\|` 라벨, `BAM\|` 메타). `('%.4s' * #form_button_text) = 'BAN\|'` |
| TAB | 탭 번호. 숫자만 있으면 JSON UI가 숫자로 바꾸므로 문자 접두(`Ta`, `Tb`) |
| FRAME | `'textures/ba/frames/' + #ba_frame`으로 텍스처 경로 조립 |
| TOKENS | 비트·플래그 토큰(아래) |
| PROGRESS | `§f` 접두로 `3/17`이 숫자로 해석되는 것을 막음 |
| PCT | `P050`. 문자 접두 후 `- 'P'`, `* 1`로 숫자화 |
| TITLE / DESC | lang 키 또는 평문, `$`로 패딩 |

- 패딩 문자 `$`(필드), `.`(토큰)와 예약 문자 `~`/`$`는 평문에서 제거한다. 뺄셈 연산은 모든 출현을 제거하므로 패딩 문자가 본문에 나오면 안 된다.
- `'%.Ns'`는 **UTF-8 바이트** 단위다. 인코더가 바이트 기준으로 자르고 채운다(한글은 3바이트).
- N번째 바이트부터 L바이트를 꺼내는 표준 체인:

```jsonc
{ "source_property_name": "('%.210s' * #form_button_text)",   "target_property_name": "#_text_head" },
{ "source_property_name": "(#form_button_text - #_text_head)", "target_property_name": "#_text_rest" },
{ "source_property_name": "('%.120s' * #_text_rest)",          "target_property_name": "#_text_raw"  },
{ "source_property_name": "(#_text_raw - '$')",                "target_property_name": "#text"       }
```

- **불리언은 위치 무관 토큰**: `~` + 그룹 대문자 + 비트 소문자(`~Xa`, `~Fo`). 존재 여부를 `(not ((#form_button_text - '~Fo') = #form_button_text))`로 검사하므로 필드 경계 계산이 필요 없다. 그룹은 `X`(x 9비트), `Y`(y 11비트), `U`/`V`(연결선 길이), `H`(캔버스 높이), `F`(플래그: `~Fc` 자식 있음, `~Fh` 부모 있음, `~Fl` 툴팁 왼쪽, `~Fs` 선택됨, `~Fp` 진행도, `~Fx` 도전, `~Fo` 달성, `~Fe` 빈 슬롯). 대문자 + 소문자 조합이라 서로 접두 관계가 생기지 않는다. 부분문자열 검사 토큰을 설계할 때의 요령이다.
- **숫자를 픽셀로: 비트 스페이서 스택**: JSON UI에는 바인딩 값으로 `offset`을 계산하는 안정적인 방법이 없다. 크기가 2의 거듭제곱(1, 2, 4 … 1024)인 `panel` 11개를 세로 스택에 두고 비트 토큰이 있을 때만 `#visible`로 켠다. 스택에서 보이지 않는 자식은 공간을 차지하지 않으므로 켜진 크기의 합이 곧 좌표(0~2047px)다. 스크롤 콘텐츠 높이도 같은 방식으로 만든다.
- **고정 위치 요소는 `collection_index`로 직접 바인딩**한다. 스크립트가 탭이 없어도 빈 레코드(`~Fe`)를 보내 인덱스를 고정한다(탭 28개 슬롯).
- **그리기 순서가 중요하면 같은 컬렉션을 layer가 다른 팩토리 여러 개로 그린다**: 모든 연결선 외곽을 먼저, 코어, 노드, 마지막에 호버 순서로 3중 팩토리를 둔다. 한 아이템 안에서 layer만 올리면 다음 아이템의 외곽선이 앞 아이템을 덮기 때문이다.
- **눌러도 제출하지 않는 버튼**: `button_mappings`를 달지 않고 호버·포커스(`focus_enabled`, `focus_magnet_enabled`)만 쓴다. 제출하는 탭 버튼은 `button.menu_select`·`button.menu_ok`를 `button.form_button_click`에 매핑한다.
- **호버 툴팁**: `allow_clipping: false`로 뷰포트 밖까지 그리고, 4000×4000 검정 이미지(alpha 0.3)로 화면을 어둡게 한다. 툴팁 제목 막대는 `alpha: 0` 라벨로 글 폭을 재고 부모를 `100%c`/`100%cm`로 맞춘다.
- **9-slice**: 모든 UI 텍스처에 `.json`(`nineslice_size`, `base_size`)을 붙인다. 예: 창 `[4,4,4,4]` / `[16,16]`.
- **다시 열면 스크롤이 맨 위로 돌아간다**: 스크롤 위치를 지정할 방법이 없어, 리스트 탭은 열린 섹션 하나만 행을 만들고 그 섹션을 맨 앞에 둔다(아코디언).
- 반복이 많은 구조(712KB 화면 JSON)는 와이어 포맷 정의(스펙 파일)를 스크립트 인코더와 UI 생성기가 공유해 **생성기로 만든다**. 레이아웃 계산을 게임 API와 분리된 순수 함수로 두면 웹 미리보기와 공유할 수 있다.

## 10. 작동팩 사례: Chest-UI의 칸 만들기 `{확인}`

Chest-UI(`115d95c`, CC BY 4.0)의 기법을 다시 쓴 것이다 (출처: chest-ui-pack, repo-chest-ui). 상자 전체 동작은 [상자 UI](./chest-ui.mdx)에 있다.

- **크기별 레이아웃을 생성 단계에서 끄기**: 같은 템플릿을 크기마다 참조하고 각자 `"ignored": "$disable_N_slots_layout"`을 준다. 값은 전역 변수 파일에 있다. 보이지 않을 템플릿까지 모두 만들면 54칸 × 3상태 × 렌더러가 여러 벌 생기므로 생성 자체를 막는다.
- **`collection_index`에 생성 시점 식**: `"$start_index": "(($size - '§c§h§e§s§t' - '§') * 1)"`, `"collection_index": "($start_index + 9)"`(COL-31). `$size`가 `'§c§h§e§s§t§5§4'`면 시작 인덱스는 54다.
- **버튼 글 머리말에서 값 꺼내기**: 버튼 글을 `stack#64dur#10§r이름§r\n설명`(고정 폭 14바이트 머리말)로 두고 수량 `(('%.8s' * T) - ('%.6s' * T))`, 내구도 `((%.14s * T) - (%.12s * T))`, 본문 `(T - ('%.14s' * T))`를 꺼낸다.
- **이미지/아이템 분기**: 칸 하나(`inventory_item@common.button`)가 `#form_button_texture`를 받아 앞 8바이트가 `textures`면 이미지, 아니면 아이템 렌더러에 `#item_id_aux`를 넣어 그린다(PAT-11).

## 11. 규칙 요약

1. 서버 폼 재스킨은 수정이 아니라 **감싸기 + 팩토리 추가**로 한다(MOD-09).
2. 제목 표식은 길고 고유하게, 포함 검사로 찾고, 글자마다 `§`를 붙여 숨긴다(HOST-34).
3. 레이아웃은 `visible`로 게이트하고 `binding_condition: always`로 판별한다. 팩토리 길이는 `visible` 조건을 건다.
4. 표식은 식에 글자로 적는다(변수는 식 안에서 치환되지 않는다).
5. 숫자 값은 문자 접두를 붙여 문자열로 유지하고, 숫자가 필요하면 `(#v - 0)`으로 바꾼다.
6. 칸이 많으면 고정 `collection_index`와 고정 픽셀 크기를 쓴다. 컨트롤 수는 곧 열기 시간이다.
7. 다른 팩과 `controls`를 놓고 경쟁하는 구조(MOD-20)를 피한다.
