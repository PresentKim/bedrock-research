# always 없이 첫 화면 채우기

[grid 버튼 목록](./grid-button-list.mdx)의 칸은 버튼 글을 잘라 이름과 설명을 그린다. 이 계산을 view 바인딩으로 하면 처음 열린 화면에서 칸이 비는 일이 있어, 흔히 바인딩에 `binding_condition: "always"`를 건다. 이 기획은 `always` 대신 **바인딩 순서**로 첫 화면을 채우고, 두 구성을 같은 grid에서 비교한다.

## 1. 문제

- 팩토리나 grid가 만든 칸 안의 바인딩은 너무 일찍 실행되어 빈 값으로 남을 수 있다(BND-07). view 바인딩이 아직 들어오지 않은 컬렉션 값을 읽으면 첫 화면에서 빈 글을 그린다.
- 컬렉션 값을 `binding_name`으로 바로 넣으면 처음부터 보이지만, view 바인딩을 거쳐 계산하면 한 번 건너뛴다는 커뮤니티 보고가 있다. 그 보고에서 쓴 해결이 두 바인딩에 `always`를 거는 것이었다.
- `always`는 값이 바뀌지 않아도 매 업데이트 다시 평가한다(BND-23). 칸이 많을 때 그 비용이 걱정된다.

## 2. 방법

같은 컨트롤의 `bindings` 배열에서 **컬렉션 바인딩을 먼저, 그 값을 읽는 view 바인딩을 뒤에** 둔다. 둘 다 조건을 쓰지 않는다(기본 `none`, BND-35).

```json title="always 판 (grid 예제 v1.3.1)"
"bindings": [
  { "binding_type": "collection", "binding_collection_name": "form_buttons", "binding_name": "#form_button_text", "binding_condition": "always" },
  { "binding_type": "view", "binding_condition": "always", "source_property_name": "('%.12s' * #form_button_text)", "target_property_name": "#text" }
]
```

```json title="순서 판 (grid 예제 v1.4.0)"
"bindings": [
  { "binding_type": "collection", "binding_collection_name": "form_buttons", "binding_name": "#form_button_text" },
  { "binding_type": "view", "source_property_name": "('%.12s' * #form_button_text)", "target_property_name": "#text" }
]
```

바인딩은 배열 순서로 평가되므로, 뒤의 view 바인딩이 읽을 때는 앞의 컬렉션 바인딩이 이미 `#form_button_text`를 넣어 두었다. 순서를 거꾸로 두면 view가 비어 있는 값을 먼저 읽는다(BND-37).

## 3. 비교 실측

같은 화면 라우터, 창, 2열 grid, 칸 모양에서 이름·설명 라벨의 바인딩만 다른 두 목록을 비교했다. 칸의 `collection_details`와 grid 길이 바인딩은 두 판 모두 `always`, 진행 막대는 두 판 모두 조건 없는 "컬렉션 다음 view"다. 6절의 애드온이 이 두 목록을 연다.

| 판 | 이름·설명 라벨 |
| --- | --- |
| A | 컬렉션 다음 view, 둘 다 `always` (grid 예제 v1.3.1과 같음) |
| V | 컬렉션 다음 view, 조건 없음 (grid 예제 v1.4.0과 같음) |

조건: Windows 1.26.65, 평지 월드, 설정의 VSync 끔, Intel PresentMon 2.6.0으로 목록을 연 채 10초씩 잼(2026-11-18, 실측).

| 상태 | fps | 프레임당 CPU 시간 |
| --- | --- | --- |
| 월드만(목록 없음) | 294.2, 294.4 | 3.23ms |
| A, 버튼 100개 | 284.0, 284.6 | 3.35ms |
| A, 버튼 2000개 | 281.9, 283.7, 284.8, 284.5 | 3.34~3.37ms |
| V, 버튼 100개 | 291.0, 289.3 | 3.27~3.28ms |
| V, 버튼 2000개 | 288.0, 291.1 | 3.27~3.30ms |

| 볼 것 | A (`always`) | V (순서만) |
| --- | --- | --- |
| 첫 화면 (100개, 2000개) | 연 지 2~3초 뒤 보이는 칸의 이름, 설명, 아이콘이 모두 채워짐 | 같음 |
| 목록을 연 채 프레임 비용 | 월드만보다 약 0.12ms 더 듦 | 월드만보다 약 0.05ms 더 듦 |
| 버튼 수에 따른 차이 | 100개와 2000개가 같음 | 100개와 2000개가 같음 |
| 여는 순간 가장 긴 프레임 (2000개, 12초 기록) | 43ms, 50ms 넘는 프레임 없음 | 43ms, 50ms 넘는 프레임 없음 |
| VSync 켬 | 60fps, 프로세스 CPU 코어 약 0.1개 | 같음 |

- `always`를 빼면 목록을 연 동안 프레임마다 약 0.07ms가 줄었다. 이 기기에서 fps로는 약 284에서 약 290이다.
- 차이가 버튼 100개와 2000개에서 같았다. 화면 밖 칸까지 매번 다시 평가했다면 2000개 쪽이 더 무거웠을 것이므로, 이 구성에서 `always` 비용은 칸 수만큼 늘지 않았다. 왜 그런지는 확인하지 않았다.
- 여는 비용은 두 판이 같았다. 칸을 만드는 비용은 바인딩 조건이 아니라 칸 수와 칸의 컨트롤 수에서 나온다([JSON UI 최적화](./index.mdx) 1절, 4절).
- VSync를 켜면 두 판 모두 60fps에 머물러 차이가 보이지 않았다. 차이는 프레임 여유가 적은 기기에서 더 드러날 수 있지만 재지 않았다.

## 4. 옮기는 순서

`always`로 첫 화면을 채운 칸을 순서 방식으로 옮기는 순서다.

1. 칸 안에서 `always`가 걸린 바인딩을 찾는다. 칸의 `collection_details`, grid·팩토리 길이 바인딩, 칸 안 라벨·이미지 바인딩으로 나눈다.
2. 라벨·이미지 바인딩마다 컬렉션 바인딩이 view 바인딩보다 **앞에** 있는지 본다. 뒤에 있으면 순서를 바꾼다.
3. 그 두 바인딩에서 `binding_condition`을 지운다.
4. view 식이 문자열을 숫자로 나누지 않는지 본다. 나누기 전에 `(#v - 0)`으로 바꾼다(EXP-16, EXP-49).
5. 칸의 `collection_details`와 길이 바인딩의 `always`는 그대로 둔다. 이 둘을 뺀 구성은 이 비교에서 재지 않았다. 라우터 창 안의 팩토리·grid는 기본 조건이면 처음에 비었다(COL-47, COL-48).
6. 목록을 열어 첫 화면, 스크롤한 아래 칸, 마우스를 올린 칸(hover 상태)을 본다.

## 5. 하지 말 것

- **컬렉션 바인딩의 `binding_name`에 식을 바로 쓰지 않는다.** `binding_name: "('%.12s' * #form_button_text)"`에 `binding_name_override: "#text"`처럼 쓴 판은 버튼 100개 목록을 열자 클라이언트가 멈췄다(Windows 1.26.65, 2026-11-18, 실측). 어느 식이 원인인지는 나누지 않았다. 바닐라 UI에는 이런 컬렉션 식 바인딩이 있다(예 `choose_realm_screen.json`의 `(not #realm_slot_is_filled)`).
- **문자열을 숫자로 나누지 않는다.** `(#text / 100)`은 Windows 1.26.65 클라이언트를 멈췄다(EXP-49). `* 1`은 숫자로 바꾸지 않는다.
- **view 바인딩을 컬렉션 바인딩 앞에 두지 않는다.** 순서가 이 방법의 전부다.

## 6. 비교 애드온

<AddonDownload id="collection-view-order" />

3절의 A, V 두 목록을 여는 애드온이다. 라우터가 폼 제목 `§b§wcv:A`, `§b§wcv:V`로 창을 고른다.

1. 파일을 열어 가져온다(모바일은 파일을 눌러 Minecraft로 연다). 새 월드에서 행동 팩 `[bedrock-research]collection-view-order-bp`로 시작하는 팩을 켠다. 리소스 팩은 의존성으로 함께 켜지고 실험 토글은 필요 없다.
2. 크리에이티브 인벤토리 아이템 분류의 맨 뒤에서 "Collection View Order Test"를 꺼낸다. `/give @s bwiki:collection_view_order_test`를 써도 된다.
3. 아이템을 사용하거나 `/scriptevent bwiki:collection_view_order`를 실행하면 판(A, V)과 버튼 수(100, 1000, 2000)를 고르는 메뉴가 열린다. 창 위쪽 글로 어느 판인지 보인다.
4. 프레임을 비교하려면 VSync를 끄고, 같은 자리에서 두 판을 차례로 열어 fps를 잰다.

- `server_form.json`은 다른 서버 폼 예제와 라우터 한 줄만 다르다([JSON UI 최적화](./index.mdx) 9절). 같은 월드에 함께 켜는 것은 규약상 가능하지만 이 애드온으로는 게임에서 확인하지 않았다.
- 메뉴와 화면의 글은 영어다.

## 7. 남은 일

- 순서 판에서 스크롤해 내려간 아래 칸이 채워지는지. 이 실측 환경에서는 목록 스크롤을 조작하지 못했다.
- 모바일에서 같은 비교.
- 칸의 `collection_details`와 grid 길이 바인딩에서도 `always`를 뺄 수 있는지.
- 컬렉션 식 바인딩이 멈춘 원인 식.
