# Optimizing: 바인딩 계산식 캐싱

칸이 많은 화면은 칸마다 거의 같은 식을 쓴다. 예를 들어 HUD 부제목에서 n번 칸을 꺼내는 식은 자르는 위치만 다르다. 지금까지는 칸 번호마다 고정 식을 생성기로 찍어 두고 `requires`로 골랐다([HUD 아이템 아이콘](./hud-item-icons.mdx) 3.3절). 이 문서는 식을 정의에 **한 번만** 두고, 칸 인스턴스에는 위치 같은 값만 변수로 넘기는 구성을 다룬다. 식 하나를 모든 칸이 다시 쓰므로 여기서는 "계산식 캐싱"이라 부른다.

결론부터 적으면, 칸 64개에서는 두 방식의 차이가 보이지 않았지만 256칸에서 프레임이 약 22 대 4~5, 512칸에서 약 14 대 1~2로 벌어졌다(6절, 실측). 그린 결과는 두 방식이 같았다(4절).

## 1. 고정 식 방식의 비용

고정 식 방식의 칸 정의는 이렇게 생겼다.

```json
"slot": {
  "$index|default": 0,
  "variables": [
    { "requires": "($index = 0)", "$aux": "(... '%.1s' ...)" },
    { "requires": "($index = 1)", "$aux": "(... '%.20s' ...)" }
  ]
}
```

- 칸 정의 하나에 칸 수만큼 `requires` 블록이 들어간다. 칸이 N개면 칸 하나에 블록 N개, 화면 전체에 N x N개다. 아이템 식과 개수 식을 따로 두면 두 배다.
- 칸 64개면 8192개, 256개면 131,072개, 512개면 524,288개다.
- 제목 팩토리가 만든 컨트롤은 제목이 바뀔 때마다 다시 만들어지므로(COL-17), HUD는 새 제목을 받을 때마다 이 블록들을 다시 거친다.

## 2. 변수가 식 안에 들어가는 규칙

| 쓰는 곳 | 예 | 결과(실측, 모바일, 2026-11-16) |
| --- | --- | --- |
| 변수 블록 식 안의 글자 변수 | `($skip_item * $subtitle_text)`, `"$skip_item": "%.20s"` | 치환되어 칸을 잘랐다 |
| 변수 블록 식 안에서 숫자로 형식 만들기 | `(('%.' + $skip_item + 's') * $subtitle_text)`, `"$skip_item": 20` | 치환되어 칸을 잘랐다 |
| 바인딩 식(`source_property_name`) 안의 변수 | `('%.11s' * (#hud_subtitle_text_string - ($skip_item * #hud_subtitle_text_string)))` | 치환되어 아이콘과 개수를 그렸다 |
| 바인딩 이름을 변수로 만들기 | `('#' + $v)`, `"$v": "hover_text"` | `#hover_text`를 읽었다(상자 화면) |
| `#` 속성이 하나도 없는 바인딩 식 | `('§r' + $v)` | 콘텐츠 로그에 "Must define a source property name in the binding!", 그 컨트롤의 바인딩이 모두 동작하지 않았다 |

- 변수 값은 **글자 하나**로 들어간다. 값이 식처럼 다시 해석되지는 않는다. 라벨 `text`에서 식을 담은 변수를 `('§r' + $변수)`로 이으면 그 식이 계산되지 않고 글자 그대로 붙었다는 기록과 맞는다([HUD 아이템 아이콘](./hud-item-icons.mdx) 4절).
- 그래서 변수에는 따옴표 없는 값을 넣는다. 서버 폼에서 `"$df_marker": "'§0§3§r'"`처럼 따옴표까지 넣은 값으로 `(#form_button_text - $df_marker)`를 쓰자 표식 버튼이 보이지 않았다(BND-33). 따옴표까지 글자로 들어가 버튼 글과 맞지 않았기 때문으로 보인다(*추론*). 따옴표가 있는 값과 없는 값을 나란히 놓고 시험하지는 않았다.
- 바인딩 식 안의 변수는 커뮤니티의 preserved title 패턴(`(#preserved_text - $update_string)`, 값 `"overlay:"`)에서도 오래 써 온 형태다(BW-title, 커뮤니티 보고).

## 3. 구성

칸 정의에는 식을 하나만 둔다. `requires`에는 늘 참인 조건을 준다.

```json
"slot_shared": {
  "type": "panel",
  "size": [ 18, 18 ],
  "$aux|default": "0",
  "variables": [
    { "requires": "($cost_on)", "$aux": "((((('%.11s' * ($subtitle_text - ($skip_item * $subtitle_text))) - 'xxxxxxxx') - 'xxxx') - 'xx') - 'x')" }
  ],
  "controls": [
    {
      "icon": {
        "type": "custom",
        "renderer": "inventory_item_renderer",
        "size": [ 16, 16 ],
        "property_bag": { "#item_id_aux": "$aux" }
      }
    }
  ]
}
```

칸 인스턴스는 위치만 넘긴다. `$cost_on`은 부모 패널에 `true`로 둔다.

```json
{ "slot0@ns.slot_shared": { "$skip_item": "%.1s" } },
{ "slot1@ns.slot_shared": { "$skip_item": "%.20s" } },
{ "slot2@ns.slot_shared": { "$skip_item": "%.39s" } }
```

- 칸 정의의 블록은 칸 수와 상관없이 하나다. 칸이 N개면 화면 전체에 N개다.
- 인스턴스 목록은 지금도 생성기로 만드는 것이 편하다. 다만 생성기가 만드는 것은 칸 위치 숫자뿐이고, 식은 사람이 읽을 수 있는 한 곳에 있다.
- 개수 라벨은 라벨 자신의 `variables`에 같은 방식으로 `$count`를 둔다(HUD 아이템 아이콘 4절의 "개수 식은 라벨 자신의 변수 블록에").
- 바인딩으로 읽는 칸도 같은 방식으로 줄어든다. 아이콘에 `property_bag`의 `#item_id_aux: 0`과 `binding_condition: "always"`를 두고, 위 식의 `$subtitle_text`를 전역 바인딩 `#hud_subtitle_text_string`으로 바꾼 view 바인딩을 `#item_id_aux`에 걸면 그려졌다(실측). 비용은 변수 블록 쪽만 쟀다.

## 4. 같은 결과인지 확인

6칸 부제목을 네 가지 칸 정의로 같은 화면에 그렸다. 네 줄 모두 두 묶음(잔디 2, 흙 3, 조약돌 16, 참나무 판자 32, 묘목 64와 그다음 6개 번호)을 같게 그렸다(실측, 모바일, 2026-11-16).

| 줄 | 칸 정의 | 칸마다 넘긴 것 |
| --- | --- | --- |
| F | 칸별 고정 식(1절) | `$index` |
| V | 변수 블록 식 하나 | `"$skip_item": "%.20s"` |
| N | 변수 블록 식 하나, 숫자로 형식 만들기 | `"$skip_item": 20` |
| B | 바인딩 식 하나 | `"$skip_item": "%.20s"` |

## 5. 비용 비교 방법

- 부제목에 64칸을 싣고, 256칸과 512칸 패널은 칸 n이 n % 64번 칸을 읽어 같은 자리에 겹쳐 그린다. 부제목 길이(1217바이트)는 그대로 두고 식의 수만 바꾼다.
- 스크립트가 매 틱 제목을 바꿔 보내므로 패널은 1초에 최대 20번 다시 만들어진다.
- 패널 아래의 노란 점은 1초마다 좌우로 오간다. 제목 팩토리 밖의 컨트롤이라 패널이 다시 만들어져도 처음으로 돌아가지 않는다. 화면이 새로 그려질 때만 점이 움직이므로, 녹화(60fps)에서 점이 움직인 프레임 수를 세면 그 구간의 화면 프레임 수가 된다.
- 같은 녹화에서 제목 글자와 패널 영역이 바뀐 프레임 수도 셌다. 이것은 패널이 실제로 다시 그려진 횟수다.

## 6. 실측

<video controls preload="metadata" width="100%" src={require('@site/static/video/hud-expression-cost.mp4').default} />

시험 팩 실측 영상(모바일, 2026-11-16). 칸별 고정 식 64, 256, 512칸, 식 하나 64, 256, 512칸 순서로 들었다. 영상의 아이템과 액션바는 시험 팩 판이고, 아래 예제 애드온은 아이템 하나로 같은 여섯 모드를 고른다.

| 칸 | 화면 블록 수(고정 식 / 식 하나) | 화면 프레임(초당, 고정 식 / 식 하나) | 패널 갱신(초당, 고정 식 / 식 하나) |
| --- | --- | --- | --- |
| 64 | 8,192 / 128 | 약 40 / 약 44 | 약 22 / 약 22 |
| 256 | 131,072 / 512 | 약 4~5 / 약 22 | 약 4 / 약 19 |
| 512 | 524,288 / 1,024 | 약 1~2 / 약 14 | 약 1 / 약 10 |

- 64칸에서는 두 방식 모두 매 틱 들어오는 제목을 따라갔고 눈으로 끊김을 알아볼 수 없었다. 별도 녹화에서도 같았다.
- 256칸부터 고정 식 방식은 화면 전체가 초당 몇 프레임으로 떨어졌다. 식 하나 방식은 같은 칸 수에서 화면 프레임이 약 5배였다.
- 식 하나 방식도 칸 수에 따라 느려졌다. 512칸에서 약 14프레임이다. 칸 생성과 레이아웃, 아이콘 그리기 비용은 남는다([JSON UI 최적화](./json-ui-performance.mdx) 1절).
- 수치는 녹화에서 센 값이고, 한 기기 한 번의 측정이다. 기기에 따라 다르다.

## 7. 적용 지침

- 칸마다 모양이 같고 값만 다른 식은 정의에 하나만 두고, 칸 인스턴스는 위치 같은 값만 변수로 넘긴다.
- 변수에는 따옴표 없는 글자나 숫자를 넣는다. 식을 변수에 담아 다른 식에 끼우지 않는다.
- 바인딩 식 안에 변수를 쓸 때도 식에 `#` 속성이 하나는 있어야 한다.
- 칸 수가 적으면(64칸 이하) 두 방식의 차이는 보이지 않았다. 이미 고정 식으로 만든 화면을 서둘러 바꿀 필요는 없다.
- 제목을 매 틱 바꾸는 구성은 이 측정을 위한 극단적인 조건이다. 실제 HUD는 내용이 바뀔 때만 보낸다(HUD 아이템 아이콘 3.5절).

## 8. 예제 애드온

<AddonDownload id="hud-expression-cost" />

1. 파일을 열어 가져온다(모바일은 파일을 눌러 Minecraft로 연다). 새 월드에서 행동 팩 `[bedrock-research]hud-expression-cost-bp`로 시작하는 팩을 켠다. 리소스 팩은 의존성으로 함께 켜지고 실험 토글은 필요 없다.
2. 크리에이티브 인벤토리 아이템 분류의 맨 뒤에서 "HUD Expression Cost"(시계)를 꺼낸다. `/give @s bwiki:hud_expression_cost_test`를 써도 된다.
3. 아이템을 쓸 때마다 모드가 바뀐다. 식 하나 64, 256, 512칸, 칸별 고정 식 64, 256, 512칸, 끄기 순서다. 액션바에 지금 모드가 나온다. 아이템을 든 동안 매 틱 새 제목이 가고, 내려놓으면 제목을 지운다.

- 칸별 고정 식 512칸은 화면이 초당 1~2프레임으로 떨어진다. 다른 모드로 바꾸거나 아이템을 내려놓으면 돌아온다.
- 가운데의 큰 제목과 긴 부제목 글자는 바닐라 제목이다. 다른 HUD 예제와 함께 켜도 되도록 숨기지 않는다. 제목은 `hx`로 시작한다.
- 화면의 글은 영어다.
