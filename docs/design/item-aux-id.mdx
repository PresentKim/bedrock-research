# Script API로 아이템 숫자 ID(aux) 추론하기

JSON UI의 `inventory_item_renderer`는 `#item_id_aux`에 `숫자 아이템 ID * 65536 + 데이터 값`을 받아 아이템을 그린다(ANI-06). 인챈트 반짝임은 32768을 더한다. 텍스처 경로로 그릴 때와 달리 블록이 3D로 나오고 반짝임도 나온다([연구 화면 8.1절](./server-form-research-screen.mdx#81-아이템-아이콘-v140)).

문제는 스크립트가 이 숫자를 알 방법이 없다는 것이다. 이 페이지는 숫자 ID가 어떻게 배치되는지(2절), 행동 팩 스크립트가 그중 무엇을 계산할 수 있는지(3절), 번호를 계산하지 않고 인벤토리 칸에 실제 아이템을 두어 엔진이 그리게 하는 방법(4절)을 다룬다.

규칙은 1.26.63 모바일에서 탐침 애드온(5절)으로 확인했다.

## 1. Script API에는 숫자 ID가 없다

`@minecraft/server` 2.11.0(정식), 2.12.0-beta.1.26.63-stable, 2.13.0-beta.1.26.70-preview.24의 타입 정의를 확인했다.

| API | 주는 것 |
| --- | --- |
| `ItemType` | `id`(문자열), `localizationKey` |
| `ItemTypes` | `get(id)`, `getAll()` |
| `BlockType` | `id`, `localizationKey` |
| `BlockTypes` | `get(id)`, `getAll()` |
| `ItemStack` | 생성자는 `(itemType, amount)`. 데이터 값 멤버가 없다 |
| `BlockPermutation.getItemStack()`, `Block.getItemStack(amount, withData)` | `ItemStack`을 돌려준다. `withData`는 블록 엔티티 데이터다 |

- 숫자 ID, 런타임 ID, 레거시 ID, aux를 돌려주는 멤버는 없다.
- `@minecraft/server-ui`의 `ActionFormData.button(text, iconPath)`는 텍스처 경로만 받는다. 아이템 타입으로 아이콘을 그리는 오버로드는 없다.
- 스크립트가 쓸 수 있는 재료는 `ItemTypes.getAll()`과 `BlockTypes.getAll()`이 주는 목록뿐이다. 바닐라 번호는 버전별 표를 스크립트에 넣어야 한다.

## 2. 숫자 ID 배치 규칙 (1.26.63)

그려지는 번호는 월드를 연 쪽(전용 서버, 또는 월드를 연 클라이언트)이 만드는 아이템 레지스트리의 네트워크 런타임 ID다. ProxyPass로 받은 1.26.0 월드의 아이템 목록과 Chest-UI의 26.20 표는 공통 이름 1824개 중 1813개가 같은 값이고, Dragonfly 서버가 커스텀 아이템에 붙인 런타임 ID * 65536으로도 커스텀 아이템과 블록이 그려졌다(Ore UI 로딩 조사, 1.26.52 Windows).

| 대상 | 숫자 ID |
| --- | --- |
| 바닐라 아이템, 블록 | 그 버전 서버 데이터의 런타임 ID. 853 이상인 아이템은 모든 팩의 커스텀 아이템 수 C를 더한다 |
| 커스텀 아이템 | 행동 팩을 쌓기 순서로, 팩 안의 아이템 파일을 대소문자를 무시한 경로 순서로 늘어놓은 자리 k(0부터)로 `853 + k` |
| 커스텀 블록 | 행동 팩을 쌓기 순서로 늘어놓고, 앞 팩부터 -9745에서 아래로 하나씩 번호를 받는다. 팩 안에서는 경로 순서의 역순이다. 블록 n개인 팩 하나면 경로 순서로 j번째(0부터)가 `-9745 - (n - 1 - j)` |

### 2.1 바닐라

- 1.26.6x의 바닐라 번호는 Dragonfly가 1.26.60 지원 커밋(2026-10-28)에 넣은 `server/world/vanilla_items.nbt`(gophertunnel 1.63.0, 아이템 2080개, -1251~884)와 맞는다.
- 커스텀 아이템이 끼어드는 자리 P는 853(붉은 관목)이다. 그 앞의 바닐라는 밀리지 않는다.
- Bedrock Wiki의 26.50 표는 1.26.63에 맞지 않는다. 1.26.60이 `frostbite_spawn_egg`를 791에 넣어 792 이후가 1씩 커졌기 때문이다. 26.50 표로 사과(882 + 커스텀 1개 = 883)를 보내면 돌풍구가 그려졌다.
- 바닐라 번호는 버전마다 바뀐다(다이아몬드는 26.30에서 335, 26.40에서 306, C-33). 스크립트는 게임 버전을 읽을 수 없으므로 바닐라 표는 애드온이 대상으로 하는 버전 하나에 맞춘다.
- C에는 상한이 있다는 기록이 있다. 커스텀 아이템이 1569개를 넘으면 더 밀리지 않는다(Bedrock Wiki 26.50, 시험하지 않음).

![번호 840~903, 커스텀 아이템 5개인 월드. 853~857이 커스텀 아이템이고 858 붉은 관목부터 밀린 바닐라가 이어져 사과가 888(883 + 5)에 있다](/img/design/item-aux-probe-840.png)

### 2.2 커스텀 아이템의 순서

팩 안에서는 아이템 파일 경로를 대소문자를 무시하고 정렬한 순서다(JavaScript `localeCompare`와 같은 결과). 다른 순서가 아닌 이유:

- 식별자 순서가 아니다. 식별자 `aux_probe_a`인 `z_first.json`이 맨 뒤에 놓였다.
- 하위 폴더를 먼저 두는 순서가 아니다. `sub/k_sub.json`이 `m_mid.json`과 `z_first.json` 사이에 놓였다.
- 바이트 순서가 아니다. `B_upper.json`이 `aux_probe_test.json` 뒤에 놓였고, `m_mid.json`이 `m-dash.json` 앞에 놓였다(바이트로는 `-`가 `_`보다 앞이다). `_`와 `-`를 가른 쌍은 이것 하나다.
- 숫자를 수로 읽지 않는다. `n10.json`이 `n9.json` 앞에 놓였다.

![번호 840~903, 두 팩. 853~854 보조 팩, 855~863 탐침 팩이 파랑(a_last), 망원경(aux_probe_test), 주황(B_upper), 연두(m_mid), 보라(m-dash), 자홍(n10), 청록(n9), 노랑(sub/k_sub), 빨강(z_first) 순서](/img/design/item-aux-probe-840-v110.png)

### 2.3 행동 팩이 여럿일 때

팩 사이의 순서는 행동 팩 쌓기 순서다. 아이템과 블록이 같은 팩 순서를 쓴다.

- 모든 팩의 경로를 합쳐 정렬하지 않는다. 보조 팩의 `c_extra.json`은 경로로는 탐침 팩의 `aux_probe_test.json` 다음이어야 하지만, 보조 팩 아이템 2개가 덩어리로 탐침 팩 앞에 붙었다.
- 활성 목록에서 두 팩의 순서를 바꾸면 아이템과 블록 모두 덩어리째 자리가 바뀐다. 팩 안의 순서와 바닐라가 밀리는 폭 C는 그대로다.

![순서를 바꾼 뒤 번호 840~903. 853~861 탐침 팩 9개, 862~863 보조 팩 2개, 864 붉은 관목](/img/design/item-aux-probe-840-swapped.png)

![순서를 바꾼 뒤 번호 -9776~-9713. -9745 금, -9746 에메랄드, -9747 다이아몬드(탐침 팩), -9748 청금석(보조 팩). 바꾸기 전에는 청금석이 -9745였다](/img/design/item-aux-probe-blocks-swapped.png)

### 2.4 커스텀 블록

- 커스텀 블록은 -9745(= -10000 + 255)부터 아래로 놓이고 3D로 그려진다. Bedrock Wiki 옛 판(1.20.20~1.21.100)의 "바닐라 최소 번호 바로 아래부터"와 "ID로는 그려지지 않는다"는 1.26.63에서 맞지 않았다. 바닐라 최소 번호 아래(-1278~-1252)는 비어 있었다.
- 팩 안에서는 경로 순서의 역순이다. 경로 순서로 마지막인 `z_first.json`이 -9745를 받았다. 식별자 순서(a, b, c)와는 다르다.
- 커스텀 블록은 아이템 범위를 밀지 않는다. 블록 아이템은 `ItemTypes.getAll()`에 들어 있지만 C는 커스텀 아이템만 센다.

![두 팩, 순서를 바꾸기 전 번호 -9776~-9713. -9745 청금석(보조 팩), -9746 금(z_first), -9747 에메랄드(m_mid), -9748 다이아몬드(a_last)](/img/design/item-aux-probe-blocks-v110.png)

### 2.5 `getAll()`이 주는 것

- 커스텀 아이템 수 C는 맞게 준다. `minecraft:`가 아니고 커스텀 블록도 아닌 것을 세면 된다.
- 순서는 믿을 수 없다. 레지스트리 순서가 같은 두 월드에서 `ItemTypes.getAll()`이 a, d, c, test, b와 c, a, d, test, b로 서로 다르게 돌려줬다.
- 디스코드(2026-07-09)에는 무료 마켓 애드온을 모두 켠 월드에서 1518개로 셌는데 실제로 밀린 폭은 1560이었다는 보고가 있다. 커스텀 아이템이 아주 많을 때의 C는 확인하지 않았다.

![커스텀 아이템 5개가 a, d, c, test, b 순서로 나온 첫 번째 월드의 메뉴](/img/design/item-aux-probe-menu.png)

![같은 레지스트리 순서에서 c, a, d, test, b 순서로 나온 두 번째 월드의 메뉴](/img/design/item-aux-probe-menu-v101.png)

## 3. 스크립트가 할 수 있는 것

| 대상 | 스크립트에서 | 방법 |
| --- | --- | --- |
| 바닐라 아이템, 블록 | 된다 | 대상 버전의 바닐라 표 + `ItemTypes.getAll()`로 센 C(853 이상만) |
| 자기 팩의 커스텀 아이템, 블록 | 팩이 맨 앞일 때만 된다 | 빌드할 때 파일 경로로 만든 표. 앞에 다른 팩이 있으면 그 팩의 아이템, 블록 수만큼 밀린다 |
| 다른 팩의 커스텀 아이템, 블록 | 안 된다 | 어느 팩 것인지, 팩 순서와 파일 경로를 스크립트가 알 수 없다 |

스크립트는 파일 경로도 팩 순서도 읽을 수 없고, `getAll()` 순서도 믿을 수 없다. 그래서 커스텀 아이템과 블록은 다른 팩과 함께 쓰일 때 번호를 확정할 수 없다.

실용적인 구성:

1. 바닐라 아이템과 블록은 aux 번호로 그린다(3D, 반짝임).
2. 자기 팩의 커스텀 아이템과 블록은 자기 리소스 팩의 텍스처 경로로 그린다. 텍스처는 팩 순서와 상관없다.
3. 자기 팩이 반드시 맨 앞에 있다고 정할 수 있는 환경에서만 커스텀 번호 표를 쓴다.

### 3.1 어디에 쓸 방법인가

행동 팩 스크립트가 번호를 계산해 UI로 보내는 방법은 **배포하는 애드온에는 권하지 않는다.** 애드온은 어떤 게임 버전에서, 어떤 팩과 함께 켜질지 모른다. 바닐라 표는 게임이 업데이트될 때마다 낡고, 커스텀 번호는 다른 팩이 앞에 오면 밀린다. 틀리면 빈 칸이 아니라 다른 아이템이 그려진다.

반대로 **사설 서버에서는 가장 좋은 방법이다.** 운영자가 게임 버전과 팩 목록, 쌓기 순서를 정하므로 표를 한 번 맞추면 계속 맞는다. 플레이어 인벤토리를 건드리지 않고, 서버 폼과 HUD 어디서나 쓸 수 있고, 아이콘 수에 제한이 없다. 서버를 업데이트할 때 바닐라 표를, 팩 구성을 바꿀 때 커스텀 번호 표를 다시 만든다. 아이템 목록을 직접 보내는 커스텀 서버(Dragonfly 등)는 번호를 스스로 정하므로 추론할 필요가 없다([HUD 아이템 아이콘 3절](./hud-item-icons.mdx#3-숫자-id를-제목에-싣는-방법)).

## 4. 번호 없이 인벤토리 칸으로 그리기

플레이어 핫바나 상자 같은 인벤토리 칸에 실제 아이템이 있으면 클라이언트가 그 칸의 `#item_id_aux`를 직접 채운다. 번호를 계산하지 않으므로 바닐라, 커스텀, 다른 팩의 아이템이 모두 맞게 그려지고 3D와 반짝임도 나온다. 대가는 플레이어 칸을 잠깐 빌리거나 컨테이너 화면을 써야 한다는 것이다.

| 방법 | 화면 | 쓰는 칸 | 성질 |
| --- | --- | --- | --- |
| 칸 백업 후 채우기 | HUD | 보여 줄 수만큼, 보이는 동안 계속 | 플레이어 아이템을 옮기므로 백업과 복원이 어긋나면 잃을 수 있다. 측정 중이다(4.4절) |
| 빈 칸 여러 개 + 잠금 확인 고정(4.1절) | HUD | 보여 줄 수만큼, 1틱 | 1틱 만에 비워도 맞았다. 가장 튼튼하다 |
| 칸 하나 + 개수 확인 고정(4.2절) | HUD | 1칸, 아이콘마다 3틱 | 3틱 간격이면 맞는다. 쌓이는 아이템만 된다 |
| 엔티티 인벤토리 화면 | 컨테이너 화면 | 플레이어 칸 0 | 엔진이 엔티티 칸을 그리므로 시간 문제가 없다. [엔티티 인벤토리 UI 기획](./entity-inventory-ui.mdx)에서 다룬다 |

안 되는 것:

| 시도 | 안 되는 이유 |
| --- | --- |
| 서버 폼 화면에서 인벤토리 컬렉션 읽기 | 17번 칸에 아이템을 넣고 `hotbar_items`, `combined_hotbar_and_inventory_items`, `inventory_items`를 읽었더니 모두 비었다. 칸을 빌리는 방법은 HUD 전용이다 |
| HUD에서 주머니(번들) 내용물 읽기 | 핫바의 주머니에서 `#bundle_item_renderer_data`와 `#item_storage_current_amount`가 비었다. 주머니 아이콘만 나온다 |
| `live_horse_renderer`로 아이템 엔티티 그리기 | 아이템 엔티티는 빈 칸이었다. 같은 방식(`#entity_id`에 버튼 글을 그대로 넣음)으로 플레이어와 갑옷 거치대는 그려졌다 |
| 아이템을 든 엔티티로 아이콘 대신하기 | 투명화한 갑옷 거치대는 든 아이템만 보였지만, 쥐는 모양이 아이템마다 다르다(손 뼈만 둔 엔티티에서 납작한 아이템은 옆에서 본 선, 커스텀 쥐는 모양) |

### 4.1 빈 칸 여러 개 + 잠금 확인 고정

1. 스크립트가 메인 인벤토리의 빈 칸(예: 9~14번)에 표시용 아이템을 한꺼번에 넣는다. 표시용 아이템에는 `lockMode = slot`, `keepOnDeath = true`, 알아볼 수 있는 `nameTag`를 건다.
2. 다음 틱에 제목을 한 번 보낸다. HUD 패널은 그 제목으로 보이게 된다.
3. HUD는 `hotbar_items`를 `collection_index` 9~35로 읽는다. 칸마다 숨긴 데이터 패널이 `binding_condition: "visibility_changed"`로 `#item_id_aux`와 `#item_lock_in_slot`을 보이게 된 순간의 값으로 고정한다.
4. 아이콘은 `source_control_name`과 `resolve_sibling_scope: true`로 데이터 패널의 값을 읽고, 고정된 `#item_lock_in_slot`이 참일 때만 보인다.
5. 스크립트가 칸을 비운다. 고정된 아이콘은 제목이 떠 있는 동안 남는다.

```json
"locked": {
  "type": "panel", "size": [ 18, 18 ], "collection_index": "$slot",
  "controls": [
    {
      "data": {
        "type": "panel", "size": [ 0, 0 ],
        "bindings": [
```

이 패널은 `collection_name: "hotbar_items"`인 스택 패널 안에 둔다. 플레이어 자신의 아이템은 잠겨 있지 않으므로, 제목이 늦게 와서 칸이 이미 비었거나 다른 아이템이 들어왔으면 아이콘이 보이지 않을 뿐 틀린 아이콘이 고정되지 않는다.

### 4.2 칸 하나 + 개수 확인 고정

칸 하나에 아이템을 차례로 넣으면서 아이콘을 하나씩 고정한다. k번째(0부터) 아이템은 `k + 2`개로 넣고, k번째 고정 칸은 그 순간의 개수가 `k + 2`일 때만 보인다. 고정 칸은 제목 글자의 길이로 단계를 받는다(`ixc:a`, `ixc:aa`, ...). 제목은 아이템을 넣은 다음 틱에 보낸다.

- `#inventory_stack_count`는 숫자가 아니라 개수 라벨 글자다. `(((#inventory_stack_count - '§r') - '§f') = 3)`처럼 서식 코드를 빼고 비교한다.
- 개수는 2부터 쓴다. 개수 1은 빈 글자와 비교해도 맞지 않았다.
- 개수 확인이 꼭 필요하다. 제목 단계만 보고 고정하면 1틱 간격에서 한 칸씩 밀려 다른 아이콘이 고정됐다. 개수를 확인하면 같은 간격에서 틀린 아이콘 대신 빈 칸이 된다.
- 검이나 도구처럼 한 개만 쌓이는 아이템은 개수를 바꿀 수 없어 쓸 수 없다.

### 4.3 기기 속도와 위험

- 두 방법 모두 늦으면 빈 칸이 되고 틀린 아이콘은 고정되지 않는다. 빈 칸이 된 아이콘만 다시 시도할 수 있다.
- 4.1절은 틱이 "언제 칸을 비워도 되는가"에만 영향을 준다. 4.2절은 아이콘마다 간격이 필요해 느린 기기에서 실패가 늘어난다.
- 빌리는 칸은 시작할 때 비어 있어야 한다. 접속할 때 표시용 아이템(이름표로 구분)을 지운다.
- 두 방법 모두 HUD 전용이고, 빌리는 동안 플레이어가 인벤토리 화면을 열면 표시용 아이템이 보인다.

### 4.4 시험 애드온

4절의 방법과 안 되는 시도를 한 애드온(Item Icon Slots)에 모았다. 아이콘은 다이아몬드, 상자, 황금 사과, 네더라이트 검과 이 애드온의 커스텀 아이템 2개(빨강, 파랑 양털 그림)이고, 칸 하나 방법은 쌓이는 아이템 12개를 쓴다.

| 메뉴 | 하는 일 |
| --- | --- |
| HUD: back up slots 9-14 and fill them | 9~14번 칸의 아이템을 백업하고 표시용 아이템을 넣어 5초 동안 보인 뒤 되돌린다 |
| HUD: 6 empty slots, lock check, clear after 1 tick / 10 ticks | 4.1절. 윗줄(Frozen)은 고정한 아이콘, 아랫줄(Live)은 지금 칸이다 |
| HUD: 1 slot, count check, 3 ticks apart / 1 tick apart | 4.2절 |
| HUD: 1 slot, no check, 1 tick apart | 4.2절에서 개수 확인을 뺀 것 |
| HUD: bundle contents | 핫바 9번째 칸에 다이아몬드와 빨강이 든 주머니를 넣고 내용물 칸과 저장량을 그린다 |
| Form: read inventory slot 17 | 17번 칸에 다이아몬드를 넣고 서버 폼에서 인벤토리 컬렉션 네 줄을 읽는다 |
| Form: entities holding items | 아이템 엔티티, 갑옷 거치대, 투명 거치대, 손 뼈만 있는 엔티티가 다이아몬드, 상자, 빨강을 들고 머리 위에 뜬다. 서버 폼이 `live_horse_renderer`로 그린다. 마지막 줄은 플레이어 자신이다 |

<AddonDownload id="item-icon-slots" />

1. 새 월드에서 행동 팩 "Bedrock Wiki Item Icon Slots BP"를 켠다. 리소스 팩은 의존성으로 함께 켜진다.
2. 크리에이티브 인벤토리 아이템 분류의 맨 뒤에서 "Item Icon Slots"(주머니 그림)를 꺼낸다. `/give @s bwiki:item_icon_slots_test`를 써도 된다.
3. 아이템을 사용하면 메뉴가 열린다. `/scriptevent bwiki:item_icon_slots`로도 열린다. HUD 메뉴는 메뉴가 닫힌 뒤 화면 위쪽 가운데에 나온다.

- 빈 칸이 필요한 메뉴는 칸이 차 있으면 채팅으로 알리고 시작하지 않는다. 6칸 메뉴는 9~14번(메인 인벤토리 첫 줄 왼쪽 6칸), 칸 하나 메뉴와 폼 메뉴는 17번, 주머니 메뉴는 핫바 9번째 칸을 쓴다.
- 백업 메뉴만 차 있는 칸을 그대로 쓴다. 백업은 스크립트 메모리와 플레이어 동적 속성에 함께 저장한다. 되돌리기 전에 월드를 나가면 다음 접속 때 동적 속성에서 되돌린다. 동적 속성에는 종류, 개수, 이름, 설명, 내구도, 인챈트만 남는다.
- 이 애드온은 `third_party_server_screen`의 `$screen_content`와 HUD 제목을 바꾸므로 다른 시험 애드온과 함께 켜지 않는다.
- 화면의 글은 영어다.
