# Script API로 아이템 숫자 ID(aux) 추론하기

JSON UI의 `inventory_item_renderer`는 `#item_id_aux`에 `숫자 아이템 ID * 65536 + 데이터 값`을 받아 아이템을 그린다(ANI-06). 인챈트 반짝임은 32768을 더한다. 텍스처 경로로 그릴 때와 달리 블록이 3D로 나오고 반짝임도 나온다([연구 화면 8.1절](./server-form-research-screen.mdx#81-아이템-아이콘-v140)).

문제는 스크립트가 이 숫자를 알 방법이 없다는 것이다. 이 페이지는 행동 팩 스크립트가 아이템 이름(`minecraft:diamond`, `bwiki:ruby`)에서 숫자 ID를 계산하는 방법을 연구한다. 바닐라 아이템과 블록, 커스텀 아이템, 커스텀 블록을 모두 다룬다.

상태: 1.26.63 모바일에서 바닐라, 커스텀 아이템, 커스텀 블록의 배치 규칙을 확인했다(5절). 바닐라는 스크립트에서 계산할 수 있다. 커스텀 아이템과 블록은 팩 쌓기 순서에 따라 밀려 스크립트로 확정할 수 없다(5.7절). 스크립트 계산은 사설 서버에 맞고 배포하는 애드온에는 권하지 않는다(5.8절). 번호를 계산하지 않고 인벤토리 칸에 실제 아이템을 두어 엔진이 그리게 하는 방법은 6절에 모았다.

## 1. Script API에는 숫자 ID가 없다

`@minecraft/server` 2.11.0(정식), 2.12.0-beta.1.26.63-stable, 2.13.0-beta.1.26.70-preview.24의 타입 정의를 확인했다.

| API | 주는 것 |
| --- | --- |
| `ItemType` | `id`(문자열), `localizationKey` |
| `ItemTypes` | `get(id)`, `getAll()` |
| `BlockType` | `id`, `localizationKey` |
| `BlockTypes` | `get(id)`, `getAll()` |
| `ItemStack` | 생성자는 `(itemType, amount)`. 데이터 값 멤버가 없다 |
| `BlockPermutation.getItemStack()`, `Block.getItemStack(amount, withData)` | `ItemStack`을 돌려준다. `withData`는 블록 엔티티 데이터다 |

- 숫자 ID, 런타임 ID, 레거시 ID, aux를 돌려주는 멤버는 없다. `getAll()`의 문서에는 결과 순서에 대한 설명이 없다.
- `@minecraft/server-ui`의 `ActionFormData.button(text, iconPath)`는 텍스처 경로만 받는다. 아이템 타입으로 아이콘을 그리는 오버로드는 없다.
- 스크립트가 쓸 수 있는 재료는 `ItemTypes.getAll()`과 `BlockTypes.getAll()`이 주는 커스텀 아이템, 커스텀 블록 목록과 그 순서뿐이다. 바닐라 번호는 버전별 표를 스크립트에 넣어야 한다.

## 2. 알려진 사실과 충돌

### 2.1 그려지는 번호는 아이템 레지스트리의 런타임 ID다

JSON UI가 그리는 번호는 서버가 아이템 레지스트리로 보내는 네트워크 런타임 ID와 같다.

- 2026-02-24 ProxyPass로 받은 1.26.0 월드의 아이템 목록(1905개)에서 다이아몬드 335, 사과 285, 돌풍구 284, 에메랄드 552, 상자 54다. Chest-UI의 26.20 표(2026-05-18)도 같은 값이고, 공통 이름 1824개 중 1813개가 같다.
- Dragonfly 서버는 커스텀 아이템에 바닐라 다음 번호를 그대로 이어 붙인다. 클라이언트가 스스로는 만들지 않는 배치인데, 1.26.52 Windows에서 이 런타임 ID * 65536으로 커스텀 아이템과 커스텀 블록이 그려졌다(Ore UI 로딩 조사).

그래서 숫자 ID를 정하는 것은 월드를 연 쪽(전용 서버, 또는 월드를 연 클라이언트)이 만드는 레지스트리다. 스크립트 추론은 그 레지스트리의 배치 규칙을 재현하는 일이다.

### 2.2 바닐라 배치

- Bedrock Wiki의 26.50 표: 바닐라는 -1246~883이다. 블록은 음수, 아이템은 0 이상이다.
- 26.40부터 데이터 기반 아이템 32개(창, 번들, 바람 막대, 시련 열쇠, 돌풍구, 사과, 발광 열매 등)가 표 끝으로 옮겨졌다. 26.50에서 852~883이다.
- 바닐라 번호는 버전마다 바뀐다. 다이아몬드는 26.30에서 335, 26.40에서 306이다(C-33).
- 1.26.63에서 26.50 표로 사과를 883(882 + 커스텀 아이템 1)으로 보냈더니 돌풍구가 그려졌다. 26.50 이후 이 범위의 배치가 바뀌었다. 852 미만의 아이템 15종은 그대로 맞았다.

### 2.3 커스텀 아이템이 들어가는 자리와 순서

| 항목 | 기록 | 근거 |
| --- | --- | --- |
| 들어가는 자리 | 26.30까지는 257부터. 1.26.0 캡처에서 커스텀 아이템 38개가 257~294이고 그 뒤 바닐라가 모두 +38 밀렸다 | ProxyPass 캡처(1.21.73, 1.26.0), Chest-UI `ID < 256` |
| 들어가는 자리 | 26.40은 850, 26.50은 852부터. 그 앞의 바닐라는 밀리지 않는다 | Bedrock Wiki, Chest-UI `ID < 850` |
| 커스텀 아이템끼리의 순서 | 식별자 문자열 순서(`color_1`, `color_10`, `color_11`, `color_2`) | ProxyPass 캡처 두 개 |
| 커스텀 아이템끼리의 순서 | 리소스 팩 쌓기 순서 | Bedrock Wiki 26.50 |
| 커스텀 아이템끼리의 순서 | 파일 이름 순서, 하위 폴더의 파일이 먼저 | 디스코드 2026-02-14, 2026-02-15 |
| 개수 세기 | `ItemTypes.getAll()`에서 `minecraft:`가 아닌 것을 세면 1개짜리 월드에서는 맞았다. 무료 마켓 애드온을 모두 켠 월드에서는 1518개로 셌는데 실제로 밀린 폭은 1560이었다 | 디스코드 2026-07-09 |
| 포화 | 커스텀 아이템이 1569개를 넘으면 더 밀리지 않는다 | Bedrock Wiki 26.50 |

순서에 대한 세 주장은 서로 다르다. 캡처 두 개는 팩 하나 안의 순서만 보여 주므로, 팩이 여럿일 때는 쌓기 순서가 먼저일 수도 있다.

### 2.4 커스텀 블록

| 기록 | 근거 |
| --- | --- |
| 바닐라 최소 번호 바로 아래부터 음수로 내려간다(1.21.100에서 -1039부터). 바닐라를 밀지 않는다. ID로는 그려지지 않는다 | Bedrock Wiki 1.20.20~1.21.100 판. 26.44 판부터 이 문장이 빠졌다 |
| 블록은 바닐라 번호를 밀지 않는다 | Chest-UI `constants.js` |
| 첫 커스텀 블록이 -9745(= -10000 + 255)이고, 파일 이름 역순으로 하나씩 내려간다. PC에서는 맞고 Android에서는 가끔, iOS에서는 틀린다 | 디스코드 2026-02-14, 2026-03-14 |
| 커스텀 블록은 aux ID로 그려지지 않는다. 번호는 -1091 근처다 | 디스코드 2026-05-12 |
| Dragonfly가 등록한 커스텀 블록이 런타임 ID * 65536으로 3D 그림이 그려졌다 | Ore UI 로딩 조사(1.26.52) |

커스텀 블록이 든 레지스트리 캡처는 아직 없다.

### 2.5 아이템이 칸에 있으면 진짜 번호를 읽을 수 있다

플레이어 핫바나 상자 칸의 `#item_id_aux`는 클라이언트가 직접 채운다. 스크립트가 계산할 필요가 없지만, 그 칸에 실제 아이템이 있어야 하고 서버 폼 화면에서는 인벤토리 컬렉션을 읽을 수 없다. 추론이 맞는지 확인하는 기준으로만 쓴다.

## 3. 추론 방법 초안

스크립트가 이름 `n`의 숫자 ID를 구하는 순서다. 굵은 글씨는 실험으로 정할 값이다.

1. `n`이 바닐라 아이템이고 표 번호가 **P** 미만이면 표 번호를 그대로 쓴다.
2. `n`이 바닐라 아이템이고 표 번호가 P 이상이면 커스텀 아이템 수 `C`를 더한다. `C`는 1569를 넘지 않는다.
3. `n`이 커스텀 아이템이면 커스텀 아이템을 **순서 O**로 늘어놓은 자리 `k`(0부터)로 `P + k`를 쓴다.
4. `n`이 바닐라 블록이면 표 번호를 쓴다.
5. `n`이 커스텀 블록이면 커스텀 블록을 **순서 O'** 로 늘어놓은 자리 `k`로 **B** `- k`를 쓴다.

정할 값:

| 값 | 후보 | 1차 실험 뒤 |
| --- | --- | --- |
| P (커스텀 아이템 시작) | 26.50은 852 | 1.26.63은 853(5.1절) |
| 순서 O | 식별자 순서, 파일 이름 순서(하위 폴더 먼저), 경로 순서, `ItemTypes.getAll()` 순서 | 팩 하나 안에서는 경로 문자열 순서. `getAll()` 순서는 열 때마다 달랐다 |
| C에 커스텀 블록의 블록 아이템이 들어가는지 | Chest-UI는 뺀다 | 들어가지 않는다(5.3절) |
| B (커스텀 블록 시작) | 바닐라 최소 번호 바로 아래, -9745 | -9745 |
| 순서 O' | 식별자 순서, 파일 이름 순서, 그 역순, `BlockTypes.getAll()` 순서 | 경로 문자열의 역순(5.3절) |
| 바닐라 표 | 레지스트리 캡처 | 1.26.60 Dragonfly `vanilla_items.nbt`가 1.26.63 실측과 맞는다(5.2절) |

스크립트는 게임 버전을 읽을 수 없으므로 바닐라 표는 애드온이 대상으로 하는 버전 하나에 맞춘다.

## 4. 1차 실험: 아이템 Aux 탐침

탐침 애드온은 커스텀 아이템 4개와 커스텀 블록 3개를 등록하고, 숫자 ID 64개를 번호와 함께 아이템 렌더러로 그린다. 그려진 그림으로 각 번호에 무엇이 있는지 직접 읽는다.

### 4.1 등록하는 것

파일 이름과 식별자의 순서를 일부러 엇갈리게 두었다. 어느 순서 가설이 맞는지가 칸의 색 순서로 드러난다.

| 파일 | 식별자 | 그림 |
| --- | --- | --- |
| `items/z_first.json` | `bwiki:aux_probe_a` | 빨간 양털 |
| `items/a_last.json` | `bwiki:aux_probe_b` | 파란 양털 |
| `items/m_mid.json` | `bwiki:aux_probe_c` | 연두 양털 |
| `items/sub/k_sub.json` | `bwiki:aux_probe_d` | 노란 양털 |
| `items/aux_probe_test.json` | `bwiki:aux_probe_test` | 망원경(실행 아이템) |
| `blocks/z_first.json` | `bwiki:aux_probe_block_a` | 금 블록 |
| `blocks/a_last.json` | `bwiki:aux_probe_block_b` | 다이아몬드 블록 |
| `blocks/m_mid.json` | `bwiki:aux_probe_block_c` | 에메랄드 블록 |

가설마다 커스텀 아이템 5개가 늘어설 순서:

| 순서 가설 | 순서 |
| --- | --- |
| 식별자 | 빨강, 파랑, 연두, 노랑, 망원경 |
| 파일 이름, 하위 폴더 먼저 | 노랑, 파랑, 망원경, 연두, 빨강 |
| 경로 문자열 | 파랑, 망원경, 연두, 노랑, 빨강 |

커스텀 블록은 식별자 순서면 금, 다이아몬드, 에메랄드이고 파일 이름 순서면 다이아몬드, 에메랄드, 금이다.

### 4.2 화면

- 첫 메뉴 본문: `ItemTypes.getAll()`과 `BlockTypes.getAll()`이 돌려준 커스텀 아이템과 블록을 그 순서대로, 그리고 커스텀 블록의 블록 아이템이 `ItemTypes.getAll()`에 몇 개 있는지 보인다.
- 번호 64칸 화면: 버튼 텍스처 자리에 `aux:` + `번호 * 65536`을 보내고 칸 아래에 번호를 적는다. 메뉴에서 고르는 범위:

| 범위 | 보는 것 |
| --- | --- |
| 840~903 | 커스텀 아이템이 들어간 자리와 순서(P, O), 밀린 바닐라(사과, 돌풍구 등). 840~851은 밀리지 않는 바닐라라 기준이 된다 |
| -1278~-1215 | 바닐라 최소 번호 아래(-1278~-1247)에 커스텀 블록이 있는지. -1246~-1215는 바닐라 콘크리트 반 블록이라 기준이 된다 |
| -9776~-9713 | 디스코드의 -9745 주장 |
| 직접 입력 | 시작 번호를 넣어 64칸 |

### 4.3 시험 순서

1. 새 월드에 탐침 애드온만 켠다. 다른 시험 애드온의 커스텀 아이템도 레지스트리에 들어가므로 끈다.
2. 첫 메뉴 본문을 찍는다.
3. 세 범위를 차례로 열어 찍는다. 840~903에서 양털 4색과 망원경이 어디 있는지, -1278~-1247과 -9776~-9713에 금, 다이아몬드, 에메랄드 블록이 있는지 본다.
4. 커스텀 블록이 두 범위 어디에도 없으면 직접 입력으로 다른 범위를 찾는다.

PC에서는 ProxyPass로 같은 월드의 아이템 레지스트리를 받아 번호를 바로 대조할 수 있다. 1.26.63 바닐라 표도 이 캡처로 만든다.

### 4.4 3차 실험: 경로 정렬 규칙과 팩 여럿

1·2차 실험으로 팩 하나 안의 배치는 정해졌다(5.4절). 3차 실험은 남은 두 가지를 가린다.

탐침 v1.1.0은 아이템 파일 4개를 더한다. 바이트 순서, 대소문자를 무시한 순서, 숫자를 수로 읽는 순서가 모두 다른 결과를 내도록 이름을 골랐다.

| 파일 | 식별자 | 그림 |
| --- | --- | --- |
| `items/B_upper.json` | `bwiki:aux_probe_e` | 주황 양털 |
| `items/m-dash.json` | `bwiki:aux_probe_f` | 보라 양털 |
| `items/n10.json` | `bwiki:aux_probe_g` | 자홍 양털 |
| `items/n9.json` | `bwiki:aux_probe_h` | 청록 양털 |

탐침 보조 팩(Item Aux Probe Extra v1.0.0)은 스크립트와 UI 없이 아이템 2개와 블록 1개만 등록하는 두 번째 팩이다.

| 파일 | 식별자 | 그림 |
| --- | --- | --- |
| `items/c_extra.json` | `bwiki:aux_probe_x` | 분홍 양털 |
| `items/y_extra.json` | `bwiki:aux_probe_y` | 하늘색 양털 |
| `blocks/c_block.json` | `bwiki:aux_probe_block_x` | 청금석 블록 |

탐침 팩 하나 안에서 커스텀 아이템 9개가 853부터 놓일 순서:

| 정렬 가설 | 순서 |
| --- | --- |
| 바이트 순서 | 주황(`B_upper`), 파랑, 망원경, 보라(`m-dash`), 연두(`m_mid`), 자홍(`n10`), 청록(`n9`), 노랑, 빨강 |
| 대소문자 무시 | 파랑, 망원경, 주황, 연두, 보라, 자홍, 청록, 노랑, 빨강 |
| 숫자를 수로 | 파랑, 망원경, 주황, 연두, 보라, 청록, 자홍, 노랑, 빨강 |

두 팩을 함께 켰을 때 보조 팩의 분홍(`c_extra`)과 하늘색(`y_extra`)이 놓일 자리:

| 팩 사이 가설 | 자리 |
| --- | --- |
| 팩 쌓기 순서대로 팩마다 이어 붙임 | 탐침 9개 앞이나 뒤에 분홍, 하늘색이 붙는다. 쌓기 순서를 바꾸면 앞뒤가 바뀐다 |
| 모든 팩의 경로를 합쳐 정렬 | 분홍은 망원경 다음, 하늘색은 노랑 다음. 쌓기 순서와 상관없다 |

블록은 탐침의 금, 에메랄드, 다이아몬드와 보조 팩의 청금석이 -9745부터 아래로 놓인다. 경로를 합쳐 정렬하면 청금석은 다이아몬드(`a_last`)와 에메랄드(`m_mid`) 사이에 들어간다.

시험 순서:

1. 새 월드에 탐침 v1.1.0만 켜고 첫 메뉴 본문과 840~903을 찍는다(정렬 규칙).
2. 같은 월드에 보조 팩을 탐침 **위에** 쌓고 다시 들어가 첫 메뉴 본문, 840~903, -9776~-9713을 찍는다.
3. 보조 팩을 탐침 **아래로** 옮기고 같은 세 화면을 찍는다.

### 5.2 1.26.60 바닐라 표

Dragonfly가 1.26.60 지원 커밋(2026-10-28)에서 넣은 `server/world/vanilla_items.nbt`(gophertunnel 1.63.0)를 풀어 26.50 표와 비교했다. 아이템 2080개, 번호 -1251~884다.

- 1.26.60은 `frostbite_spawn_egg`를 791에 넣었다. 그래서 792 이후 번호가 26.50보다 1 크다. 생성 알 851, 엔드 수정 852, 붉은 관목 853, 돌풍구 882, 사과 883, 발광 열매 884다.
- 새 음수 번호 `icicle` -1247, `ice_crystal` -1248, `disc_press` -1251이 있다. 탐침의 -1247, -1248 칸은 비었다. 실험 기능을 켜지 않은 월드라 없는 것으로 보이지만 확인하지 않았다.
- 이 표에 커스텀 아이템 5개(853부터)를 넣으면 실측과 모두 맞는다. 붉은 관목 853 + 5 = 858, 사과 883 + 5 = 888이다. 연구 화면 시험에서 883(커스텀 1개)에 돌풍구가 나온 것도 882 + 1로 맞는다.

그래서 1.26.6x에서 커스텀 아이템까지의 규칙은 다음과 같다.

1. 바닐라 번호는 그 버전 서버 데이터(Dragonfly `vanilla_items.nbt`)의 런타임 ID다.
2. P는 밀리는 묶음의 첫 번호인 853(붉은 관목)이다. P 이상인 바닐라는 커스텀 아이템 수 C를 더한다.
3. 커스텀 아이템은 행동 팩 안 파일 경로의 문자열 순서로 P부터 놓인다.

스크립트는 파일 경로를 읽을 수 없고 `getAll()` 순서도 믿을 수 없다. 그래서 자기 팩의 커스텀 아이템과 블록 번호는 빌드할 때 파일 경로로 표를 만들어 스크립트에 넣어야 한다. 런타임에 할 수 있는 것은 `ItemTypes.getAll()`로 C를 세는 것뿐이다(이 월드에서 5개로 맞았다).

남은 것:

- 행동 팩이 여럿일 때 팩 사이의 순서(팩 쌓기 순서인지, 모든 팩의 경로를 합쳐 정렬하는지). 5.5절에서 일부 확인.
- 경로 정렬이 바이트 순서인지(대문자, 숫자, `_`, `-`가 섞일 때). 5.5절에서 확인.
- 다른 플랫폼(Windows, iOS)에서도 같은지. 디스코드에는 iOS에서 틀린다는 보고가 있다.

### 5.7 결론: 스크립트가 할 수 있는 것

| 대상 | 스크립트에서 | 방법 |
| --- | --- | --- |
| 바닐라 아이템, 블록 | 된다 | 대상 버전의 바닐라 표 + `ItemTypes.getAll()`로 센 C(853 이상만) |
| 자기 팩의 커스텀 아이템, 블록 | 팩이 맨 앞일 때만 된다 | 빌드할 때 파일 경로로 만든 표. 앞에 다른 팩이 있으면 그 팩의 아이템, 블록 수만큼 밀린다 |
| 다른 팩의 커스텀 아이템, 블록 | 안 된다 | 어느 팩 것인지, 팩 순서와 파일 경로를 스크립트가 알 수 없다 |

`getAll()`은 커스텀 아이템 수 C는 맞게 주지만 순서는 주지 않는다. 팩 순서도 API로 읽을 수 없다. 그래서 커스텀 아이템과 블록은 다른 팩과 함께 쓰일 때 번호를 확정할 수 없다.

실용적인 구성:

1. 바닐라 아이템과 블록은 aux 번호로 그린다(3D, 반짝임).
2. 자기 팩의 커스텀 아이템과 블록은 자기 리소스 팩의 텍스처 경로로 그린다. 텍스처는 팩 순서와 상관없다.
3. 자기 팩이 반드시 맨 앞에 있다고 정할 수 있는 환경(서버가 팩 순서를 정하는 월드 등)에서만 커스텀 번호 표를 쓴다.

### 5.8 어디에 쓸 방법인가

행동 팩 스크립트가 번호를 계산해 UI로 보내는 방법은 **배포하는 애드온에는 권하지 않는다.** 애드온은 어떤 게임 버전에서, 어떤 팩과 함께 켜질지 모른다. 바닐라 표는 게임이 업데이트될 때마다 낡고, 커스텀 번호는 다른 팩이 앞에 오면 밀린다. 틀리면 빈 칸이 아니라 다른 아이템이 그려진다.

반대로 **사설 서버에서는 가장 좋은 방법이다.** 운영자가 게임 버전과 팩 목록, 쌓기 순서를 정하므로 표를 한 번 맞추면 계속 맞는다. 플레이어 인벤토리를 건드리지 않고, 서버 폼과 HUD 어디서나 쓸 수 있고, 아이콘 수에 제한이 없다. 서버를 업데이트할 때 바닐라 표를, 팩 구성을 바꿀 때 커스텀 번호 표를 다시 만든다. 아이템 목록을 직접 보내는 커스텀 서버(Dragonfly 등)는 번호를 스스로 정하므로 추론할 필요가 없다([HUD 아이템 아이콘 3절](./hud-item-icons.mdx#3-숫자-id를-제목에-싣는-방법)).

## 6. 번호 없이 인벤토리 칸으로 그리기

플레이어나 엔티티의 인벤토리 칸에 실제 아이템이 있으면 클라이언트가 그 칸의 `#item_id_aux`를 직접 채운다(2.5절). 번호를 계산하지 않으므로 바닐라, 커스텀, 다른 팩의 아이템이 모두 맞게 그려지고 3D와 반짝임도 나온다. 대가는 플레이어 칸을 잠깐 빌리거나 컨테이너 화면을 써야 한다는 것이다.

아래는 1.26.63 모바일에서 시험한 결과다(2026-11-14).

| 방법 | 화면 | 쓰는 칸 | 결과 |
| --- | --- | --- | --- |
| 칸 백업 후 채우기 | HUD | 보여 줄 수만큼, 보이는 동안 계속 | 플레이어 아이템을 옮기므로 백업과 복원이 어긋나면 잃을 수 있다. 시험 애드온(6.4절)으로 측정 중이다 |
| 빈 칸 여러 개 + 잠금 확인 고정(6.1절) | HUD | 보여 줄 수만큼, 1틱 | 6개를 1틱 만에 되돌려도 모두 맞았다. 가장 튼튼하다 |
| 칸 하나 + 개수 확인 고정(6.2절) | HUD | 1칸, 아이콘마다 3틱 | 3틱 간격으로 12개가 모두 맞았다. 1틱 간격은 빈 칸이 생겼다(틀린 아이콘은 없다). 쌓이는 아이템만 된다 |
| 엔티티 인벤토리 화면 | 컨테이너 화면 | 플레이어 칸 0 | 엔진이 엔티티 칸을 그리므로 시간 문제가 없다. 화면 구성과 여는 방법은 [엔티티 인벤토리 UI 기획](./entity-inventory-ui.mdx)에서 다룬다 |

안 된 것:

| 시도 | 결과 |
| --- | --- |
| 서버 폼 화면에서 인벤토리 컬렉션 읽기 | `hotbar_items`, `inventory_items` 등 시험한 네 줄이 모두 비었다. 칸을 빌리는 방법은 HUD 전용이다 |
| HUD에서 주머니(번들) 내용물 읽기 | 주머니 아이콘만 나오고 내용물과 저장량은 비었다 |
| `live_horse_renderer`로 아이템 엔티티 그리기 | 빈 칸이었다. 같은 방식으로 플레이어와 갑옷 거치대는 그려졌다(`#entity_id`에 버튼 글을 그대로 넣음) |
| 아이템을 든 엔티티로 아이콘 대신하기 | 투명화한 갑옷 거치대는 든 아이템만 보였지만, 쥐는 모양이 아이템마다 달라(납작한 아이템은 옆에서 본 선, 커스텀 쥐는 모양) 아이콘으로 쓸 수 없다 |

### 6.1 빈 칸 여러 개 + 잠금 확인 고정

1. 스크립트가 메인 인벤토리의 빈 칸(시험에서는 9~14번)에 표시용 아이템을 한꺼번에 넣는다. 표시용 아이템에는 `lockMode = slot`, `keepOnDeath = true`, 알아볼 수 있는 `nameTag`를 건다.
2. 다음 틱에 제목을 한 번 보낸다. HUD 패널은 그 제목으로 보이게 된다.
3. HUD는 `hotbar_items`를 `collection_index` 9~35로 읽는다. 칸마다 숨긴 데이터 패널이 `binding_condition: "visibility_changed"`로 `#item_id_aux`와 `#item_lock_in_slot`을 보이게 된 순간의 값으로 고정한다.
4. 아이콘은 `source_control_name`과 `resolve_sibling_scope: true`로 데이터 패널의 값을 읽고, 고정된 `#item_lock_in_slot`이 참일 때만 보인다.
5. 스크립트가 칸을 비운다. 고정된 아이콘은 제목이 떠 있는 동안 남는다.

```json
"locked": {
  "type": "panel", "size": [ 18, 18 ], "collection_index": "$slot",
  "controls": [
    {
      "data": {
        "type": "panel", "size": [ 0, 0 ],
        "bindings": [
          { "binding_type": "collection", "binding_collection_name": "hotbar_items", "binding_name": "#item_id_aux", "binding_condition": "visibility_changed" },
          { "binding_type": "collection", "binding_collection_name": "hotbar_items", "binding_name": "#item_lock_in_slot", "binding_condition": "visibility_changed" }
        ]
      }
    },
    {
      "icon": {
        "type": "custom", "renderer": "inventory_item_renderer", "size": [ 16, 16 ], "layer": 2,
        "property_bag": { "#item_id_aux": 0 },
        "bindings": [
          { "binding_type": "view", "source_control_name": "data", "resolve_sibling_scope": true, "source_property_name": "#item_id_aux", "target_property_name": "#item_id_aux" },
          { "binding_type": "view", "source_control_name": "data", "resolve_sibling_scope": true, "source_property_name": "#item_lock_in_slot", "target_property_name": "#visible" }
        ]
      }
    }
  ]
}
```

이 패널은 `collection_name: "hotbar_items"`인 스택 패널 안에 둔다. 플레이어 자신의 아이템은 잠겨 있지 않으므로, 제목이 늦게 와서 칸이 이미 비었거나 다른 아이템이 들어왔으면 아이콘이 보이지 않을 뿐 틀린 아이콘이 고정되지 않는다.

### 6.2 칸 하나 + 개수 확인 고정

칸 하나에 아이템을 차례로 넣으면서 아이콘을 하나씩 고정한다. k번째(0부터) 아이템은 `k + 2`개로 넣고, k번째 고정 칸은 그 순간의 개수가 `k + 2`일 때만 보인다.

- `#inventory_stack_count`는 숫자가 아니라 개수 라벨 글자다. `(((#inventory_stack_count - '§r') - '§f') = 3)`처럼 서식 코드를 빼고 비교한다.
- 개수 1은 빈 글자와 비교해도 맞지 않아서 개수는 2부터 쓴다.
- 고정 칸은 제목 글자의 길이로 단계를 받는다(`LAC:a`, `LAC:aa`, ...). 제목은 아이템을 넣은 다음 틱에 보낸다.
- 개수 확인이 없을 때는 1틱 간격에서 한 칸씩 밀려 **다른 아이콘**이 고정됐다. 개수 확인을 넣은 뒤 1틱 간격에서는 마지막 하나만 채워지고 나머지는 빈 칸이었다.
- 검이나 도구처럼 한 개만 쌓이는 아이템은 개수를 바꿀 수 없어 쓸 수 없다.

### 6.3 기기 속도와 위험

- 두 방법 모두 늦으면 빈 칸이 되고 틀린 아이콘은 고정되지 않는다. 빈 칸이 된 아이콘만 다시 시도할 수 있다.
- 6.1절은 틱이 "언제 칸을 비워도 되는가"에만 영향을 준다. 6.2절은 아이콘마다 간격이 필요해 느린 기기에서 실패가 늘어난다.
- 빌리는 칸은 시작할 때 비어 있어야 한다. 시험 애드온은 칸이 차 있으면 시작하지 않고, 접속할 때 표시용 아이템(이름표로 구분)을 지운다.
- 두 방법 모두 HUD 전용이고, 빌리는 동안 플레이어가 인벤토리 화면을 열면 표시용 아이템이 보인다.

### 6.4 시험 애드온

위 표의 시도를 한 애드온(Item Icon Slots v1.0.0)에 모았다. 아이콘은 다이아몬드, 상자, 황금 사과, 네더라이트 검과 이 애드온의 커스텀 아이템 2개(빨강, 파랑 양털 그림)이고, 칸 하나 시험은 쌓이는 아이템 12개를 쓴다.

| 메뉴 | 하는 일 | 볼 것 |
| --- | --- | --- |
| HUD: back up slots 9-14 and fill them | 9~14번 칸의 아이템을 백업하고 표시용 아이템을 넣어 5초 동안 실시간으로 보인 뒤 되돌린다 | 아이콘 6개, 되돌린 뒤 원래 아이템(이름, 설명, 내구도, 인챈트)이 그대로인지 |
| HUD: 6 empty slots, lock check, clear after 1 tick / 10 ticks | 6.1절. 빈 칸 6개에 넣고 1틱 또는 10틱 뒤 비운다 | 윗줄(Frozen)에 6개가 맞게 남고 아랫줄(Live)은 비는지 |
| HUD: 1 slot, count check, 3 ticks apart / 1 tick apart | 6.2절. 17번 칸 하나에 12개를 차례로 넣는다 | 3틱은 12칸이 모두 맞는지, 1틱은 틀린 아이콘 없이 빈 칸만 생기는지 |
| HUD: 1 slot, no check, 1 tick apart | 6.2절에서 개수 확인을 뺀 것 | 칸이 밀려 다른 아이콘이 고정되는지 |
| HUD: bundle contents | 핫바 9번째 칸에 다이아몬드와 빨강이 든 주머니를 넣는다 | 주머니 아이콘 옆의 내용물 칸과 저장량 글자가 비는지 |
| Form: read inventory slot 17 | 17번 칸에 다이아몬드를 넣고 서버 폼에서 인벤토리 컬렉션 네 줄을 읽는다 | 네 줄이 모두 비는지 |
| Form: entities holding items | 아이템 엔티티, 갑옷 거치대, 투명 거치대, 손 뼈만 있는 엔티티가 다이아몬드, 상자, 빨강을 들고 머리 위에 뜬다. 서버 폼이 `live_horse_renderer`로 그린다. 마지막 줄은 플레이어 자신이다 | 아이템 엔티티 줄이 비는지, 다른 줄에서 쥐는 모양이 아이템마다 다른지 |

<AddonDownload id="item-icon-slots" />

1. 새 월드에서 행동 팩 "Bedrock Wiki Item Icon Slots BP"를 켠다. 리소스 팩은 의존성으로 함께 켜진다.
2. 크리에이티브 인벤토리 아이템 분류의 맨 뒤에서 "Item Icon Slots"(주머니 그림)를 꺼낸다. `/give @s bwiki:item_icon_slots_test`를 써도 된다.
3. 아이템을 사용하면 메뉴가 열린다. `/scriptevent bwiki:item_icon_slots`로도 열린다. HUD 시험은 메뉴가 닫힌 뒤 화면 위쪽 가운데에 나온다.

- 빈 칸이 필요한 시험은 칸이 차 있으면 채팅으로 알리고 시작하지 않는다. 6칸 시험은 9~14번(메인 인벤토리 첫 줄 왼쪽 6칸), 칸 하나 시험과 폼 시험은 17번, 주머니 시험은 핫바 9번째 칸을 쓴다.
- 백업 시험만 차 있는 칸을 그대로 쓴다. 백업은 스크립트 메모리와 플레이어 동적 속성에 함께 저장한다. 되돌리기 전에 월드를 나가면 다음 접속 때 동적 속성에서 되돌린다. 동적 속성에는 종류, 개수, 이름, 설명, 내구도, 인챈트만 남는다.
- 이 애드온은 `third_party_server_screen`의 `$screen_content`와 HUD 제목을 바꾸므로 다른 시험 애드온과 함께 켜지 않는다.
- 화면의 글은 영어다.

## 7. 탐침 애드온

<AddonDownload id="item-aux-probe-extra" />

1. 파일을 열어 가져온다(모바일은 파일을 눌러 Minecraft로 연다). 새 월드에서 행동 팩 "Bedrock Wiki Item Aux Probe BP"를 켠다. 리소스 팩은 의존성으로 함께 켜지고 실험 토글은 필요 없다.

- 화면의 글은 영어다.
