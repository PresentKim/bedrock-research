# InvUI에서 사용자 입력 가로채기

InvUI(보이지 않는 컨테이너 엔티티의 상자 화면을 리소스 팩으로 다시 그린 메뉴 화면, [엔티티 인벤토리로 메뉴 화면 만들기](./entity-inventory-ui.mdx))나 서버 폼 화면에서 키보드 단축키, 숫자 키, 뒤로 가기 같은 입력을 받아 메뉴 동작에 쓰려면 어떤 입력이 어떤 버튼 ID로 들어오는지 알아야 한다. 이 문서는 `button_mappings`의 `from_button_id`로 받을 수 있는 입력을 쟀다.

버튼 ID 대응은 서버 폼 화면(`third_party_server_screen`)에서 쟀다. 가로챘을 때 원래 동작이 막히는지는 서버 폼 화면과 상자 화면(InvUI) 둘 다 쟀다(4절).

## 1. 시험 창

- 버튼 ID 279개를 모았다. Windows 1.26.65 실행 파일에서 뽑은 `button.*`, `key.*` 문자열 277개(입력이 아닌 lang 키나 컨트롤 이름도 섞여 있다), 바닐라 UI가 `from_button_id`로 쓰는 ID 중 빠진 것, 그리고 `any`다.
- 창은 `input_panel` 하나에 ID마다 전역 매핑 `{"from_button_id": <ID>, "to_button_id": "button.juc_k_<번호>", "mapping_type": "global"}`을 둔다. 대상 ID는 엔진이 모르는 ID이고, 칸마다 그 ID를 `play_event`로 받는 `alpha` 애니메이션이 회색 칸을 초록으로 덮는다. 칸은 창이 닫힐 때까지 초록으로 남는다.
- 같은 창을 `consume_event`를 적지 않은 판(k), `false` 판(l), `true` 판(n)으로 셋 두었다.
- 시험할 때는 창 하나에 동작 하나만 하고 화면을 찍었다.

## 2. Windows 키보드와 마우스

2026-11-19 Windows 1.26.65.1. 서버 폼 창이 열린 동안 키를 하나씩 눌렀다.

| 입력 | 켜진 ID |
|---|---|
| 마우스 좌클릭 | `button.menu_select` |
| 마우스 우클릭 | `button.menu_secondary_select` |
| Shift + 좌클릭 또는 우클릭 | `button.menu_auto_place` |
| Enter | `button.chat`, `button.menu_ok`, `button.return` |
| Esc | `button.menu_cancel` |
| 방향키 왼쪽, 오른쪽, 위, 아래 | `button.arrow_left`와 `button.menu_left`처럼 방향마다 `arrow_*`와 `menu_*` 둘 |
| 숫자 1~9 | `button.slot1`~`button.slot9` |
| E | `button.menu_inventory_cancel` |
| Q | `button.menu_inventory_drop` |
| Ctrl + Q | `button.menu_inventory_drop_all` |
| T | `button.chat` |
| Z | `button.mobeffects` |
| B | `key.emote` |
| `[`, `]` | `button.menu_tab_left`, `button.menu_tab_right` |

- 그 밖의 키(WASD, Space, Shift만, Tab, F1 등)는 어느 칸도 켜지 않았다.
- `button.slot0`을 켜는 키는 없었다.
- `button.jump`, `button.sneak`, `button.drop`, `button.inventory`처럼 게임 조작 이름의 ID는 화면이 열린 동안 켜지지 않았다. 화면 안에서는 같은 키가 `menu_*` 이름으로 들어온다.
- `any`는 어떤 입력에서도 켜지지 않았다.

## 3. 모바일 터치

2026-11-19 모바일(사용자 실측). 같은 창을 터치로 시험했다. 모바일에서 화면이 열린 동안 할 수 있는 입력은 화면 탭과 뒤로 가기뿐이었다(길게 누르기와 끌기로 따로 들어오는 입력은 없었다).

| 입력 | 켜진 ID |
|---|---|
| 빈 곳을 한 번 탭 | `button.menu_select` |
| 뒤로 가기 | `button.menu_cancel` |

## 4. 원래 동작이 막히는지

- 모든 ID를 전역 매핑한 창은 Windows에서 Esc로 닫히지 않았다(`consume_event`를 적지 않은 판). 창을 닫을 버튼도 숨겨 둔 상태라 게임을 끝내야 했다. 시험 애드온은 그래서 창을 10초 뒤 스크립트로 닫는다.
- 모바일에서는 `consume_event` `true` 판에서도 뒤로 가기로 창이 닫히지 않았다.
- Windows에서 세 판(적지 않음, `false`, `true`)을 비교했을 때 차이가 없었다(사용자 실측). 세 판 모두 Esc로 창이 닫히지 않았고, 세 판 모두 숫자 키가 손에 든 핫바 칸을 바꿨다. 서버 폼 화면에서 `consume_event`는 전역 매핑이 화면의 닫기 동작을 막는지에도, 게임의 핫바 전환을 막는지에도 영향을 주지 않았다.
- 바닐라 UI는 `consume_event: false`를 11곳에서 쓴다(글 입력 칸의 선택을 풀면서 같은 누름을 다른 컨트롤에 넘기는 곳 등).
- 상자 화면(InvUI)에서는 화면 안 동작이 모두 막혔다(Windows, 사용자 실측). 엔티티 상자 화면 위쪽에 버튼 ID 48개를 전역 매핑한 `input_panel`을 두고(`consume_event` 적지 않음), 바닐라 칸은 그대로 보이게 했다. E와 Esc로 화면이 닫히지 않았고, 사과 칸에 마우스를 올린 채 숫자 키를 눌러도 사과가 핫바로 옮겨지지 않았다. 다만 숫자 키는 서버 폼에서처럼 손에 든 핫바 칸을 계속 바꿨다. Q와 Ctrl+Q로 아이템이 버려지지 않았고, Shift+클릭, 좌클릭, 우클릭으로도 아이템이 옮겨지지 않았다.
- 정리하면 두 화면 모두 숫자 키의 핫바 전환은 막히지 않았고, 상자 화면의 칸 동작(옮기기, 버리기, 닫기)은 막혔다.

## 5. 바닐라 키 대응표와 비교

위키의 키 대응표([INP-21](../../json-ui/input-buttons-toggles.mdx))와 비교한 결과다.

| 대응표 | 실측 |
|---|---|
| `button.menu_select` 좌클릭 | 맞음. 모바일 탭도 같음 |
| `button.menu_secondary_select` 우클릭 | 맞음 |
| `button.menu_ok` Enter | 맞음. `button.chat`, `button.return`도 함께 들어옴 |
| `button.menu_cancel`, `button.menu_exit` Esc | `menu_cancel`은 맞음(모바일 뒤로 가기도 같음). `menu_exit`은 켜지지 않음 |
| `button.menu_up/down/left/right` 방향키 | 맞음. `arrow_*`도 함께 들어옴 |
| `button.menu_autocomplete` Tab | 켜지지 않음 |
| `button.menu_tab_left/right` 탭 키 | `[`와 `]`로 들어옴 |
| `button.menu_inventory_cancel` 인벤토리 키 | 맞음(E) |
| `any` | 켜지지 않음 |

## 6. 처음 열 때의 포커스

창을 열자마자 첫 버튼이 호버로 그려지는 것을 피하면서 방향키와 게임패드 이동은 남기는 방법을 쟀다. `$focus_enabled: false`(INP-32)는 호버를 없애지만 포커스 이동도 함께 없앤다.

시험 창은 포커스를 켠 버튼 A, B, C 셋(위에서 아래로)이고, 버튼 속성만 다른 네 판이다. 2026-11-19 Windows 1.26.65.1, 마우스를 창 밖에 둔 채 열고 방향키로 움직였다.

| 판 | 서버 폼: 처음 | 서버 폼: 아래 키 두 번 | 상자 화면: 처음 | 상자 화면: 아래 키 두 번 |
|---|---|---|---|---|
| F0 기준 | 호버 없음 | B, C(처음 포커스는 A) | A 호버 | B, C |
| F1 셋 다 `default_focus_precedence: -20` | 호버 없음 | 움직이지 않음 | C 호버 | 상자 칸으로 넘어감 |
| F2 A 0, B 5, C 10 | 호버 없음 | A, B(처음 포커스는 C, 위 키로는 B, A) | C 호버 | 상자 칸으로 넘어감 |
| F3 보이지 않는 2x2 미끼 버튼에 `default_focus_precedence: 100` | 호버 없음 | A, B(위 키로는 C, B) | 호버 없음 | 첫 키는 보이는 변화 없음, 둘째 키에 B |

- 처음 포커스는 `default_focus_precedence`가 가장 큰 컨트롤이 받았다(F2에서 C). 값이 같으면 맨 위 버튼이었다(F0).
- 서버 폼에서는 PC 마우스로 열 때 처음 포커스가 호버로 그려지지 않았다. 방향키를 누르면 그때부터 보였다. 상자 화면에서는 PC에서도 처음부터 호버로 그려졌다.
- 음수 값(F1)은 서버 폼에서 방향키 이동을 막았다. 상자 화면에서는 오히려 C가 처음 포커스를 받았다.
- 미끼(F3)가 처음 포커스를 받으면 두 화면 모두 처음에 호버가 없었고, 방향키로 버튼 사이를 다시 옮겨 다닐 수 있었다. 미끼에는 `button_mappings`가 없어 누름을 먹지 않는다. 서버 폼 F3에서 창을 연 뒤 Button A를 처음 클릭하자 그대로 눌렸다.
- 서버 폼 F3 창이 열린 직후 저절로 닫힌 적이 한 번 있었다. 바로 다시 열었을 때는 그대로 있었고, 원인은 나누지 못했다.
- 휴대폰 결과는 아직 없다. `touch-probes` 애드온의 "Focus" 항목으로 같은 판을 휴대폰에서 연다.
- `focus_reset_input_panel`(실행 파일에만 있는 문자열), `use_last_focus`, `focus_navigation_mode_*`는 재지 않았다.

## 7. 쓰는 법

- 숫자 키 단축키는 `button.slot1`~`button.slot9`로 받는다. 0번 칸 단축키는 키보드로 만들 수 없다. 받아도 손에 든 핫바 칸은 그대로 바뀌므로, 서버는 칸 변경을 함께 겪는다고 보고 처리한다.
- 탭 넘기기는 `button.menu_tab_left/right`(`[`, `]`)로 받는다.
- 뒤로 가기와 Esc는 둘 다 `button.menu_cancel`이다. 이것을 전역 매핑하면 화면을 닫을 수 없게 되므로, 닫는 버튼을 따로 두거나 서버가 닫게 한다. 상자 화면은 엔티티를 지우면 닫힌다.
- InvUI에서 `button.menu_select`, `button.menu_secondary_select`, `button.menu_auto_place`를 전역 매핑하면 칸 클릭까지 막혀 아이템을 옮길 수 없다. 칸을 쓰는 화면에서는 필요한 키(숫자 키, E, Q 등)만 매핑한다. 거꾸로 E, Q, 숫자 키만 매핑하면 상자 화면이 그 키로 닫히거나 아이템을 버리거나 옮기는 것을 막을 수 있을 것이다(키 몇 개만 매핑한 판은 재지 않음). 숫자 키의 핫바 전환은 막을 수 없다.
- 모바일에서 받을 수 있는 입력은 `menu_select`(탭)와 `menu_cancel`(뒤로 가기)뿐이므로, 키보드 단축키는 화면 버튼의 보조로만 쓴다.
- 처음 호버를 없애고 방향키 이동은 남기려면, 버튼은 그대로 두고 보이지 않는 작은 버튼(`button_mappings` 없음)에 버튼들보다 큰 `default_focus_precedence`를 준다(6절, PC 실측). 버튼에 음수를 주는 방법은 서버 폼에서 이동을 막고 상자 화면에서는 호버를 없애지 못했다.
