# JSON UI 최적화

JSON UI가 느려지는 곳은 모두 클라이언트다. 서버 폼이 무거워도 서버 TPS는 그대로이고, 폼을 연 플레이어의 화면만 멈춘다(커뮤니티 보고). 이 페이지는 다른 장에 흩어진 성능 규칙과 커뮤니티 보고를 비용이 생기는 단계별로 모은다. 규칙 ID는 각 장의 원문을 가리킨다.

## 1. 비용은 세 단계에서 나온다

| 단계 | 무엇이 비싼가 | 막는 방법 |
| --- | --- | --- |
| 생성과 레이아웃 | 컨트롤을 만들고 크기·위치를 계산한다. 화면이 열릴 때와 팩토리가 셀을 다시 만들 때 든다 | `ignored`, 팩토리 길이 0 (2절) |
| 바인딩 평가 | 바인딩과 식을 조건에 따라 다시 평가한다 | `binding_condition`, 계산을 한곳에 모으기 (3절) |
| 그리기 | 보이는 컨트롤을 매 프레임 그린다 | `visible: false`, 요소 수 줄이기 (6절) |

가장 흔한 오해는 `visible: false`가 비용을 없앤다는 것이다. **`visible`은 그리기만 막고 생성과 레이아웃은 막지 못한다**(COL-10). 서버 폼 아래 `visible`로 가린 화면은 모든 폼을 열 때마다 전부 생성·레이아웃되었고(5,546개 컨트롤 재배치 실측), 숨긴 요소도 파싱 비용이 든다는 보고가 여럿 있다. 커뮤니티에서는 렉의 주원인을 레이아웃보다 바인딩으로 보는 의견이 많다.

## 2. 만들지 않기: 생성 게이트

화면이나 탭이 여러 개면 "모두 만들고 숨기기" 대신 "필요한 것만 만들기"로 바꾸는 것이 가장 효과가 크다. 방법은 세 가지다(COL-12).

| 방법 | 평가 시점 | 조건 재료 | 비용 |
| --- | --- | --- | --- |
| `ignored` | 컨트롤 생성 시 한 번 | `$변수`만 | 생성 안 함 |
| 팩토리 `#collection_length` | 런타임, 바인딩 | `#바인딩` 식 | 0이면 생성 안 함 |
| `visible` | 매 프레임 | `#바인딩` 식 | 생성·레이아웃 비용 그대로 |

### `ignored`

- `"ignored": true`나 `$변수` 식이 참이면 컨트롤을 **아예 만들지 않는다**. 바인딩과 레이아웃 비용도 없다(FILE-16). `modifications`의 `remove`도 결과는 같다.
- `ignored`는 생성 시점에 한 번만 평가되고 `#바인딩`을 쓸 수 없다(FILE-17). 그래서 바닐라 요소를 통째로 끄거나, 팩 설정 변수로 기능을 끄는 데 쓴다.
- `ignored`는 그 컨트롤 자신의 `$` 선언을 보지 않고 부모 스코프만 읽는다. 게이트 변수는 부모에 넘기고 `ignored`는 자식에 단다(FILE-34).
- 예외적으로 HUD 타이틀 팩토리가 만든 컨트롤은 `$title_text`로 타이틀 문자열을 변수로 받으므로 `ignored`로 거를 수 있다(FILE-17, COL-17).

### 계산 길이 팩토리 (런타임 게이트)

- 팩토리의 `#collection_length`가 0이면 아무것도 만들지 않는다. `((#title_text = 'my_screen') * 1)`처럼 조건을 0/1로 바꿔 넣으면 "조건이 맞을 때만 그 화면을 만드는" 게이트가 된다(COL-11). 전체 예제는 [패턴 레시피](../json-ui/recipes.mdx)의 레시피 4(PAT-04)에 있다.
- 화면이 많으면 `property_bag` 사전 조회로 한 게이트에서 고른다. `property_bag`에 `"#route_<제목>": ["화면id"]`를 두고 `('#route_' + #title_text)`의 결과를 `#collection_length`에 넣으면 `control_ids`에서 그 화면 하나만 만든다(HOST-06, COL-22, COL-23). 게임 안 실측에서 멈춤 없이 동작했다(COL-39).
- 숨은 레이아웃 안의 팩토리 길이 바인딩을 `binding_condition: "visible"`로 두면, 보이지 않는 레이아웃은 버튼 칸을 만들지 않았다(BND-32). 다만 처음부터 보이는 레이아웃에서는 첫 프레임에 칸을 만들었다.

### 게이트의 함정

- 게이트 팩토리가 만든 레이아웃 **안에서는** 액션 폼 버튼 데이터가 `grid` + `collection_name`의 칸에만 닿았다. 고정 `collection_index` 칸과 안쪽 팩토리는 비었다(COL-40). 게이트 안의 버튼 목록은 grid로 짠다.
- 생성될 수 있는 모든 컨트롤의 식은 엉뚱한 입력(빈 문자열, 다른 폼의 본문)에서도 안전해야 한다. 숫자 속성에 문자열을 넣는 식이 모든 폼에서 생성되는 구성은 클라이언트를 멈추거나 종료시켰다(DBG-19). 숫자 속성에 넣는 식은 입력 형식을 확인하는 게이트 안에서만 생성되게 한다.
- 제목으로 고르는 레이아웃의 `#visible`에 `once`를 걸면 폼이 바뀌는 사이 이전 레이아웃이 켜진 채 남았다. 이 바인딩은 `always`로 둔다(BND-31).

## 3. 바인딩 비용 줄이기

- **한 번이면 되는 값은 `once`**: 토스트 아이콘 표시 여부처럼 한 번 정해지면 되는 값은 `"binding_condition": "once"`로 둔다. 팩토리가 컨트롤을 다시 만들면 다시 평가된다(BND-06). 큰 폼의 팩토리·grid 길이 바인딩에 `once`를 걸어 렉과 유령 버튼이 줄었다는 보고도 있다(커뮤니티 보고).
- **무거운 계산은 한곳에서 한 번**: 문자열 파싱 같은 계산은 부모나 데이터 소스 컨트롤 한 곳에서 하고, 자식은 `source_control_name`으로 결과만 받는다(BND-10). 여러 곳에서 같은 값을 쓰면 화면 루트에 크기 0짜리 데이터 소스 컨트롤을 두고 각 게이트가 그 값을 읽는다(BND-11).
- **같은 대상에 바인딩 여러 개 금지**: 같은 대상에 바인딩을 여러 개 걸면 합쳐지지 않고 마지막 것이 이긴다. 한 식으로 합친다. 같은 이름을 읽고 쓰는 바인딩(`#len`을 읽어 `#len`에 쓰기)은 루프가 되어 문자열이 계속 붙고 메모리가 는다(커뮤니티 보고).
- **반복 트릭은 짧게**: 바인딩 루프로 문자열을 반복하는 트릭은 약 20회 반복 뒤 멈춘다는 보고가 있고, 문자마다 `property_bag` 매핑을 돌리는 대소문자 무시 검색은 길게 입력하거나 지울 때 렉이 났다(커뮤니티 보고).
- **HUD 데이터 채널**: 인벤토리, 채팅, 폼, F1로 HUD가 가려져도 title·actionbar는 계속 처리된다. 무거운 바인딩이 있으면 처리가 밀려 몇 초에서 약 1분까지 멈췄다. 갱신 주기를 2~4틱으로 늘리거나 데이터 컨트롤을 `hud_content`에 둔다. 1만 자 타이틀도 사용자 바인딩을 줄이자 문제가 없었다(커뮤니티 보고).

## 4. 목록: grid와 팩토리

| 상황 | 고르는 것 | 근거 |
| --- | --- | --- |
| 같은 모양의 버튼이 많다 | `grid` (`collection_name` + `#maximum_grid_items`) | grid는 버튼 1만 개도 바로 로드했다는 보고. 3000개가 넘는 버튼 팩토리(바닐라 `long_form`의 `stack_panel`)는 숨겨도 약 60초 멈췄다(커뮤니티 보고) |
| 칸마다 정해진 버튼 하나 | 고정 `collection_index` 칸 | 줄마다 버튼 전체를 걷는 스택(48칸 격자 + 재료 줄)은 여는 데 4~5초, 칸마다 버튼 하나만 읽는 고정 배치는 약 1초였다(COL-37, COL-06) |
| 행 종류가 섞인 폼 | 행 타입 팩토리 | 매칭되는 모든 행마다 셀을 만드므로 셀 수를 세어 본다. 자기 행이 아닌 셀은 화면 밖으로 민다(COL-13) |

- 팩토리 비용은 **셀 크기 × 개수**다. 노드 하나에 컨트롤 수백 개가 든 화면은 모든 탭을 보내면 여는 데 수 초가 걸렸고, 선택된 탭의 노드만 보내도록 바꿔 해결했다(COL-18).
- 칸마다 버튼은 하나만 둔다. 누르는 것과 안 누르는 것을 둘 다 두면 컨트롤이 두 배다(COL-37).
- 버튼이 많으면 페이지로 나눈다. 다만 페이지를 많이 나눠도 폼이 열리는 데 약 30초 걸린 사례가 있어, 페이지 수보다 한 번에 만드는 컨트롤 수를 먼저 줄인다(커뮤니티 보고).
- `max_children_size`는 팩토리가 만들 최대 개수다. 같은 데이터를 공유하는 두 번째 팩토리는 보이지 않는 항목도 한도를 소모한다(COL-16).

## 5. 화면을 빨리 열기

- **첫 탭은 가볍게, 나머지는 미루기**: 상점 카드당 요소 3개를 1개로 합치고, 처음 열리지 않는 탭의 비싼 내용(버튼 텍스트, 3D 블록 렌더)을 미루고, 가장 가벼운 탭으로 열었더니 1.6초가 0.8초가 됐다(커뮤니티 보고). 탭은 2절의 게이트로 선택된 것만 만든다.
- **숨긴 폼도 메모리에 남는다**: 스타일이 다른 폼 여러 개를 숨겨 두기보다 토글 하나로 합친다는 보고가 있다(커뮤니티 보고).
- **열기 애니메이션 끄기**: `third_party_server_screen`에 `"$screen_animations": []`, `"$background_animations": []`를 주면 폼이 애니메이션 없이 바로 나타난다. 메뉴를 자주 오가는 화면에서 다음 폼이 겹치거나 깜빡이지 않는다(HOST-43).
- 요소 약 75개 정도는 무난하다는 경험치가 공유되었다(커뮤니티 보고).

## 6. 그리기 비용

- 늘 안 쓰는 요소는 `visible: false`보다 `ignored: true`로 끈다. `visible: false`는 처리가 계속되어 FPS 비용이 남는다(FILE-16, 커뮤니티 보고).
- 레이아웃 확인용 `"debug": "red"` 같은 경계 표시는 비용이 크다. 확인이 끝나면 지운다(커뮤니티 보고).
- 자식은 남기고 자기만 숨길 때는 `alpha: 0` + `propagate_alpha: false`를 쓴다. 자식의 alpha는 부모 alpha와 곱해진다(커뮤니티 보고).

## 7. 점검 순서

1. 화면 하나에 컨트롤이 몇 개 생성되는지 센다. 게임 안 디버그 오버레이(Conduit Client 등)는 요소와 바인딩 수, 팩토리 트리, FPS를 보여 준다(커뮤니티 보고).
2. `visible`로만 숨긴 큰 덩어리(다른 화면, 다른 탭)를 2절의 게이트로 바꾼다.
3. 버튼 목록을 grid나 고정 칸으로 바꾸고, 칸마다 컨트롤 수를 줄인다(4절).
4. 같은 계산을 여러 곳에서 하는 바인딩을 데이터 소스 하나로 모으고, 바뀌지 않는 값에 `once`를 건다(3절).
5. 첫 화면에서 보이지 않는 비싼 내용을 미룬다(5절).
