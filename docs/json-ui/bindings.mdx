## 개념: 바인딩은 엔진 데이터와 컨트롤 속성을 잇는 선이다

컨트롤의 속성은 두 가지 방식으로 정해진다. 정적 값(`"text": "안녕"`)과, 엔진이 계산하는 데이터(`#속성`)를 끌어오는 **바인딩**이다. 바인딩은 `bindings` 배열의 항목으로 쓰고, 항목 하나가 선 하나다. 종류는 다섯 가지다.

| `binding_type` | 읽는 곳 | 쓰임 |
| --- | --- | --- |
| `global` (생략 시 기본) | 화면이 엔진에서 받은 전역 속성 | 그대로 가져올 때 |
| `view` | 다른 컨트롤(또는 자신)의 속성, 또는 식 | 계산하거나 복사할 때 |
| `collection` | 컬렉션의 항목 속성 | 팩토리·그리드 항목 |
| `collection_details` | 컬렉션 항목 상세(눌림 집계 등) | 서버 폼 버튼 |
| `none` | 읽지 않음 | 바닐라 1회 |

### 단계별 예제

1. 가장 단순한 형태: 엔진 속성 `#hardtext`를 라벨의 `text`에 그대로 넣는다.

   ```json
   { "label": { "type": "label", "text": "#hardtext",
       "bindings": [ { "binding_name": "#hardtext" } ] } }
   ```

2. `binding_name_override`: 받은 값을 내가 정한 속성 이름에 넣는다. `#visible`, `#enabled`에 자주 쓴다.

   ```json
   { "send_button": { "bindings": [
       { "binding_name": "#using_touch", "binding_name_override": "#visible" } ] } }
   ```

3. `view` 바인딩: 다른 컨트롤의 속성을 읽어 내 속성에 쓴다. 토글이 켜졌을 때만 패널을 보이게 한다.

   ```json
   { "panel": { "bindings": [ {
       "binding_type": "view",
       "source_control_name": "my_toggle",
       "source_property_name": "#toggle_state",
       "target_property_name": "#visible" } ] },
     "my_toggle": { } }
   ```

4. 식: `source_property_name`에 괄호 식을 쓰면 계산 결과가 `target_property_name`에 담긴다. `#속성`이 하나는 들어가야 한다(BND-05).

   ```json
   { "binding_type": "view", "source_control_name": "image", "resolve_sibling_scope": true,
     "source_property_name": "(not (#texture = ''))", "target_property_name": "#visible" }
   ```

(단계 1~3은 Bedrock Wiki Intro의 설명을 다시 쓴 것이고 4는 바닐라 `server_form.json`의 `dynamic_button`과 같은 형태다.)

### Bedrock Wiki의 바인딩 키 표

<Excerpt src="bedrock-wiki" title="JSON UI Documentation, Data Binding" path="docs/json-ui/json-ui-documentation.md">

| Property | Type | Description |
| --- | --- | --- |
| ignored | boolean | If binding should be ignored (default `false`) |
| binding_type | enum | `global`, `view`, `collection`, `collection_details`, `none` |
| binding_name | string | Stores the value of the data binding name or condition with it |
| binding_name_override | string | Name of the UI element property that will apply the stored value in `binding_name` |
| binding_collection_name | string | Name of the collection of items to be used |
| binding_condition | enum | Condition for the data binding to happen: `always`, `always_when_visible`, `visible`, `once`, `none`, `visibility_changed` |

</Excerpt>

### Microsoft Learn의 바인딩 키

MS Learn `minecraft:ui_element` 문서의 `bindings` 항목은 `binding_collection_name`(컬렉션 바인딩의 컬렉션 이름), `binding_condition`(언제 평가할지), `binding_name`(바인딩할 데이터 소스, 예 `#player_name`), `binding_name_override`(값을 넣을 요소의 속성), `binding_type`, `source_control_name`(view 바인딩의 원본 컨트롤), `source_property_name`, `target_property_name`을 적는다(출처: ms-learn). 이 문서는 `binding_collection_prefix`, `resolve_sibling_scope` 등을 빼고 enum 값도 비어 있으므로 아래 표(4.1, 4.2)를 기준으로 쓴다.

## 규칙

바인딩은 엔진 데이터(`#속성`)를 컨트롤 속성으로 옮기거나, 식으로 새 속성을 계산한다. `bindings` 배열의 항목 하나가 바인딩 하나다.

### 4.1 바인딩 항목의 키

| 키 | 뜻 |
| --- | --- |
| `binding_type` | `global`, `collection`, `collection_details`, `view`, `none` |
| `binding_name` | 엔진이 주는 속성 이름(`#title_text`, `#form_button_text` …) |
| `binding_name_override` | 받은 값을 넣을 내 속성 이름(`#text`, `#visible`, `#collection_length` …) |
| `binding_collection_name` | 컬렉션 이름(`form_buttons`, `custom_form`, `container_items` …) |
| `binding_collection_prefix` | 접두사가 붙은 컬렉션의 접두사(`student_buttons` 등) |
| `binding_condition` | 언제 다시 평가할지 |
| `source_control_name` | view 바인딩에서 값을 읽을 다른 컨트롤 이름 |
| `resolve_sibling_scope` | `true`면 `source_control_name`을 형제 범위에서 찾음 |
| `source_property_name` | view 바인딩의 식 또는 읽을 속성 |
| `target_property_name` | view 바인딩 결과를 쓸 속성 |

- **[BND-01]** 바인딩 키는 위 표의 것을 쓴다. `resolve_ancestor_scope`는 바닐라에 한 번도 없으므로 쓰지 않는다(`resolve_sibling_scope`는 53회). 엔진은 이 키를 읽는다(조상 범위, BND-25·BND-36). 바닐라가 쓰지 않으므로 권장하지 않는다는 결론은 같다. `{바닐라, 코드}` (출처: VN, MJ 4.2-1, 충돌 C-07, NB-09)
- **[BND-02]** `binding_type`을 생략한 항목은 전역 속성을 읽는다(예: `{ "binding_name": "#title_text" }`). `{바닐라, 코드, 추론}` (출처: VN server_form.json:138, BC 4.1, BA 2장, BW-intro, BW-dyn)
- **[BND-03]** 바닐라가 쓰는 `binding_type` 횟수: `collection` 787, `collection_details` 287, `global` 265, `view` 240, `none` 1. 템플릿은 이 값을 변수로 받는 경우가 많다(`$store_factory_binding_type` 등). `{바닐라}` (출처: VN, 값 사전)

### 4.2 `binding_condition`

| 값 | 바닐라 | 뜻 |
| --- | ---: | --- |
| (생략) | 다수 | 엔진 기본 |
| `visible` | 135 | 보일 때 |
| `once` | 106 | 처음 한 번만 |
| `always` | 97 | 계속 |
| `always_when_visible` | 66 | 보이는 동안 계속 |
| `visibility_changed` | 7 | 가시성이 바뀔 때 |
| `none` | 6 | 데이터가 갱신될 때마다(BND-23). 공식 스키마 enum에는 없음 |

- **[BND-04]** **바인딩된 속성은 그 바인딩을 가진 컨트롤의 것이다.** 버튼에 컬렉션 바인딩을 두고 두 단계 아래 라벨에서 `#form_button_text`를 쓰면 빈칸이 된다. 값은 그것을 그리는 컨트롤이 직접 바인딩하거나, view 바인딩으로 복사한다(BND-08). `{실측}` (출처: BC-S7)
- **[BND-05]** view 바인딩 식에 `#속성`이 하나도 없으면 `Must define a source property name in the binding!` 오류가 나고, 그 컨트롤의 **bindings 배열 전체**가 버려진다. 상수를 쓰려면 `((#v = #v) * 40)`처럼 아무 속성이나 끼운다. Cinnabar 재구성은 그 바인딩 하나만 버리지만 실측을 따른다(충돌 C-43). `{실측}` (출처: BC-S12, 충돌 C-43)
- **[BND-06]** 한 번만 정해지면 되는 값(토스트 아이콘 표시 여부 등)은 `"binding_condition": "once"`로 비용을 줄인다. 팩토리가 컨트롤을 다시 만들면 다시 평가된다. `{작동팩}` (출처: BA 컬렉션과 팩토리 장, AP 4.5)
- **[BND-07]** 팩토리가 만든 셀 안의 바인딩은 너무 일찍 실행되어 빈 값으로 남을 수 있다(포커스를 잃었다 돌아오면 그제야 보임). `binding_condition: "always"`를 주거나, 팩토리 바깥에서 읽고 `source_control_name`으로 복사해 넣는다. 셀 안의 `visible`도 `always`면 즉시 적용된다. 셀은 바깥 컨트롤을 읽을 수 있지만 바깥은 셀을 읽지 못한다(BND-19). `{실측}` (출처: BC-S11, 충돌 C-11, BW-dyn)

### 4.3 view 바인딩과 다른 컨트롤 읽기

```jsonc
// 형제가 계산한 값을 받아 쓰기
{ "binding_type": "view",
  "source_control_name": "image",          // 읽을 컨트롤
  "resolve_sibling_scope": true,            // 형제 범위에서 찾음
  "source_property_name": "(not (#texture = ''))",
  "target_property_name": "#visible" }
```
(바닐라 `server_form.json`의 `dynamic_button`과 같은 형태)

- **[BND-08]** `source_control_name`으로 다른 컨트롤의 속성을 읽는다. 형제를 읽을 때는 `resolve_sibling_scope: true`를 함께 준다. `{바닐라, 작동팩}` (출처: VN 236·53회 예 server_form.json:156, BA 컬렉션과 팩토리 장, BW-intro, BW-form)
- **[BND-09]** `#visible`의 기본값은 `true`다. 식이 실패하면(지원하지 않는 연산자 등) 속성이 기본값에 남으므로 "항상 보임"이 된다. 숨김 조건이 안 먹으면 식부터 의심한다. `{실측}` (출처: BC-facts, BC 6.2-1)
- **[BND-10]** 문자열 파싱 같은 무거운 계산은 **부모(또는 데이터 소스) 한 곳에서 한 번** 하고, 자식은 `source_control_name`으로 결과만 받는다. `{작동팩}` (출처: BA 컬렉션과 팩토리 장)
- **[BND-11]** 같은 값을 여러 곳에서 읽어야 하면 화면 루트에 크기 0짜리 "데이터 소스" 컨트롤을 두고, 각 게이트가 view 바인딩으로 그 값을 읽는다. 네이티브 입력(라디오 등)을 컬렉션 아이템 안에 넣지 않고 데이터만 따로 읽는 방법이기도 하다. `{코드, 실측}` (출처: BC 4.1-(5), BC-rules)

### 4.4 바인딩과 변수

- **[BND-12]** 팩이 직접 소유한 정의(새 namespace의 정의, 재선언한 정의)에서는 `source_property_name`에 `$변수`를 써도 된다. 예: `"source_property_name": "$visible_binding"`. `{작동팩, 실측}` (출처: AP 4.2, BC-facts)
- **[BND-13]** `modifications`로 바닐라 트리에 **삽입한** 하위 트리 안에서는 바인딩의 `source_property_name`에 `$변수`를 쓸 수 없다(6가지 변형 모두 `Must define a source property name`). 같은 곳에서 `text`의 `$caption` 같은 일반 속성 치환은 된다. 그래서 삽입 트리에는 바인딩 이름을 리터럴로 박은 정의를 따로 만든다. `{실측}` (출처: BC-facts)
- **[BND-14]** 팩토리 행 인덱스 같은 값을 `$변수`로 파생 정의에 넘겨 기반의 바인딩에 쓰려 하면 바인딩이 깨지고 배열 전체가 버려졌다는 기록이 있다. 바닐라의 `factory_variables`(컬렉션과 팩토리 장 COL-15)가 이 문제를 푸는지는 측정되지 않았다. `{실측, 추론}` (출처: BC-S9, VN)

### 4.5 엔진 속성: 자주 쓰는 바인딩 대상

| 속성 | 뜻 | 근거 |
| --- | --- | --- |
| `#visible` | 보임 여부(기본 true) | VN, 모든 출처 |
| `#text` | 라벨 텍스트(`"text": "#text"`) | VN |
| `#texture`, `#texture_file_system` | 이미지 텍스처 경로 | VN server_form.json:173 |
| `#clip_ratio` | 이미지 잘라 그리기 비율(0~1) | VN 33회, BA |
| `#collection_length` | 팩토리·컬렉션이 만들 셀 개수 | VN 89회, BC-S11 |
| `#size_binding_x/y`, `#anchored_offset_value_x/y` | 크기·위치(3장 표) | VN, BC-S12 |
| `#item_id_aux` | 아이템 렌더러 입력(`id × 65536 + aux`) | VN, AP, BC-facts |
| `#toggle_state` | 토글 상태 | BC 4.2 |
| `#propagateAlpha` | 부모 alpha를 자식에 전파할지 | VN hud_screen.json:3568, AP |

- **[BND-15]** `propagate_alpha`는 바인딩 `#propagateAlpha`로도 바꿀 수 있다. 바닐라 HUD 루트가 전역 `#hud_propagate_alpha`를 `#propagateAlpha`로 받는다. 부모 `alpha: 0` + 조건부 전파로 "특정 메시지만 투명하게" 만들 수 있다. `alpha` 자체는 기본으로 자식에 전파되지 않는다(LAY-33). `{바닐라, 작동팩}` (출처: VN hud_screen.json:3567, AP 4.5, 충돌 C-15, BW-doc)
- **[BND-16]** `binding_name_override`는 엔진 이름을 내 속성으로 옮긴다. 예: `#hud_title_text_string` → `#text`, `#form_button_contents` → `#collection_length`. `{바닐라}` (출처: VN hud_screen.json, server_form.json:138, BW-intro)
- **[BND-17]** 바닐라는 바인딩 이름 자체를 변수 식으로 만든다: `"$toggle_state_binding_name": "('#' + $dropdown_name)"`. 템플릿 하나로 여러 데이터를 읽는 방법이다. `{바닐라}` (출처: VN ui_common.json:1126, storage_management.json:1325)

### 4.6 Bedrock Wiki 대조로 더한 규칙

위키(BW) 문서를 바닐라 1.26.50.4와 대조해 더한 규칙이다. 위키 문장만 있는 것은 `미검증`, 위키의 게임 스크린샷이 있는 것은 `실측`(제3자 기록)으로 표시했다.

- **[BND-18]** **값 보존(래치).** 크기 0 패널의 `property_bag`에 `"#saved": ""`를 두고, `{ "binding_name": "#src", "binding_name_override": "#saved", "binding_condition": "visibility_changed" }`로 **가시성이 바뀌는 순간에만** 원본을 복사한다. 이 패널의 `#visible`을 "새 값이 키워드를 포함하고(EXP-07) 저장값과 다를 때"로 두면, 조건이 맞는 순간 한 프레임 보였다가 저장 직후 조건이 거짓이 되어 다시 숨는다. 바깥 라벨은 `source_control_name`으로 `#saved`를 읽는다. `property_bag`은 인스턴스마다 따로라 같은 컴포넌트를 여러 개 둬도 섞이지 않는다. HUD 타이틀 채널(HOST-14)에서 "내 키워드가 든 마지막 타이틀"을 다른 타이틀이 와도 유지하는 데 쓴다. `{미검증}` (출처: BW-title, VN `visibility_changed` 7회)
- **[BND-19]** 팩토리·그리드가 만든 컨트롤은 `source_control_name`으로 **바깥** 컨트롤의 속성을 읽을 수 있지만, 바깥 컨트롤은 만들어진 컨트롤의 속성을 읽지 못한다. 공유할 값은 팩토리 바깥 데이터 소스(BND-11)에 둔다. `{미검증}` (출처: BW-dyn "Useful Information")
- **[BND-20]** `resolve_sibling_scope: true`는 `source_control_name` 검색을 형제 범위로 제한하지만, 부모와 형제의 이름이 같으면 부모가 우선한다. 읽을 컨트롤 이름은 조상과 겹치지 않게 짓는다. 원인: 형제 검색이 부모 자신부터 너비 우선으로 시작한다(BND-25). `{코드}` (출처: BW-doc Data Binding 표, CN)
- **[BND-21]** 버튼 상태 컨트롤 안에서는 상태 변수로 생성 자체를 가를 수 있다: 호버 때만 보일 자식에 `"ignored": "$default_state"`. 바닐라도 `"ignored": "$hover_state"`(2), `"visible": "$default_state"`(3), `"visible": "($hover_state or $pressed_state)"`(5)를 쓴다. INP-09의 변수 식이 `ignored`에도 된다는 뜻이다. `{바닐라, 미검증}` (출처: BW-btn, VN)

### 4.7 Cinnabar 엔진 재구성으로 더한 규칙

Cinnabar(`CN`)는 26.30 네이티브 클라이언트의 JSON UI 해석기를 재구성한 Rust 코드다. 수준은 `코드`이고, `CN-run`은 이 프로젝트가 그 평가기를 직접 실행한 결과다. 게임 실측과 다르면 실측을 따른다(충돌 C-41~C-47).

- **[BND-22]** 모르는 `binding_type`은 로그 후 `global`, 모르는 `binding_condition`은 로그 후 `none`으로 동작한다. 오타가 "조용히 다른 동작"이 되므로 값은 표에서 복사한다. `{코드}` (출처: NB-09(`binding_condition`), CN 테스트 B07·B13(`binding_type`))
- **[BND-23]** `binding_condition` 의미: `none` 데이터 갱신마다, `once` 처음 한 번, `always` 매 업데이트, `always_when_visible`·`visible` 보일 때만, `visibility_changed` 가시성이 바뀔 때만. 값 여섯 개는 엔진의 이름표와 같다(BND-35). `{코드}` (출처: NB-09(값 목록), CN(의미))
- **[BND-24]** `source_control_name`이 없는 view 바인딩은 **자기 주머니**를 읽고, 거기 없는 속성은 화면 컨트롤러(전역)에서 읽는다. 이름이 있는 view는 전역으로 떨어지지 않는다. `{바닐라, 코드}` (출처: VN 27회, NB-09(자기 컨트롤), CN 테스트 B26·B27(전역 대체), CN Zeqa 회귀)
- **[BND-25]** `source_control_name` 검색: 기본은 화면 루트부터 **너비 우선 첫 일치**, `resolve_sibling_scope`는 부모부터 너비 우선(부모 자신 포함, BND-20의 원인), `resolve_ancestor_scope`는 가장 가까운 같은 이름 조상. 숨은 하위 트리도 검색한다. 이름이 겹치면 루트에 더 가까운 쪽이 이긴다. `{코드}` (출처: NB-09(범위 세 가지), CN 테스트 B20·B25(검색 순서))
- **[BND-26]** 식 바인딩 `{"binding_name": "(식)", "binding_name_override": "#t"}`는 주머니의 `#t`에 컨트롤러의 원래 답을, 컴포넌트에는 식 결과를 준다. 다른 view가 `#t`를 읽으면 식 결과가 아니라 원래 답을 본다. 결과를 공유하려면 view 바인딩으로 계산해 새 속성에 담는다. `{코드}` (출처: CN 테스트 B08)
- **[BND-27]** 불리언 대상(`#visible`, `#enabled`, `#toggle_state` 등)은 JSON 불리언만 받는다. 전역 문자열 `'false'`를 그대로 `#visible`에 바인딩하면 숨지 않는다. 식(`(#flag = 'false')`)을 거치면 불리언이 된다. `{코드}` (출처: CN)
- **[BND-28]** `property_bag` 리터럴의 상수 식은 계산된다(`"#n": "(1 + 2)"` → 3). 부모의 `property_bag_for_children`은 자손 주머니에 합쳐지되 자손이 가진 값을 덮지 않는다. `{코드}` (출처: CN 테스트 B32·B33)
- **[BND-29]** `"text": "##글자"`처럼 `##`로 시작하는 텍스트는 바인딩이 아니라 리터럴이다. 바인딩되지 않은 `"text": "#이름"`은 빈 글자로 그려진다. `{코드}` (출처: CN 테스트 L08)

### 4.8 연구 서버 서버 실측으로 더한 규칙

연구 서버 서버(`DF`)를 만들며 Windows 1.26.52 에서 실측한 것이다. 서버 폼 하나로 여러 화면을 그리는 구조에서 얻었다.

- **[BND-31]** 제목으로 고르는 레이아웃의 `#visible`은 `binding_condition: "always"`로 둔다. `once`면 폼이 다음 폼으로 바뀌는 사이 잠깐 맞았던 레이아웃이 다음 폼 위에 켜진 채 남았다. `{실측}` (출처: DF)
- **[BND-32]** `visible: false`로 시작한 레이아웃 안 팩토리의 길이 바인딩(`#form_button_contents` → `#collection_length`)을 `binding_condition: "visible"`로 두면, 제목이 맞지 않아 숨은 레이아웃은 버튼 칸을 만들지 않았다(COL-10의 "생성은 막지 못한다"는 레이아웃 컨트롤 자체의 이야기다). 처음부터 보이는 레이아웃에 쓰면 숨은 레이아웃도 첫 프레임에 칸을 만들었다. 같은 자리에 `always_when_visible`·생략을 쓰면 첫 프레임에 만든 칸의 바인딩이 갱신되지 않아 글자·표식이 비었다. `{실측}` (출처: DF)
- **[BND-33]** 우리 정의라도 `source_property_name` 식의 **일부**로 끼운 `$변수`는 치환되지 않았다(탭·뒤로 버튼이 안 보임, 팩 검사기도 못 잡음). 식 전체를 변수로 받는 BND-12와 달리, 표식처럼 식 안에 넣는 값은 식마다 글자로 적는다. `{실측}` (출처: DF)
- **[BND-34]** `(not ((A - B) = 'z'))`처럼 빼기 결과를 같은 식 안에서 바로 비교하자 참·거짓이 뒤집혔다. 먼저 view 바인딩으로 `#변수`에 담고 `(not (#변수 = 'z'))`로 비교하니 맞았다. EXP-06처럼 단계를 나눈다. `{실측}` (출처: DF)

### 4.9 엔진 동작 분석으로 더한 규칙

Android 1.26.52.3 클라이언트의 네이티브 라이브러리를 분석해 읽은 것이다(`NB`). 수준은 `코드`다.

- **[BND-35]** `binding_condition`은 문자열이어야 하고(아니면 `- expected a string.` 오류), 값은 `none`, `once`, `always`, `always_when_visible`, `visible`, `visibility_changed` 여섯 가지다. **생략하거나 모르는 값이면 `none`**으로 동작한다(BND-22·BND-23과 같다). `{코드}` (출처: NB-09)
- **[BND-36]** view 바인딩은 `source_control_name`이 **비어 있으면 자기 컨트롤**을 읽고(BND-24), 있으면 기본·형제(`resolve_sibling_scope`)·조상(`resolve_ancestor_scope`) 범위 중 하나로 찾는다(BND-25). 두 스코프를 함께 켜면 오류를 남기고 **형제 범위**로 동작한다. `source_property_name`·`target_property_name`이 없으면 각각 `Must define a … property name in the binding!` 오류다. 컬렉션 바인딩은 `binding_collection_name`이 없으면 `Must define a collection name for the binding!` 오류다. `{코드}` (출처: NB-09)

## 커뮤니티 보고로 더한 사실 (커뮤니티)

(출처: 비공개 조사) 모두 보고 수준이다.

- 원칙: 그대로 가져오면 `global`, 계산하면 `view`.
- 같은 대상에 바인딩을 여러 개 걸면 합쳐지지 않고 마지막 것이 이긴다. 한 식으로 합친다. 같은 이름을 읽고 쓰는 바인딩(`#len` → `#len`)은 루프가 되어 문자열이 계속 붙고 메모리가 는다.
- `resolve_ancestor_scope`는 1.21.130에 생겼지만 정식판에서 동작하지 않거나 오류를 낸다는 보고와 된다는 보고가 엇갈려 `resolve_sibling_scope`를 이어 쓰라고 권한다(D-12, BND-01).
- 큰 폼의 팩토리·그리드 길이 바인딩에 `once`를 걸면 렉과 유령 버튼이 준다. 단 제목으로 고르는 레이아웃의 `#visible`은 `always`로 둔다(BND-31). view 바인딩에는 `binding_condition`을 걸 수 없다는 보고가 있으나(D-11) 레이아웃 `#visible`에 `always`·`visible`이 효과가 있었다는 실측(BND-31, BND-32)을 따른다.
- **preserved title(래치) 패턴은 동작한다.** BND-18의 값 보존은 HUD 타이틀 채널의 표준으로 2026-07까지 여러 사람이 동작을 확인했다(D-13, 가이드 수준은 `미검증`에서 상향 후보). `data_control`은 루트에 둔다는 쪽이 다수다(D-20).
- `property_bag_for_children`은 2026-05 무렵 정식판에 들어왔다(BND-28).
- 존재하지 않는 바인딩 이름(`#item_aux_id`, 정답은 `#item_id_aux`)은 오류 없이 `property_bag` 기본값을 돌려준다. 바인딩 이름은 바닐라 파일이나 JSON UI Dumper에서 복사한다.
- 모바일 크래시 보고: `binding_name` 안에 `and`를 인라인으로 쓰면 모바일이 죽었다. 계산은 view 바인딩에서 한다.

## 반영안(미적용)

- **[BND-30]** (반영안) 같은 대상에 "초기화"와 "자기 자신 + 증가" 두 view 바인딩을 걸어 반복 계산(문자열 길이 세기, 뉴턴 제곱근)하는 생성기가 있다. view 바인딩이 원본이 바뀔 때만 다시 쓰고 사슬이 수렴할 때까지 돈다는 전제(Cinnabar 발견 CN-36)가 필요하다. 반복 상한과 프레임당 처리는 확인되지 않았으므로 레시피로 쓰지 않는다. `{코드, 미검증}` (출처: jua-asajs, jua-cinnabar) 실측 과제: 이 구성이 최종 길이에 도달하는지, 몇 프레임 걸리는지. 커뮤니티의 "자기 자신을 읽고 쓰면 루프가 된다"는 보고와 맞물린다.
- **보강안(미적용)**: BND-02에 `binding_type` 생략 시 기본값이 `global`이라는 판정(C-59 해소)과 중국판 문서의 서술을 더한다. BND-26(식 바인딩이 주머니에 주는 값)에도 중국판 문서의 대응 서술이 제안되었다. BND-22 보강은 BND-02 보강과 C-59로 충분해 생략되었다. 편집기가 바인딩 이름을 어떻게 근사하는지(미리보기 한계)는 디버깅 장으로 옮긴다.
- **DF 실측 반영 메모**: 연구 서버 실측 BND-31~BND-34는 본문(위)에 이미 들어 있다. 번호는 반영안과 겹치지 않는다.
