## 개념: 컨트롤은 트리이고, 배치는 크기·앵커·스택이 정한다

화면은 컨트롤의 트리다. 부모 컨트롤의 `controls` 배열에 자식이 들어가고, 자식은 부모 안에서 크기(`size`), 기준점(`anchor_from`/`anchor_to`), 이동(`offset`), 겹침 순서(`layer`)로 놓인다. 부모가 `stack_panel`이면 자식을 한 방향으로 쌓고, `grid`면 칸에 배치한다.

### 동작하는 예제

화면 오른쪽 위에 붙은 정보 카드다. 세로 스택 안에 제목 라벨과 본문 라벨이 있고, 카드는 자식 크기에 맞게 줄어든다.

```jsonc
{
  "namespace": "my_addon",
  "info_card": {
    "type": "panel",
    "size": ["100%c + 8px", "100%c + 8px"],   // 자식 합 + 여백
    "anchor_from": "top_right",               // 부모의 오른쪽 위에 붙이고
    "anchor_to": "top_right",                 // 자기 오른쪽 위를 맞춘다
    "offset": [-4, 4],                        // 안쪽으로 밀기(오른쪽 앵커는 음수 x가 안쪽, LAY-17)
    "controls": [
      { "bg": { "type": "image", "texture": "textures/ui/white_icon",
                "color": [0, 0, 0], "alpha": 0.6, "layer": 1,
                "size": ["100%sm", "100%sm"] } },    // 가장 큰 형제에 맞춘 배경
      { "rows": {
          "type": "stack_panel", "orientation": "vertical", "layer": 2,
          "size": ["100%c", "100%c"],
          "controls": [
            { "title": { "type": "label", "text": "제목", "color": [1, 1, 0] } },
            { "body":  { "type": "label", "text": "본문", "size": ["default", "default"] } }
          ] } }
    ]
  }
}
```

크기 `"100%c"`는 보이는 자식의 합, `"100%sm"`은 가장 큰 형제에 맞춤이다(LAY-03, LAY-07). 배경에 `layer`를 낮게 주어 앞뒤를 보장한다(LAY-19).

### Bedrock Wiki의 속성 표 (기본값 포함)

| Property | Type | Default | Description |
| --- | --- | --- | --- |
| visible | boolean | `true` | If the UI element should be visible |
| enabled | boolean | `true` | If true and the element or any child has the locked state then they will be in the locked state |
| layer | int | `0` | Z-Index relative to the parent element. Higher values render above, negative values render below the parent element |
| alpha | float | `1.0` | Alpha of the element. It will only affect the UI element. Its children will be unaffected. Use `propagate_alpha` to apply to children too |
| propagate_alpha | boolean | `false` | If `alpha` should apply to all children as well |
| clips_children | boolean | `false` | Cuts off visually and interactively everything beyond the boundaries of the UI element |
| allow_clipping | boolean | `true` | If `clips_children` of an ancestor works on this element |
| use_child_anchors | boolean | `false` | Use the `anchor_from` and `anchor_to` of the children of the UI element |
| grid_position | Vector | | Position that the control will take inside the grid. Also allows modifying specific grid items of a hardcoded grid |
| collection_index | int | | Index that the control takes in the collection |
| size | Vector [width, height] | `["default", "default"]` | `"default"`, a number of pixels (`0` or `"0px"`), a percentage of the parent (`"50%"`), and sums such as `"100% - 4px"` |
| max_size, min_size | Vector | `["default", "default"]` | Maximum and minimum size the element can have |
| offset | Vector [x, y] | `[0, 0]` | Position relative to the parent, based on the top left corner |
| anchor_from | enum | `center` | Anchor point in the parent element |
| anchor_to | enum | `center` | Anchor point in the element |
| orientation | enum | `vertical` | Direction the elements stack inside `stack_panel` (`vertical`, `horizontal`) |
| grid_dimensions | Vector [columns, rows] | | Number of columns and rows the grid has |
| maximum_grid_items | int | | Maximum number of items the grid will generate |
| grid_item_template | string | | An element capable of handling collections |

Anchors allow the elements to align to a certain point. `anchor_to` is the anchor point in the element that will be attached to the `anchor_from` in the parent element. For `anchor_from: center` and `anchor_to: top_left`, the top left point of the element is in the center point of the parent element.

주의: 위키 표의 기본값 `"default"`는 "100%"와 같다고 적혀 있지만 타입마다 다르다(LAY-03, C-36). 위키는 `grid_position`을 `[row, column]`이라 쓰지만 바닐라 대조로 `[열, 행]`이 맞다(아래 LAY-29 정정과 C-48). `grid_fill_direction`의 위키 3값 중 `vertical` 외에는 바닐라 근거가 없다(LAY-26). 위키 표의 `allow_clipping` 기본값 `true`는 부모가 없는 컨트롤에만 맞고, 생략하면 부모의 값을 물려받는다(LAY-68).

### Microsoft Learn의 요소 속성 레퍼런스

MS Learn의 `minecraft:ui_element` 문서(커밋 a9fd1c0)는 요소 속성을 이름·타입·설명으로 나열한다(출처: ms-learn). 이 위키가 규칙으로 다루는 주요 항목은 다음과 같다.

| 분류 | 속성 |
| --- | --- |
| 크기·배치 | `size`(`[width, height]`, 숫자는 픽셀, `'100%'`, `'fill'`, `'100%c'`, `'100%cm'`), `min_size`, `max_size`, `offset`(`[x, y]` 픽셀), `anchor_from`, `anchor_to`, `layer`(높을수록 위), `orientation` |
| 표시 | `visible`, `alpha`(0.0~1.0), `propagate_alpha`, `color`(`[r, g, b]`), `clips_children`, `allow_clipping`, `ignored`, `shadow`, `grayscale` |
| 텍스처 | `texture`, `uv`, `uv_size`, `tiled`, `keep_ratio`, `bilinear`, `nine_slice_left/top/right/buttom`(원문 철자 그대로), `fill` |
| 텍스트 | `text`, `text_alignment`, `font_size`, `font_type`, `font_scale_factor`, `max_length`, `place_holder_text` |
| 컬렉션·그리드 | `collection_name`, `grid_dimension_binding`, `grid_item_template`, `grid_rescaling_type`, `factory`, `bindings`, `variables`, `controls` |
| 입력·포커스 | `button_mappings`(`from_button_id`, `to_button_id`, `mapping_type`, `input_mode_condition`), `focus_enabled`, `focus_change_up/down/left/right`, `default_focus_precedence`, `modal`, `consume_event`, `prevent_touch_input` |
| 스크롤·슬라이더 | `scroll_content`, `scroll_view_port`, `scrollbar_box`, `scrollbar_track`, `scroll_speed`, `slider_range`, `slider_steps` |
| 접근성 | `tts_control_type_order_priority`, `tts_ignore_count`, `tts_skip_message` |

이 문서의 enum 표(타입, 앵커 등)는 값이 비어 있고 일부 이름(`scrollbar_track`, `nine_slice_buttom`)이 바닐라와 다르다. 타입은 바닐라 사용 실적(아래 컨트롤 타입 표)으로 판단한다(LAY-01, C-34, C-60).

## 규칙

출처가 Cinnabar(`CN`, 26.30 네이티브 클라이언트의 JSON UI 해석기를 재구성한 Rust 코드)인 근거는 수준이 `코드`이고, `CN-run`은 이 프로젝트가 그 평가기를 직접 실행한 결과다. 게임 실측과 다르면 실측을 따른다(충돌 C-41~C-47). `DF`는 연구 서버를 만들며 Windows 1.26.52에서 실측한 것으로, 서버 폼 하나로 여러 화면을 그리는 구조에서 얻었다. `FFR`은 서버 폼 팩토리와 렉 시험 애드온을 모바일에서 실측한 것이다(2026-11-14). 애드온 구성은 [서버 폼 연구 화면](../design/server-form-research-screen.mdx)에 있다. LAY-59~LAY-68은 네이티브 클라이언트 역컴파일(`NB`, Windows 1.26.65.1과 Android 1.26.52.3)에서 읽은 레이아웃 규칙을 Windows 1.26.65.1 게임에서 잰 것이다(2026-11-20). 측정 창은 애드온 `addons/json-ui-claims`의 시험 창 `juc_tester.json`(서버 폼 제목 `§b§wjc:t`, `/scriptevent bwiki:json_ui_claims t`로 연다)이고, 구성은 [주장 실측](../design/json-ui-claims.mdx)에 있다. LAY-69~LAY-71은 Windows 1.26.65.1 클라이언트를 역컴파일해 읽은 것이다(2026-11-24). 같은 날의 실측은 [주장 실측](../design/json-ui-claims.mdx) 6.8절에 있고, LAY-69와 LAY-70은 게임에서 재지 않았다.

바닐라 1.26.50.4에서 `"type"`으로 쓰인 값과 횟수다(VN 전수 검색). 공식 enum(`forms/ui/ui_element.form.json`)과 다르다는 점에 주의한다.

| 타입 | 바닐라 | 공식 enum | 용도 |
| --- | ---: | :---: | --- |
| `panel` | 4,092 | O | 빈 상자. 자식 배치, 바인딩 호스트 |
| `stack_panel` | 1,461 | O | 자식을 한 방향으로 쌓음 |
| `image` | 1,318 | O | 텍스처 |
| `label` | 814 | O | 텍스트 |
| `grid` | 132 | O | 격자, 컬렉션 |
| `input_panel` | 108 | O | 입력(호버, 드래그, 모달) 받는 패널 |
| `custom` | 105 | O | `renderer`로 엔진이 그리는 것 |
| `button` | 54 | O | 버튼(대부분 템플릿 `common_buttons.*`로 씀) |
| `factory` | 36 | **X** | 데이터 종류별로 컨트롤을 만드는 팩토리 컨트롤(컬렉션과 팩토리 장) |

| `tooltip_trigger`, `selection_wheel`, `label_cycler`, `image_cycler`, `grid_page_indicator`, `carousel_label` | 2, 1, 1, 1, 1, 1 | X | 특수 |

- **[LAY-01]** 유효한 타입 목록은 공식 enum이 아니라 바닐라 사용 실적으로 판단한다. 공식 enum에는 `factory`, `collection_panel`, `tooltip_trigger`, `scroll_track` 등 바닐라가 쓰는 타입이 빠져 있다. 위키 타입표의 `scrollbar_track`은 오기이고(바닐라는 `scroll_track`, 충돌 C-34), 레거시 타입 `tab`, `grid_item`, `scrollbar`는 바닐라에 한 번도 없다. 위키가 레거시로 분류한 `carousel_label`은 바닐라에 1회 남아 있지만, Windows 1.26.65.1 엔진은 이 타입을 모르는 타입으로 거부해 만들지 않는다(ANI-46). `{바닐라, 실측}` ([출처](../reference/source-abbreviations.mdx): VN, BC-facts 공식 스키마 절, BW-doc, 2026-11-20 Windows 1.26.65.1)
- **[LAY-02]** `scroll_box`는 타입이 아니라 `ui_common.json`의 **컨트롤 이름**이다. 스크롤은 직접 조립하지 말고 `common.scrolling_panel` 템플릿을 `$scrolling_content` 등의 변수로 재사용한다. `{바닐라, 작동팩}` ([출처](../reference/source-abbreviations.mdx): VN server_form.json `scrolling_panel@common.scrolling_panel`, BA 5장, AP, MJ 4.2-2)
- **[LAY-70]** `screen_not_flushable`은 `type: screen` 컨트롤만 읽는 불리언이고 기본은 거짓이다. 값은 화면 컴포넌트의 비트로 저장되고 화면의 getter가 그 비트를 돌려주지만, 그 getter를 부르는 화면 스택 쪽 코드는 찾지 못했다. 이름으로 보아 화면 스택을 한꺼번에 비울 때(flush) 이 화면을 남기는 표시로 보이나, 효과는 추론이다. `{코드(바이너리), 추론}` ([출처](../reference/source-abbreviations.mdx): 2026-11-24 Windows 1.26.65.1 역컴파일)

### 크기

| 표기 | 뜻 | 바닐라 |
| --- | --- | ---: |
| `16` 또는 `"16px"` | 픽셀 | `px` 2,606 |
| `"50%"` | 부모 크기의 비율 | 다수 |
| `"100%c"` | 자식 기준 크기. 스택 패널과 일반 패널 모두 **보이는 자식의 합**(그리드는 LAY-03) | 2,201 |
| `"100%cm"` | 가장 큰 자식 | 419 |
| `"100%sm"` | 가장 큰 형제 | 263 |
| `"100%x"`, `"100%y"` | 자기 다른 축 크기의 비율(정사각, 비율 고정) | 162, 150 |
| `"fill"` | 스택 패널에서 남은 공간 | 668 |
| `"default"` | 내용의 기본 크기(라벨 텍스트 등) | 963 |
| `"100% - 4px"`, `"100%c + 12px"` | 식 | `%c +` 288 |

- **[LAY-03]** 크기 키워드는 위 표의 것을 쓴다. `%x`/`%y`의 "다른 축 기준"이라는 뜻은 바닐라 주석(`25%x * 56.25%`)과 용례로 판단한 것이다. `"default"`는 크기를 생략한 것과 같았고 타입마다 다르다. Windows 1.26.65.1 실측에서 패널은 부모 100%, 라벨은 텍스트 크기(`Hello` 24x10), 세로 스택 패널은 폭이 부모 100%이고 높이가 자식 합, 그리드는 자식 범위(10x10 칸 2x2는 20x20)였다([주장 실측](../design/json-ui-claims.mdx), 충돌 C-36). 코드에서 그리드의 이 크기는 자식 범위가 아니라 차원 x 템플릿 크기라서, 값은 같지만 항목 수가 차원보다 적어도 차원으로 잰다(2026-11-24 역컴파일). Cinnabar 재구성에서 생략한 크기는 스택 패널의 진행 축이면 `100%c`, 비율 이미지면 텍스처 비율, 나머지는 부모 크기다(LAY-38). 크기 식은 `%c` 등을 `%` 뒤에 쓴다(LAY-36). `{바닐라, 코드(소스), 코드(바이너리), 추론, 실측}` ([출처](../reference/source-abbreviations.mdx): VN store_search_screen.json:64 주석, VN 전수 검색, BW-doc, CN, 2026-11-18 Windows 1.26.65.1, 2026-11-24 Windows 1.26.65.1 역컴파일)
- **[LAY-04]** **스택 패널은 숨은(`#visible` false) 자식에게 공간을 주지 않는다.** 조건부 행을 접으면 아래가 올라오고, 2의 거듭제곱 크기 spacer를 켜고 끄면 합이 곧 좌표가 된다(패턴 레시피 6). `{작동팩, 실측}` ([출처](../reference/source-abbreviations.mdx): BA 4장, BC-S12)
- **[LAY-05]** 정적 컨트롤의 위치(`offset`)는 **배열을 담은 `property_bag` 키를 view 바인딩으로 `#offset`에 옮기면** 바뀐다. Windows 1.26.65.1 HUD에서 정적 `"offset": [70, 0]`인 라벨에 `"property_bag": {"#o": [10, 20]}`와 view 바인딩 `#o` -> `#offset`을 두자 라벨이 (10, 20) GUI 자리로 옮겨졌다(정적 offset을 대신함). `property_bag`에 `"#offset": [10, 20]`만 두고 바인딩을 걸지 않은 라벨은 정적 `[30, 0]` 자리에 그대로 있었다. Cinnabar 재구성도 `#offset`에 `[x, y]` 바인딩을 받는다. 코드도 같다: `#offset` 주머니 키에 **배열**이 들어오면 [0], [1]을 실수로 읽어 offset을 픽셀 항 둘로 바꾸고 다시 배치한다. 배열이 아니면 (0, 0)을 쓰고, 지금 식과 같으면 아무 일도 없다. 바인딩 식의 결과는 불리언, 정수, 실수, 문자열뿐이라 식으로 배열을 계산하지는 못한다. "바인딩할 수 없다"는 BC-S12 실측은 식 결과를 넘긴 경우였을 수 있다(추론). 값에 따라 바뀌는 위치는 **앞에 둔 spacer의 크기**를 바인딩해 스택이 다음 자식을 밀게 한다(충돌 C-44). `{실측, 작동팩, 코드(소스), 코드(바이너리)}` ([출처](../reference/source-abbreviations.mdx): BC-S12, BA 4장, 충돌 C-44, 2026-11-24 Windows 1.26.65.1 역컴파일, 2026-11-25 Windows 1.26.65.1)
- **[LAY-06]** `max_size`, `min_size`로 반응형을 만든다. 예: `"size": [314, "100% - 64px"]`, `"max_size": [314, 236]`이면 작은 화면에서 창 높이가 줄어든다. `{작동팩, 바닐라}` ([출처](../reference/source-abbreviations.mdx): BA 5장, VN max_size 204회)
- **[LAY-07]** `"100%cm"` 상자 안에 배경을 `"100%sm"`으로 두면, 안의 행이 숨을 때 상자와 배경이 함께 줄어 아래가 따라 올라온다. `{실측}` ([출처](../reference/source-abbreviations.mdx): BC-S12)
- **[LAY-08]** `"100%cm"` 패널 안에 라벨과 `"100%sm"` 버튼을 두면 버튼 히트박스가 언어마다 글자 크기에 정확히 맞는다. 같은 자리에 `"100%c"`를 쓰면 버튼이 라벨 아래로 떨어진다. `{실측}` ([출처](../reference/source-abbreviations.mdx): BC-S10)

### 크기·위치·투명도 바인딩

- **[LAY-10]** 크기 바인딩은 `#size_binding_x`, `#size_binding_y`에 값을 쓴다. 값은 픽셀이 아니라 **부모 크기의 배수**다. Windows 1.26.65.1 실측에서 폭 100 부모 안의 선언 10x10 자식에 .5를 주자 폭 50, 2를 주자 부모를 넘어 200이었고, `#size_binding_x_absolute` 20은 20이었다([주장 실측](../design/json-ui-claims.mdx)). 선언 크기에 곱한다는 S12의 해석은 틀렸고, Cinnabar 재구성(값 v를 `v×100%`로 바꾸고, `_absolute`는 픽셀)과 같다(충돌 C-14). `[1, 1]` 크기 프레임 안에 두면 값이 곧 픽셀이 된다는 S12 관측도 이와 맞다. 선언은 `["100%", "100%"]`로 둔다. 범위를 벗어난 값이 아무것도 안 그린다는 이전 기록은 `[0, 0]` 선언 때문이었을 가능성이 높다. 바닐라의 유일한 크기 바인딩(`resizing_xp_bar_with_hotbar`)은 `use_anchored_offset: true`와 함께 쓰고, 위키도 이 속성이 필요하다고 적지만, 정적 컨트롤에서는 그것 없이도 같은 50이었다(Windows 1.26.65.1 실측, 충돌 C-37). 크기 바인딩 + `use_anchored_offset` + 컬렉션 셀 조합은 피한다(LAY-14). 오프셋 바인딩 `#anchored_offset_value_x`(`use_anchored_offset: true`)는 게임에서 **부모 폭의 배수**였다: `[1, 1]` 틀의 50과 폭 100 틀의 0.5가 모두 50px이었고, 폭 100 틀의 50은 틀 밖으로 나갔다. 부모 크기 해석과 맞고, 픽셀로 옮기려면 `[1, 1]` 틀 안에 둔다. `{실측, 코드(소스)}` ([출처](../reference/source-abbreviations.mdx): BC-S6, BC-S12, 충돌 C-14, BW-doc, VN hud_screen.json:319, CN, CPR, 2026-11-18 Windows 1.26.65.1)

- **[LAY-17]** `offset`은 앵커 기준의 이동이며 크기와 같은 단위(픽셀, `%`, 식)를 쓴다. 예: `"offset": [0, "50%-68px"]`. 오른쪽이나 아래 앵커여도 축은 뒤집히지 않는다(충돌 C-49 해소): 바닐라 206개 파일 분포에서 오른쪽 앵커의 x는 음수 104 대 양수 37, 아래 앵커의 y는 음수 190 대 양수 45이고, `common.close_button`은 `top_right` 앵커에 `[-2, 2]`를 쓴다(`ui_common.json:3239-3246`). `{바닐라}` ([출처](../reference/source-abbreviations.mdx): VN hud_screen.json:2146, ui_common.json:3239-3246)
- **[LAY-43]** 앵커 값은 9개 이름(LAY-16) 중 하나와 대소문자까지 정확히 같을 때만 읽고, 그 밖의 문자열은 `center`다. Windows 1.26.65.1에서 `left`, `top`, `middle_left`, `Top_Left`는 모두 가운데에 놓였다. 이름에 `left`·`right`·`top`·`bottom`이 들어 있는지로 판정하는 Cinnabar 재구성은 게임과 다르다. `{코드(소스), 코드(바이너리), 실측}` ([출처](../reference/source-abbreviations.mdx): NB, CN, 2026-11-20 Windows 1.26.65.1)
- **[LAY-60]** `anchor_to`를 생략하면 `center`다. `anchor_from: "bottom_right"`만 준 컨트롤은 자기 가운데가 부모의 오른쪽 아래 점에 놓였다. 모서리에 붙이려면 `anchor_to`도 같은 이름으로 적는다(LAY-45). `{코드(바이너리), 실측}` ([출처](../reference/source-abbreviations.mdx): NB, 2026-11-20 Windows 1.26.65.1)
- **[LAY-38]** 스택 패널의 자식은 `offset`을 무시하고, `use_child_anchors: true`가 없으면 앵커도 무시한다. 생략한 스택 패널의 진행 축 크기는 `100%c`다. `{코드(소스)}` ([출처](../reference/source-abbreviations.mdx): CN 테스트 S04, CN)
- **[LAY-56]** `stack_panel` 자식에 준 `offset`은 스택이 정한 위치를 옮기지 않았다. 가로 스택에 칸 48개를 두고 줄마다 `offset`으로 접으려 하자 한 줄로 이어져 창 밖까지 나갔다. 2차원 배치는 세로 스택 안에 가로 스택 줄을 둔다. `{실측}` ([출처](../reference/source-abbreviations.mdx): FFR)

### 레이어와 그리기 순서

- **[LAY-18]** `layer`는 부모에 대한 **상대값**이다. 겹치는 두 컨트롤의 앞뒤는 조상 체인 전체의 레이어를 비교해야 안다. 코드에서 절대 레이어는 부모의 절대 레이어 + 자기 값(정수)이다. `{실측, 코드(바이너리)}` ([출처](../reference/source-abbreviations.mdx): BC-rules, 2026-11-24 Windows 1.26.65.1 역컴파일)
- **[LAY-19]** 같은 레이어의 형제는 **배열 순서가 그리기 순서를 보장하지 않는다**는 실측 기록이 있다. 코드에서는 그리기 항목을 절대 레이어 오름차순으로 안정 정렬하고, 같은 값이면 트리 전위 순서(배열 순서)를 유지한다. 그러므로 절대 레이어가 같은 형제는 배열 순서대로 그려져 뒤 형제가 위에 온다고 예측된다. 보장되지 않아 보인 실측은 조상 레이어 합이 달랐을 가능성이 있다(추론). 같은 절대 레이어 형제의 순서는 게임에서 따로 재지 않았으므로 앞뒤가 중요하면 레이어를 다르게 준다. `{실측, 코드(바이너리)}` ([출처](../reference/source-abbreviations.mdx): BC-rules, MJ 4.2-10, 2026-11-24 Windows 1.26.65.1 역컴파일)
- **[LAY-20]** 같은 데이터를 "모든 외곽선 → 모든 선 → 모든 노드 → 호버" 순으로 그려야 하면 한 아이템 안에서 레이어를 올리는 것으로는 부족하다(다음 아이템의 외곽선이 앞 아이템을 덮는다). 같은 컬렉션을 레이어가 다른 팩토리로 여러 번 그린다. `{작동팩}` ([출처](../reference/source-abbreviations.mdx): BA 5장)
- **[LAY-21]** 50 이상의 레이어는 바닐라에서도 흔하다. 레이어가 높다는 경고는 무시해도 된다. 2026-11-24 역컴파일에서 레이어 상한이나 경고를 내는 코드는 찾지 못했고, 레이어는 정수 합 그대로 쓰였다. `{바닐라, 추론}` ([출처](../reference/source-abbreviations.mdx): MJ 5장, 2026-11-24 Windows 1.26.65.1 역컴파일)
- **[LAY-33]** `alpha`는 그 컨트롤만 투명하게 하고 자식에는 전파되지 않는다. 자식까지 함께 투명하게 하려면 `propagate_alpha: true`를 준다(BND-15). `layer`는 음수도 되며 부모보다 아래에 그린다. 코드에서도 같다. `{코드(바이너리), 바닐라}` ([출처](../reference/source-abbreviations.mdx): BW-doc Control 표, 2026-11-24 Windows 1.26.65.1 역컴파일)
- **[LAY-67]** `layer`는 정수로만 읽는다. `"layer": "5"`처럼 문자열로 쓰면 레이어 0이 된다. `{코드(바이너리), 실측}` ([출처](../reference/source-abbreviations.mdx): NB, 2026-11-20 Windows 1.26.65.1)
- **[LAY-55]** 스크롤 영역 안에서 팩토리나 grid가 만든 칸의 라벨을 배경 이미지와 같은 레이어(기본 0)에 두면, 아이콘과 진행 막대는 바로 보이는데 글자는 무언가를 건드리기 전까지 비었다(건드린 칸만 나타나기도 했다). 라벨을 배경보다 높은 레이어(아이콘 2, 라벨 3)에 두자 열자마자 모두 보였다. 바닐라 버튼 라벨도 `layer: 2`다. `binding_condition`, 식 유무, 팩토리 유무, 자르기, 스크롤 갱신은 이 증상과 관계없었다. `{실측}` ([출처](../reference/source-abbreviations.mdx): FFR)
- **[LAY-58]** 글자와 그 아래 바탕의 조상 레이어 합이 같으면 바탕이 글자를 덮을 수 있다. 상자 화면 갤러리에서 PlayerList 이름(합 14), Badge 숫자(합 38), NumberInput 값이 보이지 않았고, 모두 레이어 합이 같은 바탕 위에 있었다. 글자 레이어를 올리자 보였다. 같은 합이면 늘 덮는지는 따로 떼어 시험하지 않았다(*추론*). 글자는 바탕보다 합이 크게 둔다. 구성은 [InvUI로 기본 컴포넌트 구현하기](../design/invui/ddui/basic-components.mdx). `{실측}` ([출처](../reference/source-abbreviations.mdx): IUC)

### 그리드

- **[LAY-25]** 그리드는 `grid_dimensions`(고정 크기) 또는 `grid_dimension_binding`(바인딩 크기), `grid_item_template`, `maximum_grid_items`로 만든다. `{바닐라}` ([출처](../reference/source-abbreviations.mdx): VN 속성 키 기준 37·79·117·11회)
- **[LAY-26]** `grid_fill_direction`은 바닐라에서 `vertical`만 쓴다. `left_to_right` 같은 값은 근거가 없다. `grid_rescaling_type`은 바닐라에서 `horizontal`(21), `vertical`(1)만 쓰고, 공식 enum의 `none`은 쓰지 않는다. 위키가 적은 `grid_fill_direction` 3값(`vertical`, `horizontal`, `none`)도 `vertical` 외에는 바닐라 근거가 없다. `grid_rescaling_type: "vertical"`은 크래시 경고가 있다(LAY-32). 상자 칸을 읽는 컬렉션 격자(`grid_dimensions: [3, 2]`, `maximum_grid_items: 6`)에 `horizontal`을 주자 윗줄 세 칸만, `vertical`을 주자 첫 칸과 격자 오른쪽 밖 한 칸만 그려졌다. 열 우선 채우기로는 쓸 수 없다. `{바닐라, 실측}` ([출처](../reference/source-abbreviations.mdx): VN, MJ 4.2-3·4, BW-doc, BW-dyn, CPR)
- **[LAY-29]** 그리드 칸에 정적 자식을 직접 놓으려면 자식에 `"grid_position": [열, 행]`을 준다(0부터). `grid_dimensions [4, 2]` 격자에서 `[3, 0]`은 오른쪽 위, `[0, 1]`은 왼쪽 아래에 놓였다(실측, 모바일, 2026-11-16, C-48). 바닐라도 71회 쓰고, 엔진이 만든 그리드의 특정 칸을 덮어쓰는 데도 쓴다. `{바닐라, 실측}` ([출처](../reference/source-abbreviations.mdx): VN, HXC, BW-dyn 스크린샷)
- **[LAY-30]** 개수가 바인딩으로 정해지는 그리드는 `grid_rescaling_type: "horizontal"`과 고정 폭을 주고 `#maximum_grid_items`(또는 `maximum_grid_items`)로 개수를 정한다. 열 수는 `floor(그리드 폭 / 템플릿 폭)`이다(160px ÷ 32px = 5열, 개수 15 → 3행). 높이는 `"100%c"`로 둔다. `{실측}` ([출처](../reference/source-abbreviations.mdx): BW-dyn 스크린샷)
- **[LAY-31]** **그리드는 숨은(`visible` false) 항목에도 자리를 준다.** 스택 패널(LAY-04)과 반대라서, 조건부 항목을 그리드에 두면 빈칸이 생긴다. 접혀야 하는 목록은 스택 패널로 만든다. Cinnabar 재구성에서도 그리드 칸 위치가 인덱스로 정해져 숨은 칸이 자리를 차지한다. Windows 1.26.65.1 실측에서 grid [4,1]의 1번 칸을 숨기자 2, 3번 칸이 x 40, 60에 그대로 있었고, 같은 칸을 가로 스택 패널에 두자 2번 칸이 x 20으로 당겨졌다([주장 실측](../design/json-ui-claims.mdx)). `{코드(소스), 실측}` ([출처](../reference/source-abbreviations.mdx): BW-dyn "Useful Information", CN, 2026-11-18 Windows 1.26.65.1)
- **[LAY-32]** `grid_rescaling_type: "vertical"`은 게임을 크래시시킬 수 있다는 경고가 있다. 바닐라는 1회(`store_item_list_screen.json`) 쓴다. 새로 만들 때는 `horizontal`을 쓴다. 2026-11-24 역컴파일에서 세로 재조정은 행 수 = max(1, floor(높이 / 칸 높이))인 식이었고 크래시로 이어지는 경로는 찾지 못했다. `{미검증, 바닐라}` ([출처](../reference/source-abbreviations.mdx): BW-dyn, VN, 2026-11-24 Windows 1.26.65.1 역컴파일)
- **[LAY-41]** 그리드 칸은 자기 `anchor`·`offset`을 무시한다. 템플릿 그리드는 행 우선 생성 순서로 칸을 채우고 용량을 넘는 칸은 만들지 않는다. 게임에서 폭 100, `grid_dimensions: [5, 1]` 격자의 칸은 20px이었고, 12px 템플릿은 칸 왼쪽 위에 붙어 마지막 항목과 오른쪽 끝 사이에 8px이 남았다. 템플릿 크기 `["100%", "100%"]`는 격자 전체 크기로 풀려 항목이 한 줄에 하나씩 세로로 쌓이며 격자 밖으로 넘쳤다. 항목을 고르게 놓으려면 칸 크기의 고정 템플릿(여기서는 `[20, 14]`)을 두고 그 안에서 가운데로 앵커한다. `{코드(소스), 실측}` ([출처](../reference/source-abbreviations.mdx): CN 테스트 D01·D08, CPR)

LAY-29의 `grid_position`이 `[열, 행]`이라는 것(C-48 해소)은 바닐라로도 확인된다: `inventory_screen.json:1200`(3x3 제작 칸의 `crafting_input_item_top_mid`가 `[1, 0]`, `mid_left`가 `[0, 1]`), `trade_screen.json:327`(`[4, 1]` 그리드의 자식이 `[0, 0]`~`[3, 0]`), `inventory_screen.json:1054`(갑옷 `[1, 4]` 그리드의 자식이 `[0, 0]`~`[0, 3]`).

### 스크롤

- **[LAY-42]** 스크롤 뷰는 역할 컨트롤(뷰포트, 내용, 트랙, 박스, 바 패널)을 이름으로 너비 우선 검색하므로 트리 안 위치는 자유지만, 넷 중 하나라도 없으면 스크롤하지 않는다. 박스 길이는 올림(트랙 길이 x 뷰포트 / 내용)이다. ## 커뮤니티 보고로 더한 사실 (커뮤니티)

(출처: 비공개 조사) 모두 보고 수준이다.

- 글자 컨트롤의 타입은 `text`가 아니라 `label`이다. 앵커 값은 `left_middle`이지 `middle_left`가 아니다(LAY-16).
- `"default"` 크기는 타입마다 다르다: 패널 100%, 라벨 텍스트 크기, 스택 패널 `["100%","100%c"]`, 그리드 `["100%c","100%c"]`(LAY-03, LAY-38과 같다). 단위 없는 문자열 `"10"`은 `Dangling number` 오류를 낸다는 보고가 있고 Cinnabar는 0으로 읽는다(LAY-34). Windows 1.26.65.1 코드에서는 둘 다 맞다: 로그를 남기고 숫자를 버려 0이 된다(2026-11-24 역컴파일).
- 숨긴 그리드 항목이 공간을 차지한다는 보고가 여럿이고 Windows 1.26.65.1 실측으로 확인되었다(D-14, LAY-31). 늘 숨길 버튼(탭, 뒤로)은 컬렉션 끝에 둔다(COL-35).
- 스택 패널 안에서 아래 정렬은 첫 자식으로 `["100%","fill"]` 패널을 넣어 남은 공간을 먹게 한다.
- 움직이는 위치가 필요하면 `use_anchored_offset: true`와 `#anchored_offset_value_x/y`(부모 크기 대비 비율)를 쓴다. Windows 1.26.65.1 실측에서 정적 패널의 값은 부모 크기의 배수로 움직였고 `center` 앵커에서는 움직이지 않았다(C-61). 고정 크기 부모와 왼쪽 위 앵커가 가장 안정적이다. `offset` 배열에 view 바인딩을 걸었다는 보고와 안 됐다는 보고가 엇갈린다(D-15). Windows 1.26.65.1 실측에서는 배열을 담은 주머니 키를 view 바인딩으로 `#offset`에 옮기자 움직였다(LAY-05).
- `#size_binding_x/y`는 "부모 대비 비율(2.5는 250%), 픽셀은 `_absolute`"라는 보고가 있어 Cinnabar 해석(LAY-10)을 뒷받침한다. Windows 1.26.65.1 실측에서도 .5는 부모 폭의 절반, 2는 두 배, `#size_binding_x_absolute` 20은 20이었다([실측 기록](../design/json-ui-claims.mdx#3-배치)). 컨트롤에 `"size": [0, 0]` 같은 명시적 자리표시 크기가 있어야 하고 값은 숫자여야 하며 잘못된 값은 크래시라는 보고가 있다. `#anchored_offset_value_*_absolute`는 있다·없다 보고가 섞였고, Windows 1.26.65.1 실측에서 `#anchored_offset_value_x_absolute`(top_left, 값 10)는 효과가 없었다. 쓰지 않는다(D-22).
- 바인딩한 `#alpha`는 0.75가 안 보이는 등 불안정하다는 보고가 있어 중간 투명도는 애니메이션이나 색으로 낸다(D-16, LAY-13). Windows 1.26.65.1 실측에서 이미지에 `"alpha": "#alpha"`를 적고 바인딩한 0.5는 정적 0.5와 같은 반투명이었고, 코드도 값을 실수 그대로 저장한다(LAY-13).
- 그리드 속성 이름은 `grid_dimensions`다(`grid_dimension`이면 타입 오류). 서브픽셀 틈이 창 모드에서 생기는 일이 있다. GUI 스케일은 읽을 수도 무시할 수도 없으므로 고정 픽셀보다 `%`를 쓴다.
- 스크롤: `common.scrolling_panel`의 변수를 쓰고 `$scrolling_pane_size`는 `size`에 명시해야 적용되며, 스크롤바 숨기기는 `"$scroll_bar_and_track_size": [0,0]`이다(LAY-02, LAY-42).
- 휴대폰은 UI를 크게 그려 화면 높이가 약 200px로 작다. 서버 폼 창은 고정 픽셀로 두고 넘치는 내용은 안쪽 스크롤로 처리한다(LAY-53, LAY-54).

## 실측이 필요한 항목

- 열린 화면에서 크기 바인딩의 재레이아웃(LAY-15). 코드는 다시 계산한다.
- ~~배열을 담은 주머니 키를 `#offset`으로 넘기면 정적 컨트롤이 움직이는지(LAY-05, C-44).~~ 해소: view 바인딩으로 옮기면 움직이고, 주머니에 `#offset`만 두면 움직이지 않는다(Windows 1.26.65.1 실측, 2026-11-25).
- 같은 절대 레이어 형제 둘이 겹칠 때 늘 뒤 형제가 위에 그려지는지(LAY-19).
- `inherit_max_sibling_width`와 `max_size`를 함께 준 컨트롤이 최대를 넘는지, 형제 둘이 모두 켰을 때의 결과(LAY-69).
- `screen_not_flushable: true`인 화면 위에서 다른 화면으로 바꿀 때 이 화면이 닫히는지(LAY-70).
- `scroll_speed` 1인 스크롤 뷰의 휠 한 칸 이동량(예측 20), 화면 `vertical_scroll_delta: 40`에서 두 배인지, 한 화면의 두 스크롤 뷰에 다른 `scroll_speed`를 줬을 때 처음 휠을 받은 쪽 값이 다른 쪽에도 쓰이는지(LAY-71). 바닐라 채팅의 한 칸은 약 56.5 클라이언트 px(GUI 약 14, 배율 4)로 15 x 20 = 300과 맞지 않았다. `chat_screen`에 병합한 `vertical_scroll_delta: 40`은 변화가 없었으나 병합이 적용됐는지 모르므로, 화면 정의를 통째로 덮거나 프로브 화면에 스크롤 뷰를 직접 두고 다시 잰다(Windows 1.26.65.1 실측, 2026-11-25).
- `[376, 250]` 패널이 잘리기 시작하는 창 크기와 GUI 배율의 관계(LAY-47).
- 뷰포트가 내용의 10%보다 작을 때 스크롤 박스에 하한이 있는지(LAY-42).
