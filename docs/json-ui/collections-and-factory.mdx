컬렉션과 팩토리는 JSON UI에서 **개수가 정해지지 않은 목록**을 그리는 장치다. 서버 폼의 버튼 수, 상자의 슬롯 수, 채팅 줄 수처럼 화면을 쓰는 시점에야 알 수 있는 데이터를 다룬다.

- **컬렉션(collection)**: 엔진이 주는 항목 목록이다. 폼 버튼(`form_buttons`), 모달 폼 행(`custom_form`), 상자 슬롯(`container_items`), 채팅 줄(`chat_text_grid`)이 있고, 항목마다 `#form_button_text`나 `#item_id_aux` 같은 값 바인딩이 따라온다. `collection_name`을 가진 컨테이너 안에서 `collection_index`로 몇 번째 항목을 읽을지 정하고, 바인딩은 `binding_collection_name`으로 어느 컬렉션을 읽을지 가리킨다.
- **팩토리(factory)**: 항목 수만큼 컨트롤을 **실행 중에 만드는** 장치다. 컨테이너의 `factory` 속성(또는 `"type": "factory"` 컨트롤)에 무엇을 만들지(`control_name`, `control_ids`)를 적고, 몇 개를 만들지는 엔진이 정하거나 `#collection_length` 바인딩이 정한다.
- **그리드(grid)**: 같은 템플릿 컨트롤을 격자로 배치하는 컨테이너다. `grid_dimensions`로 칸 수를 고정하거나 `#maximum_grid_items`로 개수를 정한다.

## 6.0 가장 작은 예제

**예 1. 고정 인덱스 슬롯**(팩토리 없이 컬렉션만 읽기, COL-06). 서버가 항상 같은 개수의 버튼을 보내면 각 칸이 몇 번째 항목을 읽을지 JSON에 박아 둘 수 있다.

```json
"tab_slots": { "type": "stack_panel", "orientation": "horizontal",
  "collection_name": "form_buttons",
  "controls": [
    { "slot0@my.tab_cell": { "collection_index": 0 } },
    { "slot1@my.tab_cell": { "collection_index": 1 } }
  ] }
```

**예 2. 개수를 바인딩으로 정하는 팩토리**(아래 Bedrock Wiki 원문의 첫 예제). 타이틀 문자열 `Count:3`에서 숫자를 꺼내 `#collection_length`에 넣으면 컨트롤이 3개 만들어진다. 0이면 아무것도 만들지 않는다(COL-11).

**예 3. 엔진 팩토리 다시 두기**(COL-14). 같은 이름의 팩토리를 하나 더 두면 같은 데이터로 두 번째 UI가 생긴다.

```json
"server_form_factory": { "type": "factory",
  "control_ids": { "long_form": "@my.long_form", "custom_form": "@my.custom_form" } }
```

### 6.0.1 Bedrock Wiki의 설명(Dynamic Content Generation)

Bedrock Wiki(`bedrock-wiki` 0930b39)는 팩토리와 그리드를 이렇게 설명한다. 원문(CC BY 4.0)을 그대로 옮긴다. 이 문서가 쓰는 `#collection_length`, `control_ids` 배열, `#maximum_grid_items`, `grid_position`의 기본 용법이다. 위키 예제는 HUD의 타이틀 문자열(`#hud_title_text_string`)을 재료로 쓴다.

<Excerpt src="bedrock-wiki" title="Dynamic Content Generation - Factories" path="docs/json-ui/dynamic-content-generation.md">

**Factories**

A factory generates UI elements specified in its `control_name` or `control_ids` properties.
- **Invocation:** Many of the vanilla factories are invoked natively by the engine. Alternatively, factories can be invoked manually by overriding the `#collection_length` property.
- **Data Binding:** For the use of `#collection_length`, the factory must reside within a collection-supporting container (e.g., `collection_panel` or `stack_panel`). The value can either be an `int` or a `string[]` based on the implementation of the factory.

**Key properties**

| Property | Type | Short Description |
| --- | :---: | --- |
| name | `string` | The unique identifier for the factory. This is critical for factories natively invoked by the engine, though custom factories can use any arbitrary string. |
| control_name | `string` | Reference to the control to be generated by the factory |
| control_ids | `Object` | An object mapping arbitrary string keys to the references of the controls to be generated. Used when generating multiple distinct controls. Must remain unchanged for natively invoked factories. |
| factory_variables | `string[]` | List of variables that should be passed to the controls generated by the factory |
| max_children_size | `int` | Maximum number of controls to be generated |

**Usage**

**Using `control_name`:**

In this case, `#collection_length` must be overridden with an `int` value. This is the number of elements that will be generated.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_factory": {
    "type": "stack_panel",
    "size": [ "100%cm", "100%c" ],
    "factory": { // Defined in a stack_panel (Supports collection)
      "name": "hud_apple_factory",
      "control_name": "hud.hud_apple" // Reference to hud_apple
    },
    "bindings": [
      {
        "binding_name": "#hud_title_text_string",
        "binding_name_override": "#count"
      },
      {
        "binding_type": "view",
        "source_property_name": "(#count - 'Count:' + 0)", // Gets the int value
        "target_property_name": "#collection_length" // Overriding #collection_length
      }
    ]
  }
}
```

Here, an integer value is sent through the title as `Count:{value}` that indicates the number of elements to generate. The bindings listed above first fetch the title string and store it in `#count`. Then, `#count - 'Count:'` gets the `int` value and `#collection_length` is overridden with this value.
**Note:** `+ 0` sets a default value of 0 if the string is empty.

**Expected result:** For title: `Count:3`

**Using `control_ids`:**

In this case, `#collection_length` must be overridden with an array of strings. The strings are the keys defined in `control_ids`. There's not much freedom with this approach as there is no way to manipulate arrays in JSON UI. Instead, we can pre-define some arrays within the `property_bag` and choose from them. The elements will be generated in the order specified in the array.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "hud_label": {
    "type": "label",
    "text": "Apple!",
    "shadow": true
  },

  "apple_factory": {
    "type": "stack_panel",
    "size": [ "100%cm", "100%c" ],
    "factory": {
      "name": "hud_apple_factory",
      "control_ids": {
        "apple": "hud.hud_apple", // An arbitrary name mapped to the reference of a control
        "label": "hud.hud_label"
      }
    },
    "property_bag": {
      // Some pre-defined arrays
      "#list1": [ "apple", "label" ],
      "#list2": [ "label", "apple" ]
    },
    "bindings": [
      {
        "binding_name": "#hud_title_text_string",
        "binding_name_override": "#choice"
      },
      {
        "binding_type": "view",
        "source_property_name": "('#list' + #choice)", // Constructing key name
        "target_property_name": "#collection_length"
      }
    ]
  }
}
```

Here, we have defined two controls in `control_ids` and two arrangements of these controls as `#list1` and `#list2`. In the bindings, we fetch the title string and store it in `#choice`, which is an integer representing the list to be selected. Then using `('#list' + #choice)`, we construct the name of the list and that list is then overridden to `#collection_length`.

**Expected result:** For title: `1` and `2` respectively

</Excerpt>

**Factory (Extra):**

You can define factories directly using `"type": "factory"` as well. These factories are always invoked natively by the engine. However, it is possible to define these factories in the ways discussed above we can also modify the control references to generate custom elements instead.

```json
{
  "main_screen_content": { // Vanilla code from server_form.json
    "type": "panel",
    "size": [0, 0],
    "controls": [
      {
        "server_form_factory": { // Name of control here acts as the factory name and thus should remain unchanged
          "type": "factory",
          "control_ids": {
            "long_form": "@server_form.long_form",
            "custom_form": "@server_form.custom_form"
          }
        }
      }
    ]
  }
}
```

</Excerpt>
<Excerpt src="bedrock-wiki" title="Dynamic Content Generation - Grids" path="docs/json-ui/dynamic-content-generation.md">

**Grids**

Grids generate and arrange UI elements in a grid layout. The elements are generated from a template control specified in its `grid_item_template` property. We can either generate a fixed number of elements by defining `grid_dimensions` or a variable number by overriding its `#maximum_grid_items` binding or `maximum_grid_items` property.

**Key properties**


:::danger
Try not to use `vertical` as the value of `grid_rescaling_type`. It may crash your game.
:::

**Usage**

:::info
Grids typically have a default size of `["100%c", "100%c"]`. It is ideal to keep the height dynamic (`100%c`). If a fixed height is applied, generated elements may overlap if the height is too small, or have unintended gaps if the height is too large.
:::

**Using `grid_dimensions`:**

It is recommended not to override the `size` property in this case, as some elements can go outside the grid bounds and mess up the layout.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_grid": {
    "type": "grid",
    "grid_dimensions": [3, 3],
    "grid_item_template": "hud.hud_apple"
  }
}
```

**Expected result:**

**Overriding `#maximum_grid_items`:**

For this to work properly, you have to modify the width of the grid. This is because the number of columns in this case will be `floor( width of grid / width of template control )`. Moreover, we need to set `grid_rescaling_type` to `horizontal`. Then we have to override `#maximum_grid_items` through bindings, or alternatively, define the `maximum_grid_items` property.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_grid": {
    "type": "grid",
    "size": [160, "100%c"], // floor(160 / 32) = 5; Meaning the grid will have 5 columns
    "grid_item_template": "hud.hud_apple",
    "grid_rescaling_type": "horizontal",
    "bindings": [
      {
        "binding_name": "#hud_title_text_string",
        "binding_name_override": "#count"
      },
      {
        "binding_type": "view",
        "source_property_name": "(#count - 'Count:' + 0)", // Gets the int value
        "target_property_name": "#maximum_grid_items" // Overriding #maximum_grid_items
      }
    ]
  }
}
```

Here, an integer value is sent through the title as `Count:{value}` that indicates the number of elements to generate. The bindings listed above first fetch the title string and store it in `#count`. Then, `#count - 'Count:'` gets the `int` value and `#maximum_grid_items` is overridden with this value.

**Expected result:** For title: `Count:15`

**Grid Position**

There might be situations where you'd want to manually add controls to the grid instead of generating them from a template. With the `grid_position` property you can place your control anywhere on the grid.

**Usage**

Let's say we have a grid with 2 columns and 2 rows and we want to place our controls in this way-


The format `[row, column]` indicates the placement within the grid, where the first integer is the row index and the second integer is the column index. The following integer is the index it takes inside the grid for a defined collection.

**The code:**

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_grid": {
    "type": "grid",
    "size": ["100%c", "100%c"], // Define it explicitly to avoid layout issues
    "grid_dimensions": [2, 2],
    "controls": [
      { 
        "apple_1@hud.hud_apple": {
          "grid_position": [0, 0]
        }
      },
      {
        "apple_2@hud.hud_apple": {
          "grid_position": [1, 1]
        }
      }
    ]
  }
}
```

**Expected result:**

**Useful Information**

- When used with a collection, Factories and Grids automatically index generated elements.
- Generated elements can access outside bindings via `source_control_name`, but outside elements cannot access bindings from generated elements.
- Invisible elements inside a Grid still occupy physical space, which can leave unintentional gaps in your UI.
- In Grids, animations linked with the `next` property can appear bugged. After the first animation, the duration divides among the grid elements, causing subsequent animations to speed up. (`flip_book` animations are the only exception).

</Excerpt>

이 원문과 이 프로젝트 실측의 차이를 정리한다.

- 위키는 `(#count - 'Count:' + 0)`을 쓴다. 결과가 숫자가 되는 이유는 EXP-26(식의 중간 결과는 생김새로 타입이 다시 정해진다)이다. 확실히 하려면 `((#count - 'Count:') - 0)`으로 쓴다.
- 위키는 팩토리를 `collection_name` 없이 `stack_panel` + `factory`만으로 만든다. 같은 방식이 실측으로 동작했다(COL-24).
- 위키는 팩토리·그리드 안의 컨트롤이 바깥 바인딩은 `source_control_name`으로 읽지만 바깥은 안쪽을 읽지 못한다고 적는다(BND-19와 같은 결론).
- 위키의 "그리드 안에서 `next`로 이은 애니메이션이 빨라지는 버그"와 `grid_rescaling_type: vertical`이 게임을 멈출 수 있다는 경고는 ANI-18(`미검증`)로 옮겼다.
- 그리드 속성 정리: `grid_dimensions`(`[열, 행]`), `grid_dimension_binding`(칸 수 바인딩 이름, 하드코딩된 이름만), `grid_item_template`(셀 정의 참조), `grid_rescaling_type`(`none`, `horizontal`, `vertical`), `maximum_grid_items`(최대 개수, 바인딩 `#maximum_grid_items`), `grid_position`(`[행, 열]`)이다. 열 수는 `floor(그리드 폭 / 템플릿 폭)`이다.

엔진이 주는 **목록 데이터**(폼 버튼, 모달 행, 상자 슬롯, 채팅 줄, 대화 버튼)를 읽는 방법이 컬렉션이고, 그 목록의 항목 수만큼 컨트롤을 **만드는** 장치가 팩토리다.

## 6.1 컬렉션 주소 지정

- **[COL-01]** `collection_name`은 `stack_panel`, `grid`, `collection_panel`에 쓴다. `panel`, `image`에 쓰면 `Unknown property [collection_name]` 오류가 난다. `&#123;실측, 바닐라&#125;` (출처: BC-facts, BC-S9, BC-S11, VN grid 66·stack_panel 25·collection_panel store_common.json:750, MJ 9장, 부록A C-01)
- **[COL-02]** `collection_index`는 **인스턴스화 지점**(부모 `controls` 안의 항목)에서만 받는다. 최상위 정의에 쓰면 거부되고, `image`에는 어디서든 거부되며, `label`에서는 조용히 무시된다. 그런데 bedrock-core가 실제로 출력하는 텍스트 캐리어는 `label` 참조에 `collection_index`를 직접 준다. 확실히 하려면 라벨을 패널로 감싸 패널 참조에 인덱스를 준다. 엔진은 컬렉션 이름을 가진 부모의 직속 자식에서만 `collection_index`를 읽는다(COL-44). `&#123;실측, 코드, 충돌&#125;` (출처: BC-facts, NB-07, BC 4.1-(4), 부록A C-31)
- **[COL-03]** 인덱스는 적용된 지점부터 **하위 트리로 상속**된다. 그래서 정의는 한 번 쓰고, 참조 N개에 인덱스와 오프셋만 다르게 주는 패턴이 성립한다. 컬렉션을 읽는 바인딩은 각자 `binding_collection_name`으로 컬렉션을 지정한다. `&#123;실측&#125;` (출처: BC-facts)
- **[COL-04]** 서버 폼 버튼은 **버튼 자신**에 `{ "binding_type": "collection_details", "binding_collection_name": "form_buttons" }`가 있어야 눌림이 그 엔트리로 집계된다. 조상만 인덱스를 주면 눌리기는 하지만 스크립트에는 `canceled`로 와서 Esc와 구분할 수 없고 로그도 없다(사용자가 닫으면 `reason=UserClosed`가 오는데, 바인딩 누락 때의 reason으로 구분되는지는 확인되지 않았다). 바닐라 폼 버튼도 같은 구조다. `&#123;실측, 바닐라&#125;` (출처: BC-S1, BC-facts, VN server_form.json:211-225)
- **[COL-05]** 인덱스 호스트가 하나도 없는 컬렉션 바인딩은 **0번** 항목을 읽는다. 바닐라 상자 라벨을 0번 슬롯 아이템으로 숨기는 데 이 성질을 썼다. `&#123;실측&#125;` (출처: BC-facts)
- **[COL-06]** 팩토리 없이 **고정 인덱스 슬롯**을 만들 수 있다: `collection_name`을 가진 스택 안에 `collection_index`를 박은 자식을 둔다. 스크립트는 항상 같은 개수의 엔트리를 보내(빈 값 포함) 인덱스를 고정한다. `&#123;작동팩, 코드&#125;` (출처: BA 5장 탭 28슬롯, BC 4.1-(3))

```json
"tab_slots": { "type": "stack_panel", "orientation": "horizontal",
  "collection_name": "form_buttons",
  "controls": [
    { "slot0@my.tab_cell": { "collection_index": 1 } },
    { "slot1@my.tab_cell": { "collection_index": 2 } } ] }
```

## 6.3 팩토리

팩토리는 두 가지 모양이 있다.

```json
// (가) 팩토리 컨트롤: type 이 factory. 바닐라 server_form 의 진입점
"server_form_factory": { "type": "factory",
  "control_ids": { "long_form": "@server_form.long_form", "custom_form": "@server_form.custom_form" } },

// (나) 컨테이너의 factory 속성: 스택/패널/collection_panel 이 셀을 만든다
"long_form_dynamic_buttons_panel": { "type": "stack_panel",
  "factory": { "name": "buttons",
    "control_ids": { "button": "server_form.dynamic_button", "label": "@server_form.dynamic_label",
                     "header": "@server_form.dynamic_header", "divider": "@settings_common.option_group_section_divider" } },
  "collection_name": "form_buttons",
  "bindings": [ { "binding_name": "#form_button_contents", "binding_name_override": "#collection_length" } ] }
```

- **[COL-08]** 팩토리는 (가) `"type": "factory"` 컨트롤(바닐라 36회, 공식 enum에 없음)이거나 (나) 컨테이너의 `"factory": { … }` 속성이다. `factory` 객체의 키는 `name`, `control_name`(한 종류) 또는 `control_ids`(종류별), `max_children_size`, `factory_variables`다. `&#123;바닐라&#125;` (출처: VN server_form.json:25·126, VN factory 키 집계)
- **[COL-09]** `control_ids`의 키는 엔진이 정한 **데이터 종류**이고, 값은 `"@ns.정의"`(바닐라 197회), `"인스턴스이름@ns.정의"`(36회), `"ns.정의"`(5회, 예 server_form.json:128)다. 액션 폼 행은 `button`, `label`, `header`, `divider`, 모달 행은 `label`, `toggle`, `slider`, `step_slider`, `dropdown`, `input`, `header`, `divider`, `multiselect`, HUD는 `hud_title_text`, `hud_actionbar_text`, 채팅은 `chat_item`이다. `&#123;바닐라&#125;` (출처: VN server_form.json:126·283, hud_screen.json:3406·3417·1040)
- **[COL-10]** **`visible`은 그리기만 막고 생성과 레이아웃은 막지 못한다.** 서버 폼 아래에 붙인 화면은 `visible`로 가려도 **모든 폼을 열 때마다 전부 생성·레이아웃**된다(5,546개 컨트롤 재배치 실측). 그 안의 슬라이더처럼 생성 시 상태를 검증하는 컴포넌트는 숨겨져 있어도 assert를 낸다. 컨트롤 자신의 `binding_condition: "visible"`도 조상이 숨었을 때 평가를 막지 못한다. `&#123;실측&#125;` (출처: BC-S8, BW-best)
- **[COL-11]** `#collection_length`를 바인딩하면 팩토리가 그 수만큼만 셀을 만든다. **0이면 아무것도 만들지 않는다.** `((#mode = 'on') * 1)` 같은 계산 길이로 "필요한 화면 하나만 생성"하는 게이트가 된다. `&#123;실측, 바닐라&#125;` (출처: BC-S11, VN server_form.json:138·300)
- **[COL-12]** 생성을 막는 방법 비교. `&#123;실측, 바닐라&#125;` (출처: BC-S8, BC-S11, VN)

| 방법 | 평가 시점 | 조건 재료 | 비용 |
| --- | --- | --- | --- |
| `ignored` | 컨트롤 생성 시 한 번 | `$변수`만 | 생성 안 함 |
| 팩토리 `#collection_length` | 런타임, 바인딩 | `#바인딩` 식 | 0이면 생성 안 함 |
| `visible` | 매 프레임 | `#바인딩` 식 | 생성·레이아웃 비용 그대로 |

- **[COL-13]** 행 타입 팩토리는 **매칭되는 모든 행마다** 셀을 만든다. 슬라이더 행이 셋이면 슬라이더 셀이 소켓마다 셋 생긴다. 자기 행이 아닌 셀은 `#anchored_offset_value_y`로 화면 밖으로 민다(`((not #mine) * 1000)`). `&#123;실측&#125;` (출처: BC-S9)
- **[COL-14]** 같은 이름의 엔진 팩토리를 **다른 위치에 한 번 더 선언**하면 같은 데이터로 두 번째 UI가 만들어진다. 세 팩이 모두 이 방법을 쓴다: `server_form_factory`(BC, BA), `hud_title_text_factory`(BA, AP), `chat_item_factory`(AP). `&#123;작동팩, 코드&#125;` (출처: BC 4.1-(1), BA 2장·6장, AP 4.1·4.5, BW-form, BW-intro)
- **[COL-15]** `factory_variables: ["$a", "$b"]`는 팩토리 호스트의 변수를 만들어진 컨트롤로 넘긴다. 엔진은 각 이름을 팩토리를 선언한 스코프에서 찾아 그 값을 넘긴다(COL-41). 바닐라에서 37회(store, pdp, marketplace_sdl, realms_settings, toast_screen 등) 쓰지만 이 프로젝트 출처 중 게임에서 실측한 곳은 없다. `&#123;바닐라, 코드&#125;` (출처: VN store_common.json 등 37회, NB-04)
- **[COL-16]** `max_children_size`는 팩토리가 만들 최대 개수다(바닐라 HUD 채팅 50, AP 토스트 12). 같은 데이터를 공유하는 두 번째 팩토리는 보이지 않는 항목도 한도를 소모한다. `&#123;바닐라, 작동팩, 추론&#125;` (출처: VN hud_screen.json:1041, AP 4.5)
- **[COL-17]** 엔진 팩토리가 만든 컨트롤은 데이터를 **변수로** 받는 경우가 있다. 바닐라 액션바 라벨은 `"text": "$actionbar_text"`를 쓰고, AP는 `hud_title_text_factory`가 만든 컨트롤에서 `$title_text`를 읽어 `ignored`로 판정한다. 변수는 생성 시 한 번 정해지므로 값이 바뀌면 팩토리가 컨트롤을 다시 만든다. `&#123;바닐라, 작동팩&#125;` (출처: VN hud_screen.json:2158, AP 4.1, 부록A C-28, BW-intro)
- **[COL-18]** 팩토리가 만드는 셀이 크면 화면 열기가 느려진다. BA는 노드 하나에 컨트롤 수백 개가 들어 모든 탭을 보내면 여는 데 수 초가 걸렸고, 선택된 탭의 노드만 보내도록 바꿨다. 셀 크기 × 개수를 줄이는 것이 먼저다. `&#123;작동팩&#125;` (출처: BA 4장)

## 6.4 폼 행과 응답 번호

- **[COL-19]** 1.26.50 바닐라의 액션 폼 컬렉션(`form_buttons`)에는 `button`뿐 아니라 `label`, `header`, `divider` 행도 들어온다. 응답의 `selection`은 버튼만 세므로 `label()`을 섞으면 컬렉션 인덱스와 `selection` 번호가 어긋난다. 데이터 채널로 쓸 때는 모든 엔트리를 `button()`으로 보내고, 누를 수 없는 셀은 버튼 매핑을 빼서 만든다. `&#123;바닐라, 코드&#125;` (출처: VN server_form.json:126-134, BC 4.1-(3))
- **[COL-20]** 모달 폼의 `custom_form` 행과 `formValues`는 1:1로 정렬된다. `label()`도 행이고 응답에는 그 자리에 `null`이 온다. `&#123;실측&#125;` (출처: BC-S3)
- **[COL-21]** 1.26.50 바닐라 `custom_form` 팩토리에 `multiselect` 행이 생겼지만 공개 Script API(`@minecraft/server-ui` 2.2.0~2.5.0-beta, `ModalFormData`와 `CustomForm` 모두)에는 이 행을 보내는 메서드가 없다. 폼 JSON을 직접 보내는 서버는 쓸 수 있다(HOST-46). `&#123;바닐라, 코드, 실측&#125;` (출처: VN server_form.json:294, MJ 4.1, MS)

## 6.5 Bedrock Wiki 대조로 더한 규칙

위키(BW) 문서를 바닐라 1.26.50.4와 대조해 더한 규칙이다. 위키 문장만 있는 것은 `미검증`, 위키의 게임 스크린샷이 있는 것은 `실측`(제3자 기록)으로 표시했다.

- **[COL-22]** `control_ids`를 가진 팩토리에 `#collection_length`로 **문자열 배열**(그 `control_ids`의 키 목록)을 주면 배열 순서대로 그 종류의 컨트롤을 만든다. 식에서 배열을 만들 수는 없으므로 `property_bag`에 배열을 미리 두고(`"#list1": ["apple", "label"]`), `('#list' + #choice)`로 이름을 조립해 고른다. `control_name` 팩토리는 정수를 받는다. `&#123;실측&#125;` (출처: BW-dyn 스크린샷 2장)
- **[COL-23]** 식이 만든 `'#이름'` 문자열은 같은 컨트롤의 `property_bag`에서 그 이름의 값으로 읽힌다(사전 조회). COL-22와 bedrock-core의 화면 라우팅(HOST-06 `('#route_' + #title_text)`)이 같은 메커니즘이다. 원리: 괄호 묶음의 결과가 `#이름` 문자열이면 그 컨트롤 주머니의 값으로 바뀐다(EXP-35). `&#123;실측, 코드&#125;` (출처: BW-dyn 스크린샷, BC 4.1-(2), CN-run)
- **[COL-24]** `#collection_length`로 직접 구동하는 팩토리는 컬렉션을 지원하는 컨테이너(`stack_panel`, `collection_panel`)의 `factory` 속성으로 둔다. 위키 예제는 `collection_name` 없이 `stack_panel` + `factory`만으로 동작했다. `&#123;실측&#125;` (출처: BW-dyn 스크린샷)
- **[COL-25]** `"type": "factory"` 컨트롤은 **컨트롤 이름이 곧 팩토리 이름**이다(`server_form_factory`). 두 번째 팩토리는 `"type": "panel"` + `"factory": { "name": "server_form_factory", … }`로 만들고, 컨트롤 이름은 원본·형제와 겹치지 않게 짓는다. 엔진은 `type: factory` 컨트롤에서 팩토리 이름을 따로 읽지 않고, 다른 타입은 `factory` 객체의 `name`을 읽는다(COL-42). `&#123;코드, 바닐라&#125;` (출처: NB-05, VN server_form.json, BW-form(이름 겹침 주의))
- **[COL-26]** 컬렉션과 함께 쓰는 팩토리·그리드는 만든 컨트롤에 인덱스를 자동으로 붙인다. `&#123;미검증&#125;` (출처: BW-dyn)

## 6.6 Cinnabar 엔진 재구성으로 더한 규칙

Cinnabar(`CN`)는 26.30 네이티브 클라이언트의 JSON UI 해석기를 재구성한 Rust 코드다. 수준은 `코드`이고, `CN-run`은 이 프로젝트가 그 평가기를 직접 실행한 결과다. 게임 실측과 다르면 실측을 따른다(부록A C-41~C-47).

- **[COL-27]** `#collection_length`는 정수, 불리언(1/0), 역할 이름 배열을 받는다. 리터럴 숫자 길이는 `control_name` 템플릿 팩토리에서만 그 수만큼 만든다. 팩토리에 없는 역할 이름은 아무것도 만들지 않는다. 엔진도 상점 화면에서 역할 이름 배열(`["tag", …]`)을 길이 값으로 준다(COL-46). `&#123;코드&#125;` (출처: NB-14(역할 이름 배열), CN 테스트 N12·B41(그 밖))
- **[COL-28]** `control_name`이 있으면 `control_ids`는 읽히지 않는다. 둘을 함께 두지 않는다. `max_children_size: 0`은 무제한이다. `&#123;코드&#125;` (출처: NB-06(`control_name` 우선), CN(`max_children_size: 0`))
- **[COL-29]** `control_name` 템플릿과 `grid_item_template`의 셀은 팩토리를 선언한 곳의 `$변수`를 본다. `control_ids`로 만든 컨트롤은 자기 변수와 `factory_variables`로 넘긴 변수만 본다. 엔진은 `control_name` 원형을 팩토리 해석 때 선언 스코프로 만든다(COL-45). `&#123;코드&#125;` (출처: NB-13(`control_name` 원형), CN, COL-15 보강)
- **[COL-30]** 엔진은 그리드 칸 수를 `#grid_number_size`, 팩토리 생성 수를 `#collection_number_size`, 컬렉션 크기를 `#collection_total_items`로 주머니에 쓴다. view 바인딩으로 읽어 "비었음" 표시 등에 쓸 수 있다. `&#123;코드&#125;` (출처: CN 테스트 B55·B41)

## 6.7 연구 서버 서버 실측으로 더한 규칙

연구 서버 서버(`DF`)를 만들며 Windows 1.26.52 에서 실측한 것이다. 서버 폼 하나로 여러 화면을 그리는 구조에서 얻었다.

- **[COL-34]** 클라이언트는 액션 폼의 `#form_button_length`를 지금까지 보인 **가장 큰 폼**의 버튼 수로 붙잡고 있었다(디버그 라벨 93, 재접속 뒤에도 93, `always_when_visible`로도 그대로). 이 값으로 격자 크기를 정하면 작은 폼에서 빈 칸이 이어진다. 칸 수는 본문 같은 데이터 채널로 따로 보낸다(EXP-45). `&#123;실측&#125;` (출처: DF)
- **[COL-35]** 줄바꿈 격자는 숨은 버튼에도 칸을 준다. 탭·뒤로·쪽 같은 표식 버튼은 칸 버튼 **뒤에** 보내고(앞에 두면 칸이 밀려 시작), 격자 크기에는 칸 버튼 수만 넣는다(넣으면 빈 줄이 하나 더 생겨 창이 몇 픽셀 스크롤됐다). `&#123;실측&#125;` (출처: DF)
- **[COL-36]** 팩토리·격자 길이를 `#form_button_contents`·`#form_button_length`의 식(`* 1`, `* (표식 일치)`)으로 계산하면 팩토리는 버튼을 만들지 않았고 격자는 식 자체가 됐다. 엔진 이름은 `binding_name_override`로 그대로 옮긴다. `&#123;실측&#125;` (출처: DF)
- **[COL-37]** 줄마다 버튼 전체를 걷는 스택을 두면(48칸 격자 + 재료 줄) 화면이 여는 데 4~5초 걸렸고, 칸마다 `collection_index`로 버튼 하나만 읽는 고정 배치(COL-06)로 바꾸니 1초쯤이 됐다. 칸마다 버튼도 하나만 둔다(누르는 것·안 누르는 것을 둘 다 두면 컨트롤이 두 배다). `&#123;실측&#125;` (출처: DF)
- **[COL-38]** `collection_index`는 `collection_name`을 가진 `stack_panel`의 바로 아래 자식에서만 먹었다. 그 자리를 `panel`로 두면 콘텐츠 로그에 `Unknown property [collection_index]`·`[collection_name]`이 찍히고 비었다(COL-01, COL-02와 같은 결론, 상자 화면 `container_items`도 같다). `&#123;실측&#125;` (출처: DF)
- **[COL-39]** 사전 조회 라우팅(HOST-06)은 동작했다: `stack_panel`에 `"property_bag": { "#df_layout_1": [ "on" ], "#df_layout_0": [] }`, `"factory": { "control_ids": { "on": "…" } }`, `#collection_length` ← `(('#df_layout_' + (조건 * 1)))`이면 조건이 맞을 때만 레이아웃이 만들어졌다. 멈춤·종료는 없었다(DBG-19와 다른 결과). `&#123;실측&#125;` (출처: DF)
- **[COL-40]** 그런데 우리 팩토리가 만든 레이아웃 **안에서는** 액션 폼 데이터가 격자(`grid` + `collection_name`)의 칸에만 닿았다. 고정 `collection_index` 칸은 비었고, `#form_button_contents`로 버튼을 만드는 안쪽 팩토리는 아무것도 만들지 않았다. `collection_panel`(`collection_name` 유무)·`stack_panel`·`control_name`·`control_ids` 모두 같았고, 칸 바인딩에 `always`를 줘도(BND-07) 그대로였다. `panel` + `factory`는 아무것도 만들지 않았다. 그래서 레이아웃이 버튼을 격자로만 읽을 때만 게이트를 쓸 수 있다. `&#123;실측&#125;` (출처: DF)

## 6.8 엔진 동작 분석으로 더한 규칙

Android 1.26.52.3 클라이언트의 네이티브 라이브러리를 분석해 읽은 것이다(`NB`). 수준은 `코드`다.

- **[COL-41]** `factory_variables`는 **배열일 때만** 읽고, 배열이 아니면 조용히 무시한다. 항목이 문자열이 아니면 `factory_variables should all be strings of json variables created higher up the tree.` 오류를 남긴다. 각 이름은 팩토리를 선언한 컨트롤의 스코프에서 찾아 그 값을 팩토리에 저장하고, 만들어진 컨트롤이 받는다(COL-15의 추론과 같다). `&#123;코드&#125;` (출처: NB-04)
- **[COL-42]** `"type": "factory"`이고 그 컨트롤에 `control_name`이나 `control_ids`가 직접 있으면 팩토리 이름을 따로 읽지 않는다(컨트롤 이름이 팩토리 이름, COL-25). 다른 타입은 `"factory": { … }` 객체가 있을 때만 팩토리를 만들고, 그 `name`이 비면 `The factory name should not be empty!`를 남긴다. `&#123;코드&#125;` (출처: NB-05)
- **[COL-43]** 팩토리는 `control_name`을 먼저 읽고 비어 있을 때만 `control_ids`를 읽는다(COL-28). `insert_location`은 값이 정확히 `"front"`일 때만 앞에 넣고 그 밖은 모두 뒤다(기본 `back`). `&#123;코드&#125;` (출처: NB-06)
- **[COL-44]** 컨트롤을 만들 때 **부모에 컬렉션 이름이 있는 컬렉션 컴포넌트가 있으면** 그 컨트롤은 자동으로 컬렉션 항목이 된다. `collection_index`는 이때만 읽혀(기본 -1) 인덱스를 고정한다. 그래서 `collection_index`는 컬렉션 부모의 직속 자식에서만 의미가 있다(COL-02, COL-38과 같은 결론). 직속 자식이지만 항목이 되면 안 되는 컨트롤(장식 패널 등)에는 `"ignoreCollectionItem": true`를 준다. `&#123;코드&#125;` (출처: NB-07)
- **[COL-45]** 팩토리 해석 경로: `"type": "factory"`이면서 `control_name`·`control_ids`를 직접 가지면 이름 없이 해석하고, 그 밖에는 타입과 상관없이 `factory`가 **객체일 때만** 해석해 `name`을 읽는다(`type: factory`에 `factory` 객체를 써도 된다). 컨트롤 하나에는 팩토리가 하나만 붙는다. `control_name`은 해석할 때 선언한 컨트롤의 변수 스코프로 바로 원형을 만들고, `control_ids`는 종류와 정의 문자열만 저장한다(COL-29의 차이). `max_children_size`는 생략하면 0이다. `&#123;코드&#125;` (출처: NB-13)
- **[COL-46]** 바닐라에 없는 `tags_factory_first_hidden_child_index`·`languages_factory_first_hidden_child_index`·`<접두어>_first_hidden_child_index`는 **상점 상세 화면 설명 컴포넌트 전용**이다. 속성 주머니의 이 정수로 몇 번째 태그·언어부터 숨기거나 다음 줄로 넘길지 정하고, 그 개수만큼 `"tag"`·`"language"`를 반복한 배열을 길이 바인딩 값으로 준다. 일반 팩토리 기능이 아니므로 서버 폼·HUD 팩토리에는 쓰지 않는다. 이 값을 누가 쓰는지는 확인하지 않았다. `&#123;코드&#125;` (출처: NB-14)
