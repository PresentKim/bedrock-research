# 결과물 점검표

이 페이지는 JSON UI 팩이나 그 설명을 만들어 남에게 넘기기 전에 보는 점검표다. 사람이 직접 만들 때도, AI에게 맡긴 결과를 검토할 때도 같은 순서로 쓴다. 규칙 ID는 [규칙 ID 전체표](../reference/rules.mdx)에서 원문을 찾는다.

## 근거의 무게

- 규칙의 수준은 **`실측` > `바닐라` > `작동팩` > `코드` > `추론`** 순으로 믿는다. `코드` 중에서는 실제 클라이언트를 읽은 `NB`가 재구성 코드인 `CN`보다 직접적이다([개요](./index.mdx)의 검증 수준).
- 커뮤니티 노트의 표시는 대략 이렇게 대응한다: *confirmed*나 여러 보고가 같으면 `작동팩`, *single report*는 `추론`, *unverified*와 **conflicting**은 `미검증`과 `충돌`이다.
- 규칙의 `실측`과 커뮤니티 보고가 다르면 규칙을 따른다. 커뮤니티 쪽에 버전이나 날짜가 있으면 버전이 바뀐 것일 수 있으니 둘 다 함께 알린다. 이미 알려진 차이는 [커뮤니티 보고와 대조](./community-reports.mdx)의 대조표(D-번호)에 판단과 함께 있다.
- `충돌`, `미검증`, *unverified*, **conflicting** 근거에 기댄 내용은 결과물에 단정하지 않고 "게임 확인 필요"로 표시한다.

## 지어내기 쉬운 것

아래는 그럴듯해 보이지만 없는 것이다. 결과물에 나오면 고친다.

- 연산자 `%`, `>=`, `<=`, `!=`, `==`, `&&`, `||`, 삼항, 사슬 비교 `(a < x < b)`(EXP-01, EXP-02, EXP-03). 범위는 `((a < #v) and (#v < b))`로 쓴다.
- `'%.' + #n + 's'` 같은 바인딩 값으로 만든 서식, `'%5.3s'` 같은 패딩 서식(EXP-25).
- `(#v * 1)` 숫자 변환(`(#v - 0)`이나 `(0 + #v)`를 쓴다, EXP-16, EXP-31), `0.5`처럼 앞자리가 있는 소수 리터럴(정수 0이 된다, EXP-27).
- 컨트롤 타입 `text`(실제는 `label`), `scroll_box`, `scrollbar_track`(LAY-01, LAY-02). 키 `grid_dimension`(실제는 `grid_dimensions`), `grid_fill_direction: left_to_right`(LAY-26).
- `resolve_ancestor_scope`(BND-01), 바닐라에 없는 렌더러 이름(ANI-05), 바닐라에 없는 바인딩 이름(`#player_health`, `#player_name`, `#item_aux_id`. 실제 아이템 바인딩은 `#item_id_aux`).
- 이미지 회전, 블러, 애니메이션 속성(`duration`, `fps`)의 바인딩, JSON UI에서 스크립트 호출, 커스텀 URL 열기.
- 리소스 팩으로 Ore UI 화면의 배치·동작 바꾸기. 26.64부터 막혔다(ALT-11). 평문 팩이 닿는 것은 게임 중 Ore UI 버튼의 텍스처와 글자색 정도다(ALT-15).
- 국제판 UI에 커스텀 모델이나 엔티티 그리기. `netease_paper_doll_renderer` 등은 중국판 전용이다(ANI-36).
- 옛 Script API: `runCommandAsync`, 메서드 `isValid()`(지금은 속성 `isValid`), `world.events.*`, `worldInitialize`, 안정판의 `chatSend`, server-ui의 `addButtonList`·`getSelectedButtonId`.

## 검증 체크리스트

보고하기 전에 하나씩 확인한다.

1. 새 파일을 `ui/_ui_defs.json`에 등록했는가. 바닐라와 같은 경로의 파일은 등록하지 않았는가(FILE-01).
2. `modifications`가 바닐라와 같은 경로 파일에 있는가(MOD-02). 배열을 직접 선언한 정의에 넣었는가(MOD-04). 바닐라 컨트롤을 `remove`하지 않았는가(MOD-05).
3. JSON이 엔진의 파서 규칙을 지키는가(뒤따르는 쉼표 없음, 키에 따옴표, FILE-30).
4. 모든 식이 괄호로 감싸였고 금지 연산자가 없는가. 모든 view 식에 `#속성`이 하나 이상 있는가(BND-05).
5. 숫자 변환이 `- 0`이나 `0 +`인가. 소수 리터럴이 `.`으로 시작하는가.
6. `'%.Ns'`의 N을 UTF-8 바이트로 셌는가. 색 코드 `§x`는 3바이트, 한글은 글자당 3바이트다(EXP-09, EXP-24).
7. 서버 폼 버튼 자신에 `collection_details` 바인딩과 `button.form_button_click` 매핑이 있는가(COL-04, INP-04).
8. `visible: false`로 숨겨서 화면을 고르지 않고 `ignored`나 길이 0/1 팩토리로 생성 단위에서 골랐는가(COL-10, COL-11).
9. 바닐라 컨트롤·바인딩·렌더러 이름을 대상 버전의 바닐라 파일에서 확인했는가.
10. 크기·위치 바인딩에 숫자가 아닌 값이 들어갈 길이 없는가(크래시, LAY-10, LAY-11).
11. 라벨의 `localize`가 의도와 맞는가(TXT-01).
12. 바닐라 사본(`bedrock-samples`의 `resource_pack`)이 있으면 정적 시뮬레이터 [mcbe-json-ui-tester](https://github.com/PresentKim/mcbe-json-ui-tester)로 화면을 돌려 엔진 오류 문구, 규칙 ID 경고, 가려진 라벨과 보이는 라벨 위치를 본다. 서버 폼은 제목과 버튼 글을, HUD는 타이틀 글을 넣어 돌린다. 프로젝트에 자체 검사기가 있으면 그것도 돌린다. 시뮬레이션과 정적 검사를 통과해도 게임에서 동작한다는 뜻은 아니다.

## 보고 형식

- 근거로 쓴 규칙 ID를 함께 적는다(예: "`(#v - 0)`으로 바꿨다(EXP-16)").
- 커뮤니티에서 온 내용은 그 노트 페이지와 시기를 밝힌다(예: "커뮤니티 노트, 2026-05 보고").
- `충돌`, `미검증`, *conflicting* 근거에 기댄 부분은 "게임 확인 필요"로 표시한다.
- 게임에서 확인하기 전에는 완료라고 하지 않는다. 정적으로 확인한 것과 게임에서 확인해야 할 것을 나눠 적는다. 실험이 필요하면 한 번에 하나만 바꾸고, 로그로 그 화면이 실제로 열렸는지 확인하고, 실험 화면을 따로 두는 방법을 제안한다(DBG-02, DBG-03, DBG-04).
