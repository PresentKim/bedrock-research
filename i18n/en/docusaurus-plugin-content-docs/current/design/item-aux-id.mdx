# Inferring numeric item IDs (aux) from the Script API

The JSON UI `inventory_item_renderer` draws an item from `#item_id_aux` = `numeric item ID * 65536 + data value` (ANI-06). Enchant glint adds 32768. Unlike drawing from a texture path, blocks show in 3D and glint shows ([research screen section 8.1](./server-form-research-screen.mdx#81-item-icons-v140)).

The problem is that a script has no way to know this number. This page researches how a behavior pack script can compute the numeric ID from an item name (`minecraft:diamond`, `bwiki:ruby`). It covers vanilla items and blocks, custom items and custom blocks.

Status: the layout rules of vanilla items, custom items and custom blocks are confirmed on 1.26.63 mobile (section 5). Vanilla numbers can be computed from a script. Custom items and blocks shift with the pack stack order, so a script cannot settle them (section 5.7). Script computation fits private servers and is not recommended for distributed add-ons (section 5.8). Ways to draw items without computing numbers, by placing the real item in an inventory slot and letting the engine draw it, are collected in section 6.

## 1. The Script API has no numeric ID

The typings of `@minecraft/server` 2.11.0 (stable), 2.12.0-beta.1.26.63-stable and 2.13.0-beta.1.26.70-preview.24 were checked.

| API | What it gives |
| --- | --- |
| `ItemType` | `id` (string), `localizationKey` |
| `ItemTypes` | `get(id)`, `getAll()` |
| `BlockType` | `id`, `localizationKey` |
| `BlockTypes` | `get(id)`, `getAll()` |
| `ItemStack` | The constructor is `(itemType, amount)`. There is no data value member |
| `BlockPermutation.getItemStack()`, `Block.getItemStack(amount, withData)` | Return an `ItemStack`. `withData` is block entity data |

- No member returns a numeric ID, runtime ID, legacy ID or aux. The docs of `getAll()` say nothing about the order of the results.
- `ActionFormData.button(text, iconPath)` in `@minecraft/server-ui` takes only a texture path. There is no overload that draws an icon from an item type.
- The only inputs a script has are the custom item and custom block lists from `ItemTypes.getAll()` and `BlockTypes.getAll()`, and their order. Vanilla numbers must be put into the script as a table per version.

## 2. Known facts and conflicts

### 2.1 The drawn number is the item registry runtime ID

The number JSON UI draws is the network runtime ID that the server sends in the item registry.

- In the item list of a 1.26.0 world captured with ProxyPass on 2026-02-24 (1905 items), diamond is 335, apple 285, wind charge 284, emerald 552 and chest 54. The Chest-UI 26.20 table (2026-05-18) has the same values, and 1813 of 1824 shared names are equal.
- The Dragonfly server appends custom items right after the vanilla numbers. The client never makes this layout on its own, yet on 1.26.52 Windows custom items and custom blocks were drawn from these runtime IDs * 65536 (Ore UI loading research).

So the numeric IDs come from the registry built by whoever opened the world (a dedicated server, or the client hosting the world). Inference from a script means reproducing the layout rules of that registry.

### 2.2 Vanilla layout

- Bedrock Wiki 26.50 table: vanilla spans -1246 to 883. Blocks are negative, items 0 and up.
- From 26.40, 32 data-driven items (spears, bundles, breeze rod, trial keys, wind charge, apple, glow berries and so on) moved to the end of the table. In 26.50 they are 852 to 883.
- Vanilla numbers change with each version. Diamond is 335 in 26.30 and 306 in 26.40 (C-33).
- On 1.26.63, sending apple as 883 (882 + 1 custom item) from the 26.50 table drew a wind charge. The layout of this range changed after 26.50. The 15 items below 852 were still right.

### 2.4 Custom blocks

| Record | Source |
| --- | --- |
| Negative numbers going down from just below the lowest vanilla number (from -1039 in 1.21.100). They do not shift vanilla. They do not draw from their ID | Bedrock Wiki revisions 1.20.20 to 1.21.100. The sentence is gone from the 26.44 revision on |
| Blocks do not shift vanilla numbers | Chest-UI `constants.js` |

| Custom blocks registered by Dragonfly drew as 3D pictures from their runtime ID * 65536 | Ore UI loading research (1.26.52) |

No registry capture with custom blocks exists yet.

### 2.5 The real number can be read when the item is in a slot

The client fills `#item_id_aux` of player hotbar and chest slots itself. No script computation is needed, but the item must really be in that slot, and a server form screen cannot read the inventory collection. It is used only as a reference to check inference.

## 3. Draft inference method

These are the steps for a script to get the numeric ID of a name `n`. Bold values are set by experiment.

1. If `n` is a vanilla item whose table number is below **P**, use the table number.
2. If `n` is a vanilla item whose table number is P or more, add the custom item count `C`. `C` does not exceed 1569.
3. If `n` is a custom item, line up the custom items in **order O** and use `P + k`, where `k` is its place (from 0).
4. If `n` is a vanilla block, use the table number.
5. If `n` is a custom block, line up the custom blocks in **order O'** and use **B** `- k`.

Values to settle:

| Value | Candidates | After the first experiment |
| --- | --- | --- |
| P (custom item start) | 852 in 26.50 | 853 on 1.26.63 (section 5.1) |
| Order O | Identifier order, file name order (subfolders first), path order, `ItemTypes.getAll()` order | Inside one pack, path string order. The `getAll()` order differed between runs |
| Whether C includes block items of custom blocks | Chest-UI leaves them out | It does not (section 5.3) |
| B (custom block start) | Just below the lowest vanilla number, -9745 | -9745 |
| Order O' | Identifier order, file name order, its reverse, `BlockTypes.getAll()` order | Reverse of path string order (section 5.3) |
| Vanilla table | Registry capture | Dragonfly's 1.26.60 `vanilla_items.nbt` matches the 1.26.63 results (section 5.2) |

A script cannot read the game version, so the vanilla table matches the one version the add-on targets.

## 5. Results

### 5.1 First experiment (mobile, 1.26.63, probe v1.0.0, 2026-11-14)

![The first probe menu. getAll() returned 5 custom items and 0 custom blocks](/img/design/item-aux-probe-menu.png)

![Numbers 840 to 903. Custom items sit at 853 to 857 in the order blue, spyglass, lime, yellow, red, and from 858 come the red shrub, shelf mushroom, spears and bundles](/img/design/item-aux-probe-840.png)

| Number | What was drawn |
| --- | --- |
| 850, 851, 852 | Banner pattern, spawn egg, end crystal. They are 849, 850 and 851 in the 26.50 table |
| 853 to 857 | Blue wool (b), spyglass (test), lime wool (c), yellow wool (d), red wool (a) |
| 858 to 889 | Red shrub, shelf mushroom, 7 spears, 17 bundles, breeze rod, ominous trial key, trial key, wind charge, apple (888), glow berries (889) |
| 890 and up | Empty |
| -1278 to -1247 | Empty |
| -1246 to -1215 | Vanilla concrete slabs and double slabs (3D) |
| -9776 to -9713 | Empty |

- The 5 custom items were placed from 853 in path string order (`a_last.json`, `aux_probe_test.json`, `m_mid.json`, `sub/k_sub.json`, `z_first.json`). That is neither identifier order nor file name order with subfolders first.
- `ItemTypes.getAll()` returned the custom items as a, d, c, test, b. That was the exact reverse of the registry order (b, test, c, d, a), but the second experiment gave a different order (section 5.3).
- There were 0 custom blocks. The block definitions lacked `minecraft:geometry`, so the game did not register them (local BDS content log: "Block needs both a geometry and material instances component"). So the empty block ranges are not a result. Probe v1.0.1 fixes this.

### 5.2 The 1.26.60 vanilla table

The `server/world/vanilla_items.nbt` that Dragonfly added in its 1.26.60 support commit (2026-10-28, gophertunnel 1.63.0) was decoded and compared with the 26.50 table. It has 2080 items, numbered -1251 to 884.

- 1.26.60 added `frostbite_spawn_egg` at 791. So numbers from 792 on are 1 higher than in 26.50: spawn egg 851, end crystal 852, red shrub 853, wind charge 882, apple 883, glow berries 884.
- There are new negative numbers: `icicle` -1247, `ice_crystal` -1248, `disc_press` -1251. The probe's -1247 and -1248 cells were empty. That looks like they are absent from a world without experiments, but this was not checked.
- Putting 5 custom items (from 853) into this table matches every measured cell: red shrub 853 + 5 = 858, apple 883 + 5 = 888. The wind charge drawn at 883 (1 custom item) in the research screen test also matches, as 882 + 1.

So on 1.26.6x the rules up to custom items are:

1. Vanilla numbers are the runtime IDs in that version's server data (Dragonfly `vanilla_items.nbt`).
2. P is 853 (red shrub), the first number of the shifting block. Vanilla numbers at P or above add the custom item count C.
3. Custom items are placed from P in the string order of their file paths inside the behavior pack.

A world where the 3 custom blocks registered, after adding `minecraft:geometry` to the block definitions.

![First menu of probe v1.0.1. 5 custom items, 3 custom blocks, 3 block items in getAll()](/img/design/item-aux-probe-menu-v101.png)

![Numbers -9776 to -9713. Diamond block at -9747, emerald block at -9746, gold block at -9745](/img/design/item-aux-probe-blocks.png)

- Custom blocks are placed downward from -9745 (= -10000 + 255). This matches the Discord claim of 2026-02-14. The old wiki revisions' "just below the lowest vanilla number" and "they do not draw from their ID" did not hold on 1.26.63.
- The order is the reverse of the file path string order. `z_first.json`, last in path order, gets -9745, and each earlier one goes one lower. Put differently, with n blocks in path order, the j-th (from 0) is `-9745 - (n - 1 - j)`. This differs from identifier order (a, b, c).
- The 3 block items of the custom blocks were in `ItemTypes.getAll()`, but they did not shift the item range. C counts custom items only.
- `ItemTypes.getAll()` returned c, a, d, test, b this time. The registry order is b, test, c, d, a, the same as in the first experiment. The `getAll()` order can change between runs, so it cannot be used to compute numbers. `BlockTypes.getAll()` returned b, c, a, which matched path order this time.

### 5.4 Rules so far (1.26.63, one behavior pack)

| Target | Numeric ID |
| --- | --- |
| Vanilla items and blocks | The runtime ID in that version's server data. Items at 853 or above add the custom item count C |
| Custom items | `853 + k`, where k (from 0) is the place in the item files sorted by path string |
| Custom blocks | `-9745 - (n - 1 - j)`, where j (from 0) is the place in the block files sorted by path string and n is the custom block count |

A script cannot read file paths, and the `getAll()` order cannot be trusted. So the numbers of a pack's own custom items and blocks must be put into the script as a table built from the file paths at build time. The only thing a script can do at runtime is count C with `ItemTypes.getAll()` (it was right, 5, in this world).

What remains:

- The order between packs when there are several behavior packs (pack stack order, or all packs' paths sorted together). Partly checked in section 5.5.
- Whether the path sort is byte order (when uppercase, digits, `_` and `-` mix). Checked in section 5.5.
- Whether other platforms (Windows, iOS) give the same result. Discord has a report that it is wrong on iOS.

| Number | What was drawn |
| --- | --- |
| 853, 854 | Pink (`c_extra`), light blue (`y_extra`). Extra pack |
| 855 to 863 | Blue (`a_last`), spyglass (`aux_probe_test`), orange (`B_upper`), lime (`m_mid`), purple (`m-dash`), magenta (`n10`), cyan (`n9`), yellow (`sub/k_sub`), red (`z_first`). Probe pack |

- The sort is case-insensitive. `B_upper` comes after `aux_probe_test`, and `n10` comes before `n9` (digits are not read as numbers), which is the "case-insensitive" prediction of section 4.4. `m_mid` comes before `m-dash`, so `_` sorts before `-`. In lowercased byte order `-` (0x2D) would come before `_` (0x5F), so this is not a plain byte comparison but a locale sort (the same result as JavaScript `localeCompare`). Only one pair separates `_` and `-`.
- Paths are not sorted together across packs. The 2 extra pack items came as one block before the probe pack items. For blocks too, the extra pack block got -9745 and the probe pack blocks continued below it.
- The extra pack was added later to a world that already had the probe on. Whether it sat above or below in the active list was not recorded.

### 5.7 Conclusion: what a script can do

| Target | From a script | How |
| --- | --- | --- |
| Vanilla items and blocks | Possible | The target version's vanilla table + C counted with `ItemTypes.getAll()` (only for 853 and up) |
| The pack's own custom items and blocks | Only when the pack is first | A table built from file paths at build time. When other packs come first, it shifts by their item and block counts |
| Other packs' custom items and blocks | Not possible | A script cannot know which pack an item belongs to, the pack order, or the file paths |

`getAll()` gives the right custom item count C but not the order. The pack order cannot be read through the API either. So the numbers of custom items and blocks cannot be settled when other packs are in use.

A practical setup:

1. Draw vanilla items and blocks from aux numbers (3D, glint).
2. Draw the pack's own custom items and blocks from texture paths in its own resource pack. Textures do not depend on the pack order.
3. Use a custom number table only where the pack can be fixed to come first (for example a world whose server sets the pack order).

### 5.8 Where to use it

Computing numbers in a behavior pack script and sending them to the UI is **not recommended for distributed add-ons.** An add-on cannot know which game version or which other packs it runs with. The vanilla table goes stale with every game update, and custom numbers shift when another pack comes first. A wrong number draws a different item, not an empty cell.

On a **private server it is the best method.** The operator fixes the game version, the pack list and the stack order, so a table that matches once keeps matching. It does not touch the player inventory, works in server forms and the HUD alike, and has no limit on the icon count. Rebuild the vanilla table when the server updates, and the custom number table when the pack setup changes. A custom server that sends the item list itself (Dragonfly and others) assigns the numbers, so it needs no inference at all ([HUD item icons section 3](./hud-item-icons.mdx#3-how-to-carry-a-numeric-id-in-the-title)).

## 6. Drawing from inventory slots without numbers

When a real item sits in a player or entity inventory slot, the client fills `#item_id_aux` of that slot itself (section 2.5). No number is computed, so vanilla items, custom items and other packs' items all draw correctly, with 3D and glint. The cost is borrowing player slots for a moment, or using a container screen.

These results were tested on 1.26.63 mobile (2026-11-14).

| Method | Screen | Slots used | Result |
| --- | --- | --- | --- |
| Back up slots, then fill them | HUD | As many as shown, for as long as shown | The method public add-ons use ([HUD item icons section 2.1](./hud-item-icons.mdx#21-inventory-mirror-the-public-waila-add-on)). It moves player items, so a backup and restore mismatch can lose them. Not tested on this page |
| Several empty slots + lock-checked freeze (section 6.1) | HUD | As many as shown, for 1 tick | All 6 were right even when restored after 1 tick. The most reliable |
| One slot + count-checked freeze (section 6.2) | HUD | 1 slot, 3 ticks per icon | All 12 were right at 3 ticks apart. At 1 tick apart, cells came out empty (no wrong icons). Stackable items only |
| Entity inventory screen | Container screen | 0 player slots | The engine draws the entity slots, so there is no timing issue. The screen setup and the ways to open it are in the [entity inventory UI plan](./entity-inventory-ui.mdx) |

What did not work:

| Attempt | Result |
| --- | --- |
| Reading inventory collections in a server form screen | All four tested rows (`hotbar_items`, `inventory_items` and others) were empty. Borrowing slots works only in the HUD |
| Reading bundle contents in the HUD | Only the bundle icon showed. The contents and fill amount were empty |
| Drawing an item entity with `live_horse_renderer` | Empty. Players and armor stands drew the same way (`#entity_id` set to the raw button text) |
| Using an entity holding the item as the icon | An invisible armor stand showed only the held item, but the held pose differs per item (flat items show as a side-on line, custom held poses), so it cannot stand in for an icon |

### 6.1 Several empty slots + lock-checked freeze

1. The script puts display items into empty main inventory slots (9 to 14 in the test) all at once. Display items get `lockMode = slot`, `keepOnDeath = true` and a recognizable `nameTag`.
2. On the next tick it sends one title. The HUD panel becomes visible with that title.
3. The HUD reads `hotbar_items` at `collection_index` 9 to 35. A hidden data panel per cell freezes `#item_id_aux` and `#item_lock_in_slot` at the moment it becomes visible, with `binding_condition: "visibility_changed"`.
4. The icon reads the data panel's values through `source_control_name` and `resolve_sibling_scope: true`, and shows only when the frozen `#item_lock_in_slot` is true.
5. The script clears the slots. The frozen icons stay while the title is up.

```json
"locked": {
  "type": "panel", "size": [ 18, 18 ], "collection_index": "$slot",
  "controls": [
    {
      "data": {
        "type": "panel", "size": [ 0, 0 ],
```

Put this panel inside a stack panel with `collection_name: "hotbar_items"`. The player's own items are not locked, so if the title arrives late and the slot is already empty or holds another item, the icon just stays hidden and no wrong icon is frozen.

### 6.2 One slot + count-checked freeze

Items go into one slot in turn, and the icons freeze one at a time. The k-th item (from 0) goes in as `k + 2` items, and the k-th frozen cell shows only when the count at that moment is `k + 2`.

- `#inventory_stack_count` is the count label text, not a number. Strip the format codes before comparing, as in `(((#inventory_stack_count - '§r') - '§f') = 3)`.
- A count of 1 did not match even against an empty string, so counts start at 2.
- The frozen cells take their step from the length of the title text (`LAC:a`, `LAC:aa`, ...). The title is sent on the tick after the item goes in.
- Without the count check, 1 tick apart shifted by one cell and froze a **different icon**. With the count check, 1 tick apart filled only the last cell and left the rest empty.
- Items that stack to 1, such as swords and tools, cannot change their count, so they cannot be used.

### 6.3 Device speed and risks

- With both methods, a late freeze gives an empty cell and never a wrong icon. Only the empty icons need a retry.
- In section 6.1, ticks only decide when the slots may be cleared. Section 6.2 needs a gap per icon, so failures grow on slow devices.
- The borrowed slots must be empty at the start. The test add-on does not start when they are full, and it clears display items (told apart by name tag) on join.
- Both methods are HUD only, and a player who opens the inventory screen while slots are borrowed sees the display items.
