# Content and rendering claim measurements

This page collects, by topic, the records measured with the same add-on as [Measuring unverified JSON UI claims](./json-ui-claims.mdx) that are not about JSON UI. Each topic page carries a short form of its result; the numbers and conditions are here.

## 1. Method

- Target: Windows 1.26.65.1, a single-player world. Measured on 2026-11-19 (one follow-up particle measurement on 2026-11-20).
- All test files are in the measurement add-on `json-ui-claims`. The download and the names of the test entities, blocks, particles and sounds are in the [measurement add-on](./json-ui-claims.mdx#8-measurement-add-on) section. Candidates that were not measured are in [items that could not be measured](./json-ui-claims.mdx#7-items-that-could-not-be-measured).
- The game language was Korean, with fancy graphics. For sound, the Windows audio session API read the maximum peak of the game process session for 9 seconds.
- Particles were spawned with `/particle` or with `/scriptevent bwiki:juc_particle <effect> <variable> <value>` (spawns 3 blocks in front of the player's view with a `MolangVariableMap`). Values were read through the color in `particle_appearance_tinting` and the size in the billboard `size` expression.
- Language and graphics mode were changed through the game options with the bedrock MCP `options_get`/`options_set` tools instead of the Ore UI settings screen, and set back to the original values (`graphics_mode` 1, `game_language` `ko_KR`) after the measurement. The language applied only after re-entering the world.

## 4. Particles

| Item | Setup | Result | Related |
|---|---|---|---|
| Particle counter | `v.spawn_counter = 0;` in the `creation_expression` of `emitter_initialization`, `v.size_counter = 0;` in its `per_update_expression`. The `emitter_shape_point.offset` expression raises `v.spawn_counter` by 1 and the billboard `size` expression raises `v.size_counter` by 1, each used as an index. 8 at once | the 8 particles sat 0.6 apart and grew in size one by one. Same sizes 2 seconds later | particles |
| `q.property` and `query.can_fly` in a particle | a particle emitted by an entity animation takes its size from `q.property('bwiki:size')` and its color from `query.can_fly`. An entity with property 8 and no `can_fly`, and one with property 2 and `minecraft:can_fly` | large red for the first, small blue for the second. The emitting entity's values | particles |
| `q.camera_rotation(1)` in a particle | color `q.camera_rotation(1) == 0 ? red : green`, size `0.1 + abs(value) / 180 * 0.5`. View yaw about -45 degrees | red in both first and third person, minimum size (value 0) | particles |
| `q.distance_from_camera` in a particle | fixed size, color `> 3 ? green : red`, about 5 blocks ahead | green (a value came through) | particles |
| Expiration expression `q.distance_from_camera > 50` | same position, fixed size, yellow | not visible (expired at once) | particles |
| `loop()` and `break` | `v.s = 0; loop(5, { v.s = v.s + 1; }); v.b = 0; loop(10, { v.b = v.b + 1; (v.b >= 3) ? { break; }; });` in `creation_expression` | `v.s` 5, `v.b` 3 | particles |
| `per_render_expression` counter | emitter `v.n = 0;`, `v.n = v.n + 1; v.my = v.n;` in `particle_initialization.per_render_expression`, size `v.my`, 6 emitted at once | all six always had the same size and grew together. It did not become a per-particle number | particles |
| `max_lifetime` expression counter | emitter `v.index = 0;`, `v.index = v.index + 1; return 2 + v.index * 2;` in `max_lifetime`, size `v.particle_lifetime * 0.025`, 5 particles | five size steps, the shortest-lived disappeared first | particles |
| `??` reassignment in `creation_expression` | `variable.r0 = (variable.r0 ?? 3);` | 3 with `/particle`, script `variable.r0` 1 gave 1, 0 gave 0 | particles |
| Entity variable | `v.ev = 1;` in the entity `pre_animation`, a particle emitted by that entity's animation reads `v.ev` | content log `unhandled request for unknown variable 'variable.ev'` | particles |
| `pre_effect_script` | `"pre_effect_script": "v.pe = 1;"` on the same emit keyframe | the particle read 1 | particles |

- `q.camera_rotation` was 0 in a particle regardless of the camera position. A particle shot in the view direction cannot be made with this query.
- `q.distance_from_camera` made `> 3` true in the color expression, and with the expiration expression `> 50` the particle disappeared at once. In the code this value is already filled in the same context before the expiration expression is evaluated (the emitter update fills it before the particle loop), so the reading that the value is empty when the expiration expression is evaluated is wrong `{code}`. The reference point the distance is measured from is unknown (it reads as the difference between the emitter position and the position of some object, but it was not settled whether that object is the camera). In a follow-up measurement (Windows 1.26.65.1, 2026-11-20) the color expression `> 6 ? 0 : 1` was red at distance about 3 and green at about 12, and the expiration expression `< 6` survived at distances 9 and 13 and disappeared at 2 and 5, matching the real distance. But `> 6`, `> 60`, `> 6 ? 1 : 0` and `6 < q.distance_from_camera` showed no particle at any distance from 2 to 13, so only the `<` results are explained and the `>` results are not `{measured}`.
- `??` kept a 0 passed by the script as a value. Reassigning with `v.x = (v.x ?? default)` in `creation_expression` did not erase the script value.
- The `max_lifetime` expression was evaluated once per particle, so an emitter counter could give each particle a number. With `per_render_expression`, every particle read the same value.

- `creaking_eyes` was not visible alone, and when drawn over the same geometry it showed only on faces whose depth matched the body. It looks like a material that draws only at equal depth, but the material definition was not checked. A comment in the vanilla creaking render controller also says this material is blended over another texture.
- `graphics_mode` 2 made the deferred query true even in a world with a pack that has no `pbr` capability. The option was written directly, so this result does not tell whether the VV choice on the settings screen is blocked. In this state the `texture_set` emission of that pack did not show.

## 8. Attachables

| Item | Setup | Result | Related |
|---|---|---|---|
| Bone name case | a bar in front of the face on attachable bones `Head` and `head` (pivot `[0, 24, 0]`), head moved up and down | both followed the head | items |

- Attachables using `binding` drew the box at the feet (root) with 1.12.0 geometry. After changing to 1.16.0, neither the `'rightitem'` string binding nor the `q.item_slot_to_bone_name(c.item_slot)` binding put the box anywhere on screen, and there was no log. So string binding, attachable `uv_anim`, and `loop` and `slot.hotbar` lookups in attachable `pre_animation` could not be judged and were removed from the add-on.
- The spear variables were checked in the files, not measured in game. Vanilla 1.26.50 `player.entity.json` declares `variable.fp_melee_spear_use_attachable_rotation_z`, `tp_melee_spear_use_attachable_rotation_z`, `fp_melee_spear_attack_attachable_rotation_z` and `tp_melee_spear_attack_attachable_position_z` as `public`, and vanilla `spear.animation_controllers.json` reads `c.owning_entity->query.ticks_since_last_kinetic_weapon_hit`.

- The non-square 48x18 and 160x8 terrain textures drew as they are on `material_instances` blocks. Their height is smaller than their width, so they were not cut into animation frames. Mipmaps at long distance were not checked.

## 11. Wiki example measurements

These are runs of the complete examples on the topic pages, with the code copied as is into a test pack. 2026-11-27, Windows 1.26.65, a creative flat world with cheats on. The test pack was made apart from the `json-ui-claims` add-on and is not in the repository. The only additions for reading results were `/scriptevent` handlers in the script (title, form, particle, entity spawn) and lines that write results to chat.
