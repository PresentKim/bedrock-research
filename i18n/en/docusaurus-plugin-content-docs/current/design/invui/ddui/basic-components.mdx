# Building basic components with InvUI

To see whether a chest screen can replace server forms (DDUI, CustomForm), a gallery test pack (IUC) redrew the Ore UI components that [ore-ui-react](https://github.com/PresentKim/ore-ui-react) supports in a chest screen. The screen is built the way the [entity inventory menu](../entity-inventory-ui.mdx) describes (the chest screen of an invisible container entity, redrawn with a resource pack). This page covers 25 basic components. Sliders are on [Building sliders with InvUI](./slider.mdx), and enhanced components such as item grids and input are on [Building enhanced components with InvUI](./enhanced-components.mdx).

The only path from the chest screen to the server is a slot button press (a quick move, [entity inventory menu section 2.5](../entity-inventory-ui.mdx#25-a-button-that-reaches-the-script)). The server passes values to the screen through slot item names (section 2.4 of the same page). Every component is built from these two paths alone.

Notation:

- Measured: checked on mobile 1.26.63 with a test pack outside the wiki (IUC, `invui-components`), 2026-11-16. The version in parentheses is that test pack's version. The "Measured (example add-on v1.0.0, ...)" line in each component of section 3 was checked with the example add-on of this wiki.
- Tester: static simulation in the [JSON UI tester](../../../tools/jsonui-tester.mdx) (jsonui-tester).
- Mock: a Node run that imitates `@minecraft/server`.
- *Inference*: a cause guessed from a result. It was not tested on its own.

Sizes and colors were copied from the ore-ui-react CSS (1 GUI px = 0.2rem). The original CSS marks most values as estimates itself, so they can differ from the in-game Ore UI.

## 1. Shared framework

### 1.1 Window

The window is a dark 410x214 panel. The top row has `InvUI`, the page name, `<` `>`, a Pages button, and the version with the page number. The bottom row is a status line that shows the last press the server handled. Pages are drawn in the 394x168 area between them.

### 1.2 Pages are visibility panels

All page panels are built at the start, and each one is visible only while the name in slot 1 (the page key) equals its key.

```json
"gate": {
  "type": "panel", "size": [ 394, 168 ], "collection_index": 1,
  "bindings": [
    { "binding_type": "collection", "binding_collection_name": "container_items", "binding_name": "#hover_text", "binding_condition": "always" },
    { "binding_type": "view", "binding_condition": "always", "source_property_name": "((#hover_text - '§o' - '§f' - '§r') = 'toggle')", "target_property_name": "#visible" }
  ]
}
```

- At first a factory cell keyed by the page key built each page. No slot reads inside the pages worked. The toggle and the checkbox appeared only for a moment, with their animation, at the instant of a page change (measured, v1.1.0). Collection and view bindings inside controls built by a keyed factory seem not to work (*inference*). So pages became visibility panels, and page switching worked (measured, v1.2.1).
- So that hidden pages do not keep evaluating slots, the generator changes `binding_condition` from `always` to `visible` for page bindings that do not set `#visible`. The visibility bindings of the page panels and of the page picker stay `always`.
- This change must copy each binding object. When the generator edited a shared binding object in place, the slot reads of the page panels also became `visible` conditioned. Only the page opened first was shown, and after moving to another page no page showed again, even after coming back. A hidden panel does not read its slot again, so it never became visible again (measured, v1.2.0). Copying the bindings fixed it (measured, v1.2.1).

### 1.3 Slot layout

The entity has 243 slots (HOST-16).

| Slot | Content |
| --- | --- |
| 1 | Page key |
| 2, 3 | Page name, status line |
| 4 | Page picker state (`open`, `closed`) |
| 5 | Footer (version, page number) |
| 6, 7, 8 | Pages, `<`, `>` buttons |
| 10 to 189 | Slots used by the current page. Page number n is slot 10 + n |
| 190 to 214 | The 25 page picker buttons |

On a page change the script clears slots 10 to 189 and fills only the new page's button slots with button items.

### 1.4 Page modules

A page is a pair: the script module `bp/scripts/pages/<key>.js` and the generator module `tools/pages/<key>.mjs`.

| Script module `page` | Content |
| --- | --- |
| `key`, `title` | The page key (slot 1) and the name shown on screen |
| `slots` | Names for page numbers. The generator and the script use the same numbers |
| `buttons` | The page numbers used as buttons |
| `init()` | The first state. It is kept per player and per page, so it survives a visit to another page |
| `render(state)` | `{ number: text }`. The script writes only changed slots, as paper names |
| `press(state, n)` | Handles button n. The returned text goes to the status line |
| `tick(state)` | Optional. Called every tick (toast lifetimes, the self-filling progress bar) |

- The script module uses no game API, so the generator can import it as is.
- The generator module exports `ui = { page, build(ctx) }`. `ctx.slot(n)` turns a page number into a slot number and checks the range. `ctx.def(name, body)` makes a `<key>_<name>` definition and returns its reference text.
- `gen-ui.mjs` collects the slot numbers of buttons mapped to `button.container_auto_place` in the UI, checks that they equal `buttons`, and stops if they differ.
- `check-page.mjs` starts each page from its first state, presses each button once and runs a tick, and checks that `render` never writes a button slot, that every value is text, and that no value is digits only (section 2).

### 1.5 Page picker

Pressing Pages makes the server write `open` to slot 4, and 25 page name buttons (5 columns by 5 rows, 74x14 each) appear on a cover panel at layer 40. Pressing one goes to that page and closes the cover. The test pack had 45 picker buttons on the same cover with no diagnostics in the tester (v1.4.0). The 25 button layout is new in this example add-on and was not checked in the tester.

## 2. Drawing rules

| Rule | Evidence |
| --- | --- |
| A label draws only text. A slot name of digits only, or a value that starts with a digit after an expression, becomes a number and is not drawn | [Entity inventory menu section 2.4](../entity-inventory-ui.mdx#24-drawing-from-slot-names-lore-and-durability) (measured), EXP-30. A digits-only NumberInput value did not show (measured, v1.2.1) |
| Values that start with a digit get a format code in front (`§0`, `§r`), or are read by a label that removes only `§o` and keeps `§f` (`keepFormat`) | Badge numbers drew with `§r` and `keepFormat` (measured, v1.4.2) |
| Text and icons added to a slot button go into a layer 20 panel that is always above the button faces | Accordion titles were hidden by the button face (measured, v1.3.0) |
| Text gets a higher layer sum than the fill under it | Below |
| A slider's default bar and hover bar are not the same control | Below |

Layer sums. PlayerList names and Badge numbers did not show (measured, v1.4.1). Both texts sat on a fill with the same layer sum (the sum of all ancestor layers). Raising the text layer in every such place made all the missing text show (measured, v1.4.2). The inference is that with equal sums the fill can cover the text (*inference*). The NumberInput value text also had the same sum of 4 as its field fill (*inference*, raised in v1.4.0). From v1.4.2 the test pack checks each page, in its first state and after four button presses, for drawings with an equal or higher layer sum that cover the middle of a text (tester). For the same reason the selected text of Segment and Tabs, the active text of Chips, and the Toast text were raised too. None of these was seen hidden.

Slider bars. When one slider control used the same bar for `default_control` and `hover_control`, the dark track disappeared while a finger was on the slider (measured, v1.1.0). A separate hover bar fixed it. Details are on [InvUI sliders](./slider.mdx).

### 2.1 Replaying animations

Drawings that replay when a server value changes, such as the toggle thumb, the check mark, the tab panel, the carousel track and toasts, go in a small factory cell keyed by a slot name (`keyedCell`). A new key builds a new control, so its animation starts from the beginning ([entity inventory menu section 8.2](../entity-inventory-ui.mdx#82-animation-replay), ANI-37, COL-22). These cells mostly hold drawings without bindings. If the *inference* in section 1.2 holds, bindings inside a keyed factory may not work. Only the TextBlock variant cell holds a slot label inside. In the example add-on measurement, changing the variant changed the lines (section 3.18).

## 3. Components

All 25 were run in game with example add-on v1.0.0 and behaved as designed. Each component ends with that measurement and its clip. In the test pack, every component had no diagnostics in the tester and no errors in the mock after pressing every button and running 40 ticks (v1.1.0, v1.4.0).

- Shows: a 32x15 base (a white bar on the green left half, a ring on the gray right half) and a 17x17 thumb that rises 2 above it. A disabled example that cannot be pressed sits beside it.

- Measured: a toggle built the same way switched with every server answer in the input test pack (probe v1.3.0). In IUC, while pages were keyed factories (v1.1.0), it showed only at the instant of a page change.

### 3.25 Breadcrumb

- Shows: a path of up to 5 levels and up to 4 items under the current level.
- Build: the 5 path cells and 4 item cells are slot buttons. The server writes `link`/`current`/`none` per path cell, and `dir`/`leaf`/`none` with a name per item. A press on an earlier level goes back, and a press on an item goes in. Names are written with `§7`, `§f` or `§r` in front and read with `keepFormat`.

Measured (example add-on v1.0.0, mobile 1.26.63, 2026-11-16): the path went into Worlds, Creative and Backups and back to Home, and the empty level message showed.

## 4. Example add-on

1. Open the file to import it (on mobile, tap the file and open it with Minecraft). In a new world, turn on the behavior pack whose name starts with `[bedrock-research]inventory-ui-basic-components-bp`. The resource pack turns on with it as a dependency.
2. Take "Inventory UI Basic Components" (map) from the end of the items category of the creative inventory, or use `/give @s bwiki:inventory_ui_basic_components_test`.
3. Hold the item and tap the middle of the screen to open the gallery (the entity in front of the view, C2 in [entity inventory menu section 3](../entity-inventory-ui.mdx#3-ways-to-open-the-screen)).
4. Change pages with `<` `>` and Pages and press the components. The status line at the bottom shows the press the server received.
