# Building enhanced components with InvUI

This is one of the pages on a gallery test pack (IUC) that drew Ore UI style components in a chest screen to see whether a chest screen can replace server forms (DDUI, CustomForm). The screen is built the way [Building menu screens from an entity inventory](../entity-inventory-ui.mdx) describes (the chest screen of an invisible container entity, redrawn with a resource pack). Basic components such as toggles, buttons and tabs are in [Building basic components with InvUI](./basic-components.mdx), and sliders and the drag split experiments are in [Building sliders with InvUI](./slider.mdx). This page covers 17 components that combine many slot buttons or need much server-side computation.

In a chest screen, the only paths to the server are slot presses (quick move) and changes to slot items. The server gives values to the screen through slot item names (entity inventory page sections 2.4 and 2.5). Every component below uses only these two paths.

Labels:

- **Measured**: checked in game with the IUC test pack (`invui-components`). 1.26.63 mobile, 2026-11-16. The version in parentheses is the test pack version the record comes from. The "Measured (example add-on v1.0.0, ...)" line in each component was checked with the example add-on of this wiki.
- **Tester**: no diagnostics in the [JSON UI tester](../../../tools/jsonui-tester.mdx) static simulation.
- **Mock**: a Node run imitating `@minecraft/server` pressed every button and ran ticks without errors.
- *Inference*: an interpretation that no test separated.

## 1. Shared frame

### 1.1 Window and slot layout

The window is a dark 410x214 panel. The top row has the page name, `<` `>` and a Pages button, and the bottom row has the status text written by the server. The entity has `inventory_size: 243`.

| Slots | Content |
| --- | --- |
| 1~8 | Frame: page key, page title, status line, picker state (`open`/`closed`), footer, Pages, `<`, `>` |
| 10~189 | Slots used by the current page. Inside a page they are numbered 0~179 |
| 190~206 | 17 page picker buttons (5 columns) |

On a page change the server clears slots 10~189 and fills only the button slots of the new page.

### 1.2 Pages are visibility panels

All pages are built up front, and only the panel whose page key matches the name in slot 1 is visible. The generator changes the bindings outside the visibility decision to `binding_condition: "visible"`, so hidden pages do not evaluate them. Only the bindings that decide visibility stay `always`.

- The first build chose pages with a factory cell keyed by the page key. None of the slot reads inside it worked (measured, v1.1.0). Collection and view bindings appear not to work inside controls made by a factory (*inference*).
- The first visibility panel build showed only the page opened first. The generator edited a shared binding object in place, so the slot reads of the page panels also got the `visible` condition, and a hidden panel never read its slot again to become visible (measured, v1.2.0). Copying the binding before changing it made page switching work (measured, v1.2.1).

### 1.3 Page modules

Each page has one script module (`bp/scripts/pages/<key>.js`) and one UI module (`tools/pages/<key>.mjs`). The script module uses no game API, so the generator imports it as is and checks that the slot buttons placed in the UI match the script's button list.

| Field | Content |
| --- | --- |
| `buttons` | Page slot numbers used as slot buttons |
| `init(env)` | Initial state per player and page. `env` has `playerId` and `playerName` |
| `render(state, env)` | Returns, per slot number, text (a paper name) or `{ item, count, name, marker }` (a real item) |
| `press(state, slot, env)` | Handles a slot button press. The returned text goes to the status line |
| `tick(state, env)` | Work every tick (countdown, drag settling) |
| `sense(state, read, env)` | Reads the items in the page slots every tick. `read(n)` returns `{ item, count, marker }` or nothing |

Pages leave requests in their state instead of calling the game API. The frame handles and clears the requests after `press` and after `tick`.

```js
function applyRequests(player, state) {
  if (state.animation) {
    player.playAnimation(state.animation);
    delete state.animation;
  }
  if (state.collectMarkers) {
    collectMarkers(player);
    delete state.collectMarkers;
  }
}
```

Items written with `marker: true` carry lore unique to this add-on. `collectMarkers` removes items with that lore from the player inventory and the cursor (`cursor_inventory`). Slot button items carry different lore, and the server removes them from the player inventory every tick.

### 1.4 Text and prebuilt variants

- A label did not draw a value the server wrote as a digits-only slot name (measured, v1.2.1, NumberInput). Slots that show numbers get a leading `§r`. `tools/check-page.mjs` reports a digits-only value as a failure.
- Values that start with a digit, or keep color codes, are drawn by a label that removes only `§o` (table cells, countdown time, shop messages).
- When a text and the background under it have the same layer sum, the background can cover the text (*inference*). Raising the text layer in those places made all the missing text appear (measured, v1.4.2). Text and icons added to slot buttons sit in a layer 20 panel, so they always draw above the button face.
- Continuous values (bar widths, chart heights, colors) pick one of several prebuilt variants with a slot name key. A factory cell picked by key holds only static drawings without bindings (the measurement in section 1.2). A factory cell is rebuilt when its key changes, so an animation inside it plays again from the start (entity inventory page section 8.2).

## 2. Input components

### 2.1 TextInput

There is a name field (16 characters) and a password field (12 characters), with an on-screen keyboard below. The keyboard has four rows (digits, `qwertyuiop`, `asdfghjkl`, `zxcvbnm`) plus Shift (caps lock), Back, Clear and Space. The password is masked with `*`, and an eye button shows it. ## 5. Components whose rows the server computes

For a list whose row count changes, the UI does not create rows. The server computes the visible rows, writes them in order into fixed row slots, and writes an empty value (`off`, `none`) into the rows left over.

### 5.1 Table

A 12 player leaderboard (Player, Kills, Deaths, Score). Tapping a header sorts by that column, and tapping it again flips the direction. Tapping a row selects it, and Prev and Next go 5 rows at a time. At the ends the paging button becomes a drawing that cannot be pressed.

- The server sorts and pages, and writes into 5 row slots (20 cell slots and 5 row state slots). The sort column and direction go through one slot name (such as `c3d`) that picks the header arrow.
- A row button stands for a row position on screen, not a player. The server finds the player at that position in the list currently shown.
- Checked: tester, mock (v1.4.0), example add-on measurement (below).

Measured (example add-on v1.0.0, mobile 1.26.63, 2026-11-16): sorting by Score showed the arrow on the header, and Prev and Next paged the rows.

## 6. PatternLock

A lock pattern drawn by dragging sticks through a 3x3 grid of dot cells. The drawing order shows as numbers on the dots. The first pattern of 4 or more dots is saved, and later patterns are compared with it. Set / Unlock switches the mode, and Forget removes the saved pattern.

Measured (example add-on v1.0.0, mobile 1.26.63, 2026-11-16): drawing 1-2-3-6-5-8-9 saved the pattern. A different drawing gave "Wrong pattern" and the same one gave "Unlocked". While dragging, the vanilla item hover box showed the stick name and lore ("Drag me", "Inventory UI Enhanced Components marker") next to the finger.

<video controls preload="none" width="100%" poster={require('@site/static/img/design/invui/ddui/enhanced/patternlock.jpg').default} src={require('@site/static/video/invui/ddui/enhanced/patternlock.webm').default} />

### 6.1 Drawing with a drag split

The dot cells and the stick cell use vanilla chest slot mappings instead of slot buttons (`button.container_take_all_place_all`, `button.container_take_half_place_one`, `button.coalesce_stack`, `button.shape_drawing`, `button.container_slot_hovered`). The stick cell holds 64 marker sticks.

1. Tap the stick cell to pick up the sticks.
2. Without lifting the finger, drag across the dot cells. The engine splits the sticks over the cells it passes.
3. Every tick the server reads the marker stick count of each dot cell with `sense` and adds the cells whose count grew to the path.
4. When the cells have not changed for 20 ticks, the drag counts as settled and is judged. Each dot counts once.
5. After judging, the server empties the dot cells, refills the stick cell to 64, and removes the marker sticks from the player inventory and the cursor with `collectMarkers`.

With fewer than 4 dots the result is "Too short"; in set mode the pattern is saved; in unlock mode the result is "Unlocked" or "Wrong pattern".

### 6.2 Checked

- Saving, "Wrong pattern" and "Unlocked" came out right (measured, v1.4.8). A result appears only after settling, so the settling step also ran in game (*inference*).
- In DragLab, which tested the same drag method, tapping the stick cell and then dragging made the server receive the passed cells in order, almost every tick. Passing 11 cells put 5 sticks in each with 9 left in hand. Holding the stick cell and dragging right away placed nothing. Passing a cell again changed nothing. Stopping outside a cell left the item held (measured, v1.4.5).
- So the server settles and resets on its own. Imitating a drag and waiting 25 ticks emptied the cells, brought back 64 sticks and removed the marker sticks from the player inventory (mock, v1.4.6). There is no game record of whether marker sticks on the cursor are collected.
- When the server refilled the stick cell during a drag, the held stack was released and the drag ended (measured, v1.4.9). Only emptying the cells runs the sticks out (measured, v1.4.8). So the server cannot know that a drag passed the same cell twice, and PatternLock counts each dot once. The experiments are described in [Building sliders with InvUI](./slider.mdx).
- Tester and mock (v1.4.8): drawing 1-2-3-6 saved the pattern and put 1, 2, 3, 4 on the dots. The same pattern gave "Unlocked", 1-4-7-8 gave "Wrong pattern", and two dots gave "Too short".

## 8. Example add-on

<AddonDownload id="inventory-ui-enhanced-components" />

1. Open the file to import it (on mobile, tap the file and open it with Minecraft). In a new world, turn on the behavior pack starting with `[bedrock-research]inventory-ui-enhanced-components-bp`. 3. Hold the item and tap the middle of the screen to open the window. The first page is TextInput.
4. Use `<` `>` to move between pages, or press Pages to pick one of the 17. The bottom line shows the last press the server handled.
5. On the PatternLock page, tap the stick cell on the left once to pick the sticks up, drag through the dots without lifting, then lift. The result appears a second later. The frame clears the page slots when you leave for another page, so the page's `enter` refills the sticks when you come back.

- The text on screen is in English.
- The entity name is `§b§w§i§u§e` and the UI namespace is `iuenh`. Hiding vanilla uses the same marker `entity_ui_hide_vanilla` and property `#entity_ui_vanilla_visible` as the other examples.
- The generator is in `tools/`. `node tools/gen-ui.mjs` rebuilds `rp/ui/iuenh.json`, and `node tools/check-page.mjs <key>` checks a page's button list and slot names.
