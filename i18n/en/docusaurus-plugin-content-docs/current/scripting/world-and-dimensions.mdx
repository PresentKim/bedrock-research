## Getting a dimension and querying entities

`Dimension` is the central entry point for querying and changing world state (spawning entities, changing blocks, placing terrain features and so on). You get a dimension with `world.getDimension("overworld")`, and it is better for performance to get it once and reuse it (Source: ms-learn, `creator/Documents/scripting/world-apis.md`).

```javascript
import { world } from "@minecraft/server";
const overworld = world.getDimension("overworld");

// entity query: filter with EntityQueryOptions
const skeletons = overworld.getEntities({ type: "minecraft:skeleton" });

// players only
for (const player of overworld.getPlayers()) {
  player.runCommand("say Hello from script");
}
```

`EntityQueryOptions` filters by location, distance, type, name, property values and so on. The same options can be given to `getPlayers()`.

## Reading and writing blocks

Pick blocks with `getBlock(location)`, `getBlockAbove/Below` and `getTopmostBlock`, and get several cells with `getBlocks(volume)`. Writing is `setBlockType` and `setBlockPermutation`, and filling an area is `fillBlocks(volume, permutation)`.

```javascript
const location = { x: 10, y: 64, z: 10 };
const block = overworld.getBlock(location);      // the chunk must be loaded
const top = overworld.getTopmostBlock({ x: 10, z: 10 });
overworld.setBlockType({ x: 15, y: 65, z: 15 }, "minecraft:diamond_block");

const biome = overworld.getBiome(location);       // biome query
```

The practical tips are these. Use `setBlockType` for one cell and `fillBlocks` for a wide area, and use `spawnEntity` and `spawnItem` only in loaded chunks. For player interaction use `getPlayers` instead of `getEntities`. Split very large areas with `system.runJob` and a temporary ticking area (Source: ms-learn, `world-apis.md`, `system-run-guide.md`).

## World-wide API

`world` has `getAllPlayers`, `getDimension`, `getEntity(id)`, `getDay`, `getTimeOfDay/setTimeOfDay`, `getAbsoluteTime`, `getMoonPhase`, `getDifficulty`, `gameRules`, `seed`, `scoreboard`, `structureManager`, `tickingAreaManager`, `getLootTableManager`, `getPackSettings`, `playMusic/queueMusic/stopMusic` and so on (Source: ms-learn, `World.md`).

```javascript
world.setTimeOfDay(1000);
world.gameRules.doDayLightCycle = false;
world.sendMessage({ translate: "my.pack.welcome" });
```

## Particles, sound, camera

`Dimension.spawnParticle("minecraft:...", location, molangVariables)`, `Player.playSound`, `Dimension.playSound`, `player.camera.setCamera(...)`, and on the screen UI side `player.onScreenDisplay.setTitle/setActionBar` are the basic effect APIs. The particle and sound definitions themselves are resource pack data, and the script only calls them. These are world-changing calls, so in a `before` event defer them with `system.run`.

```javascript
overworld.spawnParticle("minecraft:totem_particle", { x: 0, y: 70, z: 0 });
player.playSound("random.levelup");
player.onScreenDisplay.setTitle("§6Welcome", { fadeInDuration: 10, stayDuration: 40, fadeOutDuration: 10 });
```

## Debug shapes

The debug shapes of `@minecraft/debug-utilities` draw spatial information in the world. There are `DebugBox` (collision range, area), `DebugSphere` (radius), `DebugLine` (connecting points), `DebugArrow` (direction), `DebugCircle` (range) and `DebugText` (3D label), and runtime statistics are handled with `collectRuntimeStats()`, plugin statistics with `collectPluginStats()`, and warning thresholds with `disableWatchdogTimingWarnings()` (Source: ms-learn, `creator/Documents/scripting/developer-tools.md`). Do not use them in add-ons for public release.

## Custom dimensions

Custom dimensions are registered with `dimensionRegistry` in `system.beforeEvents.startup`, and were stabilized around 26.30 (there is also a report that it was 1.26.20). The notes below summarize the registration method and limits.

## Community notes

Below are details and workarounds on blocks, chunks, structures and effects gathered from the community research.


`*confirmed*`, `*single report*` and `**conflicting**` are reliability marks for reports. The basis of this page is community reports, and they may differ from the official Mojang documentation.

### Blocks, dimensions, chunks, structures

#### Block and BlockPermutation

- **Position**: `block.location` is the integer corner -> the center is `block.center()`/`bottomCenter()`. A report that `block.x/y/z` are pure values so cheaper than `block.location`, and a report that destructuring `{x,y,z} = block` makes several API calls so read `block.location` once, conflict (**conflicting**; either way cache repeated access). Most APIs accept any object with x/y/z. Property access such as `entity.location` is also an API call.
- **Neighbors**: `above()/below()/north()/south()/east()/west()`, `offset()`. At the top of the world `above()` is air, and at the bottom `below()` throws. Next upper air: `block.above()?.isAir`. `Block.typeId` cannot be undefined, and the block itself is undefined only in unloaded chunks.
- **Permutations**: `BlockPermutation.resolve(id, states)` (new from type + full states), `perm.withState(name, value)` (derived from an existing one), `getState`, `getAllStates()` (a record), `block.setPermutation`, `block.setType("air")` (no resolve needed). Copying state: `target.setPermutation(source.permutation)` or `BlockPermutation.resolve(target.typeId, origin.permutation.getAllStates())`. Serialization (no `toJSON`): `typeId + '|' + JSON.stringify(getAllStates())`. Valid values: `BlockStates.get('age').validValues` (min/max summed across states of the same name; a non-iterable array) or try/catch `withState`. Cycling states `(cur+1) % count`. Deprecated states are also exposed. If you put a state value not in the block JSON into `withState`, you get "Failed to set property", so put the same value with `/setblock` to separate the cause. JSON block states have ~16 values per state. Codec between numeric data values and states: `https://gist.githubusercontent.com/WavePlayz/63a3bc1cdd8426450780b19762dc17f5/raw/minecraft-block-state-codec.js` (1.26.53, based on intrinsicblockstateslist).
- **Block updates**: `setPermutation`/`setType` do not cause block updates (doors and levers, and vanilla multi-blocks become half doors) -> change to air and then place again. For double blocks such as doors, `setType` fails, so `runCommand("setblock ...")`. Open/close of custom blocks goes through custom component state (instead of setblock in events).
- **Multi-blocks** (`minecraft:multi_block_part`, vertical only): `block.getParts()` (including itself, the order is observed to be the same as the `multi_block_part` state; undefined for chests and beds), the state must be set on all parts (`setType`/`setPermutation` on one part breaks or duplicates the block), and rotation is `withState("minecraft:cardinal_direction", ...)` on each part permutation. `BlockComponentBlockBreakEvent.brokenBlockPermutation` has no `getParts()`. Custom doors use the multi-block feature. There is no state change event. Canceling a multi-block placement leaves ghost parts.
- **Beds**: No color state (stored in the block entity, `localizationKey` is always white; `getItemStack().localizationKey.split('.')[2]` worked in some versions) -> colored beds only via structures. Placement needs both halves: `BlockPermutation.resolve("minecraft:bed", {head_piece_bit, direction})`, direction 0..3 = south, west, north, east (head offsets z+1, x-1, z-1, x+1). A sleeping pose teleport feature for custom beds was added.
- **State-related facts**: Water is always `minecraft:water` (source/flowing is the liquid depth state), `block.isWaterlogged`, `setWaterlogged(bool)`, `canContainLiquid("Water")`/`BlockPermutation.canContainLiquid`, `isLiquid`. The slab `minecraft:vertical_half` is the same for bottom and double (use the double slab id). `direction` and `cardinal_direction` are two forms of the same direction. Lever `open_bit`, dispenser `triggered_bit`, leaves `persistent_bit`. Crop age `getState('growth')`. Natural generation versus placed cannot be told apart (record on placement). Odd ids: `minecraft:darkoak_standing_sign`, `golden_rail` (powered rail), `reeds`, `tropicalfish`, `zombie_villager_v2`, `closed_eyeblossom`/`open_eyeblossom`, `small_dripleaf_block`. `BlockTypes.getAll()` also includes unreleased blocks.
- **Other Block APIs**: `block.hasTag/getTags`, `getLightLevel()`/`dimension.getLightLevel(pos)` (stable), `getSkyLightLevel` (a downward raycast, not the sun position), `getRedstonePower`, `getMapColor()` (once beta, 0~1 RGB floats, undefined for many vanilla blocks; the `minecraft:map_color` component only for some blocks; a case of generating a static table of map colors for 1084 blocks), `getItemStack()` (pick-block), `localizationKey`, `SignComponent.setText(text, SignSide.Front)`/`setWaxed` (no glow setter), `isAir`, `isSolid` (still beta in 2026-11 so undefined in stable 2.11, and a single report that `isAir`/`isLiquid` are the same; no plan to stabilize - alternatives are `getBlockFromRay` with `includePassableBlocks:false` or an 8-corner raycast full-block check), `isValid`. The block collision box cannot be changed (use states/permutations), block dynamic tint is impossible (entity render controller), and explosion resistance is not exposed (table). `minecraft:replaceable` cannot be turned off by permutation. For connecting tables/chairs, `minecraft:connection_rule`.

#### Block lookup, fill, raycast

- **`dimension.getBlocks(volume, filter, allowUnloaded)`**: Returns a ListBlockVolume -> `getBlockLocationIterator()` (a BlockVolume built from a small corner can produce relative coordinates so you must add the origin). An efficient way to find blocks in a range (`includeTypes`; a measurement where a `getBlock` loop took 9 seconds and `getBlocks` 3 seconds). It gives only a location iterator, so cache any Block references you need separately. `ListBlockVolume` is also used to detect blocks a player touched. A report in 2.8.0 that it returned a cut volume. A case where `containsBlock(volume, {blockFilter})` gave true without obsidian, and a bug where `excludeTypes` is wrong when a waterlogged stair is in the subchunk (MCPE-241274). `CompoundBlockVolume` cannot be passed to `containsBlocks`/`fillBlocks`. For simple volume checks, computing directly is faster than `isInside`.
- **`dimension.fillBlocks(volume, perm|type, { ignoreChunkBoundErrors, blockFilter: {includeTypes, includePermutations} })`**: The fast path for mass placement (one big call is much faster than many small calls - the cost is per native call). Big volumes are slow, so cut into chunks and `runJob` (example of filling 1000x1000: 32x32x32 `BlockVolume` pieces + `runJob` + `yield`, a `ListBlockVolume` per block type, `tickingarea add circle` via `runCommand`). The `matchingBlock` replace filter problem (unresolved, per-block handling recommended). Greedy merging. `cloneBlocks` reduces lag if you exclude air with a mask. Repeating `setBlockType` in a loop is also possible.
- **`getTopmostBlock({x,z}, minHeight)`**: Very fast (~5 ms/chunk vs raycast ~40 ms), skips transparent/non-solid blocks (leaves, cobweb, water, ice) and can return a non-solid such as a button, returns above the bedrock roof in the Nether, and undefined if the column is not loaded. There is a report that it is beta even in 2.8.0-beta (other reports use it normally, the stable status is *unverified*).
- **`dimension.getBlockFromRay(origin, dir, {maxDistance, includePassableBlocks, includeLiquidBlocks, excludeTypes})`** (on Dimension, not World): `BlockRaycastHit` (`.block`, `.face`, `.faceLocation`) or undefined (`?.block`). It stops at the first solid and cannot return air (implement DDA yourself for targeting air positions). `maxDistance` is a **Manhattan distance** (check yourself if you need Euclidean; a limit of about 320 blocks reported). It can skip very thin blocks and corners and is based on the collision box, not the selection box. `includePassableBlocks:false` hides liquids even with `includeLiquidBlocks:true` -> `true` + `excludeTypes`. Reaching an unloaded chunk gives `LocationInUnloadedChunkError` (distance limit/try-catch).
- **`faceLocation` bug**: Since 1.21.90 it is based on the nearest corner toward the world origin, not block local, so negative coordinates need a `1 - face` correction (edges are inexact), it is wrong on the -x/-y/-z faces, and in about 1% of cases it cannot tell top/bottom hits apart (MCPE-236442, MCPE-227192, MCPE-223452). Workaround: if the face is Up/East/South and the value on that axis is 0~1e-6, make it 1 (1e-7 is too small, and an unconditional +1 breaks non-full blocks). The `faceLocation` of `playerInteractWithBlock` is also reported broken (multi-hitbox blocks like drawers are hard). The ray origin is `getHeadLocation()` + 0.1.

```js
const EPSILON = 1e-6;
function fix(hit){ const f = hit.faceLocation;
  if (hit.face == Direction.Up    && f.y >= 0 && f.y <= EPSILON) f.y = 1;
  if (hit.face == Direction.East  && f.x >= 0 && f.x <= EPSILON) f.x = 1;
  if (hit.face == Direction.South && f.z >= 0 && f.z <= EPSILON) f.z = 1;
  return hit; }
```

- **Entity ray/lookup**: `player.getEntitiesFromViewDirection({maxDistance, includeFamilies})` is `{entity, distance}[]`, and `getBlockFromViewDirection({maxDistance})` is undefined for air. `dimension.getEntitiesFromRay` was reported to return 0, so a `getEntities` volume is more reliable. `EntityRaycastOptions` has no `minDistance`. For precise hits, the slab method on a cached AABB (`https://tavianator.com/2022/ray_box_boundary.html`). Field of view (FOV) checks use the dot product of the look and target vectors vs cos(angle), and occlusion `getBlockFromRay` (exclude glass with `excludeTypes`). Mobile aims without a cursor, so look-based hit detection is unstable. A script cannot know "whether it is visible on screen".
- **`getEntities(EntityQueryOptions)`**: `type` (only one), `excludeTypes` (array; no `includeTypes`), `families` (array, plural), `tags`, `excludeTags`, `location` + `maxDistance` (`maxDistance` needs a location), `volume` (like dx/dy/dz fixed to at least one block so it over-selects -> for entities on a block use `getEntitiesAtBlockLocation`), `closest`. For several types, one `getEntities()` + a JS Set filter makes fewer engine calls than iterating per type. `entity.matches({families:['monster']})`. Documentation `https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityfilter` . One user reported it was limited to 16 blocks (unresolved).

#### Chunks and ticking areas

- **Unloaded chunks**: `getBlock` is undefined or throws (`LocationInUnloadedChunkError` -> try/catch), `setBlockType` and so on fail, and entities in unloaded chunks are inaccessible from script (invalid; scoreboard participants remain). It follows the simulation distance (not the render distance). `dimension.isChunkLoaded(loc)` is the only native chunk information (moderate cost, limit the frequency). In the "unloaded but in memory" chunks that technical players use, `getBlock` fails and `getBlockFromRay` works. On switching to spectator, chunks can briefly unload on the server. `/particle` works in unloaded chunks but the API does not. An already loaded chunk cannot be unloaded.
- **`world.tickingAreaManager`** (TickingAreaManager): appeared in 2025-12 beta -> 2.7.0-beta in 2026-02 -> a report in 2026-03 that it is "now stable" (*unverified*). `createTickingArea(id, {dimension, from, to})` is an async `Promise<void>` (it used to return a TickingArea; there was a time when the documentation and types disagreed), `hasTickingArea`, `removeTickingArea`, `getAllTickingAreas`; only X/Z of from/to matter. The limit is not the number of areas but the **number of ticking chunks per pack** (reported as 255, with a report of about 300; overlaps are counted twice), more generous than the 10-limit of `/tickingarea`. It disappears from the API's view on `/reload` or rejoining and is removed automatically on world/server shutdown. When used instead of the command, no `runTimeout` is needed.
- **"Created != loaded"**: The promise resolves before the chunk is loaded or it takes ~8 ticks. There is a report that doing the work after a fixed 3 ticks (2 ticks is unstable) without awaiting the promise worked even at a distance of 4 million blocks, and a report that polling `dimension.getBlock(to)` is faster, from 8 ticks to 2 ticks. A bug where `getEntities` missed entities in the area, a leak where old script memory is not released on `/reload` after creating an area (reported as MCPE-236954), and a 1000x1000 build stopping at 1/10 (resumes when the player approaches, unresolved). `/schedule on_area_loaded` is also an alternative (cannot be canceled). TickingAreaError has no chunk count information.
- **Patterns**: For far away/unknown chunks -> check `isChunkLoaded`, otherwise a temporary 1-chunk ticking area -> wait -> work -> remove. For filling an area, load 16x16 XZ columns at a time (`x += 16`) -> `fillBlocks` -> unload, with a global generator-based queue (`class ChunkFiller { requests; *generator() }`). Safe teleport: temporary area + `getTopmostBlock` + skip non-solid/lava/water. To keep entities across dimensions: one ticking area per dimension on entering the dimension. A `minecraft:tick_world` entity (radius in chunk units) could not load unloaded chunks reached by teleport and was reported broken (MCPE-229817). Pre-generating chunks is done by changing one block and changing it back to force a save (*single report*). Ender pearl-type projectiles shot by script do not load chunks. There is no "chunk first generated" event -> a per-chunk DP marker.
- **UnloadedUtils** (github.com/Nytreon/UnloadedUtils, MIT): Reads unloaded chunks without error with `StructureManager.createFromWorld`, and writes into unloaded chunks with structure *blocks* (not commands or the StructureManager). Slow, placements pile up in a queue in read-only chunks beyond the render distance, entities in fully unloaded chunks cannot be teleported (short ticking area -> tp -> delete), "read-only" versus unloaded state cannot be told apart synchronously, and `/reload` breaks the timing. Background article: `https://bedrockwiki.com/books/chunks/page/unloaded-chunks` . Command blocks run before scripts in a tick, and the scheduled-tick phase processes only 100 events per chunk (the rest wait, a risk of abusing command block starvation). Old chunk loader: ChunkLoader V1.2.0 github.com/gamezaSRC/ChunkLoader.

#### Structures

- **`world.structureManager`**: `get(id)`, `place(id, dimension, location)`, `createFromWorld(...)`, `createEmpty`, `Structure.setBlockPermutation`, `getWorldStructureIds()` (only saved/loaded ones), `getPackStructureIds()` (2.8.0-beta; for pack structure ids the folder name is the namespace, and the default save name is `mystructure`). `StructureSaveMode.World|Disk` (Disk is permanent). Vanilla structures cannot be loaded. Structures placed by script are not subject to the 3x3 chunk limit of structure generation, but the maximum XZ size cannot be extended, so split into several structures. Better than structure blocks for arena restoration. StructureManager is stable.
- **Cautions**: A bug where BP structures are not recognized after the first run, large structures such as 96x96 can crash the native call so use jigsaw pieces, loading is asynchronous so wait a fixed number of ticks, place the next after the previous structure is loaded (to prevent corruption), and the game does not unload structures. `/structure` fails in non-ticking chunks, and it is resolved by id at load time, so if you save a different area under the same id before the chunk loads, all pending loads use the latest data. Replacing a big map takes 20~30 seconds -> a custom dimension per map. A case where "can't find structure" was caused by an undefined player/name. Structure format v2 (26.50.24, smaller, cannot be read by old versions). Spread lag with `/structure load ... animation`. `runCommand("place ...")` (jigsaw) is disabled in scripts.
- **jigsaw and dimensions**: Place jigsaw with the native `world.structureManager.placeJigsawStructure(identifier, dimension, location, options?)`, which takes a BlockBoundingBox (options `ignoreStartHeight`, `includeEntities`, `keepJigsaws`, beta `liquidSettings`). Large structures that failed with the command worked with the native API, but there is a case of a watchdog crash on a 138x138 jigsaw. `/place structure` in a function or command block at world start was not placed because the chunk was not loaded. When placing a structure in a custom dimension, move there with `player.teleport(pos, { dimension })` to load the chunk and then `world.structureManager.place(name, dim, pos)`. jigsaw also works in custom dimensions.
- **Feature placement**: `dimension.placeFeature(feature, location, true)` (throws if the tree trunk cannot be placed, vanilla rules apply), `Dimension.placeFeatureRule()` (blocking, expensive in bulk). `/place feature` cannot be run from scripts so use `placeFeature`, but there is a bug report that only features that have a feature rule are registered, and it does not work for growing multi-cell wide trees. Entities cannot run `/place`, so request the script with `/scriptevent`. Checking for a structure at a location: `dimension.getGeneratedStructures(location)` (1.21.120 beta, an error if unloaded; no locate -> poll the player position).

#### Custom dimensions

- **History**: `DimensionRegistry.registerCustomDimension` introduced in the 2026-04-08 Preview beta -> left beta around 2026-06-18, ~26.30 stable. The 1.26.20 release documentation already has a custom dimension section and the 2026-06-26 API documentation also marks it stable, which conflicts with the report that it has been stable since 1.26.20 (**conflicting**). Documentation: `https://learn.microsoft.com/en-us/minecraft/creator/documents/scripting/custom-dimension-api-tutorial?view=minecraft-bedrock-stable` , `https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/dimensionregistry?view=minecraft-bedrock-experimental`
- **Usage**: `system.beforeEvents.startup.subscribe(e => e.dimensionRegistry.registerCustomDimension("ns:id"))`, and movement is `entity.teleport(loc, { dimension })`. It must be registered on every load (if you stop registering it, it is invalid, and if you register again the builds come back; players in an unregistered dimension go to the Overworld), and the terrain does not need to be regenerated. Deleting data is not possible from script (NBT/leveldb editor). Only a single registration method (no choice of gravity, atmosphere, friction or biome), no terrain generation, features do not work (2026-05), and time and weather are shared with the Overworld (a world clock is planned for 26.50). You cannot enumerate custom dimensions with `world.getDimension` -> since 26.50.26 `DimensionTypes.get/getAll` return them (only after startup). An unresolved case where teleport works in an item use handler and gives `Dimension 'custom:test' is invalid` in a custom command. Opening a form right before a portal/dimension move hides the loading screen.
- **State in 2026-09~11**: Stable dimensions are tied to the Overworld height and clock, a custom clock and height were added in the Preview, and there is a mention that in the next release dimensions will be defined in JSON (dimension.json). `Dimension.localizationKey` of a custom dimension returns a key without a namespace (for example `dimension.dimensionName1000`) and conflicts with other add-ons (MCPE-244151). A case where per-dimension `fillBlocks` gave an unloaded-chunk error even though the chunk looked loaded, and a case where one dimension's terrain appeared to bleed into another custom dimension, are unresolved. The upper limit on the number of dimensions is unknown.
- **Imitating terrain**: Generate per chunk with noise + `fillBlocks`, put a bedrock marker at the bottom of each chunk to tell whether it was generated without separate storage, and the same seed gives the same world (a DayZ-style template). A case of reaching 10 chunks/second at render distance 64 chunks with a custom scheduler + batching. Landing platforms by structure loading. A dimension can also be used as ItemStack storage.

#### Biome, weather, time, game rules

- **Biome**: `dimension.getBiome(location).id` (BiomeType; stable since 2.3.0/2.4.0, needs a loaded chunk), `findClosestBiome(location, biomeId, {boundingSize})` (beta; imitates /locatebiome; "not a function" means beta is not used/a game restart is needed; an error reported in 2026-05), `BiomeTypes` (once beta only -> copy the result of `getAll()` in beta and hard-code it in stable code), custom biomes `BiomeTypes.get(id)`. `Biome.getTags()`/climate are beta and not exposed, and vanilla biome tint cannot be changed. For old versions (1.14), environment_sensor + scriptevent (the 1.14 module has no `getBiome`, and pre-1.18 ids such as `minecraft:swampland` do not match). A report that `findClosestBiome` was renamed `calculateClosestBiomeFromSeed` and became stable (*single report*).
- **Climate workaround**: Precipitation and temperature are still not on `BiomeType` in 2026-11. There are the methods of reading `BlockMapColorComponent.tintedColor` of a block actually placed in the world and caching per biome (permutation resolve does not work, and it is unreliable in biomes with custom grass color), hard-coding a biome table, or spawning a custom entity that gets a tag through a temperature filter, reading the tag after 1 tick and removing it.
- **Weather**: `dimension.setWeather("Thunderstorm", ticks)`, `getWeather()` is beta even after 2.8, there is no `isInRain`, and weather is global to the Overworld (per-biome rain breaks in multiplayer).
- **Time and other world**: `world.getMoonPhase()`, `world.getAbsoluteTime()`, `world.getDefaultSpawnLocation()` (0,32767,0 if not set), `player.getSpawnPoint()` (`{x,y,z,dimension}`)/`setSpawnPoint()`, `world.gameRules.spawnRadius/showDeathMessages/keepInventory/naturalRegeneration` (the locator bar game rule was renamed `playerWaypoints`), `WorldClock` (26.50+ beta, `isPaused` stops only the world clock), the world seed (a 26.0 Preview property; previously not exposed), `world.playMusic()` (the MusicOptions fade was wrong for a long time). There is no equivalent of `/tick freeze`.
- **Creating explosions**: `dimension.createExplosion` (a nonlinear jump from radius 4 to 5, and for shaped craters compute a sphere/ellipsoid block list yourself), `Entity.setOnFire`.
- **Dynamic lighting**: Every tick place `minecraft:light_block` (`block_light_level`) around the entity and erase the previous position.


### Visual and audio effects: particles, sound, camera, debug shapes

#### Particles

- **`dimension.spawnParticle(id, loc, MolangVariableMap)`** (to everyone) and **`player.spawnParticle(id, loc)`** (to that player only; 2.0.0 stable, not possible with an RP alone). Blocks have no `spawnParticle`, so use `block.dimension`. The position is the emitter position, so correct with `block.location + 0.5`.
- **MolangVariableMap**: `setFloat("r", 5)` -> `v.r` in the particle JSON (named without a prefix; no boolean, true=1), `setColorRGBA`, `setVector3`, `setSpeedAndDirection("variable.actor", speed, dir)` -> `variable.actor.speed/direction_x..`. "unable to find member variable .x/.y/.z" means you did not pass the variable the particle uses. Few vanilla particles accept color (colored_flame). Vanilla particles: `https://github.com/Mojang/bedrock-samples/tree/main/resource_pack/particles`
- **Limits**: Cannot be modified after spawning (an emitter entity or respawn), it is client-side so script hit detection and timing cannot be synchronized (use entities), and it is not ray traced. More than ~100~400 per tick lags the client -> use a single Snowstorm custom particle. Particles that follow a player from the server are delayed. A script cannot read particles. A `gfx:line` single line renderer particle (minimum thickness 0.001, minimum lifetime 0.05, `dash_count`, `projecting_cap` 0~3, `is_dashes_per_block`, `is_last_filled`).

#### Animation and passing client variables

- **`entity.playAnimation(name, {controller, blendOutTime, nextState, players, stopExpression})`**: The same `controller` string cancels the previous animation, and a different string plays simultaneously. For a player it affects only the player's own geometry/animation (attachables are not affected). Animations are client-side so a script cannot read or stop what is playing, and playing right after spawn goes out of sync. The swing animation is hard-coded. Two arguments. A report that if `controller` is omitted the default `"__runtime_controller"` is used and there is no leak. A controller of the same name is overwritten until the client reloads. A report that using the shortname `"root"` on a player stops the animation and it is not visible in first person. Repeated playback is possible only with an animation controller.
- **Molang variable injection**: `player.playAnimation("animation.x.dummy", {controller: "<unique>", stopExpression: "v.bp_x=1; return 0;"})` + a dummy animation (`{"format_version":"1.10.0","animations":{"animation.x.dummy":{"animation_length":0.05}}}`) runs Molang on the client (floats only). Attachable side `parent_setup`: `t.bp_animation = v.bp_animation ?? 0.0;`, reading `t.*` in `pre_animation`; per player, `t.player_name='${player.name}'` and comparison with `q.get_name`. Caution: reusing the same controller name means variables are not updated on later calls, and random names pile up controllers and drop FPS (after 30~60 minutes, not recoverable) -> derive the name from variable + value such as `animation_controller_${ns}_${name}_${value}`. The variable persists until set again (reset on skin change, exclude the paper doll with `q.is_in_ui? 0 : {...}`), and for other players to see it, resend on join/range entry. This approach depends on the `temp` variable leak (a bug) and is fragile. The option itself does not pass Molang variables, so the `/playanimation ... "v.x=1;" ctrl` command is an alternative. A cleaner path is client-synced entity properties (with a count limit) - attachables read player properties with `c.owning_entity -> q.property` to switch animations/render controllers.
- **Attachable limits**: Particle/sound locators break inside attachables (use the player client entity; only the locators of the first render controller are recognized). A report that repeated playAnimation updates break, and for smooth movement entities are the only way. First-person detection is not possible from script (`variable.is_first_person`, attachable `c.is_first_person`).
- **Item sway (first-person gun)**: Sample yaw every tick `d = ((y - prevY + 540) % 360) - 180`, smooth `v = prev*0.4 + d*0.6`, ignore sneaking/samples older than 2 ticks/|v| &lt; 2.2 degrees/tick -> `startItemCooldown("look_left"|"look_right", 10)`. The attachable `pre_animation` reads `q.cooldown_time_remaining('<prefix>_look_left')`, a state cannot restart itself so duplicate a/b states are needed, a `c.is_first_person` gate, and animation length = cooldown (10 ticks, `hold_on_last_frame`).
- **Choice**: BP animation controllers are trigger based and cheap, while scripts have a higher ceiling and are easier to compose. Running a function on right click is also possible with a player.json controller (`query.is_using_item && query.is_item_name_any('slot.weapon.mainhand', 'ns:item')` -> `on_entry` `/function`). Whether something is held uses `query.is_item_name_any`/`q.equipped_item_any_tag`. Fall detection: `!q.is_on_ground && q.vertical_speed` -> scriptevent.

#### Sound

- **`dimension.playSound`/`player.playSound`**: Volume 1 = radius 16 blocks (to widen it, volume and the sound definition `max_dist`, format 1.20.20, MCPE-154378), pitch default 1. A sound that follows the player uses `"category": "ui"` in sound_definitions (no attenuation). Opinions differ on the default of the `player.playSound` position. The volume differs from `/playsound`. Sounds are `sounds/` + `sound_definitions.json` (`https://wiki.bedrock.dev/concepts/sounds`).
- **`stopSound`**: `Player.stopSound` is beta, and in stable use `runCommand("stopsound ...")`.
- **SoundInstance** (26.30 preview/beta, 26.40): `playSound` returns an instance - loop, maximum length, `stop`, `seekTo`, pause/fade, `durationInfo` (broken for a week). No position update/entity attachment (repositioning = stop + play + seekTo). A server sound definition must be registered in both the RP and BP. Occasionally silent/delayed (a fix planned for 26.50). Long music drifts, so splitting into ~5 second pieces is the community solution. MCPE-240513 (1.26.40, including Linux server builds): a `playSound` call made the player's JS properties read-only -> fixed in 26.50, and before that wrap `/playsound` (losing SoundInstance).
- **Other**: Switching the sound listener for a dungeon-style camera is not possible.

#### Camera

- **`player.camera`**: `setCamera("minecraft:free", {location, facingLocation, rotation, easeOptions:{easeTime, easeType:"Linear"}})` (a free camera does not follow dimension changes, so clear after moving -> reapply; looking with `targetEntity`/`offsetFromTargetCenter` did not work), `setCamera("minecraft:first_person", {entityOffset, easeOptions})` (moves only the visual, the server eye height and interaction raycast stay -> no workaround other than `minecraft:scale`), `"minecraft:follow_orbit"` (`viewOffset`), `clear()` (only returns to the last client perspective and does not force first person -> `setCamera('minecraft:first_person', {ease:{easeTime:0}})`), `fade({fadeColor, fadeTime:{fadeInTime, holdTime, fadeOutTime}})` (RGB only, no alpha, hold maximum ~10 seconds, minimum 0.5 seconds), `setFov` (about 30~110, ease options, no `getFov` to read the current FOV), `attachToEntity({entity, locator: EntityAttachPoint.Head})` (beta; only in third-person/orbit presets -> true first-person spectating is impossible, and a report that it did not work in 2026-04), `playAnimation(spline, options)` (Catmullrom/Linear splines; the game crashes if `rotationKeyFrames` is empty, "Linear needs at least 2 control points" actually needs 3, rotation interpolation does not take the shortest path so make yaw/pitch/roll continuous values (356, 360, 361...); clear may not erase the animation; initially position only), `addShake` (beta 2.11/26.50 preview; if missing, the npm types are old). In first person you can use only FOV, shake and fade. A free camera has no roll, but the Vector3 rotation keyframes of `camera.playAnimation` can give roll on a predetermined path (not possible while riding). A Catmullrom spline actually needs 4 control points, and the "move camera to point" method ignores rotation. The `control_scheme` of a camera preset is not applied, while the `/controlscheme` command is. The real camera position cannot be read (Molang `query.camera_rotation`, `distance_from_camera`). Documentation: `https://jaylydev.github.io/scriptapi-docs/latest/classes/_minecraft_server.Camera-1.html` , `https://learn.microsoft.com/en-us/minecraft/creator/documents/camerasystem/cameracommandintroduction?view=minecraft-bedrock-stable`
- **Ride camera**: To change the camera by script, the experimental camera features were needed, and repeated camera commands overwrite `/camera @s clear`. Following a fast mount with a free camera + teleport jitters (unresolved). The death camera cannot be removed (instant respawn + your own presentation). There is no clean way to force-close the inventory (damage/dimension change; `/camera fade` does not close it).

#### Debug shapes and TextPrimitive

- **`@minecraft/debug-utilities`** (beta only): `DebugShape` subclasses (`DebugArrow/Box/Circle/Line/Text`), `new DebugBox(minCorner)` + `bound = {x,y,z}` (a size, not a corner), `timeLeft`, lowercase `debugDrawer.addShape(box)`. `location` is read-only, and if you do not give `setLocation()` a dimension, it renders in all dimensions -> prototype patch so the `location` setter preserves `this.dimension`. `rotation` does not work on non-static shapes (box), and `DebugText.rotation` works with `useRotation = true`. `visibleTo` (a player array, 26.0.x changelog). `depthTest` could not hide text behind blocks. Debug lines ignore `.scale` (thick lines are several lines -> expensive), but they are still a cheaper outline method than entities/particles. Debug colors are ignored under Vibrant Visuals. Once disabled on Realms because of a settings mistake. Documentation: `https://stirante.com/script/debug-utilities/1.0.0-beta.1.26.40-preview.31/classes/DebugText.html`
- **TextPrimitive / PrimitiveShape** (around 26.20, `@minecraft/server`; beta in 2.8.0, a report of stable in the Preview): `world.primitiveShapesManager.addText(new TextPrimitive(location, "text"), dim)`, `setText()` (create once and track with a Map), `remove()`, `attachedTo = entity` (then `location` is an offset relative to the entity, for example the head `{x:0,y:2,z:0}`; giving world coordinates makes it invisible; the text direction is fixed in world space), `scale`, `visibleTo: Player[]`, `timeLeft`, `color` (RGBA, text alpha ignored; one primitive per color), `backgroundColorOverride`, `textBackfaceVisible`, `depthTest` (unstable with VV on), rotation in degrees + `useRotation = true` (poor rotation quality). A world-wide limit of 1000, text up to 128 lines x 128 characters (changed in 26.20.22/26), does not follow entity rotation, no shadow. For floating text without an entity (text attached to an entity beyond the render distance looks odd). `depthTested`/render distance were also backported to name tags. Documentation: `https://stirante.com/script/server/2.8.0/classes/TextPrimitive.html`

#### Graphics, aim assist, locator bar

- **`@minecraft/server-graphics`**: Dynamically changes some Vibrant Visuals (not RTX) settings from script. 26.40 preview.20 beta (`BiomeWater.setWavesDepth/DirectionIncrement/Frequency/FrequencyScaling/Mix/Octaves/Pull/Shape/Speed/SpeedScaling` - waves must be turned on in the pack for an effect; per-biome custom water cannot turn waves on, so turn them on with `depth: 0` in `RP/water/default_water.json` and redefine depth in the custom water file, manifest PBR is needed, and export to match the game version) -> left beta in the 2026-08-11 Preview. Value tuning is the Editor Mode "Vibrant Visuals" button. Per-pixel effects (DOF, motion blur) are impossible (a shader is needed). Water/grass tint is biome based so it cannot be changed dynamically. Fog per graphics mode is by script or subpacks. Documentation: `https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server-graphics/minecraft-server-graphics?view=minecraft-bedrock-experimental` , changelog `https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server-graphics/changelog?view=minecraft-bedrock-stable` , `https://stirante.com/script/server-graphics/1.0.0-beta.1.26.40-preview.20/classes/BiomeWater.html` , `https://learn.microsoft.com/en-us/minecraft/creator/documents/vibrantvisuals/watercustomization?view=minecraft-bedrock-stable`
- **Fog**: Stable has only `/fog` push/pop (removal pops by the user string given at push, not the fog ID; the transition time cannot be set), and beta has FogSettings (`https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/fogsettings?view=minecraft-bedrock-experimental`). Per-region fog is script + `/fog`.
- **Aim assist (beta)**: `BP/aim_assist/presets/*.json` (`minecraft:aim_assist_preset`: `identifier`, `item_settings`, `default_item_settings`, `hand_settings`, `exclusion_list`, `liquid_targeting_list`; format 1.21.50~1.21.110) and `BP/aim_assist/categories/categories.json` (`minecraft:aim_assist_categories`), and the camera preset `aim_assist.preset`. You cannot create new categories with JSON (only `minecraft:bucket`, `empty_hand` and `default` can be overridden) -> declare an empty category and in script `new AimAssistCategorySettings("ns:name")`, `setBlockPriorities`, `world.getAimAssist().addCategory(...)`, then `new AimAssistPresetSettings(id)`, `setItemSettings`, `addPreset` (category first, inside `system.run`; tested on 2.7.0-beta). The default preset is `minecraft:aim_assist_default`.
- **Locator bar**: `player.locatorBar.addWaypoint(...)`, `getAllWaypoints()`, `LocationWaypoint`, `WaypointTexture.Circle`, `CustomTexture` (0.0~1.0 units, small textures). The most performant way to point at coordinates (action bar; a custom compass is an alternative). Vanilla player waypoints are only via game rules. A problem where a waypoint added in `playerSpawn` disappears after rejoining (suspected bug -> store in a DP and re-add). Documentation: `https://stirante.com/script/server/2.8.0-beta.1.26.20-preview.23/classes/LocatorBar.html`
