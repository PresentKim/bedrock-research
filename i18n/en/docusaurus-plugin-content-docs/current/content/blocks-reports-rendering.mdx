# Block community reports - geometry, rendering, mining, placement

These are individual reports from community research (2025-10-22 ~ 2026-11-13) that the preceding documents of this page did not summarize. The `[uNNN date]` at the end of each item is the research note number and the report date, and `(single report)` marks content reported by only one person.

#### Model size and format

- **Size limit**: about 30x30x30px including rotation ("1 + 14/16ths" per axis, that is 14px outside the 16 cube). The error is "Total length of parts for schematic ... greater than 1 + 14/16ths". A model taller than about 30px (1.8 blocks) disappears in the game. Only cubes are allowed, and poly_mesh and locators give a "is not included within the unit cube" error. Avoid complex rotated cubes. Larger shapes are made with several blocks, multi-block or entities. Size is checked before the transformation is applied (MCPE-236317). Exceeding the size also shows as "contains N boxes outside the error bounds of (-0.875..1.875)", at least 1px on each axis must be inside the unit cell, and in one case a transformation scale of 2 gave the same error.
- **Old formats and shadows**: blocks that exceed the limit with an old format (1.21.0) look dark or broken after the shadow rendering change of the 26.0 line, so raise the format_version. Geometry broken when scale is not 1 was fixed with format 1.21.0 or higher. If the geometry file format_version is an old value such as 1.12, the block may be invisible. (single report)
- **Rotation angles**: transformation rotation works only in multiples of 90 degrees. For 45 degrees, duplicate a rotated bone and turn it on and off with a state.
- **Fallout of invalid geometry**: if one subchunk has a block with invalid geometry, every geometry-based block in that subchunk (including cobwebs) is not rendered ("A block must have baked material data in order to tessellate"). Find the cause (a model too large, a texture that is not 16x16 and so on) in the Content Log.
- **z-fighting offset (conflicting)**: one answer says to shift about 0.001, and another says z-fighting remains if block inflate is under 0.05. For a lily pad style plane, raise it 0.1~0.2 in Y, and avoid per-direction z-fighting with per-direction geometry.
- **Decimals**: coordinates are rounded to one decimal place (15.98/7.99 get rounded). Fix z-fighting with 7.9 or `inflate`. Using a second decimal place causes gaps and render errors.
- **UV**: Bedrock drops faces that have no explicit UV. If it is fine in Blockbench but has holes in game, use per-face UV (`uv`, `uv_size` on `north/south/east/west/up/down`) instead of the box UV `[0,0]`. Turn off faces that will not be seen instead of crowding them into a corner (https://wiki.bedrock.dev/blocks/block-models#removing-faces). Planes with zero thickness are also supported. After the Preview that removed padding, UVs outside the texture bleed into neighboring atlas tiles with no warning (worked around with a script that removes UVs that are too large or zero).
- **One PNG per model**: using several PNGs on one model failed.
- **Scale cap (old format)**: when the geometry `scale` was capped at about [2,1,2] in new versions, there is a case of going down to format 1.20.80 to bring back `onBreak` and large scale (the old way, not recommended). (single report)

#### Vanilla geometry

- **What can be used**: `minecraft:geometry.full_block` and `minecraft:geometry.cross` and so on (the `minecraft:` prefix is required, list https://wiki.bedrock.dev/blocks/vanilla-block-models). For cross use `alpha_test_single_sided` to avoid flicker. Other vanilla models such as slime, lantern, cauldron and sign must be made by hand. Reusing full_block reduces pack size.
- **cross internals**: `minecraft:geometry.cross` extracted from BDS `.rdata` is 2 cubes (origin [-10.2,0,0], size [20.4,16,0], Y axis +-45 degrees, pivot [0,8,0], material instance "cross", format 1.21.60).
- **Characteristics of full_block**: the bottom face is rotated 180 degrees (fixed in format 1.26). It has no named main bone, so culling rules cannot reference a bone, and UV lock does not apply either. An `opaque` full_block is forced into unit cube culling (opaque only since 2026-06-02). Transforming a full_block with transformation breaks culling (MCPE-241209). The only way to cast shadows on neighbors is `minecraft:geometry.full_block` + `opaque` (hardcoded).
- **`minecraft:embedded_visual`**: for flower pots only.

#### bone_visibility

- **Format**: written inside the `minecraft:geometry` object as `{"identifier": ..., "bone_visibility": {...}}`, and values are booleans or Molang. In 1.26.20+ a raw boolean fails with `invalid string`, so use the strings `"true"`/`"false"` or 0/1 (MCPE-238524, a schema bug, with a mention that Mojang fixed it later). A key controls only the cubes directly under that bone and ignores nested groups, and adding `*` to the end of the key includes nested bones. Bone visibility does not accumulate across permutations, so a 6-face block like glow lichen needs all 64 permutations.
- **Uses**: showing flowers in pots, doors/hinges, cake stages, wall torch variants, fence connections and so on. Flower pot example: give several bones a material instance keyed by bone name. `"minecraft:material_instances": {"*":{"texture":"pot","render_method":"opaque"},"flower":{"texture":"flower_1","render_method":"alpha_test_single_sided"}}`.

#### Collision/selection boxes

- **Multiple collision boxes**: `minecraft:collision_box` accepts an array of boxes (boxes only, no curved surfaces). They appeared in the 1.21.130 Preview (1.21.130.26, 2025-11) as an Upcoming Creator Features experiment and became stable in 26.0. The extended collision height left the experiment and no longer needs the 1.21.130+ format. There is a report that it also worked in 1.20.80. A single report says there is a limit of 16 boxes (unverified). Stair example: `[{"origin":[-8,0,-8],"size":[16,8,16]},{"origin":[-8,8,0],"size":[16,8,8]}]`. Before 1.21.130 the player was pushed out by geometry that did not fill the cell.
- **Collision size**: up to about 16x30x16 (about 8px upward). A `random_offset` bug shifted collision by one block in one case. `collision_box: []` is not "no collision" but full collision. A transformation can push the box out of block space (MCPE-236325, not fixed). There is also a report that the height grew to 24 (unverified).
- **Format**: `minecraft:selection_box` accepts `true` (full block) or `{"origin":[-8,0,-8],"size":[16,8,16]}`, and collision_box takes the same format. Molang cannot change the box per state, so use permutations. The bounding box setting in Blockbench has no effect in game. With `collision_box: false` entities pass through, and a block where entities stand but only items fall cannot be made. There is a report that it gets blocked when the collision box crosses between two other custom blocks (unverified).
- **Selection box**: only one (arrays are not supported). It can be defined up to 24 model units, but the engine clips it to block bounds and it goes outside only visually (Mojang is investigating). The outline is the enclosing cube. Projectiles use the selection box, so do not turn off `selection_box` if arrows should hit. Conversely, having only collision makes a "barrier that projectiles pass through". The only way to hide outlines globally is adventure mode.
- **Step detection**: if the collision height is about 3.2px (0.2 block) or less, it is a "thin" block that cannot be stood on (the footstep sound and particles of the block below remain) and `onStepOn`/`onEntityFallOn` do not fire (wiki 3.2, measured about 3.25, 4px recommended in practice). One reporter reported that about 0.4 block or more is needed, so it is **conflicting**. For spike blocks, put the spike on a 4px floor cube, or use `onEntityFallOn` (gives the fall distance, does not fire when walking) or scripts. See `GetBlocksStandingOnOptions`.
- **Spawning**: entities spawn on blocks with full collision.
- **No collision check API**: there is no API to tell whether a collision box is full or partial. There are hacks of summoning an entity to see if it is pushed out or raycasting.
- **Tools**: Kaioga's Collision Box Editor https://kaioga5.github.io/block-collision-viewer/ (source https://github.com/kaioga5/block-collision-viewer/), Blockbench plugin https://www.blockbench.net/plugins/block_multi_collisions (auto-generation, ignores cube rotation, and after moving a bone auto-generation uses the old origin, a bug). There is a report that east/west look flipped between the preview and the game (not reproduced).

#### transformation

- **`minecraft:transformation`**: specifies rotation/scale/translation, and scale is around the block center. Collision/selection box scale applies only when that component is specified explicitly (MCPE-238027, judged "invalid", disputed). A block rotation cannot exclude specific bones and there is only UV lock. `uv_lock` rotates square faces around the face center, not the block center. Snowlogging ignores transformation (MCPE-240710).
- **Five coordinate systems**: model/collision/selection (model units, bottom center, x+ is west), leashable offset (x+ is east), transformation translation/pivot (block units, center), voxel shape (model units, bottom north-west corner), item_display_transforms. Mojang plans to move placement/support to voxel shapes, and voxel shapes have a limit of 4500 unique ones after deduplication on world load.

#### Item display

- **`minecraft:item_visual`**: changes the hand/inventory model with `{geometry, material_instances}` (no `minecraft:` prefix here). `carried_textures` in `blocks.json` does not work. If the item looks upside down because the default `block_face` is down, define item_visual to fix it.
- **item_display_transforms**: needs block geometry format 1.21.110+ (before that the GUI model was misaligned, https://learn.microsoft.com/en-us/minecraft/creator/reference/content/blockreference/examples/itemdisplaytransforms?view=minecraft-bedrock-stable). Defaults: firstperson_righthand rotation [0,45,0] scale 0.4, thirdperson_righthand translation [0,2.5,0] rotation [75,225,0] scale 0.375. To match the vanilla slab use `thirdperson_righthand.translation [0,2.9,1.5]` and `firstperson_righthand [0,1.58,0]`. A wrong property name (`translate`) crashes the game. `fit_to_frame:false` is forced to center in icons (MCPE-240720). Rotation also rotates the icon shadow (MCPE-235788). GUI fixes regressed several times (MCPE-234752). Dropped item size is adjusted with the ground transform.
- **Block as an item**: put `minecraft:block_placer {block, replace_block_item:true}` on an item with the same identifier as the block. It must be the same ID to be pick-blockable (otherwise `<ns>:item.<id>` appears), and a flat 2D icon, `max_stack_size`, head-wearing `minecraft:wearable` and `minecraft:glint` can be used. If you omit the icon it is rendered as a block. A custom block cannot exist without a block item. Docs: https://wiki.bedrock.dev/blocks/blocks-as-items (#replacing-block-items).
- **Side effects of item overrides**: it inherits block tags (MCPE-235805). Block-oriented AI such as `move_to_block` and `lay_egg` fails (MCPE-240457), and `lay_egg` crashes. Using the `tile.ns:block` prefix in `move_to_block` target_blocks fixes blocks that share the ID with the item but not replace_block_item blocks. There is also a bug that using an item with the same ID makes mob spawning and `avoid_block` ignore the block. Item overrides turn off fast bridging (MCPE-234686). The problem of appearing in the furnace recipe book "items" category (MCPE-236444) was fixed.
- **`aligned_placement`**: this value of `minecraft:block_placer` affects the `block_face` state.
- **State specification in `block_placer`**: the `block: {name, states}` form needed the latest format and a valid icon, and without them the item was invisible with "Missing icon for data-driven item" (unresolved).
- **3D block models**: the only way to get a 3D block model is a custom block (vanilla is tied to the deprecated blockshape).

#### material_instances

- **Basics**: a block that uses geometry must use `minecraft:material_instances`. Keys are face names (`up`, `down`, `north` ..., not top/bottom, `*` is the default, and custom face names from Blockbench also work). The fields of each instance are `texture` (not `textures`), `render_method`, `face_dimming` (bool), `ambient_occlusion` (a number in 1.26.20+, `0.55` for sand-style partial darkening), `tint_method` and `isotropic`. `eau_occlusion`/`brightness_gamma` do not exist. The texture name is a key of `terrain_texture.json` (not a path). Vanilla textures must also be defined in terrain_texture, and a short name (`diamond_ore`) alone is not enough (a single report says it is fine if it is also in blocks.json).
- **Not merged**: material instances are not merged. If you define every face, `*` is not used, and AO/face_dimming are repeated per face. light_emission is a separate component. To give several bones per-face textures, use per-face UV and per-face instance names. A typo in a terrain key silently becomes a missing texture.
- **No mixing render_method**: instances of one block cannot mix render_method ("MaterialInstances can't mix and match"). A block mixing opaque and translucent is thought to be impossible. For a beacon style, set both to blend.
- **Choosing a render method**: `alpha_test_to_opaque` fixes disappearing at a distance and is used for leaves. `alpha_test` is for cutouts. `blend` has ordering problems, so put translucent cubes last or use `alpha_test_single_sided`/`double_sided`. With complex geometry, blend is drawn over blocks in front. A `double_sided` block disappears at half the render distance. Opaque with transparent pixels looks black. For cobweb/outline style use `alpha_test_single_sided`. Making it with an add-on maker app ignores `blend`/`alpha_test`, so write the JSON by hand. `render_method` is a material instance field, not in blocks.json. Custom leaves set the alpha of opaque pixels to 1 and use `alpha_test_to_opaque` so that they do not disappear at a distance, and you cannot set separate textures by distance. Transparent render methods break shadows. Use opaque for blocks like dirt. Distance-based render method docs: https://wiki.bedrock.dev/blocks/block-visuals-intro#distance-based-render-methods.
- **emissive/shaded**: `emissive` was renamed to `shaded` (an alias of face_dimming/ambient_occlusion). True glow works only in Vibrant Visuals, and `"emissive": true` existed (briefly) in format 1.21.120+ with Upcoming Creator Features. A glowing texture without VV/RTX is impossible, so make an illusion of glow with a flipbook (https://wiki.bedrock.dev/blocks/flipbook-textures).
- **Tint**: `tint_method: grass` tints every non-alpha pixel (with vanilla grass_side even the dirt part). `alpha_masked_tint` needs 1.21.120+ and the toggle, became an experiment again in the Preview, and had a problem tinting transparent pixels until 26.0. For transparent blocks use `tint_color`, not `overlay_color` (https://wiki.bedrock.dev/blocks/block-tinting#texture-tinting). Even laying a custom texture over a tinted vanilla leaf could not stop the tint.
- **Texture size**: it need not be 16x16, but normal cube UVs assume 16, so other sizes need custom geometry. Textures must be square (otherwise they are read as animation frames or cropped). 8x8 is stretched to 16x16. A 64x64 whole-model atlas makes huge cracks and break particles, so use several 16x16 per-face textures (create "blank" textures in Blockbench). Carpet (1px model) also uses one 16x16.
- **Texture size problem in 1.26**: from 1.26, textures that are not a power of two or a multiple of 8 (66x66, 18x18) create lines between blocks and missing faces. Fix by changing to 64x64 or 32x32 and matching the UV.
- **Shrinking to 8x8 after editing the RP**: there is a workaround of copying the RP, modifying the copy and overwriting the original. Do not keep `contents.json`. An error that a texture is not defined was suspected to be a leading space in the name and was solved by clearing the cache.
- **"Invalid or incomplete texture list" warning**: a warning that appears even though it works.

#### Shading, AO, shadows

- **Custom block AO**: AO is broken, so flowers/crops with a model inside a neighbor look dark or black. `ambient_occlusion: false` helped only a little and was fixed to turn it off completely in the 1.26.10 Preview/26.10. Only opaque full blocks cast AO. The `ambient_occlusion` property means received AO, not cast AO (a feature request). Fixed: vanilla slabs casting AO onto custom blocks (MCPE-236307), the custom/vanilla AO difference (MCPE-237493). The darker side of sand slabs looks like a game bug (sand is 0.55 per face). It is also the cause of PBR textures looking different from vanilla.
- **Fully bright blocks**: a block that emits no light and has no shading is made with `face_dimming` false + `ambient_occlusion` 0 (https://wiki.bedrock.dev/blocks/block-visuals-intro#shading). Dark animated item blocks and a cauldron darker than vanilla were fixed this way too. If too bright, adjust `minecraft:light_dampening`. AO/dimming can be toggled with permutations.
- **Black faces against walls**: add a plane, move the face 0.1 forward, or use custom culling (or live with it). For a head shadow, put one more top-UV plane 0.125 above the floor. Reduce the shadow under crops by raising the model.
- **Lighting artifacts**: lighting artifacts of custom slabs/stairs are reduced with `minecraft:light_dampening` and geometry culling rules. With `light_dampening` of 1 or higher mobs below do not burn in sunlight, and at 15 light bleeding is also blocked. Put it on full blocks so light does not leak. With high dampening the grass below turns into dirt and path blocks revert (related to solidity, nothing to do except lowering dampening).
- **26.0 / VV problems**: in 26.0 some custom blocks rendered black until the hotfix. Brightness mismatches in VV were fixed by checking the MER/subsurface scattering path. Texture layering breaks only in VV. VV turns off face dimming for entities but not for blocks. The block dynamic atlas compositing in VV (MCPE-237912) was fixed but items are not yet. The automatic attachable of a held block ignores MER (MCPE-237517). The combination of `blend` and reflective MER is unresolved.
- **PBR/MER**: works with `*.texture_set.json` + `_mer` and the pack capability "pbr". The only cause of one user's failure was `.png` in the terrain_texture path. A report that files made with the "create material" button of a Blockbench Bedrock block project apply without a texture-set when placed next to the texture, and an answer to set the `.texture_set` file together, are **conflicting**. The glowing part of a custom block works only in Vibrant Visuals.
- **Shadows and inventory display**: shadows on the sides of a model sunk into the ground were fixed in 1.26.10. Geometry with random offset or sticking out into a neighboring cell is drawn dark. A block invisible only in the inventory after 26.50 was solved by replacing it or setting Vibrant Visuals brightness to 100% (MCPE-241108).

#### Texture variations and flipbooks

- **Weighted variations**: write it in `terrain_texture.json` as below. It needs block (material) format 1.21.110 or higher, and below that it is handled without weights. Vanilla dirt uses `flattened_dirt`, stone `flattened_stone`, and sand the `flattened_sand`/`red_sand` keys (`stone` is kept for compatibility). A custom block can reference only the first entry of a vanilla texture array. Crimson/warped planks are in `textures/blocks/huge_fungus/crimson_planks`. Break particles do not follow variations. When buried in snow it returns to the first variation. Docs: https://learn.microsoft.com/en-us/minecraft/creator/documents/variationsblocktexture?view=minecraft-bedrock-stable.
  ```json
  {"textures": {"variations": [{"path": "textures/blocks/x", "weight": 50}, {"path": "textures/blocks/x2", "weight": 50}]}}
  ```
- **Adding variations to vanilla blocks**: change the terrain_texture entry of a vanilla key to `variations` (for example stone_bricks). To change vanilla faces with blocks.json, use `"textures": {"up","side","down"}`. The short grass override key is `short_grass` (not `tallgrass`). Vanilla block textures cannot be rotated by data, so use a pre-rotated PNG. A variation array without weights always uses the first entry.
- **Flipbook**: use `flipbook_textures.json` entries (`flipbook_texture`, `atlas_tile`, `ticks_per_frame`) and register the atlas_tile in terrain_texture as well. Because of mipmapping it falls back to the terrain_texture texture at a distance, so if it is not defined there it becomes a black/purple texture. There is a flipbook example using `minecraft:geometry.full_block` and `blend`. Thin stripes also blur from mipmapping, so use a separate thin block.
- **Break particles**: `minecraft:destruction_particles {texture}` (format 1.21.90+) sets the texture when breaking. Cracks grow across the whole texture. The particle texture bug (MCPE-234708) was fixed.
- **blocks.json**: for blocks that use data-driven tessellation only `sound` is valid. Putting `textures` on a geometry block gives "trying to override the Geometry component with blocks.json settings" / "override geometry ... not supported" errors. blocks.json maps vanilla blocks to terrain names. An attempt to do per-state textures with blocks.json failed with two states. The `format_version` of blocks.json is a string (`"1.1.0"`), and going above 1.21.40 gives an unsupported warning. As of 2026-08~10 blocks.json is needed only for sound and random textures. In one case a leftover default namespace from bridge. made textures get lost.
- **Hardcoded vanilla rendering**: chests, beds and banners are rendered as block entities. The copper golem statue texture is hardcoded and blocks.json changes only break particles (Mojang mention). Beds have no color state (stored in the block entity, all are `minecraft:bed`). The color is obtained with `block.getItemStack().localizationKey` ("item.bed.red.name"), but there is a report that it returns white.

### Culling rules

- **Setup**: put `minecraft:block_culling_rules` (format 1.21.80) in an RP `block_culling/` file and reference it from `minecraft:geometry`. Vanilla-style leaves:
  ```json
  "minecraft:geometry": {"identifier": "geometry.x", "culling": "namespace:culling.example", "culling_layer": "minecraft:culling_layer.leaves"}
  ```
  The rule fields are `cull_against_full_and_opaque`, `condition` (`same_block`, `same_culling_layer`) and `geometry_part`. `geometry_part.face` must be a single string, and an array gives "Failed to parse block culling file". Docs: https://wiki.bedrock.dev/blocks/block-culling, https://learn.microsoft.com/en-us/minecraft/creator/reference/content/blockcullingreference/examples/blockcullingrules/block_culling.
- **Constraints**: a rule only removes parts of the model and cannot turn them on, and checks a neighbor in only one direction. There is one rule per face but also one per bone, so to remove top and bottom together, split the bone. A culling rule cannot be used on full_block geometry, so make the model yourself. If a 3D ore is rendered even when surrounded, culling rules are needed. `cull_against_full_and_opaque:false` is ignored (MCPE-240757). If permutations have different transformations, the culling layer breaks (MCPE-234754). A warning about an undefined culling layer ("same_culling_layer but geometry has no culling layer defined") remains.
- **Connecting textures**: possible only with glass-style model culling (hiding faces/bones next to the same block) or a mod (https://www.curseforge.com/minecraft-bedrock/addons/connecting-textures). There is also a connected glass template that checks 4-direction neighbors with scripts. A connection table can be made with per-bone culling `"condition": "same_block"` and `cull_against_full_and_opaque: false`, but it fails at T intersections. Otherwise set per-leg states with onPlace/onBreak scripts. A "cave block" (a block that lets what is below show through) is also made with culling.
- **voxel shape**: voxel shapes in the BP `shapes` folder are a new feature and are currently used only for culling faces hidden by other blocks. In the 26.40 Preview they moved from experimental to the default vanilla BP, but because of regex validation custom blocks cannot use vanilla voxel shapes (MCPE-240758, intended "for now"). Vanilla block shape IDs shifted from the wiki values: sculk_sensor 125, azalea/flowering_azalea 132, glow_frame 133, glow_lichen 134, and there are undocumented sculk_shrieker and sculk_vein (they need 64 state values like glow lichen). The voxel shape bounds check was fixed on 2026-02-17.
- **voxel shape experiment and leaves**: when leaves became see-through, turning off the voxel shapes experiment fixed it.
- **Current role of voxel shape**: voxel shape currently affects only culling, so for per-permutation shapes geometry and culling must be redefined each time. Docs: https://learn.microsoft.com/en-us/minecraft/creator/documents/voxelshapes?view=minecraft-bedrock-stable.

### Sound

- **blocks.json `sound`**: still valid. `default` is a stone sound with only a different pitch (https://wiki.bedrock.dev/blocks/block-sounds). A blocks.json sound changes every block of that name, and to change it globally replace the audio file of the same name. End moss sounds are `moss_block` and `moss_carpet`, and the wood placement sound is `use.wood`. The gold block uses the same "metal" sound as stone, and iron/copper have their own IDs. No placement sound plays when placing in water (vanilla has the same bug). The instrument sound component was added in 1.26.30.
- **Registering custom block sounds**: copy the `sand` entry into `block_sounds` in RP `sounds.json` and register it as `namespace:block`. The `minecraft:sound` block component in the changelog is not in the docs, so see the changelog and schema. There is no block component that plays ambient sounds.

#### Mining speed

- **Tool tags**: putting `"tag:minecraft:is_pickaxe_item_destructible": {}` (or axe/shovel/hoe) as a component outside `destructible_by_mining` makes vanilla tools mine fast and applies Efficiency automatically. The tag is adjusted in proportion to hardness, so for axes `tag:minecraft:is_axe_item_destructible` is better than `item_specific_speeds`, and the `<material>_tier` tag is used only to lock tiers. A custom pickaxe must check this tag in the digger component. `tag:stone` has no known effect. Docs: https://wiki.bedrock.dev/blocks/tool-based-destruction (including the loot table section and mining penalty).
- **`item_specific_speeds`**: an array of `{item, destroy_speed}` in `minecraft:destructible_by_mining`, with item written like `{"tags": "q.all_tags('minecraft:is_pickaxe','minecraft:stone_tier')"}`. Tier tags such as `minecraft:wooden_tier` exist but `minecraft:is_wooden_pickaxe` does not. Vanilla pickaxe tags are `minecraft:digger`, `is_pickaxe`, `is_tool` and `<tier>_tier`. Below format 1.21.30 it fails without a warning (there is also a report that it did not work in 1.20.60). Whether per-tool entries override Efficiency is disputed. One opinion is that `item_specific_speeds` ignores Efficiency, so use digger (`use_efficiency: true`) + block tags. The pattern of a block mined only by a specific tool: `seconds_to_destroy: 999`, an entry with `q.all_tags(...) && q.any_tag(...)` and `destroy_speed: 1`, and the same tags in the loot condition. If destroy_speed is greater than seconds_to_destroy, a dev pack validation error occurs.
- **Matching vanilla speed**: `seconds_to_destroy` is not real seconds, and by default the real time is 1.5 times the value. Vanilla is 3.33 times slower when mining with the wrong tool, but custom blocks are not, so multiply it yourself. Method: `seconds_to_destroy` = vanilla hardness x 3.33 (bare hand), `item_specific_speeds[].destroy_speed` = hardness (for example brick 6.66 and 2 for `q.any_tag('minecraft:is_pickaxe')`) + pickaxe tag. Another formula is the wiki default x 2/3. The wiki penalty formula: right tool hardness x 1.5, wrong tool x 5, but Bedrock always applies 1.5, so wrong tool = H x 5/1.5 and right tool = H. Reference values: log style axe 1.975, stone style 6.63 with about 1.9 per tool.
- **Tags that do not work**: tier destroy tags (`minecraft:iron_tier_destructible`) and sword/mace tags (`is_sword_item_destructible`) have no effect on drops and penalties of custom blocks (MCPE-189586). `minecraft:is_shears_item_destructible` was fixed around 2026-08. There is no "drop only with the right tool" option. Block tags (`is_pickaxe_item_destructible`, tiers) are for mining speed, and item tags (`minecraft:is_pickaxe`, `minecraft:diamond_tier`, custom tags in item `minecraft:tags`) are for loot conditions/recipes. Only the loot table decides whether it drops.
- **`minecraft:digger` limits (as of 2026-02)**: a custom item with digger is always treated as the right tool for vanilla blocks (a custom sword mines stone faster) and drops regardless of tier. It does not reduce durability and supports only integer speeds (vanilla sword speed is not possible), and there is no `sword_efficient` block tag or custom tier. The first-person tool animation is also broken. Durability can be reduced with scripts, but it takes more than 10 API calls and instant-break blocks cannot be filtered out. `use_efficiency` works since 1.20.30. Tool durability loss on custom blocks must be done with scripts.
- **Deciding whether it can be broken**: there is no API, so keep your own list. Vanilla unbreakable blocks: command_block, chain_command_block, repeating_command_block, end_portal_frame, bedrock, structure_block, barrier, allow/deny.

#### Explosions

- **`minecraft:destructible_by_explosion`**: for `explosion_resistance` use the blast resistance from minecraft.wiki. Negative values are not accepted (the docs wrongly say negative/0 explodes easily). Explosion destruction resistance is about 5 times weaker than the vanilla value, so there is advice to give the expected value x5 with a comment. Even with `false` the Wither breaks blocks. Raise the resistance very high or cancel the destruction with a custom component.

#### Loot tables

- **Basics**: specify with `"minecraft:loot": "loot_tables/..."`. With a custom table the block does not drop itself unless you list it explicitly, and to drop both an item and the block use two pools. A loot table inside a permutation also works. Entry names must be real item IDs (there is a report that it became the `item:xyz` form and an opinion that it is a namespace problem, so unresolved). The `set_data` function and `count {min,max}` make data value drops (for example snowball data 2).
- **`match_tool`**: give item tags (for example `["minecraft:is_shears"]`) to `minecraft:match_tool_filter_all/any/none`. Without `"count": 1` an empty hand matches too. It needs a held item, so leaf loot cannot be reproduced. For tier-only drops list the allowed pickaxes in the `items` list. Since 26.30 (user report), match_tool makes ore not drop from explosions or a bare hand, and the "bare hand" condition can no longer be expressed with `match_tool_filter_none`, so use scripts. A Count 1 drop ignores explosions, and pistons or loss of support can drop both pools, so use onBreak for exact control.
- **Silk Touch**: hardcoded, ignores loot tables, and cannot be blocked even with an empty loot table. Workarounds are canceling `world.beforeEvents.playerBreakBlock` and in `system.run` doing `block.setType("minecraft:air")`, playing the sound, removing the default drops and creating the item with a script that checks Silk Touch, or replacing with air in `onBreak`. Wiki: https://wiki.bedrock.dev/meta/blocks-items-qna#disabling-silk-touch.
- **No loot table vs empty table**: a block with no loot table specified drops itself, and to drop nothing use an empty loot table.
- **Fortune**: the vanilla Fortune formula cannot be reproduced or reliably nerfed with loot tables, so scripts are recommended. Enchantment matching on the wiki works only up to level 2. There is no Fortune loot function for blocks (only looting for mobs), and it is approximated with per-enchant-level pools or several `set_count` entries with Fortune conditions.
- **Ore XP**: XP cannot be given by loot, so use a script that spawns `minecraft:xp_orb` in `onPlayerBreak` if it is not Silk Touch (https://wiki.bedrock.dev/blocks/ore-loot-tables#xp-reward-script). The consensus is items by loot table and only XP by script. In scripts you can read block + tool loot with `getLootTableManager()` (https://stirante.com/script/server/2.10.0/classes/LootItemCondition.html).
- **Vanilla loot cannot be changed**: vanilla block drops cannot be changed except for the new "data-driven" vanilla blocks of 26.50. The only way is deleting the drop and generating it with scripts. Sapling chance is also changed with a leaf-break script. Chiseled bookshelf loot is possible only indirectly. On 2026-10-24 there was again an answer that vanilla block loot cannot be overridden so drop with scripts. There is a report that the new blocks of the Poplar update are not data-driven (single report), and vanilla block definitions are not in the game's vanilla BP either.
- **Per-state drops**: the dropped item texture does not change per state, so a separate item is needed. For a block like a leaf litter pile, a loot table per state is easier than scripts.
- **Achievements**: to keep achievements even with a behavior pack, put `"metadata": {"product_type": "addon"}` in the manifest.

#### placement_filter

- **Format**: `{"conditions":[{"allowed_faces":["up"],"block_filter":["minecraft:glass",{"tags":"q.any_tag('dirt')"}]}]}`. The block filter list is limited to 64. There is no general "solid/non-solid" check or efficient tag that requires full support, and you cannot require all conditions at once. A vanilla-style filter is `"block_filter":[{"tags":"q.any_tag('dirt')"}]` (tag list https://wiki.bedrock.dev/blocks/vanilla-block-tags). ciosciaa shared a vanilla-compliant filter data.json.
- **Breaking on loss of support**: unstable. It works only when blocks are listed concretely in the filter (glass types are not caught by tags), and with cardinal+tag it stays if only one side is valid. With only `allowed_faces` and no `block_filter`, it only blocks placement on other faces. Client prediction always uses the default permutation/`block_face="down"`. The filter ignores rotation (MCPE-236323). To make dependent blocks (doors, supports) break exactly along, delete neighbors in the destroy event. Example: `allowed_faces: ["up"]` and `query.any_tag('minecraft:is_pickaxe_item_destructible',...) && !query.any_tag('minecraft:crop','one_way_collidable','plant')`.
- **Placing on every face (amethyst cluster style)**: `placement_position` defaults to "down", so that permutation is active before placement. Let the down permutation survive on every face, or in `beforeOnPlayerPlace` decide `e.permutationToPlace = ...withState("ns:hanging","true")` with `e.face` and the `e.block.above()/below()` tags, and otherwise handle with `e.cancel = true`.

#### support and connection_rule

- **`minecraft:support`**: `{"shape": "fence"|"stair"}`. It decides only what can attach to the block and is unrelated to collision. It blocks torches, levers, buttons and redstone dust from attaching to a face. If `stair` has no cardinal_direction/vertical_half, no face counts as full. A fence blocks the sides and allows only the top. Without the trait a torch cannot be attached. It cannot be used in permutations. On a custom fence `{shape:"fence"}` breaks its own connections. The vanilla face support types are none, center, edges and both (pressure plate top is center, button is both, door is edges, and edges exist only on the tops of composters and cauldrons).
- **`minecraft:connection_rule`**: went from the 1.21.130 beta experiment to stable in 26.0 and needs format 1.26.0+ (blocks below 1.26.0 fail as "experimental", so raise to a value such as 1.26.10). It decides what connects to this block, not what this block connects to. `accepts_connections_from`: `"none"` (blocks fence/wall/pane/bars connections and also blocks its own type, useful for custom plants and so on), `"only_fences"` (wooden fences + only customs that have the trait/tag, excluding panes, walls, bars and nether brick fences), `"all"` (all fences, walls, panes, bars, customs). There is no "same block" option, so connecting to itself needs scripts or culling. `enabled_directions` can be used for fence gates in permutations but there was also a crash (MCPE-236302) and advice to ignore it. Per-permutation filters do not work and it cannot be read from scripts. Docs: https://learn.microsoft.com/en-us/minecraft/creator/reference/content/blockreference/examples/traits/connection?view=minecraft-bedrock-stable.
- **connection_rule and rotation bug**: Mojang's workaround is to put the direction after transformation in `enabled_directions` (for example `"enabled_directions":["north"]` for rotation [0,180,0]). Adding the `minecraft:cardinal_connections` trait also worked. Querying `minecraft:connection_north` and so on in the connection_rule of base components gives all false and can crash with an update loop. Connections ignore rotation (MCPE-235806). The problem of the new trait breaking multiplayer (fence connections MCPE-235104) was fixed in the 26.0 release.
- **Custom fences and vanilla**: for a custom fence to connect to the vanilla nether brick fence it needs the `minecraft:has_fence_connections` tag (the vanilla nether fence does not connect to wooden fences). There was no tag to stop panes/walls from connecting to custom blocks before 26.0. Vanilla `minecraft:connection_up/down` appeared on some vanilla blocks in the Preview, but custom blocks cannot use them.
- **`tag:one_way_collidable`**: stops pushing out a player inside the block (https://wiki.bedrock.dev/blocks/vanilla-block-tags).

#### Liquids

- **`minecraft:liquid_detection`**: decides waterlogging and breaking in water. The only liquid kind is water, and lava interaction cannot be set.
  ```json
  "minecraft:liquid_detection": {"detection_rules":[{"can_contain_liquid":true,"liquid_type":"water","on_liquid_touches":"no_reaction"}]}
  ```
  `on_liquid_touches` is `"blocking"`, `"popped"` or `"no_reaction"`. Flowing water breaks "popped" blocks, but does not break a block placed in water. `stops_liquid_flowing_from_direction` blocks water flow from a specific direction (https://wiki.bedrock.dev/blocks/block-components#liquid-detection). It ignores transformation rotation (MCPE-234654) and has a flow bug (MCPE-234648). It was experimental/Preview as of 2026-02.
- **`use_liquid_clipping`**: a known bug present in 26.0 that has never worked (MCPE-236319). For z-clipping where the water texture shows through behind custom stairs, the only way is to inflate the geometry by about 0.001.
- **`liquid_clipped` (item)**: `minecraft:liquid_clipped` is an item component. Since 26.10, if true on a block placer item it is placed only on water (lily pad style). Normal placement in water is left false. Lily pad style placement works with `liquid_clipped: true` on the item, and scripts are needed only for survival behavior.
- **Survival in water**: a seagrass style block needs a tick custom component that checks `isWaterlogged`. It is unrelated to `enforce_survivability_rules` of features. A transparent block placed in flowing water gets a water texture variant, and the splash sound is removed with `/stopsound`. Custom fluids, water/powder snow fog and custom cauldron liquids are impossible (imitated with scripts + `/fog`).

#### Snowlogging

- **Component**: `"minecraft:precipitation_interactions": {"precipitation_behavior": "snowlogging"}` (the changelog/schema name is `snow_log_no_collision`). It must have no collision and was experimental until 1.26.30. To avoid being buried like flowers in snow, use `none`.
- **Bugs**: scripts cannot access the extra layer (onPlace fires for the snow layer). A size with only one axis at 0 or an empty array passes the zero-collision validation (MCPE-240708 "invalid"), and arbitrary collision is allowed in permutations. When buried in snow, containers drop their items, static color `light_emission` can fail, and texture variations return to the first value. The bug where random_offset returned to the center was fixed in the 26.30 Preview. The snow layer may not update on top of a snowloggable block (MCPE-237495). The snow layer on custom blocks cannot be blocked in worldgen.

### Redstone

- **`minecraft:redstone_producer`**: replaces the "block swap + redstone block below" hack used for buttons. It gives power (0 or 15) per permutation. `strongly_powered_face` is a single direction (a string, not "all" and not an array) and a warning appears if omitted. To make redstone dust connect to the block, use `connected_faces`. With `transform_relative: true` faces are relative to the block itself (a flipped model needed north instead of south). `connected_faces` follows the transform but `strongly_powered_face` needs an entry in every permutation. There is also a report that it must be defined in every permutation whose output changes for it to update. From 1.26.20 it must also be in the base `components` to be placed in a permutation. The same block cannot be both a producer and a consumer in its main components.
  ```json
  "minecraft:transformation": {"rotation": [0,180,0]},
  "minecraft:redstone_producer": {"power": 15, "connected_faces": ["east","south"], "strongly_powered_face": "east", "transform_relative": true}
  ```
- **producer bugs**: the output direction does not update when the permutation changes (MCPE-242205), and it does not face adjacent dust correctly (MCPE-242204). The strong output requirement (MCPE-234635) and emission update (MCPE-234647) were fixed in the 2026-03 Preview. There was a report that changing the signal strength in a permutation does not apply.
- **`minecraft:redstone_consumer`**: `min_power`, `propagates_power`. Used together with format 1.26.0+ and the `onRedstoneUpdate` (`e.powerLevel`) custom component, and cheaper than a per-tick check (stable in 26.0). Without turning on `propagates_power` it does not conduct even with full geometry (the default does not change to `redstone_conductor`, MCPE-232715 intended behavior). For side dust to connect, `redstone_conductivity.redstone_conductor` is needed. A consumer has no direction so a repeater cannot be made, and it cannot bend or pull dust. It also turns on from a redstone torch placed beside it (unlike the vanilla redstone lamp). A block that is also a consumer cannot give comparator output.
- **onRedstoneUpdate notes**: it also fires on first placement and chunk load, so toggle blocks such as doors/trapdoors need a separate power state to detect a change. The beta `firstUpdate` boolean filters the initial load event (still beta in 2026-07). `previousPowerLevel` can be less than the consumer's `min_power` (a docs error) and is 0 on the first update when a chunk starts ticking. Do not use onTick for redstone behavior.
- **Power loss and conduction**: detect power loss with consumer `min_power` 0. Redstone updates fire for more than power changes (https://wiki.bedrock.dev/blocks/block-events#redstone-update). A custom block that does not conduct blocks the button signal from the other side (redstone-conductivity docs). There are also complaints that the conductor setting does not guarantee conduction.
- **Lit/unlit ore**: change light_emission and texture with a `pro:lit` state and a `query.block_state('pro:lit') == true` permutation, and revert with random tick or tick.

### Other components

- **`minecraft:friction` (conflicting)**: there is a report that the default is 0.4 so the 0.6 on the wiki is wrong. Opinions split on direction. Two reporters think the wiki explanation is backwards (one: higher is more slippery and lower is stickier, 0.2 is almost slime; another: lower means more friction and higher means less, and it works properly only on boats). One reporter says higher friction reduces slipperiness but raises speed, and thinks that one value changes two internal things together so a soul sand style block is impossible. One reporter said too high makes you fly off or be very slippery. Making it as slow as vanilla slime does not work even with 0.1. If you want the default, omit it.
- **`minecraft:flammable`**: the value is an object (`catch_chance_modifier`, `destroy_chance_modifier`, `lava_flammable`), not `false`. `lava_flammable` works in format 1.26.20+ and is silently ignored below. The default is `"never"` even with `flammable:true` (MCPE-240718, intended behavior), so the docs' "true = same as planks (catch 5, destroy 20)" is no longer true. Before this component, lava was always treated as igniting, and a block that burns forever (netherrack) or a flammable block immune to lava could not be made. Fire and soul fire are hardcoded (the soul_fire base blocks tag is an item tag).
- **`minecraft:replaceable`**: accepts only `{}` and makes a block replaceable like grass.
- **`minecraft:crafting_table`**: gives a custom crafting UI (https://wiki.bedrock.dev/blocks/block-components#crafting-table). There is no furnace component. A furnace returning a bucket is done with an inventory change script.
- **`minecraft:map_color`, `minecraft:display_name`**: specify the block map color (the map color of vanilla blocks cannot be changed). `BlockMapColorComponent` does not work on vanilla blocks (MCPE-240722). Name composition is done inside the display_name component, not on the localization side. The problem of `Block#localizationKey` ignoring display_name (MCPE-235802) was fixed.
- **`minecraft:flower_pottable` + `minecraft:embedded_visual`**: needs format 1.21.124+ (before that the plant sat on top of the pot). Even if every permutation has geometry + material_instances, it must also be in the root separately (MCPE-237910). From 1.26.20 it is banned in permutations. Pot pinning/pick block/transparency bugs (234585/234586/234599) were fixed.
- **`minecraft:chest_obstruction`**: applies to chests, ender chests, trapped chests and copper chests and not to shulkers. The `"shape"` mode uses the collision box and fails if it overlaps origin [-7,0,-7] size [14,8,14]. Several boxes are merged into one AABB and follow the transformation. In formats before 1.26 it ignores permutation differences. Kaioga stairs set it to never. There is a report that `minecraft:chest_obstruction` broke blocks in format 1.26.20 (unresolved, single report).
- **Tags (conflicting)**: the older format writes block tags as `"tag:ns:name": {}` components (items/biomes use `minecraft:tags`). From format 1.26.20 a `"minecraft:tags": ["ns:tag"]` array replaces it and `tag:*` cannot be used in the new format, and 1.21.130 has no `minecraft:tags`. However, there is a report that around 1.26.20 the opposite happened, the array did not load and the `tag:` form was needed, so it is **conflicting** (check block-format-history). More recent 2026-08~09 reports confirm that in 1.26.20+ the `"minecraft:tags": [...]` array is correct, the old `tag:` key is a schema error, and `minecraft:tags` parse errors are fixed by raising to format 1.26.20 or higher. Attach a namespace to tags (`Block.getTag`). Whether slashes are allowed in tag names is not confirmed. A planks tag for recipes needs a block item that has the planks tag. `query.block_neighbor_has_any_tag`/`block_has_any_tag` can no longer be used.
- **leashable**: the default `[0,0,0]` must be the block center. The mining destruction property name is wrongly named. A scheduled tick can fire even without a hook.
- **Sulfur cube (26.20 Preview)**: picks up a custom block that has the `minecraft:sulfur_cube_archetype_bouncy` tag (https://wiki.bedrock.dev/items/vanilla-item-tags). The problem of material_instances blocks being drawn very small (MCPE-238028) was fixed on 2026-05-14.
- **Cushion**: flower/leaf cushions treat custom blocks as solid.
- **Plants and the grass below**: if the `light_dampening` of a custom plant is not 0, the grass below becomes dirt (safe at the default 0). In 2026-05 it turned to dirt even with `collision_box: false` (waiting for a solidity change).
- **inside_block_notifier**: the entity's `minecraft:inside_block_notifier` cannot use a custom block state as a condition.
- **Mob spawning**: mobs (including custom ones) did not spawn on custom full blocks of an old format, but this was fixed in format 1.21.90+ (one user needed 1.26.0). The block must be solid/opaque. One reporter said entities do not spawn if a custom block is used as the biome `top_material` (2026-06).
- **trial spawner**: it spawns only when natural mob spawning rules are on. A workaround is to block natural hostile mob spawning with BP spawn_rules (format 1.8.0 `minecraft:spawns_on_block_filter: ["minecraft:deny"]` / weight 0). The ominous setblock and loot of a vault are seeded by position.
- **Component ordering (ciosciaa's suggestion)**: METADATA (display name, loot, transformation, random offset, tags) -> PRESENTATION (geometry, material instances, item visuals, embedded visuals, destruction particles, map color) -> PHYSICS (selection/collision box, friction, light dampening/emission, precipitation, destructible by mining/explosion, liquid detection, flammable, movable) -> RELATIONS (placement filter, replaceable, support, connection rule) -> FEATURES (redstone, crafting table, leashable, flower pottable) -> EVENTS (tick, fall-on).

### Patterns made with blocks (doors, slabs, stairs, fences, crops and so on)

- **Doors**: in `onPlayerInteract(event, definition)` toggle a boolean state with `permutation.withState` and play the sound with `dimension.playSound(sound, block.center())`. Parameter example: `"ns:door": {"block_state":"ns:open_bit","enable_sound":"open.wooden_door","disable_sound":"close.wooden_door"}`. Open/hinge are handled with `bone_visibility` Molang (`"door_open": "q.block_state('ns:open_bit') && !q.block_state('ns:door_hinge_bit')"`). A 2-tall door sets both halves (before multi-block there were 2 blocks, and the bottom placed the top with a script). Define the geometry once in the base, and omit the base collision/selection box if permutations set them. Combine block and item with `block_placer` + `replace_block_item` and use the `minecraft:is_axe_item_destructible` tag. The hinge/direction logic of vanilla fence gates remembers the last interaction so it is hard to reproduce (3 state bits + a player rotation check script).
- **Trapdoors and pressure plates**: a trapdoor does `block.permutation.withState("ns:open", !isOpen)` in `onPlayerInteract({block, dimension})` and plays `open.wooden_trapdoor`/`close.wooden_trapdoor` at `block.center()`. A pressure plate toggles a boolean with `onStepOn`/`onStepOff`, but a thin plate is hard because of the height constraint (the vanilla plate uses a scheduled tick over the box). Kaioga recommends block_entity. Vanilla doors react to wind charges through projectile-hit, and custom blocks need a tick component or a projectile hit event.
- **Slabs**: switch one full-block geometry with two bones using `vertical_half` and add a double state. To replicate vanilla slab behavior use `minecraft:support {shape:"stair"}` + `minecraft:vertical_half` (without cardinal/facing traits). support cannot be in permutations, so keep the double slab as a separate block file. They do not stack automatically, so scripts are needed.
  - Method 1: check `minecraft:vertical_half`, `blockFace` and the held item in the `ns:is_double_slab` state and `beforeEvents.playerInteractWithBlock` (`isFirstEvent`). After `event.cancel = true`, do `withState(state, true)` in `system.run` and reduce the item. Registering an empty `beforeOnPlayerPlace` component made the client do the server-side check and fixed the glitch.
  - Method 2 (Sky Dimensions): make the item not place itself with `"minecraft:block_placer": {"aligned_placement": true, "block": "...", "replace_block_item": true, "use_on": [{"tags": "q.any_tag('this_tag_should_not_be_used_on_any_block')"}]}` (or `"tags": "false"`) and let an item custom component handle placement and merging. The swing animation remains, and using both events needs `activeUses` tracking.
  - Method 3: in the item component `onUseOn`, look at `usedOnBlockPermutation`, `blockFace`, `faceLocation.y` and `minecraft:vertical_half`, and place a half in the adjacent cell or set `namespace:double` to true (`BlockPermutation.resolve(typeId, {...})`). `faceLocation.y` is flipped at y&lt;=0 (MCPE-236442, still open on 2026-08-29), so it must be corrected.
  - After 26.20 a ghost block shows when placing a double slab (a placement cancel bug). Double slabs cannot be pick-blocked.
- **Stairs**: the 26.0 stable traits (`placement_direction` + `vertical_half` + `corner_and_cardinal_direction`) combine into 40 permutations. Following the vanilla shape needs many bones and visibility toggles, or several geometries. UV lock changes only the UV mapping and does not affect direction bindings, and it does not work properly on rotated stairs. It needed per-permutation geometry (main + east/west) or bone UV adjustment, `"isotropic": false`, and `uv_lock` false for some textures (smooth stone). Collision uses two multi boxes. The selection box stays a full cube (you cannot select behind the empty corner like vanilla). There is a stair self-cornering bug MCPE-234801. The dmahonjr template (waterlogging, direction, uv_lock, corners) shrank from 83KB to 27KB in format 1.26.20, but there is a report that it breaks in 1.26.50.
- **Fences, walls, panes**: in the fence template, a collision width of exactly 16 gives a water glitch, so use 15.999. `use_beta_features` in the template broke client joining. A fence gate needs a custom component (`dma:fence_gate`, script module 2.5.0+/2.6.0-beta), and fences also connect to the front and back of the gate. In the wall template (26.0+ connection trait) `sticky:"same"` blocks piston movement so use "none", and panes must be treated as attachable to walls. The upper part of a wall depends on the connections and the wall above, so 6 boolean states are needed. A custom pane was not possible natively on stable releases before 1.26 and needed scripts (100-300 lines, permutation switching) (https://wiki.bedrock.dev/blocks/custom-glass-blocks). There is no vertical connection trait, and vanilla wall states (165 wall shapes) are not exposed. Mojang (2026-06-23) said vanilla stair/wall shapes cannot yet be made data-driven.
- **Crops and vines**: grow with `minecraft:tick` (or `onRandomTick`, cheaper) + `permutation.withState(state, value+1)`, and handle the fully grown stage with a permutation condition component. Crops that are safe to step on: https://wiki.bedrock.dev/blocks/custom-crops. If farmland is below, give slow_falling to prevent trampling (a 10-block check, and mobGriefing affects only non-players). For vines (tip/body blocks, `ns:age`, `ns:sheared`), `onRandomTick` turns the tip into a body and places a new tip below. Bone meal does `cancel = true` in `playerInteractWithBlock` and is handled with `system.run`. Survival consumption does `stack.amount--; slot.setItem(stack)` with `getEquipmentSlot(EquipmentSlot.Mainhand)` and skips in `GameMode.Creative` (v2 is uppercase, v1 is `GameMode.creative`). Custom nylium bone meal scans neighbors with `dimension.getBlock`, finds air above a valid floor, and calls `spawnParticle("minecraft:crop_growth_emitter")` and `playSound("item.bone_meal.use")`. Vanilla plants cannot be placed on custom blocks, and sugar cane style support did not work with the sand tag.
- **Saplings**: features are placed on top of saplings, so the sapling must be in the feature's `may_replace` or erased first. Use `dimension.placeFeature`. Cloning vanilla saplings became possible with new APIs.
- **Stripping logs**: if there is an axe in the main hand, do `block.setType(stripped)` in `onPlayerInteract`, and reduce durability with `item.getComponent("minecraft:durability").damage++` and then `slot.setItem(item)` (`ItemStack.damage()` does not exist).
- **Delayed replacement and 2-tall blocks**: replacing a block after a delay is done with `system.runTimeout`. A 2-tall block places the upper block with `permutationToPlace` in `beforeOnPlayerPlace` and copies `minecraft:cardinal_direction` (a 1-tick delay in the preview). A die is made with a random state on placement + rotation permutations.
- **Other vanilla-style things**: stackable blocks (sea pickle style) https://scriptlabsmc.vercel.app/templates/stackable-block, and the numeric state template of turtle eggs/candles is community thread 1434287459591782442. A bouncy block does `applyImpulse` from the `onEntityFallOn` fall distance (bounces 1 tick after landing), and fall damage is canceled in before entity hurt by checking the cause fall and the block below. Climbing works only with onTick + impulse. Cactus damage uses `system.runInterval` instead of per-block ticks. Fire detection is done with a tick component that checks for `minecraft:fire` nearby. A portal is made as a normal block with custom geometry, collision, an animated texture and an axis state (a 1x2 wall portal is unresolved).
- **Structure void style blocks**: a transparent block that is visible only when held is made with `minecraft:geometry.full_block`, `minecraft:collision_box: false`, `"*": {texture:"invisible", render_method:"blend"}`, `minecraft:selection_box: true`, a repeating `minecraft:tick` interval [1,1], and an onTick that emits `minecraft:shulker_bullet` particles when the player holds the item (format 1.21.90). With `player.spawnParticle` only that player sees it. Barrier visibility is hardcoded.
- **Summoning entities from blocks**: have a `complete` boolean state, and the tick of the complete=false permutation summons the entity and then changes complete to true. Entities in structures use the same method of "a ticking block summons and erases itself".
- **Dynamic lighting**: dynamic lighting add-ons all place or move a `light_block` at the player position.
- **Updating multi-block structures**: walk the neighbors with a BFS queue and a visited Set keyed by `x,y,z`, comparing typeId and `minecraft:cardinal_direction` (recursion without visited loops forever). Pass `block.permutation` to `setPermutation` instead of setblock air. A `Block` object is created anew on every access, so using position + permutation can be faster. To break blocks from scripts use `/setblock ... destroy` with runCommand.
- **Template collections**: Kaioga's Block Templates (https://github.com/Kaioga5/Kaioga-s-Block-Templates) started with 71 vanilla block recreations and is about 80 now. Each is a BP+RP pair and a .mcaddon for double-clicking, with comments and no experimental toggles. It targeted the 1.26.40 stable release and was updated to 1.26.50 on 2026-09-16 (distributed for the stable release only). It includes cactus, cake, vines (random tick spread, shears only), ladder, walls, snow layers, ore, doors (split into 4 custom components for teaching) and slime blocks. In 1.26.50 the slab/fence/trapdoor icons changed. Most vanilla geometry was taken from the Java vanilla pack, PRs are not accepted and issues are welcome.

### What blocks cannot do and entity alternatives

- **Impossible (replace with entities or scripts)**: falling/gravity blocks (a custom falling entity with the same texture), animation controllers and continuous animation, chests/containers (before 26.50 block_entity), signs/text (bone-based "Primitive Shapes" text is a temporary alternative), custom fluids, barrier visibility, end gateway effect, blocks visible through walls, non-solid blocks that cannot be attached (ladder/button style), blocking mob pathing (decided by the entity-side `behavior.avoid_block`), setting vanilla map colors, modifying/replacing vanilla blocks (chests and so on, cannot be replaced with the same ID), dispenser detection and dispenser-style behavior (other than rebuilding a custom dispenser), XP drops from blocks (scripts needed), an invisible pumpkin (the texture turns black), neighbor change events (onNeighbourUpdate, expected "around .60/.70").
- **Entity alternative patterns**: interactive furniture, item displays, storage drawers and pedestals are made with invisible entities (summoned on placement, removed on destruction, collision from entity components). Inventory block = inventory entity, and `player.openInventory` does not exist, so make sure the entity does not die on the interaction path. An entity chest can despawn on close and save its inventory with scripts, but many entities cause lag. The state switch trick is to hide the block, summon a non-interactive entity, erase it, and set the new state. To protect against `/kill @e`, give minimum health 1, and `/tp` can be blocked only by a script that saves coordinates and teleports back. Needing one more click on a furniture entity is because the hitbox is small, so enlarge the hitbox or track entity interaction. The barrel template is an entity container + block state (https://github.com/Alien-Edds/Barrel).
- **Custom heads**: 16 directions, wearable. The charged creeper drop is hardcoded, and only the wither skeleton loot is data-driven (`chance` condition). Block geometry has no Molang, so there are only 4 head bones. N-way rotation reduces scripts.
- **What custom wood sets lack (2026-02)**: sign text, double slab pick block, shelf item display/comparator, block sounds for sound blocks, lava flammability (added later in 1.26.20). In 2026-07 the assessment was that shelves are impossible, boats are awkward and sign writing is impossible, and on 2026-09-08 an assessment came out that everything except pressure plates (stairs, fences, doors, buttons, trapdoors) is possible. The axe animation that makes stripped logs is vanilla only.
- **Other impossible things**: billboard-style blocks (imitated with particles + invisible geometry), brushable blocks, acting as soil for vanilla plants, ender pearl style chunk loading, shulker box behavior, a new storage block type before block entities.
