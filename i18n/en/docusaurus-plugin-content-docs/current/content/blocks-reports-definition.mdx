# Block community reports - definition and custom components

These are individual reports from community research (2025-10-22 ~ 2026-11-13) that the preceding documents of this page did not summarize. The `[uNNN date]` at the end of each item is the research note number and the report date, and `(single report)` marks content reported by only one person.

#### format_version

- **Only the format_version of the block file matters**: custom components and new features are opened by the `format_version` of the block JSON. The manifest `min_engine_version` affects only the Molang/commands of the BP, so keep it at the latest. A 1.21.90 block got the new traits working just by raising the number to 1.26.0 (no component changed format between 1.21.90 and 26.0). If the Realm is not yet on that version, it is ignored or fails.
- **Effects per format_version (compiled by ciosciaa, changelogs are often wrong)**: 1.19.10 map color/flammability, 1.19.20 friction, 1.19.40 geometry + material_instances, 1.19.50 collision + crafting table, 1.19.60 display name, selection, adjacency filter, 1.19.80 transformation, 1.20.10 Molang bone visibility in geometry, 1.21.30 mining destructibility hardness override, 1.21.70 intrinsic particles + `isotropic`, 1.21.90 UV lock + destruction particle count, 1.21.110 atlas tile in texture variations, 1.21.120 alpha-based tint masking, 1.26 fix for hardcoded full-block bottom face rotation, 1.26.20 trailing comma, tags component, block entity component, visual rotation state binding in geometry, lava flammability, versioned Molang in permutation conditions, flower-pot display fix, relaxed identifier/state name validation, stricter placement_direction/geometry validation, flower_pottable banned inside permutations, a redstone producer must also be in the root to be placed in a permutation, 1.26.30 instrument sound component. Multiple collision boxes also worked in 1.20.80 (the bug fix is in 1.26.30). Blockception suggests the tags component for every version, but it is actually tied to the version.
- **1.26.20 new parser**: the `ambient_occlusion` boolean was removed and it accepts a number 0-10 (using a boolean gives an unrelated "invalid string" error). Error messages have no location info. In 1.26.20 `menu_category` was wrongly required for blocks with item overrides ("Menu Category should not have an empty value", workaround `"menu_category": {"category": "none"}`, fixed by 2026-03-31). Going back to an older version such as 1.21.130 still loads but loses the new components, so it is not recommended.
- **Components outside `components` are silently ignored**: for example, `"minecraft:collision_box": false` placed outside `components` gives a unit cube collision with no error. `"minecraft:collision_box": false` inside `components` works in both the stable release and the Preview.
- **Version notation**: the block format_version is written in the game version form such as `1.26.30`, and `"26.30"` does not work. Using a version newer than the game gives `Unexpected version for the loaded data`. (single report)
- **`permutations` location**: put it directly under `minecraft:block`, not inside `description`.
- **"Blocks between client and server do not match" join error**: it was fixed in 1.21.121 by removing tick/state components and in 1.21.130 by removing the `minecraft:connection` trait (error code "Boat"), with no log warning.
- **1.16.100-style syntax is dropped**: use the 1.21.10+ format. Blocks from the 1.16 era appear as "?" / "update block" until migrated (using 1.21.130 is recommended).

#### Legacy renames

- `minecraft:entity_collision` -> `minecraft:collision_box`, `minecraft:block_light_dampening` -> `minecraft:light_dampening`, `minecraft:pick_collision` -> `minecraft:selection_box`, `minecraft:block_light_emission` -> `minecraft:light_emission`, `minecraft:destroy_time` -> `minecraft:destructible_by_mining.seconds_to_destroy`, `minecraft:rotation` -> `minecraft:transformation`, the `minecraft:block_property` query -> `q.block_state`, `properties` -> `states` (renamed in 1.20.30, with no plan to revert). `minecraft:ticking` does not exist and is `minecraft:tick`. `minecraft:foil` on block icons became the item `minecraft:glint`. Block events (`events`, `minecraft:on_placed`, `set_block_state`) were removed around 2024, so use scripts.

#### File locations and names

- **Texture mapping files**: put `terrain_texture.json` (singular) and `item_texture.json` in `RP/textures/` (not the pack root). Putting the `.png` extension in a path breaks PBR texture sets. Invalid JSON or a UTF-8-SIG (BOM) file gives "failed to parse".
- **lang keys**: blocks are `tile.<ns>:<id>.name` (blocks keep `.name`), and items are `item.<ns>:<id>.name`. Do not use uppercase in identifiers.
- **menu_category**: put it directly inside `description` (not inside `traits`). Values are lowercase (`"Construction"` or the typo `menu_catagory` silently hides it from creative). A `category` key has never existed on blocks. To hide, use `"none"` or omit it (`hidden` is invalid). Omitting was allowed again from Preview 26.20.23. If you use `replace_block_item`, the item's menu_category takes priority. `register_to_creative_menu` stopped working in 1.26.20. Group example: `minecraft:itemGroup.name.slab`. In one case a `minecraft:` prefix on a custom group name caused problems and removing it fixed them, and `is_hidden_in_commands` is separate from hiding in creative. (single report)
- **Where geometry and name translations go**: block geometry files go in RP `models/blocks/` (not `models/entity/`). Block name translations go in RP `texts/en_US.lang`. `/reload` rereads only scripts, and `/reload all` rereads everything.
- **Blocks of a removed pack**: the identifier and states remain in the world and are restored when the pack is turned on again. Meanwhile they look like missing textures, and you cannot specify a replacement block or delete them automatically.
- **traits location**: put `traits` inside `description`.
- **Subfolders**: subfolders of `blocks/` usually work too. One user got `light_emission` working by moving the file directly under `blocks/`, but it is not confirmed as general (the cause in another case was bridge. not saving). (single report)
- **Minimal light emission example (valid in 1.26.30)**: `"minecraft:geometry": {"identifier":"minecraft:geometry.full_block"}`, `material_instances`, `"minecraft:light_emission": 15`. The spelling is `light_dampening` (not "damping").

#### Reading the Content Log

- **Order of block errors**: the first line says the block is invalid, the second says which component, the third gives the reason (the real cause), and the fourth is data that does not match the format_version. "Unexpected version for the loaded data" usually comes along with an earlier real error, so scroll up in the log. In the 2026-03 Preview and 1.26.x it also appeared as a harmless bug.
- **"block named X used in a blocks.json file does not exist in the registry"**: means block JSON loading failed. Get the full log from the Settings > Creator tab and find the cause (one case was a wrong `selection_box`). Troubleshooting doc: https://wiki.bedrock.dev/blocks/troubleshooting-blocks.
- **Missing registry warning**: the pack is not turned on or not fully reloaded. Restart the world or take the pack out and put it back. After changing geometry/textures, put it in a development pack and use `/reload all`.
- **Editor false positives**: the Blockception VS Code extension wrongly flags `minecraft:geometry.full_block` and the `wool`/`carpet` block filter ("mcbehaviorpack.blocks.missing"). The bridge. schema wrongly rejects `block_face`, integer `count` and numeric `ambient_occlusion`. bridge. had a breakage report in 2025-12. AI chatbots hallucinate a lot on Bedrock add-on topics.

#### Registration

- **v2 registration method**: 
  ```js
  import { system } from "@minecraft/server";
  system.beforeEvents.startup.subscribe(({ blockComponentRegistry }) => {
    blockComponentRegistry.registerCustomComponent("ns:id", { onPlace(e) {}, onTick(e) {} });
  });
  ```
  In the block JSON, write `"ns:id": {}` directly in `components`. The requirements are block format 1.21.90+, `@minecraft/server` 2.0.0+ in the BP manifest, and a script entry in `modules` (`{"type":"script","language":"javascript","entry":"scripts/main.js",...}`). The component file must be imported from the entry file. One reporter's note said a `minecraft:custom_components` array is needed, but that is the old format that has been invalid since 1.21.90.
- **Manifest version conflicts**: conflicting gametest dependency versions break script loading. At that time on the stable release use `@minecraft/server` `2.7.0` and server-ui `2.0.0`, and leave out the unused `@minecraft/server-gametest`. (single report)
- **"child 'x:y' not valid here" / "component found in input but not present in Schema"**: the causes are the component not registered with the API, registered in the wrong registry (itemComponentRegistry), an old format_version (for example 1.20.80), no script module in the manifest, a script error or wrong import, or one of several manifests in a folder. `bone_visibility` placed outside `minecraft:geometry` gives the same error. Wrapping in a fake `minecraft:components` object is not a solution.
- **Registration timing**: importing main one tick late, as in `system.run(() => import("./main"))`, breaks startup registration. If there is even one script error, block/item components may not attach. `/reload` does not run startup again.
- **Other warnings**: "Block custom component 'x' is not being used by a block" means the format_version or location is wrong. "component used on block but not registered in script" means it is not registered or the `@minecraft/server` metadata version is wrong. Right after the 2026-03 block schema change, every custom component got `No transformer found for component ... Cannot downgrade from modern slice to legacy component` (MCPE-237057). In betas with Upcoming Creator Features on at that time, custom components could not be used.
- **Parameter nesting**: the nesting depth of custom component parameters is at most 2. `tag` is also a valid custom component namespace.

#### Hooks

- **Available hooks**: `onPlace`, `onTick`, `onRandomTick`, `onPlayerInteract`, `beforeOnPlayerInteract`, `onPlayerBreak` (formerly `onPlayerDestroy`), `onBreak`, `onStepOn`, `onStepOff`, `onEntityFallOn`, `beforeOnPlayerPlace`, `onRedstoneUpdate`. `beforeEvents.blockTick`, `permutation.getMaterial()`, `onEntityStepOn` and `onEntityInside` do not exist.
- **onBreak**: appeared as an experiment in 1.21.130. It gives `brokenBlockPermutation` and `entitySource` and also fires when broken by pistons, explosions and loss of support. It is used when breaking both sides of a 2-tall block, making explosion-only loot, and preserving the broken block's state. It does not fire when broken by a survivability failure (MCPE-240755).
- **onPlayerInteract**: blocks normal use and placement against that block (placing works only while sneaking). Vanilla interaction conditions were not ported and this is not treated as a bug. Even if it is on only one permutation, every permutation becomes interactable (MCPE-225746). If any active custom component exists, the block becomes interactable. To avoid blocking, use `world.beforeEvents.playerInteractWithBlock` and handle it inside `system.run` (the after event fires only on interactable blocks).
- **beforeOnPlayerPlace**: change `e.permutationToPlace` or block with `e.cancel = true` (no placing on water and so on). Using this hook turns off client prediction, which makes fast bridging hard. Putting it inside a permutation did not suppress prediction (MCPE-238017, fixed around 2026-05-19, opaque/blend only). On a `replace_block_item` block it runs after the block is placed. There is also a report that a block placed by an item does not call this hook.
- **onPlace notes**: fires on every placement (including fill/setblock). With `onPlace` alone, the client prediction of player placement remains and flickers briefly, and defining `beforeOnPlayerPlace` skips the prediction. If broken in the same tick, `e.block` can be `minecraft:air` (after events reflect the later state). It can run before neighbors settle, so delay with `system.run`.
- **Tick timers**: `minecraft:tick` has no count limit and supports delayed queued ticks, but one block cannot have two tick timers. `onRandomTick` is preferred for performance (crop growth, falling leaf particles). Vanilla leaf particles ignore randomtickspeed, so the two cannot be matched at the same time. To turn ticking off, use one state and two permutations (only one containing `minecraft:tick`). Each permutation can have a different tick interval range. After the 2025-11 late hotfix there is a report that random tick blocks do not tick after the world loads/updates, and a case where a heavy tick component that changes several states every tick crashed the game. (single report)
- **Scheduled tick throughput**: for each chunk-dimension pair only 100 blocks per tick run scheduled-tick behavior, the rest cycle, and all countdowns decrease (400 blocks with a 4-tick timer stabilize after 8 ticks).
- **Tick performance**: when about 30 pressure plates in one area used block `onTick`, 10-15ms spikes occurred. Player-side ticks (checking the block under the player) or the projectile hit event are recommended. To find every instance, building a position registry with `onTick` is practical (dimension searches are impractical).
- **Side effects of permutation changes**: if you change the permutation of a placed block with `onTick`/a redstone clock, the player cannot place against that block during that tick (an old problem).
- **Hand swing**: half of the block component events force the hand swing animation.

#### Permutations and the custom component bug (MCPE-234714)

- **Symptom**: only the custom components of the last (bottom-most) matching permutation apply, and those defined elsewhere are ignored (presumably merged into one `minecraft:custom_components` value). If it is in both the root and the default permutation, only the permutation side is read. Other components and ticking can also break. The workaround is to define every custom component in every permutation. Unresolved as of 2026-10.

#### States

- **Rules**: state names need a namespace (`gen:type`). Without it, `Identifier must have a namespace / Failed to create Block State Description` appears. At most 16 values per state, an integer range is `{"values":{"min":0,"max":15}}`, and string/boolean arrays also work. If you need more, use two states. A limit on state string length is not confirmed (1000 characters were valid, and chat crashes at about 450).
- **Bitmask**: to attach 6 faces like moss/sculk vines, set faces to 1,2,4,8,16,32 and use sums 1-63. 8 one-bit states can imitate a byte.
- **Every combination is generated**: a block always creates every permutation of its states. You cannot reuse vanilla states that have fewer values. A changed state in an existing world updates only when it ticks.
- **Block components are not saved**: components are derived from the permutation (identifier + state values), and the only thing saved is the queued tick of `minecraft:tick`. There is no `block.setTexture` and the server has no concept of textures. To change geometry with scripts, tie permutations to a state and use `block.setPermutation`.
- **Script API side**: many state values are strings (`turtle_egg_count: "one_egg"`, `inner_left` of the stair `minecraft:corner` and so on). `BlockStates.get(name).validValues` gives the value list, but flattened legacy types such as `stone_type`, `sand_type`, `dirt_type` and `old_leaf_type` give `[]`. `BlockPermutation.getAllStates()` gives only current values. `BlockStates.getAll` is an arbitrary union, and deprecated states such as `color` and `old_log_type` are also exposed for compatibility (cannot be fixed until Script API 3.0).
- **States are local to the block type**: `mojang-blocks.json` lists shared states (for example `rail_direction` is shared by `rail` and `activator_rail`, but activator_rail has no rotation values), but generating every combination creates permutations that do not exist. One way is to try `BlockPermutation#withState` and skip failures. Legacy states are excluded from the palette hash. Mojang (mammerla) answered that the engine has no central record of valid states per type, so no extra metadata will come. Internal blocks that are in the palette and Script API but not in the metadata: chalkboard (a dedicated direction state 0-15), client_request_placeholder_block, deprecated_anvil, deprecated_purpur_block_1/2, end_gateway, glowingobsidian, info_update, info_update2, invisible_bedrock, moving_block, netherreactor, reserved6, stonecutter.
- **Data values**: item data values work in `testfor`/`give` but block data values do not. Block aux IDs are fixed, and item numeric IDs are assigned at runtime (vanilla IDs above 256 get pushed by add-on content, and some vanilla blocks have stable negative IDs, for example sulfur about -1125). 3D block rendering in `beacon.item_renderer` needs that ID.
- **Command autocomplete**: renumbers numeric state values from 0 (MCPE-236301).
- **Per-type registration**: if a 2-value state with the same name is on blocks A and B, the permutations total 4 (not shared between types). Vanilla internal state names (`weirdo_direction`, `pillar_axis`) differ from the trait states for creators.
- **States in structures**: there is a report that placing a structure with custom blocks by command places the wrong state unless you specify the state explicitly. (single report)

#### Permutation rules and limits

- **Writing rules**: components may overlap between permutations or with the base, but do not repeat the same condition. Permutations can be separate by feature (rotation 4 + texture 2) and need not be a Cartesian product. Conditions can use `&&`, `||` and parentheses. Merge identical results with `||`. A condition can see only its own states and not neighbors. Example: `"condition": "q.block_state('mistvale:growth') < 7"`.
- **Permutation limits**: at most 65,536 permutations per block type (there is also a separate second limit, and vanilla is about 16,000). One add-on can register up to 32,767 blocks including vanilla. There is also a world-wide permutation warning (one add-on 40k, "framed blocks" about 93,220). Connecting texture blocks exceed the limit. For add-ons that turn textures into states, the suggestion was to map one numeric state to an X,Y grid or use entities.
- **Bit limit and real numbers**: block state combinations are limited to 16 bits (2^16 permutations), and beyond that the error `Block X has 5 states that use 20 bits. The maximum supported number of bits is 16 (2^16 permutations)` appears. Permutation count reports: 10,000 is recommended, a warning when the world total exceeds 65,536 (67,850 reported), 150,000 on a server is real performance degradation, thousands or more cause a delay on first join, about 100,000 blocks in one pack gave half the registry missing and the creative categorization freezing, and a 16,384-permutation block case.
- **States vs separate blocks**: one opinion is that there is no meaningful performance difference between states and separate blocks, and another is that separate blocks are better for redstone and lighting (stacked slabs and so on). Decide by whether each variant needs its own item. For 40 colors (wool, concrete style) separate files are better. Traits probably count toward the permutation count like states. Kaioga says the placement-position trait adds 6 states and doubles permutations, so he handles rotation with states + scripts.

#### Direction traits

- **Trait example**:
  ```json
  "traits": {
    "minecraft:placement_direction": {"enabled_states": ["minecraft:cardinal_direction"], "y_rotation_offset": 180},
    "minecraft:placement_position": {"enabled_states": ["minecraft:block_face"]}
  }
  ```
  Using `q.block_state('minecraft:block_face')` without the trait gives "making use of non-registered block state".
- **placement_direction vs placement_position**: `placement_direction` (`minecraft:cardinal_direction` N/E/S/W or `minecraft:facing_direction`) follows the direction the player looks, furnace style. `placement_position` (`minecraft:block_face`, `minecraft:vertical_half`) follows the clicked face, log/pillar style. Make the model front face north and give `y_rotation_offset: 180`. `y_rotation_offset` is supported only for some hardcoded `enabled_states`. With corner+cardinal it fails if cardinal is not included (MCPE-240709, intended behavior).
- **Pillar rotation permutations**: depending on `q.block_state('minecraft:block_face')`, give `minecraft:transformation` rotation west/east `[0,0,90]`, north/south `[90,0,0]`, up/down `[0,0,0]`. Another example is up `[90,0,0]`, east `[0,-90,0]`. Template: https://github.com/Kaioga5/Kaioga-s-Block-Templates/tree/main/templates/1.20.80/logs.
- **`/setblock` direction**: placing a `block_face` trait block with `/setblock` gives the default `down` (the vanilla item frame is the same). A cardinal block also faces differently than when placed by hand, so specify the state explicitly. The `cardinal_direction` order (NWSE) differs from expectations, so west is not -90/270. The block's `north()/south()/east()/west()` are world-relative neighbors regardless of `cardinal_direction`.
- **N-way / 16-way rotation**: `minecraft:sixteen_way_rotation` / `n_way_visual_rotation` were confirmed in the 2026-08-04 stable release (https://wiki.bedrock.dev/blocks/n-way-rotation#sixteen-way-rotation, heads https://wiki.bedrock.dev/blocks/custom-heads). They cannot be used inside permutations, and a permutation that overrides geometry removes them. They do not work with hardcoded full-block models. The bug where the rotation was not visible to remote players/BDS/Realms (MCPE-241952) was reportedly fixed in 26.60.28/29, but there is a report on 2026-09-28 that it still does not work on Realms. It does not follow structure rotation (MCPE-243539, 2026-10-08). The problem of the 16-way y rotation offset being ineffective was fixed.
- **Random rotation**: a lily pad style texture gets position-based random rotation with the material instance `"isotropic": true`. To randomize per placement, use `e.permutationToPlace = e.permutationToPlace.withState("minecraft:cardinal_direction", directions[Math.floor(Math.random()*4)])` in `beforeOnPlayerPlace`. Model variants decide their state the same way.
- **Structure rotation**: custom directional blocks that do not use block traits (state-based rotation) rotate wrongly when saved in a structure and rotated. Pipe/connection blocks placed by scripts need their connection state recomputed after loading a structure (unresolved).

#### Connection and stair traits

- **`minecraft:connection` trait**: `enabled_states: ["minecraft:cardinal_connections"]` adds the automatically managed `minecraft:connection_north/south/east/west` states. It can be used in `bone_visibility` or permutations without scripts, and is reflected on the client faster than the script method. There are no up/down connections, and it cannot be limited to similar blocks or tags. It connects to vanilla full blocks, custom blocks without `connection_rule`, and blocks with the `minecraft:has_fence_connections` tag under a rule other than "none". Mojang (Brock) said it is a temporary solution and will be extended with voxel shapes. Using `y_rotation_offset` breaks connections with blocks that have no offset. Putting a connection trait or the `has_fence_connections` tag in a permutation crashes the game (MCPE-236302).
  ```json
  "minecraft:geometry": {"identifier":"geometry.fence","bone_visibility":{"north":"q.block_state('minecraft:connection_north')","centre":"true"}}
  ```
- **`minecraft:corner_and_cardinal_direction`**: used as an enabled state of `placement_direction`, with 4 directions x 5 corners (none, inner_left, outer_left, inner_right, outer_right) = 20 permutations, and adds a `minecraft:corner` state. For `blocks_to_corner_with` give a list of block IDs or `{"tags":"q.any_tag('mytag')"}` (Molang). There is no `minecraft:cornerable_block` tag, so use a custom tag or your own ID. Connecting with vanilla stairs needed the Beta APIs experiment in 26.0, and a non-connecting bug remained in 2026-04. The bug where corner became none next to an inner piece (MCPE-232019) was fixed in 26.10. Docs: https://wiki.bedrock.dev/blocks/block-traits#placement-direction.
- **`minecraft:vertical_half`**: a `placement_position` enabled state that decides top/bottom of a slab.
- **Custom stair trait bugs**: in 2025-12 there was a report that the built-in trait for stairs had bugs (later stable in 26.0). The bug where corner inner/outer swap in the custom stairs/slabs of the drop-3 experiment template is MCPE-241321 (filed 2026-08-05). There is still no standard for merging custom slabs.

### Multi-block (`minecraft:multi_block`)

- **Definition**: `"traits": {"minecraft:multi_block": {"enabled_states":["minecraft:multi_block_part"], "parts": 2, "direction": "up"}}`. Docs: https://learn.microsoft.com/en-us/minecraft/creator/documents/multi-blocks?view=minecraft-bedrock-stable, https://wiki.bedrock.dev/blocks/multi-blocks.
- **Stabilization history (some versions conflicting)**: vertical multi-block was due to be stable in 1.26.40 but was dropped (error 'no parser available for version 1.26.40' in the stable release). Mojang said it is stable in the 1.26.50 release (docs updated 2026-08-04). In the 1.26.20 stable release, with format_version 1.26.20 or higher, the Upcoming Creator Features gate was accidentally lifted and then hotfixed in 2026-05. The 1.26.10/1.26.20 formats needed the experiment. Horizontal multi-block (beds) went through the 1.26.40 Preview experiment and became stable in 26.50, and needs the matching format_version. One reporter wrote that it is stable in 26.40 and one wrote that it was still a beta API in 26.21. The final stable release is taken to be 26.50.
- **Requirements and limits**: `minecraft:movable` must be defined (immovable or popped, piston movement is not supported). `placement_filter`, `replaceable`, `random_offset`, `movable`, `precipitation_interactions` and `minecraft:block_entity` are root only (putting them in a permutation gives "Component ... is not valid in multi block permutations"). block_entity was first banned and became valid again around 1.26.50, and one is attached per part. Putting `precipitation_interactions` in a permutation makes the whole block fail to load from 26.30.25. For direction traits only `cardinal_direction` works (connection, placement_position and n-way are not supported). Random offset for horizontal multi-block is going to be banned.
- **Direction**: if `placement_direction` turns on `cardinal_direction`, the trait's `direction` is ignored and it follows the placement direction (including `y_rotation_offset`). No extra permutations are needed. Only one axis is supported, so make 3D/multi-axis with scripts. Other direction values are accepted but have no effect.
- **Behavior**: placing the base part places the rest. Placing a non-base part with `setblock`/`fill` fails (silently before, fixed 2026-03-11). Breaking any part breaks them all, and only the loot of the part broken first drops. Loot can differ per part, so put the loot in a permutation conditioned on `q.block_state('minecraft:multi_block_part')`. Doors always drop from the bottom part. `onBreak` fires once and `onPlayerBreak` does not fire. Non-base parts skip the entity collision check on placement (same as Java beds). `Dimension#fillBlocks` behaves differently from `/fill`. Each part counts as one pending tick.
- **State changes (changes over time)**: in 2026-04, changing the state of part 0 matched the other parts, and changing another part destroyed it with "failed to set property". From 2026-05 (around 1.26.20), the states of all parts must be changed in the same tick, and changing only part 0 breaks the block. Mojang (brozef92) said that setting one part at a time with scripts/commands was blocked on purpose. `permutationToPlace` in `beforeOnPlayerPlace` updates all parts.
- **Scripts**: `block.setType(typeId)` places the default permutation (the first part) and creates the whole thing. `setPermutation()` places only one part, and writing to part 0 creates only a ghost part on the client. To change states, set each part with `block.getParts()` (order guaranteed):
  ```js
  part.setPermutation(BlockPermutation.resolve(part.typeId, {...states, "minecraft:multi_block_part": part.getState("minecraft:multi_block_part")}));
  ```
  In a random tick, read `minecraft:multi_block_part` and skip if it is not 0. The vanilla door is a legacy method that changes only the upper state.
- **Block entities and inventory**: each part gets a separate block entity and they are not synced (the vanilla double chest is also 2 linked entities). There is no way to detect inventory changes, so there is a duplication risk when two players use different parts. Canceling `PlayerBreakBlockBeforeEvent` on a non-root part makes the state diverge. A block_entity container on a non-root part broke the block when used in 26.50, and did not in 26.70.
- **Vertical limit and typos**: there is a report that vertical multi-block goes up to 4 cells (single report). A typo such as `minecraft:multi_blockPart` in a condition causes block registration to fail.
- **Other bugs**: a part with its selection box turned off is treated as 16x16x16 in outline calculation. Running `fill ... replace bed[...]` in chat with a custom multi-block can crash (it works silently in command blocks or functions). The bug of no outline without a selection box (MCPE-237089) was fixed, the random offset bug is MCPE-237071, and survivability (MCPE-237498) was fixed. Multi-block and placement filter bugs were fixed in the 26.20 Preview.
- **Multi-block and flower pots**: a multi-block that defines geometry/materials only in permutations gives an error if the root has `minecraft:flower_pottable` (MCPE-237910, judged intended behavior but disputed).
- **voxel shape and outlines**: Mojang said it intends multi-block + voxel shape to be used for outlines beyond block bounds.
- **Proposal stage**: the `multi_part_sync` / `forwarded_states` flags for custom states and a script state change event are on brozef92's to-do list.

### Block entities, containers, dynamic properties

- **`minecraft:block_entity`**: arrived in Preview 26.30.28. Experimental in 26.40, and in 26.50 the block entity itself (dynamic property storage) is no longer experimental while `container {slot_count}` is still experimental. The UI is barrel style only (modifiable with JSON UI), with no chest rendering and no hopper suction. Before that, blocks had no dynamic properties and there was no piston move event.
- **State in 2026-10~11**: the answer that containers are still experimental (only dynamic properties are stable) was repeated. The format is `{"minecraft:block_entity": {"container": {"slot_count": 9}}}`, it needs Upcoming Creator Features and format 1.26.20 or higher, and in a world created without the toggle it disappears from creative. There is also a report that it is experimental in both the 26.60 stable release and Preview and has at most 54 slots (unverified).
- **Container title**: `title` inside container (a localization key such as `tile.chest.name`, a plain string works for testing). Example: `"minecraft:block_entity": {"dynamic_properties": true, "entity_storage": true, "container": {"slot_count": 16, "title": "Synthesis"}}`. It is not in the bedrock.dev wiki or the VS Code extension, so see Microsoft Learn.
- **What cannot be done**: falling blocks (the hardcoded `minecraft:falling_block` entity) and animations cannot be made. A chest opening animation is imitated by changing geometry in steps with states and permutations (stiff). A multi-block sharing one block entity also does not work yet. A way to connect a custom UI to a block entity container is not confirmed (only a rumor of showing a UI with a specially named item in slot 1).
- **Bugs**: changing container items with scripts after a redstone update closes the open UI (26.50, presumed bug). A snowlogged container block entity drops its items.
- **Carrying over to items**: giving `dynamic_properties:true` to the loot function `carry_over_block_entity_data` passes block dynamic properties to the item (26.40, Upcoming Creator Features).
- **Storage methods before block entities**: keep per-block data in world or entity dynamic properties (kept after script reload and restart). Entity-based storage lags with many blocks and disappears with `/kill @e`. clone/fill cannot be intercepted.
- **Item display**: a block entity can show items with an attachable (an entity pretending to be a block, with manual bone and slot mapping). Mojang said it is working on custom block containers.
- **Requests**: a `minecraft:ender_chest`/`spawner` component API was requested.
