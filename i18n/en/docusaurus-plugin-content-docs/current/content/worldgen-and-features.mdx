# Worldgen - features, structures, jigsaw

The center of add-on worldgen is features, feature rules, structure files and jigsaw. Biomes and custom dimensions are in [Biomes and dimensions](./biomes-and-dimensions.mdx). The evidence is community research (2025-10~2026-11), the Bedrock Wiki (0930b39) and the MS Learn feature reference (Source: private research). Verification levels are `(confirmed)`, `(conflicting)`, `(single report)` and `(unverified)`.

## Key summary

1. A feature generates naturally (and is registered and validated) only if a feature rule references it. One feature can use only the 3x3 chunks around the origin chunk (-16..+32 from the origin), and anything outside is cut off.
2. Vanilla features/feature rules are modified by overriding with the same identifier (`iterations: 0` disables them) or replaced. The latest vanilla files are in `data/definitions/` in the BDS download.
3. `q.noise()` is independent of the seed (the same in every world). `q.get_level_seed_based_fraction` cannot be used in features. To use it like a seed, add a coordinate offset yourself.
4. The terrain shape cannot be changed with biome files.
5. Jigsaw files go in BP `worldgen/structures`, `worldgen/structure_sets` (plural), `worldgen/template_pools` and `worldgen/processors`. `max_depth` is at most 20 and `max_distance_from_center` is at most 128. Jigsaw generates before features.
6. Entities stored in a structure appear only when generated by jigsaw (`doMobSpawning` needed) and are ignored in feature placement (`structure_template_feature`). `/locate` finds only jigsaw structures and custom biomes.
7. For custom blocks placed by worldgen, `onTick`/`onPlace` often do not run.

## 1. Concept and minimal example

A feature decides "what is placed and how", and a feature rule decides "where and how often". Both go in the BP (`BP/features/`, `BP/feature_rules/`; putting them in the RP fails silently). The smallest natural generation example is an ore. The feature defines an ore clump that turns one stone into another block, and the feature rule decides the count per chunk, the y distribution and the biome condition. The distribution of the vanilla diamond feature rule is triangle `[-144, 16]` (`overworld_underground_diamond_ore_feature`, format 1.13.0, placement pass `underground_pass`, `coordinate_eval_order` zyx).

```json
{
  "format_version": "1.13.0",
  "minecraft:feature_rules": {
    "description": {
      "identifier": "wiki:my_ore_feature_rule",
      "places_feature": "wiki:my_ore_feature"
    },
    "conditions": {
      "placement_pass": "underground_pass",
      "minecraft:biome_filter": [ { "test": "has_biome_tag", "operator": "==", "value": "overworld" } ]
    },
    "distribution": {
      "iterations": 8,
      "coordinate_eval_order": "zyx",
      "x": { "distribution": "uniform", "extent": [ 0, 16 ] },
      "y": { "distribution": "uniform", "extent": [ -32, 64 ] },
      "z": { "distribution": "uniform", "extent": [ 0, 16 ] }
    }
  }
}
```

`iterations` is the number of attempts per chunk, and `scatter_chance` is the probability per chunk. The feature rule file name must equal the name part of the identifier (MCPE-242144). There is no rule for feature file names.

## 2. Feature and feature rule basics

- A feature is generated only if a feature rule (a root feature) exists. A feature that no feature rule references is not registered or validated, but can still be used with `/place`. If you need validation, make a harmless feature rule. A feature can be used from commands/scripts only when a rule or processor list references it (MCPE-242142). The starting points are the features introduction on MS Learn, the wiki world-generation/generating-custom-ores, and the Features docs on bedrock.dev.
- If format_version does not match the feature type, a `description missing places_feature` error appears. `no valid version passed` means format_version is missing.
- `iterations` is the number placed in the area decided by the distribution rule (count per chunk) and is rounded to an integer (0.4 is 0, 0.5 is 1). Less than 1 is impossible. `scatter_chance` is the probability per chunk, written as a percent (0-100, 5 = 5%, 0.40 = 0.4%) or `{numerator, denominator}`. With `iterations` 0 the rule is off. Start tests with scatter_chance 100 and iterations 1 and lower them.
- 3x3 chunk limit: a feature can edit only the origin chunk and the 3x3 chunks around it. The origin is the minimum x/z corner of the middle chunk, so the reach is -16..+32 (48x48). Blocks outside the origin chunk ignore the placement pass order. Large structures and trees being cut at chunk borders is not a bug and gives no log error. Put structures at the center of a chunk at 16x16 or smaller, placed at x=z=8. A large range such as scatter x/z extent [0,64] pushes structures outside the border and gets them cut.
- Chunk-covering distributions: the `fixed_grid` extent must be `[0,15]` and `uniform` must be `[0,16]` to cover the whole chunk. A grid distribution extent that does not go beyond the origin is offset wrongly (MCPE-242145). Negative values in fixed_grid behave strangely, so put one more scatter in front and put the negative offset directly in x/y/z. A feature with no offset and x=y=z=0 is placed at the chunk minimum corner y=0. Feature rules are evaluated per chunk and biome filters per block.
- Placement passes: put trees in `first_pass`/`before_surface_pass`, ground decoration in `after_surface_pass` and ore in `underground_pass`. Ore mostly runs later than features and sees previously placed stone as valid, so it also overwrites `final_pass` structures. To make a patch bigger, put one more copy in another pass (`final_pass`).
- Features have no version, so new changes can break existing features. Placement has been observed to differ between PC and mobile (a bug).
- On superflat, biomes, structure sets and feature rules do not run. `/place featurerule`, `/place feature` and `/place jigsaw` work in loaded chunks of a flat world. `/place` cannot be run from command blocks or functions. `/place feature` and natural placement can place things differently.
- Script placement is `Dimension.placeFeature` / `placeFeatureRule`. There are reports that coordinates are ignored and questions about performance overhead. One complex feature blocks the main thread for about 1 second. A method that splits into 16x16x16 cubes and decides the next job with `system.runJob` has been used.
- Generate features with code. There is a recommendation to generate features and Molang with TS/Python/JS scripts instead of nesting by hand. Feature/scatter placement is faster than scripting.
- Debugging: in non-Molang-debug builds `q.log` does not exist, so in-game debugging is hard. If scatter does not work it is usually a JSON error (a missing comma), so lint and check the Content Log. Recreate the world every time you change biomes/features (old chunks stored on disk create square borders). You can also delete only the db files and keep the seed.
- Getting vanilla files: vanilla feature/feature rule identifiers are in `metadata/command_modules/mojang-commands.json` of the sample pack. The files are in `data/definitions/` of the BDS zip, the PC install folder, the APK and the old features_archive.zip (1.18). The vanilla BP template on GitHub has no biome features or feature rules. Not every vanilla feature/rule is in the current files, and many basic vanilla features are not data-driven (MCPE-242143).

## 3. Worldgen Molang

- `v.originx/z` is the feature rule origin (chunk-aligned, a multiple of 16). It is set only when entering a scatter feature, so store it yourself if needed. `worldx/worldz` is the current placement position and is updated immediately, but it does not exist in the feature_rule context. If you put y before x/z in `coordinate_eval_order` together with heightmap, `unknown variable variable.worldz` appears, so put y last. The Molang variable context carries through the whole feature tree. Chunks load in arbitrary order, so derive decisions from world coordinates (for example `math.mod(v.originx,256)`). A range object accepts Molang only in the extent lower/upper bounds and does not accept it in step size and grid offset.
- To place at a specific coordinate, check the chunk origin with iterations Molang (y is fixed in the rule). Returning 0 places nothing.

```text
"iterations": "math.floor(v.originx/16)==math.floor(100/16)&&math.floor(v.originz/16)==math.floor(100/16) ? 1 : 0"
```

- `q.noise()` is a single 2D Perlin-like function independent of the seed. The value is roughly -1..1 and skews toward both ends, so normalize with `/2+0.5`. Use a coordinate offset as the salt instead of a seed. Scales below 8 are almost useless, use low frequencies for large zones and 1/256-1/64 for patches. There is no 3D noise. An example zone that takes up about 14% of the world at biome size:

```text
"iterations": "v.freq=1/8192;v.q=100*(q.noise(v.worldx*v.freq,v.worldz*v.freq)*0.5+0.5); return(v.q>=34&&v.q<=47)?1:0;"
```

  To keep structures from overlapping, use a different noise zone and frequency per structure or use jigsaw.
- `query.get_level_seed_based_fraction` fails in 1.26.10 features with `does not exist or not supported in this context` (it works only in animations/particles). The seed fraction query cannot be used in worldgen (MCPE-240790 / 242120).
- `q.heightmap` vs `q.above_top_solid`: the correct call is `q.heightmap(v.worldx, v.worldz)` (wrong arguments crashed world loading). The heightmap is the world surface including sea level and cave entrances. `q.above_top_solid` ignores that, so it fixes features not appearing on custom surface blocks, trees on water and pond/cave problems. However, above_top_solid reacts to every "solid" including leaves. A custom block without `light_dampening` is treated as transparent and affects terrain generation. The `q.above_top_solid` offset limit was reported as 3 chunks (48 or more breaks generation).
- A slope check compares the `q.heightmap` difference between the center and the corners in the scatter's iterations Molang before the structure (1 if all are 2 or less, else 0). y is `q.above_top_solid(v.worldx, v.worldz) - 2`.
- `q.has_biome_tag` is used in the per-block check `"iterations": "q.has_biome_tag('ocean')?1:0"`. It is not in the docs, but it accepts coordinates (`q.has_biome_tag(tag, x, y, z)`). It takes one tag per call and returns a boolean. Biomes are 3D, so y matters. Inside scatter it is reliable only after the grid spread (single-block context), and blocks at the chunk edge +15,+15 do not return the real biome. For proper biome filtering use feature rules. There is a bug that the three biome queries work only in conditional list features (MCPE-242119). Feature rules and custom biomes are linked with a custom tag in `has_biome_tag` of `minecraft:biome_filter`.
- Biome border blending loops downward from blend_dist, checks the 8 neighbors with `!q.has_biome_tag(...)`, sets `v.blend_factor` from the distance and uses `v.height = math.lerp(q.heightmap(...)-64, custom, v.blend_factor)`. The third argument of `math.lerp` must be 0-1.

## 4. Notes by feature type

- `single_block_feature` can replace by state (ore_feature cannot). Use `{"name":"kado:stable_air","states":{"kado:purpose":"skybox"}}` in `places_block`. The weighted array `[{block:{name, states:{...}}, weight}]` worked in the latest Preview. Block traits (`placement_position`/`block_face`) seem not to apply in feature placement. For `may_attach_to` give direction keys and a block list or `{ "tags": "query.any_tag('log')" }`. Weights are silently truncated.
- `ore_feature` suits ore-like things and is faster than scatter + single block. Bugs: client async with `place` (242115), x/z +8 offset (242122), wrong `count` name (242125), `may_replace` silently required (242127), block states ignored in `may_replace` (242128), tag block descriptors impossible in `may_replace` (242124), output position always (0,0,0) (242129). Large ores (about 200 blocks crash) stop at 16 blocks in the negative direction, so give a +8,+8 offset with scatter. Change vanilla ore rarity by overriding the rule with the same ID and using scatter_chance. To make it more common toward -64, use triangle `[-16, -64]`. For ore use features, not jigsaw.
- With `scatter_feature`, make pillars by giving only the `y` distribution with no step_size. To cover every surface block of a chunk, the feature rule places Feature A once at 0,-64,0, with A = scatter (`fixed_grid` x/z 0..15, `"y": "q.above_top_solid(v.worldx, v.worldz)"`, 256 times) and B = a single block feature. To cover the full Y range, iterations must match the dimension (for example 64x320), and large numbers slow world loading.
- `aggregate_feature` and `sequence_feature`: an aggregate with `early_out` (first success/first failure) is widely used in Mojang files as a conditional. Sequence has bugs, so use aggregate. A first-failure early-out keeps placing after a failure if the failing item is not the first (MCPE-242141). When joining 48x48 pieces into a 96x96 structure, use an `early_out: first_failure` sequence with per-piece offsets and snap to the 48 grid with checks such as `(v.worldx-v.originx)/48`.
- The `conditional_list` feature became stable on 2026-09-15 and replaces the scatter+aggregate pattern (in one project 544 features became 435).
- The height difference filter feature (new in 2026-05) samples only intersection positions (MCPE-238744), scans from the dimension floor/ceiling rather than the input y (238745), and ignores non-solid blocks. Molang cannot be used in the radius.
- `snap_to_surface_feature` works on only one surface. There is a `random_vertical` name error (242117), and it attaches in the opposite direction on non-air blocks (242118). For cave floor blocks, put the feature rule at Y -60..40, and a "floor" snap_to_surface places a single_block_feature with `may_attach_to` stone/deepslate and `may_replace` air. If the `min`/`max` order of the search feature is swapped, repetition breaks (242130).
- `geode_feature` is very tricky (advice is to use mcstructure). A layer accepts only one block (no weighted pool) and ignores crack properties. `inner_placements` accepts only `{name}`, so custom bud blocks all face "down".
- `multi_block_feature` (1.26.40) places every part of a multi-block (single_block_feature places only part 0). If `enforce_placement_rules` is true it places only when air/water is allowed as support, so have the feature rule place snap_to_surface and have that place the multi-block feature.

```json
{ "places_block": "test:block", "enforce_placement_rules": false, "may_replace": [ "minecraft:air" ] }
```

- A 2-tall flower uses `minecraft:multipart_block_column_feature` with `tip_block` (`upper_block_bit: true`), `frustum_block` (`upper_block_bit: false`), `height_range` 2..2, `direction: "UP"`, `may_replace` air and `may_place_on` grass_block.
- `cave_carver_feature` is biome-dependent and 8-directional. For water, set water instead of air. y is relative to the input coordinate of the parent feature/rule. Cave size is controlled with `width_modifier`, radius multiplier, `y_scale` and `height_limit`. There is no carver for craters.
- Other: the fossil feature is not placed at the input position (242159/242161). Horizontal tree decoration needs a block that has both `cardinal_direction` and `growth` states (242146). `minecraft:feature_pool_element` can reference only hardcoded vanilla features.
- Moss spread (bone meal) is decided by `replaceable_blocks` of the vanilla feature `minecraft:moss_patch_bonemeal_feature` (`minecraft:vegetation_patch_feature`, format 1.16.0). Copy it into `BP/features/` and add blocks (it overrides the identifier, so no feature rule is needed).
- To remove leaves from a tree feature, set `leaf_blocks` to air. The `range_min` of `branch_start_offset_from_top` must be 0 or less.

## 5. Terrain changes and modifying/removing vanilla generation

### Terrain

- Terrain cannot be changed by add-ons. Terrain is made first by hardcoding, and the biome `noise_type` changes only the surface. Changes are done with features that place air/stone. For tall mountains, use a rule that adds blocks to existing highlands, or in mountain-tag biomes (cherry_grove, frozen_peaks, grove, jagged_peaks, meadow, snowy_slopes, stony_peaks) place mcstructure peaks with scatter -> weighted_random -> structure_template_feature. A large body of water is filled with water up to about y=62 on the surface before biome features, so correction is slow. Changing sea level (63) did not work with noise parameters. Checklist: no 3D noise, erase vanilla directly, use the seed only as an offset.
- Building terrain from scratch: chunk-level scatter (fixed_grid x/z 0..15, iterations Molang ending in `return 256;`) -> column-level scatter (Y fixed_grid [0, terrain_height-1], iterations returns a normalized multi-octave `q.noise` height). Only 3x3 chunks can be queried, so blending with biomes is hard.
- Deeper oceans are made with scatter + single_block_replace. The documented `sea_floor_depth` has no effect and changes only the surface layer thickness. A 2-block-deep ocean is impossible with biomes alone, so use a biome filter rule to cut the terrain down to a constant Y and place 2 blocks of water.

```text
"iterations": "v.oldfloor=q.above_top_solid(v.worldx,v.worldz); v.olddepth=62-v.oldfloor; v.adddepth=math.clamp(3*v.olddepth,0,90); v.newfloor=v.oldfloor-v.adddepth; return v.adddepth;"
```

- Removing water: overriding the vanilla underwater cave carver rules (`overworld_underwater_cave_carver_feature` / `underground_underwater_cave_carver_feature`) with a custom carver removes a lot of underground water. A carver can be overridden but an aquifer cannot.
- To turn stone into netherrack, use 16x16 chunk fixed_grid scatter -> 256 column features -> a single block feature, and put ore in a later pass. Emptying the End is a rule that places air with a single block per chunk. Some vanilla blocks such as islands and chorus are placed after add-on rules, so erase them later with scripts.
- A custom End "biome": the End is one biome so custom biomes do not work, so make all related rules check the same low-frequency noise range.

```text
"iterations": "v.biome = 100*(1 + q.noise(v.originx/8000, v.originz/8000))/2; return v.biome >= 28 && v.biome <= 45;"
```

- The height limit is decided by the server packet. In vanilla you cannot build above the Nether ceiling.

### Modifying/removing vanilla generation

- Override principle: modify by giving a feature/feature rule the same identifier as vanilla (a `minecraft:` prefix cannot be used for new features). Turn it off with `iterations: 0` or by removing `distribution`. Without the feature file, a rule whose `places_feature` points to an unknown ID gives an error. To stop vegetation, copy the vanilla rule and set iterations to 0. The `foliage` rule is for grass/flowers, and tree rules are separate files.
- Replacing/removing trees: vanilla tree features were moved to legacy and cannot be called directly from custom rules. Change only the `places_feature` of the vanilla tree rule (keep the identifier, for example `minecraft:roofed_forest_surface_roofed_tree_feature_rules`) to your own feature. The name pattern is `<biome>_surface_trees_feature`, and feature names are oak_tree_feature, spruce_, birch_, jungle_, acacia_, dark_oak (roofed_tree_feature), mangrove_, cherry_ and azalea_tree_feature. To remove, point to a single_block that places `minecraft:air` or set iterations to 0. To turn every tree into one kind, override the surface-tree rules of all biomes while keeping their names.
- Bamboo density is decided by the iterations Molang of `bamboo_jungle_after_surface_bamboo_feature.json`. The vanilla value is `math.clamp(math.trunc(math.ceil((query.noise(math.trunc(variable.originx / 80), math.trunc(variable.originz / 80)) + 0.3) * 160)), 15, 160)`, and to reduce it use `+0.1`, `*20` and clamp 0..5.
- Vanilla structure frequency and villages: in 2025-11~12 this was thought impossible, but a 2026-10 case reduced the frequency of abandoned campsites by overriding the structure set's `separation`/`spacing`, and a 2026-11 case replaced the plains village with a custom village. There is still no way to override villages while keeping vanilla generation rules.
- Things that cannot be erased: leaves, vines, glow lichen and mineshafts cannot be fully replaced/removed. Removing mineshafts and custom biomes inside Nether/End biomes were impossible as of 2025-11~12. End structures (End ships, islands) are not biome-based and cannot be erased, and the End pillars are at fixed coordinates. Caves are part of the base terrain pass and cannot be turned off.

## 6. Custom blocks in worldgen

- Ticks do not run: for custom blocks placed by features, `onPlace`/`onTick`/`minecraft:tick` are not reliably initialized (confirmed as a stable release bug). They do not run until the block is broken and placed again. Only blocks placed inside the selected 16x16 chunk (x/z 0..15) tick, and blocks in neighboring chunks are only placed. Negative extents in the distribution make it unstable. Search + feature instead of scatter, and `final_pass` instead of `after_surface_pass`, worked. Biome surface builder blocks do not run queued ticks.
- A .mcstructure block with tick data in its NBT fired scheduled events twice. The workaround was to delete that block position/tick entry in the NBT, and it was fixed in the 2026-03 Preview (MCPE-236362).
- Placement features use a hardcoded list of surface blocks. A custom grass made with `minecraft:geometry.full_block` does not grow trees/flowers/mushrooms, so copy the vanilla list and add the block. For features on custom grass, restrict may_replace to air.
- A world made of only custom blocks lagged/crashed at render distance 5 and above, and the cause was a custom stone block that used custom geometry (fixed with proper culling or vanilla cube geometry).

## 7. Structure files and structure_template_feature

### .mcstructure

- The location is `structures/<namespace>/<name>.mcstructure` and the identifier is `namespace:name`. Without a namespace folder `structure not found` appears, but jigsaw also finds subfolders. Load with `/structure load ns:name` or the script `world.structureManager`. Do not use spaces in file names. When reproducing vanilla structures, put them in a different folder under `structures/`.
- Structure block saving is at most 64x64x64. The mcstructure maximum is 64x384x64, but for performance a 16x16 center placement is better. An about 35x64x50 structure was not generated at all by structure_template_feature while an about 32x35 one was (unresolved). If larger, split it into jigsaw pieces.
- Get structure void with `/give @s structure_void`. Save void instead of air in the structure so existing blocks and terrain show through and trees do not overwrite it. Plain air replaces water/waterlogged blocks. .mcstructure does not store void (index -1 outside the palette). Loading a structure replaces existing blocks (including leaves), and only where there is void do existing blocks remain.
- Structure loot: structure files and loot tables can go in subfolders (the loot path starts with `loot_tables/`). A lootless copy saved in the world by a structure block with the same name takes priority over the BP one, so run `/structure delete <name>` and load again. Chest loot is put in with NBT editing, the jigsaw processor and random loot tools. Pot loot uses the same processor method.
- Tile entity NBT: trial spawner, vault and suspicious sand loot are tile entities, so edit the structure NBT with a structure editor. Leave the vault's `state_updating_resumes_at` at 0. Suspicious sand loot can also be set with the jigsaw processor. There are no custom tile entities, so a fully custom trial spawner block cannot be made.

### structure_template_feature

It is format 1.13.0 and uses `structure_name` (for example `mystructure:abc/def/ghi/oaktree` -> `BP/structures/abc/def/ghi/oaktree.mcstructure`), `adjustment_radius` (raising to 8-16 finds a spot), `facing_direction` (random is possible) and `constraints` (`grounded`, `unburied`, `block_intersection.block_allowlist`). There is no blocklist. If only air is allowed, it fails when even one non-air block exists. The condition needs `any_of` and `==` (the typo `=` breaks it).

```json
"constraints": {
  "grounded": {},
  "unburied": {},
  "block_intersection": { "block_allowlist": [ "minecraft:air", "minecraft:stone", "minecraft:dirt", "minecraft:grass" ] }
}
```

- Minimal natural generation is a `surface_pass` feature rule placing `structure_template_feature` with `scatter_chance`, `y: "query.heightmap(variable.worldx, variable.worldz)"` and a `has_biome_tag` filter. A floating structure uses `unburied` + `block_intersection.block_allowlist ["minecraft:air"]`, adjustment_radius 0 and rule y uniform [100,240].
- Placement geometry: the corner of the selected chunk is the origin, and the structure grows +x/+z from the rolled x/z. Anything beyond the 3x3 chunk range (-16..32, 48x48) is cut. A 48x48 structure moves the origin to (-16,-16) with a negative `extent` in the rule's x/z. `rotate_around_center` moves the pivot to the selected position and fits up to 33x33. If you fix the scatter offset at 8,8 the pivot is at the chunk center. The `rotate_around_center` bug was fixed in 1.26.30, but the new `ground_level` option has the same problem.
- Entities in a structure placed by a feature are not generated. Put command blocks or custom blocks inside the structure or use jigsaw. There is a report that jigsaw blocks inside a structure placed by a feature do not work and a report that jigsaw now works together with features. (conflicting)

## 8. Jigsaw structures

Jigsaw is a system separate from features/feature rules. Jigsaw blocks inside pieces (.mcstructure) mesh with other pieces to grow a structure. So it gets around the feature size limit (3x3 chunks) and supports `/locate structure`. A single-piece "jigsaw structure" with no jigsaw block is also a way to place a large structure with only a start_pool.

### Files and minimal setup

- Folders are BP `worldgen/structures` (renamed from the earlier `worldgen/jigsaw_structures`, and old examples do not work), `worldgen/structure_sets` (plural, a singular folder fails silently), `worldgen/template_pools` and `worldgen/processors` (processor lists must be here, otherwise `Missing referenced asset`). The folder name is `worldgen`, not `world_gen`. Put .mcstructure files in the outer `structures/`. A template pool + structure settings are required, a structure set is needed only for natural generation, and a processor is optional. Data-driven jigsaw has been stable since the 1.21.50.26 Preview. The last jigsaw format change was around 1.21.100, so use that format.
- The `minecraft:jigsaw` fields are `step`, `start_pool`, `max_depth`, `start_height`, `heightmap_projection`, `terrain_adaptation`, `max_distance_from_center`, `dimension_padding` and `biome_filters`. A structure set has `minecraft:structure_set`, with placement `minecraft:random_spread` having `salt`, `spread_type: linear`, `separation` and `spacing` (numbers, required). Without them it does not appear in the `/place structure` list. A template pool is `minecraft:template_pool`, and its elements have `element_type: minecraft:single_pool_element`, `location`, `processors`, `projection`, `weight` and `fallback`. `legacy_single_pool_element` is not supported.
- `projection` must go inside the `element` object (next to `element_type`, `location` and `processors`), and `weight` goes outside. If misplaced it is silently ignored and becomes `rigid`.
- `location` is a structure file path, not an identifier. Write it relative to `structures/` without the pack namespace prefix (for example `3008_plots/room0`). An `Empty or non-existent pool` error is usually a wrong pool ID/namespace/location, so check the case too. JSON parse errors (`Invalid encoding in string`, `document root must not be followed by other values`) are stray characters or a duplicate root in the pool file.

### Jigsaw blocks and connections

- Naming rules: `name` = the name of this block itself, `target name` = the name to look for, `target pool` = the template pool to search. The generating block finds a piece in the pool whose jigsaw `name` equals its own target name and picks randomly by `weight`. A generate-only jigsaw needs only target + pool (name can be `minecraft:empty`), and the receiving side needs only a name. A pool that references only its own start piece finds nothing. The start_pool must be a piece with connecting jigsaws, and other pieces must be in the target pool. In jigsaw block text it is safer not to use characters that are not on the keyboard.
- Selection priority decides which wins when two jigsaws contest the same spot (higher wins), and placement priority is the order of candidate jigsaws within a piece. A vertical (UP/DOWN) jigsaw randomly rotates the child piece around the Y axis. `joint_type: aligned` places while matching the line markings of both jigsaw blocks and works only on the placing block. The rotation of a horizontal jigsaw cannot be turned off and always rotates to match the target jigsaw (`rollable` is for vertical only). You cannot force the direction or change a jigsaw's pool with a processor.
- For piece alignment, check whether jigsaw blocks mesh with `/place structure ... keepJigsaws=true`. `/place jigsaw <pool> <target> <depth> ~~~ true` is a better debugging command. `/place structure` needs a structure set and some fail. There is a report that `start_jigsaw_name` does not work (2026-08-17).

### Limits and spacing

- `max_depth` at most 20 (7 before 1.21, ancient city 7, village 6), `max_distance_from_center` at most 128 (Chebyshev radius, diameter 256, default 128, village 80), maximum structure 256x256, about 20 chunks in every direction. To extend roads and cities raise both. If generation stops early, check both.
- Piece bounding boxes within one structure do not overlap (a piece that fits completely inside its parent piece is an exception). Separate structures overlap unless they are in the same structure_set. There is no exclusion zone, so to separate them put them in the same set. Terrain-matching pieces (roads) can overlap and cover houses through a bug (MCPE-224012). The workaround is to save the road structure at a height of about 25.
- separation must be less than half of spacing (spacing must be more than twice separation). Raising separation moves them farther apart, and changing `salt` moves positions. Java and Bedrock give the same position for the same values and the same seed.
- An exact count is impossible. Only the start piece is guaranteed. You cannot force N rooms or limit the count. Make a piece that should appear only once the start piece. Reimplementing with scripts loses terrain adaptation.
- A fallback pool is tried when no element fits and when max_depth is reached (corridor end caps). It is not guaranteed and gets the same distance and space constraints.

### Height, projection, terrain adaptation

- `start_height` uses `{"type":"constant","value":{"absolute":0}}`. `uniform` needs `min` and `max` (`"min": {"absolute": 50}, "max": {"absolute": 150}`). start_height decides only the start piece position relative to `heightmap_projection`. To start at the sea floor use `heightmap_projection: ocean_floor`. `dimension_padding` (watch the spelling), for example `{"top": 25, "bottom": 10}`, keeps away from the height limits. The processor's "ignore start height" must be true for a fixed Y.

```json
{
  "format_version": "1.21.100",
  "minecraft:jigsaw": {
    "description": { "identifier": "wiki:hut" },
    "biome_filters": [ { "test": "has_biome_tag", "operator": "==", "value": "plains" } ],
    "step": "surface_structures",
    "start_pool": "wiki:hut/start",
    "max_depth": 4,
    "start_height": { "type": "constant", "value": { "absolute": 0 } },
    "heightmap_projection": "world_surface",
    "terrain_adaptation": "beard_thin",
    "max_distance_from_center": 80,
    "dimension_padding": { "top": 10, "bottom": 10 }
  }
}
```

- projection: `rigid` does not follow terrain. `terrain_matching` fits a piece (a road) to the terrain height and ignores start_height (rigid in the air). It works only in natural generation, not with `/place`.
- `terrain_adaptation` is `bury`, `beard_box`, `beard_thin` or `none`. The start piece is always buried in the ground, so save a layer of structure void at the bottom or split the structure. The problem of ships always appearing on a pedestal was fixed with `"none"` and the correct start_height (`"absolute": 1`). To avoid floating, `beard_thin` is best. The adaptation box uses blocks of the local biome and cannot be controlled. It does not work in the Nether and the End.
- Jigsaw cannot compare terrain height with the piece origin or pick pool elements by height, and it cannot make a structure generate only on specific blocks. Workarounds are a post-placement script, the `minecraft:protected_blocks` processor and a feature pool element. For the foundation of a floating structure, attach a large block cube under the structure with jigsaw and use a `minecraft:protected_blocks` processor with the ground block tag.
- Jigsaw does not handle biome borders. Several biomes need `any_of` (otherwise it does not generate). The alternative is to attach a custom tag to all the biomes you want.

```json
"biome_filters": [ { "any_of": [
  { "test": "has_biome_tag", "operator": "==", "value": "plains" },
  { "test": "has_biome_tag", "operator": "==", "value": "taiga" }
] } ]
```

### Generation order and features

- Jigsaw always generates before features, so features can overwrite it. Use a `block_allowlist` constraint on the feature side and use structure void so trees do not dig in. Trees and features also generate inside jigsaw, and to block that, do not use a grass/dirt tag floor. A piece placed with `/place` covers grass but natural generation does not. Custom jigsaw always overwrites vanilla structures regardless of the generation step.
- `minecraft:feature_pool_element` was added to template pools in the latest Preview around 2026-03-11. It can reference only hardcoded vanilla features and has bugs in natural structures. Jigsaw inside a feature placed this way is not triggered.

### processor

- At the time of 2025-11 Bedrock had only `minecraft:rule`. In late 2025-11 block protection processors were added (valid but not in the docs): `minecraft:protected_blocks` (blocks specified by tag are not covered by the piece, and `value: not_feature_replaceable` also blocks overwriting), `minecraft:block_ignore` and `minecraft:capped`. The ancient city has no `block_rot` processor.
- To give loot to a directional chest, a processor applies after placement, so each state needs a rule (4 chests). Give `minecraft:blockstate_match` (not `block_match`) with `"block_state": {"name":"minecraft:chest","states":{"minecraft:cardinal_direction":"east"}}`, a `block_entity_modifier` `{"type":"minecraft:append_loot","loot_table":"loot_tables/..."}` and an `output_state` with the same state. The only modifiers are `passthrough` and `append_loot`. State keys in processors need a namespace (`minecraft:vertical_half`). You cannot give loot to only specific chests or decide spawner mobs. Per-biome processors are also impossible, so split the structure. A processor does not edit entities.
- To fill the air under a piece (mine rails and so on), put a floor block in the structure and use a `minecraft:rule` processor (`input_predicate` block_match FLOORBLOCK, `location_predicate` block_match `minecraft:air`, `output_state` oak_planks) together with a `minecraft:block_ignore` processor that lists FLOORBLOCK. The floor stays as structure void and only the air becomes planks.
- `random_group` in `pool_aliases` works. Putting the same structure with different processors in one set gives an error.

### Entities

Entities stored in a structure file appear when generated by jigsaw (the `doMobSpawning` game rule must be on or they silently vanish). They do not appear in feature placement. There is a bug where they are randomly dropped with about 1/50 probability. The workaround is to have a ticking block summon them and erase itself.

### Overriding vanilla structures

- Custom jigsaw can place vanilla structure templates and connect to that jigsaw, but it does not generate vanilla jigsaw. As of 2025-12 only trail ruins and trial chambers could be overridden, and in 2026-04 tests it overwrote abandoned campsites, trail ruins, villages, parts of trial chambers and even the ancient city. Pillager outposts, strongholds and shipwrecks are hardcoded.
- Modifying trial chambers: to erase pieces that make the water pattern, put `end.json` in `worldgen/template_pools/trial_chambers/chambers`. Place the pool in creative with `/place structure minecraft:trial_chambers ~~~ true true` and find it by examining jigsaw blocks. By changing the start pool it can be reduced to one small custom structure. Mobs can be added with pool aliases, but spawn_overrides is not exposed yet.
- For vanilla structure files there is material converting the 822 vanilla `.nbt` files from the 1.21.131 BDS zip with nbt-to-mcstructure (some block entities such as spawners are lost). Vanilla jigsaw pools are hardcoded except trial ruins/chambers. Villages use hardcoded data-mode structure blocks.
- Impossible: adding custom pieces to vanilla villages, changing structure biome rules, structure pools with custom spawn_overrides, `/locate` ignoring rare structures. The jigsaw docs are old.

### Nether and End

- Nether: `heightmap_projection` (`world_surface`) projects onto the Nether ceiling/bedrock. Use `"heightmap_projection": "none"` with `start_height` uniform `{min:{above_bottom:28}, max:{above_bottom:70}}`, `"step":"surface_structures"`, `"terrain_adaptation":"beard_box"`, `max_depth` 4 and `has_biome_tag` biome_filters. It is still awkward. A feature must put all blocks to replace in the `allow`/replace list.
- End: there are no biomes, so jigsaw cannot be generated on the outer islands (worked around with a rare spacing 140/separation 300 or tag-based biome_filters). A working example gave `the_end` in `biome_filters`, `dimension_padding {top,bottom}` and `terrain_adaptation: beard_thin`.

### Other jigsaw

- An infinite structure (SCP-3008 style) is built with a ticking area + command block system. Armor stands on bedrock markers mark expansion points, functions erase duplicates, and each cell generates its neighbors. `/schedule on_area_loaded` and `/tickingarea preload` load chunks in order.
- Seed trick: if you fix the jigsaw `start_height`, the random seed uses the input y of the place command, so the input y acts as your own RNG seed.
- After 1.21.12x, combining two structure add-ons crashed in some areas and it was narrowed down to one .mcstructure of one pack (MCPE-232661). There is a case where a generation crash after adding many pieces was fixed by deleting pieces that were missing jigsaw blocks.
- Java datapack structures cannot be converted directly (the jigsaw format differs). Most Java jigsaw tutorials apply. Convert Java NBT to .mcstructure with JaylyDev/nbt-to-mcstructure (python). Behavior packs (BP) do not support subpacks.
