# Worldgen community reports - features, terrain, structures, jigsaw

These are individual reports from community research (2025-10-22 ~ 2026-11-13) that the preceding documents of this page did not summarize. The `[uNNN date]` at the end of each item is the research note number and the report date, and `(single report)` marks content reported by only one person.

### Worldgen: feature and feature rule basics

- **Basic structure**: a feature is generated only if a feature rule (= a root feature) exists. Feature files go in the BP (putting them in the RP fails silently). A feature that no feature rule references is not registered or validated, but can still be used with `/place`. If you need validation, make a harmless feature rule. A feature can be used from commands/scripts only when a rule or processor list references it (MCPE-242142). The starting points are the MS "features introduction", the wiki world-generation/generating-custom-ores, and https://bedrock.dev/docs/stable/Features.
- **Files and folders**: feature file names need no rule such as `<dimension>_..._feature.json`. The feature rule file name must equal the name part of the identifier (MCPE-242144). If the format_version does not match the feature type, a "description missing `places_feature`" error appears. "no valid version passed" means the format_version is missing. There is a report that referencing a feature in a subfolder needs a path relative to the features folder. (single report)
- **Biome filter format**: the filter is `"test": "has_biome_tag"` (`has_tag` fails silently). Features are placed only by tag, not by biome ID. To exclude oceans use `{"test":"has_biome_tag","value":"ocean","operator":"not"}`, and the temperature range filter values are 0~1. A working rule example used format 1.26.0, `surface_pass` and a uniform extent.
- **iterations and scatter_chance**: `iterations` is the number placed in the area decided by the distribution rule (count per chunk) and is rounded to an integer (0.4 -> 0, 0.5 -> 1). Less than 1 is impossible. `scatter_chance` is the probability per chunk, written as a percent (0-100, 5 = 5%, 0.40 = 0.4%) or `{numerator, denominator}`. A rare structure was fixed from 1/100 -> 1/1000, but there is a case where two still appeared stuck together even at 1/1500 (cause unknown). With `iterations` 0 the rule is off. Start tests with scatter_chance 100 and iterations 1 and lower them.
- **3x3 chunk limit**: a feature can edit only the origin chunk and the 3x3 chunks around it. The origin is the minimum x/z corner of the middle chunk, so the reach is -16..+32 (48x48). Blocks outside the origin chunk ignore the placement pass order. Large structures and trees being cut at chunk borders is not a bug and gives no log error. Put structures at the center of a chunk, at 16x16 or smaller, placed at x=z=8 (not perfect). A large range such as scatter x/z extent [0,64] pushes structures outside the border and gets them cut.
- **Chunk-covering distributions**: the `fixed_grid` extent must be `[0,15]` and `uniform` must be `[0,16]` to cover the whole chunk (may be a bug). A grid distribution extent that does not go beyond the origin is offset wrongly (MCPE-242145). Negative values in fixed_grid behave strangely, so put one more scatter in front and put the negative offset directly in x/y/z. A feature with no offset and x=y=z=0 is placed at the chunk minimum corner y=0. Feature rules are evaluated per chunk and biome filters per block.
- **Placement passes**: put trees in `first_pass`/`before_surface_pass`, ground decoration in `after_surface_pass` and ore in `underground_pass`. Ore mostly runs later than features and sees previously placed stone as valid, so it also overwrites `final_pass` structures (granite on stone). Avoid stone in structures. There is also a default order bug (carrots hidden by leaves and fallen trees). To make a patch bigger, put one more copy in another pass (`final_pass`). The full order is pregeneration_pass, first_pass, before_underground_pass, underground_pass, after_underground_pass, before_surface_pass, surface_pass, after_surface_pass, before_sky_pass, sky_pass, after_sky_pass, final_pass. before_surface_pass was suggested for custom structures. If a feature does not appear or is covered by trees in a specific biome (dark forest, old growth birch forest), check whether trees are placed first and check the pass.
- **Features have no version**: new changes can break existing features. Placement has been observed to differ between PC and mobile (a bug).
- **Superflat**: biomes, structure sets and feature rules do not run. `/place featurerule`, `/place feature` and `/place jigsaw` work in loaded chunks of a flat world (x/z are followed and y uses the rule's y). `q.noise` also works on flat worlds. `/place` cannot be run from command blocks or functions. `/place feature` and natural placement can place things differently (a case where the rule gave +37).
- **Script placement**: can be placed with `Dimension.placeFeature` / `placeFeatureRule`. There is a report that coordinates are ignored (saltysean, single report) and a question about performance overhead (unresolved). One complex feature blocks the main thread for about 1 second. nusiq split into 16x16x16 cubes, tracked where things were placed and decided the next job with `system.runJob`. Whether script placement also has the 3x3 chunk limit is unknown (presumed not).
- **Generate features with code**: there is a recommendation to generate features and Molang with TS/Python/JS scripts instead of nesting by hand. One condition takes scatter 1 + aggregate 1 + scatter 1 (nusiq). Feature/scatter placement is faster than scripting, and mazes and fractals are possible too.
- **Debugging**: in non-Molang-debug builds `q.log` does not exist, so in-game debugging is hard. There is a workaround of printing the heightmap array with an external simulator. If scatter does not work it is usually a JSON error (a missing comma), so lint and check the Content Log. Recreate the world every time you change biomes/features (old chunks stored on disk create square borders). You can also delete only the db files and keep the seed. Chunks are saved only when modified or part of jigsaw, so pruning regenerates them. There are cases where "No definition found for feature" was solved by restarting, a crash with no log on teleport was fixed by reducing scatter/iterations, and loading near jigsaw was slow or crashed in 1.21.131.
- **Getting vanilla files**: vanilla feature/feature rule identifiers are in `metadata/command_modules/mojang-commands.json` of the sample pack. The files are in `data/definitions/` of the BDS zip (https://www.minecraft.net/en-us/download/server/bedrock), the PC install folder (XboxGames), the APK (for example the 26.20 folder), the old features_archive.zip (1.18) and vanilla_1.17.0 (geodes). The vanilla BP template on GitHub has no biome features or feature rules. The community copy https://github.com/llgava/mcbedrock-features is not the latest. The Mojang samples (https://github.com/Mojang/bedrock-samples) have `roofed_forest_surface_roofed_tree_feature_rules.json`. Not every vanilla feature/rule is in the current files (the old roofed forest tree rule was dropped from the default instance). Many basic vanilla features are not data-driven (MCPE-242143). The PC install path is `C:\XboxGames\Minecraft for Windows\Content\data\definitions`. After the "Wilderness bound" update, BDS feature files were bundled into `.brarchive` (bedrock-server-1.26.51.1, a community unpacker exists), and old version files are found in the GitHub samples. The ancient debris rule is not in the samples, and biome files are taken from bedrock-samples at the matching version tag. Community-shared material: `features__rules_vanilla.json` (kiteob), the Overworld ore feature/rule zip, mesa gold, underwater magma, pumpkin after_surface.

### Worldgen Molang (coordinates, noise, heightmap, biome queries)

- **`v.originx/z` vs `v.worldx/z`**: `originx/originz` is the feature rule origin (chunk-aligned, a multiple of 16: 74992, not 75000). It is set only when entering a scatter feature, so store it yourself if needed. `worldx/worldz` is the current placement position and is updated immediately, but it does not exist in the feature_rule context. If you put y before x/z in `coordinate_eval_order` together with heightmap, "unknown variable variable.worldz" appears, so put y last. There is advice to use worldx/z for height queries. The Molang variable context carries through the whole feature tree. Temporary variables persist across thousands of chunks in natural placement but are not shared between `/place feature` and natural placement. Chunks load in arbitrary order, so derive decisions from world coordinates (for example `math.mod(v.originx,256)`). A range object accepts Molang only in the extent lower/upper bounds and does not accept it in step size and grid offset.
- **Placing at a specific coordinate**: check the chunk origin with iterations Molang (y is fixed in the rule). Returning 0 places nothing.
  ```
  "iterations": "math.floor(v.originx/16)==math.floor(100/16)&&math.floor(v.originz/16)==math.floor(100/16) ? 1 : 0"
  ```
- **`q.noise()`**: a single 2D Perlin-like function independent of the seed (the same in every world). The value is roughly -1..1 and skews toward both ends, so normalize with `/2+0.5`. Use a coordinate offset as the salt instead of a seed (there is also a way to pick the offset with Molang random). Scales below 8 are almost useless. Use low frequencies for large zones and 1/256-1/64 for patches. Elektrika said not to depend on it. kiteob's zone example (takes up about 14% of the world at biome size):
  ```
  "iterations": "v.freq=1/8192;v.q=100*(q.noise(v.worldx*v.freq,v.worldz*v.freq)*0.5+0.5); return(v.q>=34&&v.q<=47)?1:0;"
  ```
  To keep structures from overlapping, use a different noise zone and frequency per structure or use jigsaw. Use Perlin Fiddle for noise prototyping. There is no 3D noise.
- **Seed query**: `query.get_level_seed_based_fraction` fails in 1.26.10 features with "does not exist or not supported in this context" (it works only in animations/particles, a bug ticket exists). The seed fraction query cannot be used in worldgen (MCPE-240790 / 242120).
- **`q.heightmap` vs `q.above_top_solid`**: the correct call is `q.heightmap(v.worldx, v.worldz)` (wrong arguments crashed world loading). The heightmap is the world surface including sea level and cave entrances. `q.above_top_solid` ignores that, so it fixes features not appearing on custom surface blocks, trees on water and pond/cave problems. Use it in custom biomes. However, above_top_solid reacts to every "solid" including leaves. A custom block without `light_dampening` is treated as transparent and affects terrain generation (there is no way to skip it until isSolid is flattened). The `q.above_top_solid` offset limit was reported as 3 chunks (48 or more breaks generation and 47 or less works).
- **Slope check**: compare the `q.heightmap` difference between the center and the corners in the scatter's iterations Molang before the structure (for example 1 if all are &lt;= 2, else 0). y is `q.above_top_solid(v.worldx, v.worldz) - 2`.
- **`q.has_biome_tag`**: per-block check `"iterations": "q.has_biome_tag('ocean')?1:0"`. It is not in the docs, but it accepts coordinates (`q.has_biome_tag(tag, x, y, z)`, found by stirante). It takes one tag per call and returns a boolean (negate with `!`). Biomes are 3D, so y matters. About 48 calls per column caused no noticeable performance drop. Inside scatter it is reliable only after the grid spread (single-block context), and blocks at the chunk edge +15,+15 do not return the real biome (ocean tag). For proper biome filtering use feature rules (scatter first and check the biome filter). There is a bug that the three biome queries work only in conditional list features (MCPE-242119). Biome tag borders do not match exactly with the chunk biome filter of feature rules. Feature rules and custom biomes are linked with a custom tag in `has_biome_tag` of `minecraft:biome_filter`.
- **Biome border blending (arexon)**: loop downward from blend_dist, check the 8 neighbors with `!q.has_biome_tag(...)`, set `v.blend_factor` from the distance and use `v.height = math.lerp(q.heightmap(...)-64, custom, v.blend_factor)`. The third argument of `math.lerp` must be 0-1, and Molang has no `1..8` range.

### Notes by feature type

- **`single_block_feature`**: can replace by state (ore_feature cannot). Use a block descriptor with states in `places_block`: `{"name":"kado:stable_air","states":{"kado:purpose":"skybox"}}`. The weighted array `[{block:{name, states:{...}}, weight}]` worked in the latest Preview (stair `weirdo_direction` 0 west, 1 east, 2 north, 3 south, `upside_down_bit`). Custom states work, but block traits (`placement_position`/`block_face`) seem not to apply in feature placement. A custom `minecraft:facing_direction` state or rotating a ceiling block failed. For `may_attach_to` give direction keys and a block list or `{ "tags": "query.any_tag('log')" }`, and there is a case of making directional shelf mushrooms with `auto_rotate:false` + a custom state. Weights are silently truncated (weighted random/growing plant).
- **`ore_feature`**: suits ore-like things (including infested blocks). It is faster than scatter + single block. 7 bugs: client async with `place` (242115), x/z +8 offset (242122), the `count` name is misnamed (242125), `may_replace` silently required (242127), block states ignored in `may_replace` (242128), tag block descriptors impossible in `may_replace` (242124), output position always (0,0,0) (242129). Large ores (about 200 blocks crash) stop at 16 blocks in the negative direction, so give a +8,+8 offset with scatter. A large ore feature can make layers such as new stone/deepslate (confirmed by saltysean). Change vanilla ore rarity by overriding the rule with the same ID and using scatter_chance, not iterations 500. The ore amount is set by the rule `iterations` and the ore_feature `count`, and for rare ores lower both (for example 1 and 2). `count` does not accept a range, so put several rules with different counts. The skeleton example is underground_pass, `has_biome_tag overworld`, y -64..0. The vanilla diamond distribution is triangle `[-144, 16]` (`overworld_underground_diamond_ore_feature`, format 1.13.0, `underground_pass`, `coordinate_eval_order` zyx), and to make it more common toward -64 use triangle `[-16, -64]`. For ore use features, not jigsaw.
- **`scatter_feature`**: make pillars by giving only the `y` distribution with no step_size. If registration fails, reduce iterations. To cover every surface block of a chunk, the feature rule places Feature A once at 0,-64,0, with A = scatter (`fixed_grid` x/z 0..15, `"y": "q.above_top_solid(v.worldx, v.worldz)"`, 256 times) and B = a single block feature. To cover the full Y range, iterations must match the dimension (for example 64x320), and large numbers slow world loading. Surface layers are made with a Y offset `fixed_grid`.
- **`aggregate_feature` and `sequence_feature`**: an aggregate with `early_out` (first success/first failure) is widely used in Mojang files as a conditional. Sequence has bugs (vertical stacking, undocumented side effects), so use aggregate. The offset must be inside the placed feature. A first-failure early-out in aggregate/sequence keeps placing after a failure if the failing item is not the first (MCPE-242141). The docs are also vague about `early_out`. When joining 48x48 pieces into a huge 96x96 structure, pieces shift by 16 if the origin chunk differs, so use an `early_out: first_failure` sequence with per-piece offsets and snap to the 48 grid with checks such as `(v.worldx-v.originx)/48`.
- **`snap_to_surface_feature`**: works on only one surface. The `random_vertical` name is misnamed (242117) and it attaches in the opposite direction on non-air blocks (242118). Cave floor blocks: put the feature rule at Y -60..40, and a "floor" snap_to_surface places a single_block_feature with `may_attach_to` stone/deepslate and `may_replace` air (avoids the sea floor). There was a suggestion to save amethysts placed on a ceiling with structure void because air remains above them. Search feature: if the `min`/`max` order is swapped, repetition breaks (242130), and not every condition references the search buffer (242132).
- **`geode_feature`**: very tricky ("use mcstructure"). A layer accepts only one block (no weighted pool) and ignores crack properties. `outer_layer`/`alternate_inner_layer` exist only in the docs sample and are not official fields. `inner_placements` accepts only `{name}`, so custom bud blocks all face "down" (or up). The onPlace custom component fires only with `/place`. A suggestion to put states in the feature file was not confirmed.
- **`multi_block_feature` (1.26.40)**: places every part of a multi-block (single_block_feature places only part 0, only the lower half). `{"places_block":"test:block","enforce_placement_rules":false,"may_replace":["minecraft:air"]}`. If `enforce_placement_rules` is true it places only when air/water is allowed as support, so have the feature rule place snap_to_surface and have that place the multi-block feature. The docs were published on 2026-07-30 on learn.microsoft.com (featuresreference ... minecraft_multi_block_feature). Before that, aggregate -> scatter -> a per-part state single block (like vanilla tall_grass) was used. There is also a report that it was still broken at 1.26.40.
- **2-tall flowers**: vanilla double flowers (peony/lilac) are placed through the `double_plant` path. The alternative is `minecraft:multipart_block_column_feature` with `tip_block` (`upper_block_bit: true`), `frustum_block` (`upper_block_bit: false`), `height_range` 2..2, `direction: "UP"`, `may_replace` air and `may_place_on` grass_block.
- **`cave_carver_feature`**: biome-dependent and 8-directional. For water, set water instead of air. y is relative to the input coordinate of the parent feature/rule (confirmed with `project_input_to_floor` and sequence), so the problem of being placed at about -64 is unresolved. There is no carver for craters. The skip probability is inverted (not reported). Cave size is controlled with the `width_modifier`, radius multiplier, `y_scale` and `height_limit` fields. Docs: wiki.bedrock.dev/world-generation/feature-types.html#carver-features.
- **`disk_feature` and `sculk_patch_feature`**: `minecraft:disk_feature` (1.26.0) uses `block`, `half_height`, `radius` and `replaceable_blocks`, and `minecraft:sculk_patch_feature` (1.16.0) uses `ground_block`, `surface`, `vertical_range`, `growth_chance`, `horizontal_radius` and `cant_place_sculk_vein_on`.
- **growing plant feature**: it also works on non-plant blocks, so it can be used for stone pillars (`body_blocks`, `head_blocks`, `growth_direction`, `height_distribution`). Cactus-style growth is made with scatter + `math.random`.
- **Other features**: the fossil feature is not placed at the input position (242159/242161). Horizontal tree decoration needs a block that has both `cardinal_direction` and `growth` states (242146). The multiface feature seems broken. A kelp `growing_plant` cannot block its tip. `spring_feature` was not found. A fallen trunk makes fallen logs. `minecraft:feature_pool_element` can reference only hardcoded vanilla features.
- **Moss spread (bone meal)**: decided by `replaceable_blocks` of the vanilla feature `minecraft:moss_patch_bonemeal_feature` (`minecraft:vegetation_patch_feature`, format 1.16.0). Copy it into `BP/features/` and add blocks (for example `minecraft:bone_block`). It overrides the vanilla identifier, so no feature rule is needed and order does not matter.
- **Tree features**: to remove leaves, set `leaf_blocks` to air (tree features are in the BDS package, not in biome files). With an azalea-style format (needs trunk tilt) two kinds of leaves can be used, and it did not work with oak. If leaves appear only on top of logs or the trunk is short, raise the trunk height. The `range_min` of `branch_start_offset_from_top` must be 0 or less (`outside [-2147483648,0]` error). The wiki tree generation page is old, and requests for new examples got no answer until 2026-10. Floor limits are done with `may_grow_on`, vanilla examples are in BDS, and saplings place a structure. Docs: https://wiki.bedrock.dev/world-generation/feature-types#tree-features.

#### Terrain

- **Terrain cannot be changed by add-ons**: terrain is made first by hardcoding, and the biome `noise_type` changes only the surface. Changes are done with features that place air/stone (`q.noise(v.worldx, v.worldz)`, `q.heightmap()`, `q.above_top_solid()`). For tall mountains, use a rule that adds blocks to existing highlands, or in mountain-tag biomes (cherry_grove, frozen_peaks, grove, jagged_peaks, meadow, snowy_slopes, stony_peaks) place mcstructure peaks with scatter -> weighted_random -> structure_template_feature. Large bodies of water are not features: the surface is filled with water up to about y=62 before biome features, so only correction by air replacement is possible and the correcting worldgen is slow. Changing sea level (63) did not work with noise parameters, so use a feature that fills water up to the target height. kiteob checklist: no 3D noise, erase vanilla directly, use the seed only as an offset, reference works Realistic Landscapes (Shapescape), C++ mod loader LeviLamina.
- **Building terrain from scratch (nusiq)**: chunk-level scatter (fixed_grid x/z 0..15, iterations Molang ending in `return 256;`) -> column-level scatter (Y fixed_grid [0, terrain_height-1], iterations returns a normalized multi-octave `q.noise` height). Only 3x3 chunks can be queried, so blending with biomes is hard. The Fast Biome Generation Template (1.20.30) decides biome positions with Molang and feeds column features directly (erase the existing world first, the Molang still works, the features need updating).
- **Deeper oceans**: made with scatter + single_block_replace. The documented `sea_floor_depth` has no effect and changes only the surface layer thickness. Example pack `Deeper_Ocean_BP.zip` (kiteob). A 2-block-deep ocean is impossible with biomes alone, so use a biome filter rule to cut the terrain down to a constant Y and place 2 blocks of water (neighbor blending lerps by sampling neighboring chunk biome tags). An ocean world uses a "remover" feature to carve space or turns dirt into water columns (seagrass ends up floating).
  ```
  "iterations": "v.oldfloor=q.above_top_solid(v.worldx,v.worldz); v.olddepth=62-v.oldfloor; v.adddepth=math.clamp(3*v.olddepth,0,90); v.newfloor=v.oldfloor-v.adddepth; return v.adddepth;"
  ```
- **Removing water**: overriding the vanilla underwater cave carver rules (`overworld_underwater_cave_carver_feature` / `underground_underwater_cave_carver_feature`) with a custom carver removes a lot of underground water. A carver can be overridden but an aquifer cannot. Water left after turning ocean water into air is erased by overriding the seagrass/kelp rules. Overriding `springs` and similar helps only partly.
- **Stone to netherrack**: 16x16 chunk fixed_grid scatter -> 256 column features -> a single block feature, ore in a later pass. Emptying the End: a rule that places air with a single block per chunk. Some vanilla blocks such as islands and chorus are placed after add-on rules, so erase them later with scripts (End_Void_BP.zip). For placing structures in the End void, `scatter_chance` and random y work (End_Void_v2_BP.zip).
- **Custom End "biome"**: the End is one biome so custom biomes do not work. Make all related rules check the same low-frequency noise range. Blur the border with high-frequency, low-amplitude noise, a minimum size is not guaranteed, and Voronoi noise is an alternative.
  ```
  "iterations": "v.biome = 100*(1 + q.noise(v.originx/8000, v.originz/8000))/2; return v.biome >= 28 && v.biome <= 45;"
  ```
- **Ocean depth and river banks**: there is an answer that the deepest ocean you can make with biomes alone is about 38 blocks, and lowering sea level needs editing every Overworld biome file (single report). Dirt banks beside rivers come from terrain dropping below y 62, so raise the noise.
- **End ore**: use the `the_end` tag in the rule. Two reports say custom block features in the End did not work except ore features.
- **Height limit**: the height limit is decided by the server packet. It can be changed with LeviLamina, and in vanilla you cannot build above the Nether ceiling.

#### Modifying/removing vanilla generation

- **Override principle**: modify by giving a feature/feature rule the same identifier as vanilla (a `minecraft:` prefix cannot be used for new features). Turn it off with `iterations: 0` or by removing `distribution`. Without the feature file, a rule whose `places_feature` points to an unknown ID gives an error. Some, such as firefly bushes, have no exposed feature file. To stop vegetation, copy the vanilla rule and set iterations to 0. The `foliage` rule is for grass/flowers, and tree rules are separate files.
- **Replacing/removing trees**: vanilla tree features were moved to legacy and cannot be called directly from custom rules. Change only the `places_feature` of the vanilla tree rule (keep the identifier, for example `minecraft:roofed_forest_surface_roofed_tree_feature_rules`) to your own feature. The name pattern is `<biome>_surface_trees_feature`. Feature names: oak_tree_feature, spruce_, birch_, jungle_, acacia_, dark_oak (roofed_tree_feature), mangrove_, cherry_, azalea_tree_feature. To remove, point to a single_block that places `minecraft:air` (with iterations 1 it is one air cell per chunk) or set iterations to 0 (confirmed in dark forest). To turn every tree into one kind, override the surface-tree rules of all biomes while keeping their names. Leaf litter has no rule and is merged into the aggregate of the tree rules. Reference add-on: IceCraft Studios "No Trees" https://github.com/IceCraft-Studio/No-Trees-MC-Beh/releases/tag/v1.3.0.
- **Bamboo density**: vanilla jungle bamboo is decided by the iterations Molang of `bamboo_jungle_after_surface_bamboo_feature.json`. The vanilla value is `math.clamp(math.trunc(math.ceil((query.noise(math.trunc(variable.originx / 80), math.trunc(variable.originz / 80)) + 0.3) * 160)), 15, 160)`, and to reduce it use `+0.1`, `*20` and clamp 0..5, or use `math.random_integer(1, 5)` or 0.
- **Things that cannot be erased**: leaves, vines, glow lichen and mineshafts cannot be fully replaced/removed. Removing mineshafts and custom biomes inside Nether/End biomes were impossible as of 2025-11~12. Vanilla structure frequency and villages were changed by the structure set override below.
- **structure set override**: in 2025-11~12 changing structure frequency and removing villages was thought impossible, but on 2026-10-26 the frequency of abandoned campsites was reduced by overriding the structure set's `separation`/`spacing`, and on 2026-11-01 the plains village was replaced with a custom village by overriding the structure set. Replacing vanilla village structures has many bugs, so there is also advice to override the meeting point with an empty file and build your own village jigsaw (2026-09).
- **Adding vegetation and biome weights**: adding vegetation with a behavior pack keeps the original biome content. `multinoise_generation_rules` weight 0 leaves fragments (no other method confirmed). End structures (End ships, islands) are not biome-based and cannot be erased. The End pillars are at fixed coordinates. Deepslate may not be a feature, and surface/lower blocks are replaced with the biome surface builder. Caves are part of the base terrain pass and cannot be turned off.

### Custom blocks in worldgen

- **Ticks do not run**: for custom blocks placed by features (`pregeneration_pass` cave carver, single_block_feature and so on), `onPlace`/`onTick`/`minecraft:tick` are not reliably initialized (confirmed as a stable release bug). They do not run until the block is broken and placed again. Details: only blocks placed inside the selected 16x16 chunk (x/z 0..15) tick, and blocks in neighboring chunks are only placed. Negative extents in the distribution (use 0..16 instead of -8..8) make it unstable. Search + feature instead of scatter, and `final_pass` instead of `after_surface_pass`, worked. Biome surface builder blocks do not run queued ticks. A single block feature does not trigger queued ticks (there is also a claim that it was fixed later).
- **Lava and onTick**: lava placed with single_block_feature does not tick so it does not flow. The question of onTick not running for blocks placed by features/structures still had no answer in 2026-11.
- **Snow layers**: snow layers generate after features and pile on top of custom blocks, and `final_pass` does not avoid it. Place them under a solid block or avoid cold biomes.
- **Duplicate tick data in structures**: a .mcstructure block with tick data in its NBT fired scheduled events twice (the normal delay + the saved remaining tick_delay). The workaround was to delete that block position/tick entry in the NBT (keeping the tag itself), and it was fixed in the 2026-03 Preview (MCPE-236362).
- **Surface block list**: placement features use a hardcoded block list. A custom grass made with `minecraft:geometry.full_block` does not grow trees/flowers/mushrooms, so copy the vanilla list and add the block. Giving the dirt tag does not make every plant grow. Custom seagrass also appeared only when the surface block (custom glowing grass) matched. For features on custom grass, restrict may_replace to air.
- **Other**: there is a case where it appears in Plains but not in Basalt Deltas (unresolved). There is also a report (unresolved) that adding random ticking to a custom cactus growing-plant feature turns the block off. A world made of only custom blocks lagged/crashed at render distance 5 and above, and the cause was a custom stone block that used custom geometry (fixed with proper culling or vanilla cube geometry).

#### Structure files

- **Location and name**: `structures/<namespace>/<name>.mcstructure` and the identifier is `namespace:name`. Without a namespace folder "structure not found" appears, but jigsaw also finds subfolders. Load with `/structure load ns:name` or the script `world.structureManager`. Do not use spaces in file names (`klee_boss (1)`). A wrong export gives a missing `format_version` error. To keep things from breaking when reproducing vanilla structures, put them in a different folder under `structures/`.
- **Size**: structure block saving is at most 64x64x64 (the NBT editing workaround was blocked in 1.20.50). The mcstructure maximum is 64x384x64 (minimum 1x1x1), but for performance a 16x16 center placement is better. The docs say 64x64 works, but an about 35x64x50 structure was not generated at all by structure_template_feature while an about 32x35 one was (unresolved). If larger, split it into jigsaw pieces. StructureLimitRemoverPC (github.com/JORICK404/StructureLimitRemoverPC) removes the structure block export limit (supported 26.51 at the time, 26.60 announced). Several structure blocks, jigsaw pieces and files over 48x48 exported with Amulet can also be used.
- **.mcstructure v2**: structures exported from the Preview around 2026-10 use the new compression, so they do not load in the stable release, and structure editors show a blank screen until updated. Temporary tool https://ludwigbooysen.github.io/mcstructure-table-editor/, changelog search https://searchlog.beyondbedrock.org/?q=Mcstructure.
- **Mobile export**: Android gives "Export operation not supported" from 1.21.132, and Android 11+ and iOS cannot export either. Workarounds: bundle as `.mcworld` and convert at https://bloxelizer.com/converter , extract level.dat, Levi Launcher, HoloPrint.
- **`structures/` location**: put it at the BP root. There is a 2026-11 report that `/structure load` may not accept additional folder levels (unverified, which differs from the subfolder behavior above).
- **structure void**: get it with `/give @s structure_void`. Save void instead of air in the structure so existing blocks and terrain show through and trees do not overwrite it. Plain air replaces water/waterlogged blocks. If you do not fill air with StructureVoid before export, "void blocks" show around natural structures. .mcstructure does not store void (index -1 outside the palette). So structure_void is not preserved when converting from Java, but air turned into void is kept. Loading a structure replaces existing blocks (including leaves), and only where there is void do existing blocks remain. There is no vanilla way to skip replacement.
- **Structure loot**: structure files and loot tables can go in subfolders (the loot path starts with `loot_tables/`). A lootless copy saved in the world by a structure block with the same name takes priority over the BP one, so run `/structure delete <name>` and load again. There is also a report that chests placed by a subfolder structure lost their loot. Chest loot is put in with NBT editing, the jigsaw processor and random loot tools (wiki.bedrock.dev/loot/randomized-structure-loot). Pot loot uses the same processor method (https://wiki.bedrock.dev/loot/randomized-structure-loot#example), but a custom pot is replaced and loses the original pattern.
- **Tile entity NBT**: trial spawner, vault and suspicious sand loot are tile entities, so edit the structure NBT with the MCBE Essentials structure editor (https://mcbe-essentials.github.io/structure-editor/) (spawn potentials, equipment loot, distance, reward loot table, normal + ominous). Leave the vault's `state_updating_resumes_at` at 0. Suspicious sand loot can also be set with the jigsaw processor. There are no custom tile entities, so a fully custom trial spawner block cannot be made. A custom vault works with NBT editing. There is a case where editing the spawner NBT `normal_config`/`ominous_config`/`spawn_data` had no effect, a case that succeeded by copying a bogged spawner and changing only the id, and a case that succeeded by editing with a VS Code NBT viewer plugin.
- **Custom tree with fruit**: needs a custom .mcstructure.

#### structure_template_feature

- **Fields**: format 1.13.0, `structure_name` (for example `mystructure:abc/def/ghi/oaktree` -> `BP/structures/abc/def/ghi/oaktree.mcstructure`, the new format is `abc:def/ghi/oaktree`), `adjustment_radius` (raising to 8-16 finds a spot), `facing_direction` (random is possible), `constraints` (`grounded`, `unburied`, `block_intersection.block_allowlist`). There is no blocklist. If only air is allowed, it fails when even one non-air block exists. To protect a jigsaw city from trees, the allowlist must have air, grass and dirt. The condition needs "any_of" and `==` (the typo `=` breaks it). The "Cannot find behavior pack structures definition" error was fixed by restarting the IDE.
  ```json
  "constraints": {"grounded": {}, "unburied": {}, "block_intersection": {"block_allowlist": ["minecraft:air","minecraft:stone","minecraft:dirt","minecraft:grass"]}}
  ```
- **Minimal natural generation**: a `surface_pass` feature rule places `structure_template_feature` (`structure_name`, `adjustment_radius`, `constraints: {"grounded": {}}`) with `scatter_chance`, `y: "query.heightmap(variable.worldx, variable.worldz)"` and a `has_biome_tag` filter. Floating structure setup example: `unburied` + `block_intersection.block_allowlist ["minecraft:air"]`, adjustment_radius 0, rule y uniform [100,240]. Placing over lava combines constraints.
- **Placement geometry**: the corner of the selected chunk is the origin, and the structure grows +x/+z from the rolled x/z. Anything beyond the 3x3 chunk range (-16..32, 48x48) is cut. A 48x48 structure moves the origin to (-16,-16) with a negative `extent` in the rule's x/z. `rotate_around_center` moves the pivot (floor(size/2) of x/z) to the selected position and fits up to 33x33 (-16..16). If you fix the scatter offset at 8,8 the pivot is at the chunk center and 48x48 works (member test). The `rotate_around_center` bug was fixed in 1.26.30, but the new `ground_level` option has the same problem. The cut differs by facing_direction, and random rotation beyond 48x48 can be cut.
- **No entities**: entities in a structure placed by a feature are not generated. Put command blocks or custom blocks inside the structure (command blocks can turn off, so custom blocks are recommended) or use jigsaw. Jigsaw blocks inside a structure placed by a feature do not work. However, there was a remark on 2026-08-23 that "jigsaw now works together with features", so it is **conflicting** (it may be in the feature_pool_element context). A report that structure entities generated by a feature rule lose components was closed as Works As Intended, and Mojang said entities should not be loaded by feature rules. There is no feature that restricts which blocks a structure template can place.
- **Structure location maps**: using a structure identifier as the `destination` of the loot function `exploration_map` works in chests and trade tables. Getting it directly with `/loot` or scripts always points to the cached location. To make structure maps work, build it with jigsaw.
- **Custom tree structures**: place with structure_template_feature or tree_feature and pick one of 5-10 variants with weighted_random_feature. Wrap the surroundings in structure_void so terrain is not carved.
- **Intruding into underground/caves**: when jigsaw or trees get eaten by caves/features, one team used a custom "fake air" block (a custom component) that turns into air by itself over time. There was also advice to change the placement pass or erase water/diorite in the bounding box with scripts.

#### Files and minimal setup

- **Folders**: BP `worldgen/structures` (renamed from the earlier `worldgen/jigsaw_structures`, and old examples do not work), `worldgen/structure_sets` (plural, a singular folder fails silently), `worldgen/template_pools` and `worldgen/processors` (processor lists must be here, otherwise "Missing referenced asset"). The folder name is `worldgen`, not `world_gen`. Put .mcstructure files in the outer `structures/`. A template pool + structure settings are required, a structure set is needed only for natural generation, and a processor is optional. `/` can be used in identifiers. supernova uses format_version 1.21.100 (the last jigsaw format change was around then). Data-driven jigsaw has been stable since the 1.21.50.26 Preview (it turned 1 year old on 2025-10-30).
- **`minecraft:jigsaw` fields**: `step`, `start_pool`, `max_depth`, `start_height`, `heightmap_projection`, `terrain_adaptation`, `max_distance_from_center`, `dimension_padding`, `biome_filters`. **structure set**: `minecraft:structure_set`, with placement `minecraft:random_spread` having `salt`, `spread_type: linear`, `separation` and `spacing` (numbers, required). Without them it does not appear in the `/place structure` list. **template pool**: `minecraft:template_pool`, and its elements have `element_type: minecraft:single_pool_element`, `location`, `processors`, `projection`, `weight` and `fallback`. `legacy_single_pool_element` is not supported. Official example: https://learn.microsoft.com/ja-jp/minecraft/creator/reference/content/worldgenreference/examples/jigsawjigsawstructures?view=minecraft-bedrock-stable.
- **`projection` location**: it must go inside the `element` object (next to `element_type`, `location` and `processors`), and `weight` goes outside. If misplaced it is silently ignored and becomes `rigid`. It is a required field and by the schema it seems usable with any `element_type`.
- **Object-form fields and processor references**: `dimension_padding` and `max_distance_from_center` are also written as objects (`{"top":3,"bottom":3}`, `{"horizontal":116,"vertical":80}`). In a pool, reference a processor list with `"processors": "ns:name"`. Even if the referenced processor list does not exist, generation still happens but an error log remains.
- **`location`**: a structure file path, not an identifier. Write it relative to `structures/` without the pack namespace prefix (for example `3008_plots/room0`). An "Empty or non-existent pool" error is usually a wrong pool ID/namespace/location, so check the case too. Do not use the `mystructure:` prefix in the pool. JSON parse errors ("Invalid encoding in string", "document root must not be followed by other values", "Invalid asset path ...") are stray characters or a duplicate root in the pool file.
- **Jigsaw without jigsaw**: a single-piece "jigsaw structure" with no jigsaw block is also a way to place a large structure with only a start_pool (bypassing the feature size limit) and gets `/locate` support. Jigsaw is a system separate from features/feature rules, so `/locate structure` works and feature rules are not used.

#### Jigsaw blocks and connections

- **Naming rules**: `name` = the name of this block itself, `target name` = the name to look for, `target pool` = the template pool to search. The generating block finds a piece in the pool whose jigsaw `name` equals its own target name and picks randomly by `weight`. If all use the same name, name must equal target name. A generate-only jigsaw needs only target + pool (name can be `minecraft:empty`), and the receiving side needs only a name. A pool that references only its own start piece finds nothing: the start_pool must be a piece with connecting jigsaws, and other pieces must be in the target pool. Entity pools also need a target name. Do not put name, target pool and target name all on one jigsaw block, and split into a placer (target pool + target name) and a connector (name). Put the connector of a 3-cell doorway in a consistent position. In jigsaw block text it is safer not to use characters that are not on the keyboard (euro/pound/yen).
- **Priority and rotation**: selection priority decides which wins when two jigsaws contest the same spot (higher wins), and placement priority is the order of candidate jigsaws within a piece. A vertical (UP/DOWN) jigsaw randomly rotates the child piece around the Y axis. `joint_type: aligned` places while matching the line markings of both jigsaw blocks and works only on the placing block (check that the marking directions are the same). The rotation of a horizontal jigsaw cannot be turned off and always rotates to match the target jigsaw (`rollable` is for vertical only). Laying a jigsaw block on its side does not rotate the piece. A vertical block rotates randomly, so you need to make only one orientation. You cannot force the direction or change a jigsaw's pool with a processor.
- **Checking piece alignment**: check whether jigsaw blocks mesh with `/place structure ... keepJigsaws=true`. `/place jigsaw <pool> <target> <depth> ~~~ true` is a better debugging command. `/place structure` needs a structure set and uses worldgen techniques so some (for example Anchor) fail. There is a report that `start_jigsaw_name` does not work (2026-08-17, it worked before). If it works with `/place structure` but natural generation does not or `/locate` hangs for 5~10 seconds, check `biome_filter` and the structure set. A case where the structure set stopped after a fix is unresolved.
- **`/place jigsaw` and vanilla pools (2026-11)**: for ancient cities/bastions only the middle piece appears, and the pillager outpost is not jigsaw. A feature pool reports only success and places nothing. Using a vanilla pool as start_pool gives a missing asset error, and with a feature_pool_element element `/place jigsaw` fails.

#### Limits and spacing

- **Limits**: `max_depth` at most 20 (7 before 1.21, ancient city 7, village 6, infinite structures impossible), `max_distance_from_center` at most 128 (Chebyshev radius, diameter 256, default 128, village 80), maximum structure 256x256, about 20 chunks in every direction. To extend roads and cities raise both. If generation stops early, check max depth and distance from the center.
- **Overlap**: piece bounding boxes within one structure never overlap. The exception is a piece that fits completely inside its parent piece. Separate structures overlap unless they are in the same structure_set (salt matters only when spacing/separation are the same). There is no exclusion zone, so to separate them put them in the same set. Terrain-matching pieces (roads) can overlap and cover houses through a bug (MCPE-224012). The workaround is to save the road structure at a height of about 25 (the road on the floor and 24 cells of air above). `use_expansion_hack` was also mentioned.
- **Spacing**: separation must be less than half of spacing (spacing must be more than twice separation, as in spacing >= 5 with separation 2). Raising separation moves them farther apart, and changing `salt` moves positions. Java and Bedrock give the same position for the same values and the same seed.
- **Exact counts are impossible**: only the start piece is guaranteed. You cannot force N rooms or limit the count (stronghold portal style). Make a piece that should appear only once the start piece (several is not possible). Reimplementing with scripts loses terrain adaptation. A custom stronghold example is in channel 1459006306915581984.
- **fallback pool**: tried when no element fits and when max_depth is reached (used for corridor end caps). It is not guaranteed and gets the same distance and space constraints.

#### Height, projection, terrain adaptation

- **`start_height`**: use `{"type":"constant","value":{"absolute":0}}`. `uniform` needs `min` and `max` (`"min": {"absolute": 50}, "max": {"absolute": 150}`, and `value` gives a schema warning), and there is a report that a structure appeared in the sky. start_height decides only the start piece position relative to `heightmap_projection`. For a fixed Y (sea floor y=20 and so on), leave heightmap_projection out and use absolute, and to start at the sea floor use `heightmap_projection: ocean_floor`. A negative start_height lowers it. `dimension_padding` (watch the spelling, not "dimensional_padding"), for example `{"top": 25, "bottom": 10}`, keeps away from the height limits, and giving about 100 each pushes a 64x64x64 structure into flat areas. "Out of bounds" may be a placement outside the height limits. The processor's "ignore start height" must be true for a fixed Y. An old example has `"start_height": {"type":"constant","value":{"absolute":-70}}`.
- **projection**: `rigid` does not follow terrain. `terrain_matching` fits a piece (a road) to the terrain height and ignores start_height (so the village elevation range cannot be set, and it is rigid in the air). It works only in natural generation, not with `/place`. Terrain-matching roads cannot really be made smooth. One author fixed a terrain_matching/rigid mix that did not generate by placing the two jigsaw blocks again. There is a report that terrain-matching pieces summoned entities 5-10 cells underground (not reproduced).
- **`terrain_adaptation`**: `bury`, `beard_box`, `beard_thin`, `none`, and also `encapsulate`. The vanilla counterparts are trial chambers encapsulate, trail ruins bury, ancient city beard_box, villages/outposts beard_thin and bastions none. There is a report that adaptation is per whole structure (single report). The start piece is always buried in the ground, so save a layer of structure void at the bottom or split the structure. beard_box places it in the ground without filling (seen as intended because of villages). The problem of ships always appearing on a pedestal was fixed with `"none"` and the correct start_height (`"absolute": 1`). To avoid floating, `beard_thin` is best. To bury, use a y offset in start_height + `none` (bury changes the surroundings). The adaptation box uses blocks of the local biome and cannot be controlled. Terrain adaptation is the only way to make a structure overwrite neighboring pieces. It does not work in the Nether and the End.
- **Cannot judge terrain height**: jigsaw cannot compare terrain height with the piece origin or pick pool elements by height, and it cannot make a structure generate only on specific blocks. There is also no option to limit the coordinate range (features can do it with distribution). Workarounds are a post-placement script, making a "bridge" with the `minecraft:protected_blocks` processor, and making pillars with a feature pool element (pillars do not stop at the ground and overwrite cave air. There is no cave air block, so there is an idea of running a cave air replacement one pass earlier).
- **Foundations of floating structures**: attach a large block cube under the structure with jigsaw and use a `minecraft:protected_blocks` processor with the ground block tag (wiki.bedrock.dev/world-generation/jigsaw-structures#protected-blocks-processor). It also overwrites cave air.
- **Biome borders**: jigsaw does not handle biome borders at all (villages cross borders in both Java and Bedrock). If a large structure is cut at a biome border, use jigsaw. Several biomes need `any_of`. Otherwise it does not generate, so the alternative is to attach a custom tag to all the biomes you want.
  ```json
  "biome_filters": [{"any_of":[{"test":"has_biome_tag","operator":"==","value":"plains"},{"test":"has_biome_tag","operator":"==","value":"taiga"}]}]
  ```

#### Generation order and features

- **Jigsaw before features**: as in Java, jigsaw always generates before features, so features can overwrite it. Use a `block_allowlist` constraint on the feature side and use structure void so trees do not dig in. Trees and features also generate inside jigsaw. To block that, do not use a grass/dirt tag floor (rooted dirt also has the `dirt` tag) or use a floor where features cannot be placed (a successful block whitelist case). A piece placed with `/place` covers grass but natural generation does not. Custom jigsaw always overwrites vanilla structures regardless of the generation step.
- **`minecraft:feature_pool_element`**: added to template pools in the latest Preview around 2026-03-11 (corresponds to the feature element in Java). It can reference only hardcoded vanilla features, may behave differently in structure set generation and `/place structure`, and has bugs in natural structures. Jigsaw inside a feature placed this way is not triggered. The jigsaw block of this element faces up and the target pool need not be specific (`minecraft:bottom`). In the `feature` field write a feature ID (for example `minecraft:hay_pile_feature`).

#### processor

- **Kinds**: at the time of 2025-11 Bedrock had only `minecraft:rule` (3 tp elements, and no `spawn_overrides` either). In late 2025-11 block protection processors were added (valid but not in the docs): `minecraft:protected_blocks` (blocks specified by tag, for example the stone tag is not covered by the piece, and `value: not_feature_replaceable` also blocks overwriting), `minecraft:block_ignore` and `minecraft:capped`. Used when a tower foundation should replace grass but leave stone (with the limit that it also fills air under caves). Example pack `New_Project.mcaddon` (`test:hut`). The ancient city has no `block_rot` processor. There are 4 processor types, and copper door aging needs about 2000 lines of combination rules.
- **Loot for directional chests**: a processor applies after placement, so each state needs a rule (4 chests, and barrels use a `facing_direction` number). Give `minecraft:blockstate_match` (not `block_match`) with `"block_state": {"name":"minecraft:chest","states":{"minecraft:cardinal_direction":"east"}}`, a `block_entity_modifier` `{"type":"minecraft:append_loot","loot_table":"loot_tables/..."}` and an `output_state` with the same state. The only modifiers are `passthrough` and `append_loot` (no `clear`). State keys in processors need a namespace (`minecraft:vertical_half`). You can see the state list with `/setblock ~~~ chest[`. You cannot give loot to only specific chests, decide spawner mobs or add chiseled bookshelf loot. Per-biome processors are also impossible, so split the structure. A processor does not edit entities. Randomly swapping blocks is possible, but replacing candles is unclear.
- **Filling the air under a piece (mine rails and so on)**: put a floor block in the structure and use a `minecraft:rule` processor (`input_predicate` block_match FLOORBLOCK, `location_predicate` block_match `minecraft:air`, `output_state` oak_planks) together with a `minecraft:block_ignore` processor that lists FLOORBLOCK. The floor stays as structure void and only the air becomes planks.
- **pool alias**: `random_group` in `pool_aliases` works. Putting the same structure with different processors in one set gives an error. In a template pool, if the location is the same and only processors differ, the first processor is always used, so use different file names.
- **Missed recognition**: there are reports that a processor list does not recognize many blocks (suspected bug, with a suggestion to check IDs such as `minecraft:grass`). There is also a report that barrel loot did not work in a processor and only chests did (unverified).

#### Entities

- **Generated only by jigsaw**: entities stored in a structure file appear when generated by jigsaw (the `doMobSpawning` game rule must be on, otherwise they silently vanish). Not in feature placement. There is a bug where they are randomly dropped with about 1/50 probability (not reported). The workaround is to have a ticking block summon them and erase itself. To give wolves/villagers a biome variant, save an invisible, motionless entity (`minecraft:physics`, `minecraft:transformation`, a spawned event after 4 seconds) or use a tag-checking `execute` instead of a timer. Entities can now be summoned with jigsaw.

#### Overriding vanilla structures

- **What can be overridden**: custom jigsaw can place vanilla structure templates and connect to that jigsaw, but it does not generate vanilla jigsaw. As of 2025-12 only trail ruins and trial chambers could be overridden (template pools can be edited, and the trial chamber code is not public but nearly the same as Java). In 2026-04 tests it overwrote abandoned campsites, trail ruins, villages, parts of trial chambers and even the ancient city (`/place` is not possible). If you override vanilla pool/structure files, the vanilla and custom pools run together. Pillager outposts and strongholds are hardcoded, and shipwrecks are hardcoded too.
- **Editable range**: only jigsaw-based vanilla structures (including ruined portals) can be edited with template pools, and desert temples and strongholds are hardcoded. Custom biomes do not get vanilla villages, and a custom village can be `/place`d with extra jigsaw. To add buildings to a vanilla pool, modify the vanilla file, and overriding villagers with jigsaw changes all villagers. There is a vanilla village missing-profession bug MCPE-226264 (snowy village shepherd, plains fletcher, savanna mason).
- **Data-mode structure blocks**: they exist in Bedrock too, and the data field is stored in the block entity but not visible in the UI (shows outpost, coral reef and village logic). There is a bastion jigsaw example in bedrock-samples.
- **Modifying trial chambers**: to erase pieces that make the water pattern, put `end.json` in `worldgen/template_pools/trial_chambers/chambers` (piece `trial_chambers/corridor/end_2`). Place the responsible pool in creative with `/place structure minecraft:trial_chambers ~~~ true true` and find it by examining jigsaw blocks. By changing the start pool it can be reduced to one small custom structure. Mobs can be added with pool aliases (editing the spawner jigsaw NBT), but spawn_overrides is not exposed yet.
- **Vanilla structure files**: there is material converting the 822 vanilla `.nbt` structures from the 1.21.131 BDS zip with Jayly's nbt-to-mcstructure (some block entities such as spawners are lost). Vanilla jigsaw pools are hardcoded except trial ruins/chambers (found in the APK from the data-driven jigsaw experiment days). The trial chamber NBT is in old folders (1.21.0/1.21.30/1.21.50), and the trail ruins jigsaw files are in the shared zip `experimental_jigsaw_structures_3.zip` (old APK). Villages use hardcoded data-mode structure blocks (bastions and ancient cities are next candidates). Replacing vanilla structure files broke the ancient city.
- **Porting the ancient city**: a data-driven jigsaw port was done Preview-only until `minecraft:feature_pool_element` stabilizes. There is no list pool element and no `block_rot` processor. The bedrock name is `minecraft:sculk_patch_feature_ancient_city`. Shrieker hack: delete `minecraft:target` in the air feature filter so that only the target block remains as a marker and a script replaces it.
- **Impossible**: adding custom pieces to vanilla villages, changing structure biome rules, structure pools with custom spawn_overrides, `/locate` ignoring rare structures. Community requests: converting hardcoded vanilla structures to the add-on style (like trial chambers), `use_expansion_hack`, `legacy_single_pool_element` -> `single_pool_element`, and an official way to override villages while keeping vanilla generation rules/biome limits/processors/connections. The jigsaw docs are old.

#### Nether and End

- **Nether**: `heightmap_projection` (`world_surface`) projects onto the Nether ceiling/bedrock. Use `"heightmap_projection": "none"` with `start_height` uniform `{min:{above_bottom:28}, max:{above_bottom:70}}`, `"step":"surface_structures"`, `"terrain_adaptation":"beard_box"`, `max_depth` 4 and `has_biome_tag` biome_filters. It is still awkward (a case where a structure became a soul sand box). Terrain generation is bad, so floating structures are realistic. A feature must put all blocks to replace in the `allow`/replace list. There is other advice to use a negative start_height and `world_surface`. `heightmap_projection` is **conflicting**: there is an answer that says to delete the field and that `"none"` is invalid, which disagrees with the `"none"` setup above. A case where an absolute -20 start_height was calculated from the ceiling was fixed with `{"type":"uniform","min":{"above_bottom":20},"max":{"below_top":100}}`. Padding that hangs on the ceiling blocks generation, and for 48x48 or smaller use a feature rule. Use `dimension_padding` to avoid mountains or water. In the Nether and the End only none works among terrain adaptations.
- **End**: there are no biomes, so jigsaw cannot be generated on the outer islands (worked around with a rare spacing 140/separation 300 or tag-based biome_filters). Bedrock has no midlands/highlands biome tags. A working example gave `the_end` in `biome_filters`, `dimension_padding {top,bottom}` and `terrain_adaptation: beard_thin`. In the End jigsaw sometimes shows up and `beard_box` does not work as expected.

#### Other jigsaw

- **Infinite structure (SCP-3008 style)**: built with a ticking area + command block system. Armor stands on bedrock markers mark expansion points, functions erase duplicates, and each cell generates its neighbors. `/schedule on_area_loaded` and `/tickingarea preload` load chunks in order, and a per-area chunk bitmap can be kept in scripts.
- **Seed trick**: if you fix the jigsaw `start_height`, the random seed uses the input y of the place command and the structure is placed at start_height, so the input y acts as your own RNG seed (values outside the world also work). The structure block seed is used only together with integrity.
- **Crashes**: after 1.21.12x, combining two structure add-ons crashed in some areas and it was narrowed down to one .mcstructure of one pack (MCPE-232661, confirmed by Mojang 2025-12-02). There is also a case where a generation crash after adding many pieces was fixed by deleting pieces that were missing jigsaw blocks.
- **Java conversion**: Java datapack structures cannot be converted directly (the jigsaw format differs). But most Java jigsaw tutorials apply. Convert Java NBT to .mcstructure with https://github.com/JaylyDev/nbt-to-mcstructure (python, put .nbt in `structures` and run `cli/__main.py`).
