Collections and factories are the mechanism by which JSON UI draws **lists whose size is not fixed**. They handle data that is known only when the screen is used, such as the number of server form buttons, the number of chest slots and the number of chat lines.

- **Collection**: the list of items the engine provides. There are form buttons (`form_buttons`), modal form rows (`custom_form`), chest slots (`container_items`) and chat lines (`chat_text_grid`), and each item comes with value bindings such as `#form_button_text` or `#item_id_aux`. Inside a container that has `collection_name`, `collection_index` decides which item to read, and a binding points to which collection to read with `binding_collection_name`.
- **Factory**: a mechanism that **creates controls at runtime** as many as there are items. In the container's `factory` property (or a `"type": "factory"` control) you write what to create (`control_name`, `control_ids`), and how many to create is decided by the engine or by the `#collection_length` binding.
- **Grid**: a container that places the same template control in a lattice. Fix the cell count with `grid_dimensions` or set the count with `#maximum_grid_items`.

## 6.0 The smallest examples

**Example 1. Fixed-index slots** (reading only a collection without a factory, COL-06). If the server always sends the same number of buttons, you can hardcode in JSON which item each cell reads.

```json
"tab_slots": { "type": "stack_panel", "orientation": "horizontal",
  "collection_name": "form_buttons",
  "controls": [
    { "slot0@my.tab_cell": { "collection_index": 0 } },
    { "slot1@my.tab_cell": { "collection_index": 1 } }
  ] }
```

**Example 2. A factory whose count is set by a binding** (the first example of the Bedrock Wiki original below). If you take the number out of the title string `Count:3` and put it into `#collection_length`, 3 controls are created. If it is 0, nothing is created (COL-11).

**Example 3. Placing the engine factory again** (COL-14). If you place one more factory of the same name, a second UI is created from the same data.

```json
"server_form_factory": { "type": "factory",
  "control_ids": { "long_form": "@my.long_form", "custom_form": "@my.custom_form" } }
```

**Factories**

A factory generates UI elements specified in its `control_name` or `control_ids` properties.
- **Invocation:** Many of the vanilla factories are invoked natively by the engine. Alternatively, factories can be invoked manually by overriding the `#collection_length` property.
- **Data Binding:** For the use of `#collection_length`, the factory must reside within a collection-supporting container (e.g., `collection_panel` or `stack_panel`). The value can either be an `int` or a `string[]` based on the implementation of the factory.

**Key properties**

| Property | Type | Short Description |
| --- | :---: | --- |
| name | `string` | The unique identifier for the factory. This is critical for factories natively invoked by the engine, though custom factories can use any arbitrary string. |
| control_name | `string` | Reference to the control to be generated by the factory |
| control_ids | `Object` | An object mapping arbitrary string keys to the references of the controls to be generated. Used when generating multiple distinct controls. Must remain unchanged for natively invoked factories. |
| factory_variables | `string[]` | List of variables that should be passed to the controls generated by the factory |
| max_children_size | `int` | Maximum number of controls to be generated |

**Usage**

**Using `control_name`:**

In this case, `#collection_length` must be overridden with an `int` value. This is the number of elements that will be generated.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_factory": {
    "type": "stack_panel",
    "size": [ "100%cm", "100%c" ],
    "factory": { // Defined in a stack_panel (Supports collection)
      "name": "hud_apple_factory",
      "control_name": "hud.hud_apple" // Reference to hud_apple
    },
    "bindings": [
      {
        "binding_name": "#hud_title_text_string",
        "binding_name_override": "#count"
      },
      {
        "binding_type": "view",
        "source_property_name": "(#count - 'Count:' + 0)", // Gets the int value
        "target_property_name": "#collection_length" // Overriding #collection_length
      }
    ]
  }
}
```

Here, an integer value is sent through the title as `Count:{value}` that indicates the number of elements to generate. The bindings listed above first fetch the title string and store it in `#count`. Then, `#count - 'Count:'` gets the `int` value and `#collection_length` is overridden with this value.
**Note:** `+ 0` sets a default value of 0 if the string is empty.

**Expected result:** For title: `Count:3`

**Using `control_ids`:**

In this case, `#collection_length` must be overridden with an array of strings. The strings are the keys defined in `control_ids`. There's not much freedom with this approach as there is no way to manipulate arrays in JSON UI. Instead, we can pre-define some arrays within the `property_bag` and choose from them. The elements will be generated in the order specified in the array.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "hud_label": {
    "type": "label",
    "text": "Apple!",
    "shadow": true
  },

  "apple_factory": {
    "type": "stack_panel",
    "size": [ "100%cm", "100%c" ],
    "factory": {
      "name": "hud_apple_factory",
      "control_ids": {
        "apple": "hud.hud_apple", // An arbitrary name mapped to the reference of a control
        "label": "hud.hud_label"
      }
    },
    "property_bag": {
      // Some pre-defined arrays
      "#list1": [ "apple", "label" ],
      "#list2": [ "label", "apple" ]
    },
    "bindings": [
      {
        "binding_name": "#hud_title_text_string",
        "binding_name_override": "#choice"
      },
      {
        "binding_type": "view",
        "source_property_name": "('#list' + #choice)", // Constructing key name
        "target_property_name": "#collection_length"
      }
    ]
  }
}
```

Here, we have defined two controls in `control_ids` and two arrangements of these controls as `#list1` and `#list2`. In the bindings, we fetch the title string and store it in `#choice`, which is an integer representing the list to be selected. Then using `('#list' + #choice)`, we construct the name of the list and that list is then overridden to `#collection_length`.

**Expected result:** For title: `1` and `2` respectively

**Factory (Extra):**

You can define factories directly using `"type": "factory"` as well. These factories are always invoked natively by the engine. However, it is possible to define these factories in the ways discussed above we can also modify the control references to generate custom elements instead.

```json
{
  "main_screen_content": { // Vanilla code from server_form.json
    "type": "panel",
    "size": [0, 0],
    "controls": [
      {
        "server_form_factory": { // Name of control here acts as the factory name and thus should remain unchanged
          "type": "factory",
          "control_ids": {
            "long_form": "@server_form.long_form",
            "custom_form": "@server_form.custom_form"
          }
        }
      }
    ]
  }
}
```

</Excerpt>

**Grids**

Grids generate and arrange UI elements in a grid layout. The elements are generated from a template control specified in its `grid_item_template` property. We can either generate a fixed number of elements by defining `grid_dimensions` or a variable number by overriding its `#maximum_grid_items` binding or `maximum_grid_items` property.

**Key properties**


:::danger
Try not to use `vertical` as the value of `grid_rescaling_type`. It may crash your game.
:::

**Usage**

:::info
Grids typically have a default size of `["100%c", "100%c"]`. It is ideal to keep the height dynamic (`100%c`). If a fixed height is applied, generated elements may overlap if the height is too small, or have unintended gaps if the height is too large.
:::

**Using `grid_dimensions`:**

It is recommended not to override the `size` property in this case, as some elements can go outside the grid bounds and mess up the layout.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_grid": {
    "type": "grid",
    "grid_dimensions": [3, 3],
    "grid_item_template": "hud.hud_apple"
  }
}
```

**Expected result:**

**Overriding `#maximum_grid_items`:**

For this to work properly, you have to modify the width of the grid. This is because the number of columns in this case will be `floor( width of grid / width of template control )`. Moreover, we need to set `grid_rescaling_type` to `horizontal`. Then we have to override `#maximum_grid_items` through bindings, or alternatively, define the `maximum_grid_items` property.

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_grid": {
    "type": "grid",
    "size": [160, "100%c"], // floor(160 / 32) = 5; Meaning the grid will have 5 columns
    "grid_item_template": "hud.hud_apple",
    "grid_rescaling_type": "horizontal",
    "bindings": [
      {
        "binding_name": "#hud_title_text_string",
        "binding_name_override": "#count"
      },
      {
        "binding_type": "view",
        "source_property_name": "(#count - 'Count:' + 0)", // Gets the int value
        "target_property_name": "#maximum_grid_items" // Overriding #maximum_grid_items
      }
    ]
  }
}
```

Here, an integer value is sent through the title as `Count:{value}` that indicates the number of elements to generate. The bindings listed above first fetch the title string and store it in `#count`. Then, `#count - 'Count:'` gets the `int` value and `#maximum_grid_items` is overridden with this value.

**Expected result:** For title: `Count:15`

**Grid Position**

There might be situations where you'd want to manually add controls to the grid instead of generating them from a template. With the `grid_position` property you can place your control anywhere on the grid.

**Usage**

Let's say we have a grid with 2 columns and 2 rows and we want to place our controls in this way-


The format `[row, column]` indicates the placement within the grid, where the first integer is the row index and the second integer is the column index. The following integer is the index it takes inside the grid for a defined collection.

**The code:**

```json
{
  "hud_apple": {
    "type": "image",
    "texture": "textures/items/apple",
    "size": [32, 32]
  },

  "apple_grid": {
    "type": "grid",
    "size": ["100%c", "100%c"], // Define it explicitly to avoid layout issues
    "grid_dimensions": [2, 2],
    "controls": [
      { 
        "apple_1@hud.hud_apple": {
          "grid_position": [0, 0]
        }
      },
      {
        "apple_2@hud.hud_apple": {
          "grid_position": [1, 1]
        }
      }
    ]
  }
}
```

**Expected result:**

**Useful Information**

- When used with a collection, Factories and Grids automatically index generated elements.
- Generated elements can access outside bindings via `source_control_name`, but outside elements cannot access bindings from generated elements.
- Invisible elements inside a Grid still occupy physical space, which can leave unintentional gaps in your UI.
- In Grids, animations linked with the `next` property can appear bugged. After the first animation, the duration divides among the grid elements, causing subsequent animations to speed up. (`flip_book` animations are the only exception).

</Excerpt>

The differences between this original and this project's measurements are as follows.

- The wiki uses `(#count - 'Count:' + 0)`. The reason the result becomes a number is EXP-26 (the type of an intermediate result of an expression is decided again by its appearance). To be sure, write `((#count - 'Count:') - 0)`.
- The wiki builds a factory with only `stack_panel` + `factory` without `collection_name`. The same approach worked in measurement (COL-24).
- The wiki says controls inside a factory or grid read outside bindings with `source_control_name` but the outside cannot read the inside (the same conclusion as BND-19).
- The wiki's "bug where animations chained with `next` inside a grid speed up" and the warning that `grid_rescaling_type: vertical` can freeze the game were moved to ANI-18 (`unverified`).
- Grid property summary: `grid_dimensions` (`[column, row]`), `grid_dimension_binding` (the binding name for the cell count, hardcoded names only), `grid_item_template` (a reference to the cell definition), `grid_rescaling_type` (`none`, `horizontal`, `vertical`), `maximum_grid_items` (maximum count, binding `#maximum_grid_items`), `grid_position` (`[row, column]`). The column count is `floor(grid width / template width)`.

The way to read the **list data** the engine provides (form buttons, modal rows, chest slots, chat lines, dialogue buttons) is a collection, and the mechanism that **creates** controls as many as the items of that list is a factory.

## 6.1 Collection addressing

- **[COL-01]** `collection_name` is used on `stack_panel`, `grid` and `collection_panel`. Using it on `panel` or `image` gives an `Unknown property [collection_name]` error. `&#123;measured, vanilla&#125;` (Source: BC-facts, BC-S9, BC-S11, VN grid 66, stack_panel 25, collection_panel store_common.json:750, MJ chapter 9, Appendix A C-01)
- **[COL-02]** `collection_index` is received only at the **instantiation point** (an item inside the parent's `controls`). Written in a top-level definition it is rejected, on an `image` it is rejected anywhere, and on a `label` it is silently ignored. However, the text carrier that bedrock-core actually outputs gives `collection_index` directly to a `label` reference. To be sure, wrap the label in a panel and give the index to the panel reference. The engine reads `collection_index` only on direct children of a parent that has a collection name (COL-44). `&#123;measured, code, conflict&#125;` (Source: BC-facts, NB-07, BC 4.1-(4), Appendix A C-31)
- **[COL-03]** The index is **inherited down the subtree** from the point where it was applied. So the pattern of writing the definition once and giving N references only a different index and offset holds. Bindings that read a collection each specify the collection with `binding_collection_name`. `&#123;measured&#125;` (Source: BC-facts)
- **[COL-04]** A server form button counts a press toward that entry only if **the button itself** has `{ "binding_type": "collection_details", "binding_collection_name": "form_buttons" }`. If only an ancestor gives the index, it can be pressed but the script receives `canceled`, which cannot be told from Esc, and there is no log (when the user closes it, `reason=UserClosed` arrives, but whether the reason for a missing binding can be told apart was not confirmed). Vanilla form buttons have the same structure. `&#123;measured, vanilla&#125;` (Source: BC-S1, BC-facts, VN server_form.json:211-225)
- **[COL-05]** A collection binding with no index host at all reads item **0**. This property was used to hide the vanilla chest label with the slot 0 item. `&#123;measured&#125;` (Source: BC-facts)
- **[COL-06]** You can make **fixed-index slots** without a factory: put children with hardcoded `collection_index` in a stack that has `collection_name`. The script always sends the same number of entries (including empty values) to fix the index. `&#123;working pack, code&#125;` (Source: BA chapter 5 tab 28 slots, BC 4.1-(3))

```json
"tab_slots": { "type": "stack_panel", "orientation": "horizontal",
  "collection_name": "form_buttons",
  "controls": [
    { "slot0@my.tab_cell": { "collection_index": 1 } },
    { "slot1@my.tab_cell": { "collection_index": 2 } } ] }
```

## 6.3 Factories

A factory has two forms.

```json
// (a) A factory control: type is factory. The entry point of vanilla server_form
"server_form_factory": { "type": "factory",
  "control_ids": { "long_form": "@server_form.long_form", "custom_form": "@server_form.custom_form" } },

// (b) The factory property of a container: a stack/panel/collection_panel creates the cells
"long_form_dynamic_buttons_panel": { "type": "stack_panel",
  "factory": { "name": "buttons",
    "control_ids": { "button": "server_form.dynamic_button", "label": "@server_form.dynamic_label",
                     "header": "@server_form.dynamic_header", "divider": "@settings_common.option_group_section_divider" } },
  "collection_name": "form_buttons",
  "bindings": [ { "binding_name": "#form_button_contents", "binding_name_override": "#collection_length" } ] }
```

- **[COL-08]** A factory is either (a) a `"type": "factory"` control (36 uses in vanilla, not in the official enum) or (b) the `"factory": { … }` property of a container. The keys of the `factory` object are `name`, `control_name` (one kind) or `control_ids` (per kind), `max_children_size` and `factory_variables`. `&#123;vanilla&#125;` (Source: VN server_form.json:25 and 126, VN factory key tally)
- **[COL-09]** The keys of `control_ids` are **data kinds** the engine decides, and the values are `"@ns.definition"` (197 uses in vanilla), `"instancename@ns.definition"` (36 uses) and `"ns.definition"` (5 uses, for example server_form.json:128). The action form rows are `button`, `label`, `header` and `divider`, the modal rows are `label`, `toggle`, `slider`, `step_slider`, `dropdown`, `input`, `header`, `divider` and `multiselect`, the HUD ones are `hud_title_text` and `hud_actionbar_text`, and chat's is `chat_item`. `&#123;vanilla&#125;` (Source: VN server_form.json:126 and 283, hud_screen.json:3406, 3417 and 1040)
- **[COL-10]** **`visible` only stops drawing and does not stop creation and layout.** A screen attached under the server form is **fully created and laid out every time any form is opened**, even if hidden with `visible` (measured with 5,546 controls repositioned). A component inside it that validates its state at creation, such as a slider, raises an assert even when hidden. The control's own `binding_condition: "visible"` also does not stop evaluation when an ancestor is hidden. `&#123;measured&#125;` (Source: BC-S8, BW-best)
- **[COL-11]** If you bind `#collection_length`, the factory creates only that many cells. **If 0, nothing is created.** A computed length like `((#mode = 'on') * 1)` becomes a gate that "creates only the one screen needed". `&#123;measured, vanilla&#125;` (Source: BC-S11, VN server_form.json:138 and 300)
- **[COL-12]** A comparison of ways to stop creation. `&#123;measured, vanilla&#125;` (Source: BC-S8, BC-S11, VN)

| Method | When evaluated | Condition material | Cost |
| --- | --- | --- | --- |
| `ignored` | Once at control creation | `$variable` only | Not created |
| Factory `#collection_length` | Runtime, binding | `#binding` expression | Not created if 0 |
| `visible` | Every frame | `#binding` expression | Creation and layout cost stay |

- **[COL-13]** A row type factory creates a cell **for every matching row.** If there are three slider rows, three slider cells are created per socket. Cells that are not their own row are pushed off screen with `#anchored_offset_value_y` (`((not #mine) * 1000)`). `&#123;measured&#125;` (Source: BC-S9)
- **[COL-14]** If you **declare an engine factory of the same name once more at another location**, a second UI is created from the same data. All three packs use this method: `server_form_factory` (BC, BA), `hud_title_text_factory` (BA, AP) and `chat_item_factory` (AP). `&#123;working pack, code&#125;` (Source: BC 4.1-(1), BA chapters 2 and 6, AP 4.1 and 4.5, BW-form, BW-intro)
- **[COL-15]** `factory_variables: ["$a", "$b"]` passes the factory host's variables to the created controls. The engine looks up each name in the scope that declared the factory and passes its value (COL-41). Vanilla uses it 37 times (store, pdp, marketplace_sdl, realms_settings, toast_screen, etc.), but none of this project's sources measured it in game. `&#123;vanilla, code&#125;` (Source: VN store_common.json and others 37 uses, NB-04)
- **[COL-16]** `max_children_size` is the maximum number a factory creates (vanilla HUD chat 50, AP toast 12). A second factory sharing the same data uses up the limit even on invisible items. `&#123;vanilla, working pack, inferred&#125;` (Source: VN hud_screen.json:1041, AP 4.5)
- **[COL-17]** Controls created by an engine factory sometimes receive data **as variables.** The vanilla actionbar label uses `"text": "$actionbar_text"`, and AP reads `$title_text` in a control created by `hud_title_text_factory` and decides with `ignored`. A variable is decided once at creation, so when the value changes the factory recreates the control. `&#123;vanilla, working pack&#125;` (Source: VN hud_screen.json:2158, AP 4.1, Appendix A C-28, BW-intro)
- **[COL-18]** If the cells a factory creates are big, opening the screen is slow. BA had hundreds of controls in one node, so opening took several seconds when all tabs were sent, and it was changed to send only the selected tab's node. Reducing cell size x count comes first. `&#123;working pack&#125;` (Source: BA chapter 4)

## 6.4 Form rows and response numbers

- **[COL-19]** The action form collection (`form_buttons`) in 1.26.50 vanilla receives not only `button` but also `label`, `header` and `divider` rows. The `selection` of the response counts only buttons, so mixing in `label()` shifts the collection index and the `selection` number. When using it as a data channel, send every entry with `button()` and make cells that must not be pressable by removing the button mapping. `&#123;vanilla, code&#125;` (Source: VN server_form.json:126-134, BC 4.1-(3))
- **[COL-20]** The `custom_form` rows of a modal form and `formValues` line up 1:1. A `label()` is also a row and `null` arrives in its place in the response. `&#123;measured&#125;` (Source: BC-S3)
- **[COL-21]** A `multiselect` row was added to the `custom_form` factory in 1.26.50 vanilla, but the public Script API (`@minecraft/server-ui` 2.2.0~2.5.0-beta, both `ModalFormData` and `CustomForm`) has no method that sends this row. A server that sends the form JSON directly can use it (HOST-46). `&#123;vanilla, code, measured&#125;` (Source: VN server_form.json:294, MJ 4.1, MS)

## 6.5 Rules added from the Bedrock Wiki comparison

These are rules added by comparing the wiki (BW) documents with vanilla 1.26.50.4. Those with only wiki sentences are marked `unverified`, and those with in-game screenshots in the wiki are marked `measured` (third-party record).

- **[COL-22]** If you give a factory with `control_ids` a **string array** (the list of keys of that `control_ids`) through `#collection_length`, it creates controls of those kinds in array order. An expression cannot build an array, so put the array in `property_bag` in advance (`"#list1": ["apple", "label"]`) and pick it by assembling the name with `('#list' + #choice)`. A `control_name` factory takes an integer. `&#123;measured&#125;` (Source: BW-dyn, 2 screenshots)
- **[COL-23]** A `'#name'` string made by an expression is read as the value of that name in the same control's `property_bag` (dictionary lookup). COL-22 and bedrock-core's screen routing (HOST-06 `('#route_' + #title_text)`) are the same mechanism. Principle: if the result of a parenthesized group is a `#name` string, it is replaced by the value in that control's bag (EXP-35). `&#123;measured, code&#125;` (Source: BW-dyn screenshot, BC 4.1-(2), CN-run)
- **[COL-24]** A factory driven directly by `#collection_length` goes in the `factory` property of a container that supports collections (`stack_panel`, `collection_panel`). The wiki example worked with only `stack_panel` + `factory` without `collection_name`. `&#123;measured&#125;` (Source: BW-dyn screenshot)
- **[COL-25]** For a `"type": "factory"` control, **the control name is the factory name** (`server_form_factory`). Make a second factory with `"type": "panel"` + `"factory": { "name": "server_form_factory", … }` and name the control so it does not collide with the original or siblings. The engine does not read a factory name separately from a `type: factory` control, and other types read `name` of the `factory` object (COL-42). `&#123;code, vanilla&#125;` (Source: NB-05, VN server_form.json, BW-form (beware of name collision))
- **[COL-26]** Factories and grids used with collections automatically attach an index to the controls they create. `&#123;unverified&#125;` (Source: BW-dyn)

## 6.6 Rules added from the Cinnabar engine reconstruction

Cinnabar (`CN`) is Rust code that reconstructs the JSON UI parser of the 26.30 native client. The level is `code`, and `CN-run` is the result of this project running that evaluator directly. If it differs from game measurement, follow measurement (Appendix A C-41~C-47).

- **[COL-27]** `#collection_length` accepts an integer, a boolean (1/0) and an array of role names. A literal numeric length creates that many only in a `control_name` template factory. A role name not in the factory creates nothing. The engine also gives a role name array (`["tag", …]`) as a length value on the store screen (COL-46). `&#123;code&#125;` (Source: NB-14 (role name array), CN tests N12 and B41 (the rest))
- **[COL-28]** If `control_name` exists, `control_ids` is not read. Do not put both together. `max_children_size: 0` is unlimited. `&#123;code&#125;` (Source: NB-06 (`control_name` first), CN (`max_children_size: 0`))
- **[COL-29]** Cells of a `control_name` template and of `grid_item_template` see the `$variables` of where the factory was declared. Controls made by `control_ids` see only their own variables and those passed with `factory_variables`. The engine builds the `control_name` prototype in the declaring scope when resolving the factory (COL-45). `&#123;code&#125;` (Source: NB-13 (`control_name` prototype), CN, COL-15 reinforcement)
- **[COL-30]** The engine writes the grid cell count as `#grid_number_size`, the factory creation count as `#collection_number_size` and the collection size as `#collection_total_items` into the bag. A view binding can read them for use such as an "empty" indicator. `&#123;code&#125;` (Source: CN tests B55 and B41)

## 6.7 Rules added from the research server measurement

These were measured on Windows 1.26.52 while building the research server (`DF`). They came from a structure that draws several screens with one server form.

- **[COL-34]** The client held the action form's `#form_button_length` at the button count of the **largest form** seen so far (debug label 93, still 93 after reconnecting, unchanged with `always_when_visible` too). If you set the grid size from this value, empty cells continue in a smaller form. Send the cell count separately through a data channel such as the body (EXP-45). `&#123;measured&#125;` (Source: DF)
- **[COL-35]** A wrapping grid gives cells to hidden buttons too. Send marker buttons such as tab, back and page **after** the cell buttons (if placed before, the cells start shifted), and put only the number of cell buttons in the grid size (putting more made one extra empty row and the window scrolled a few pixels). `&#123;measured&#125;` (Source: DF)
- **[COL-36]** When the factory and grid lengths were computed with expressions of `#form_button_contents` and `#form_button_length` (`* 1`, `* (marker match)`), the factory did not create buttons and the grid became the expression itself. Move engine names as they are with `binding_name_override`. `&#123;measured&#125;` (Source: DF)
- **[COL-37]** With a stack that walks whole buttons per row (a 48-cell grid + a material row), the screen took 4~5 seconds to open, and switching to a fixed layout that reads only one button per cell with `collection_index` (COL-06) made it about 1 second. Also put only one button per cell (having both a pressable one and a non-pressable one doubles the controls). `&#123;measured&#125;` (Source: DF)
- **[COL-38]** `collection_index` took effect only on a direct child of a `stack_panel` that has `collection_name`. When that place was a `panel`, `Unknown property [collection_index]` and `[collection_name]` were printed in the content log and it was empty (the same conclusion as COL-01 and COL-02, and the same for the chest screen `container_items`). `&#123;measured&#125;` (Source: DF)
- **[COL-39]** Dictionary lookup routing (HOST-06) worked: with `"property_bag": { "#df_layout_1": [ "on" ], "#df_layout_0": [] }` on a `stack_panel`, `"factory": { "control_ids": { "on": "…" } }`, and `#collection_length` bound from `(('#df_layout_' + (condition * 1)))`, the layout was created only when the condition matched. There was no freeze or exit (a different result from DBG-19). `&#123;measured&#125;` (Source: DF)
- **[COL-40]** However, **inside** a layout created by our factory, action form data reached only the cells of a grid (`grid` + `collection_name`). Fixed `collection_index` cells were empty, and an inner factory that creates buttons from `#form_button_contents` created nothing. `collection_panel` (with or without `collection_name`), `stack_panel`, `control_name` and `control_ids` were all the same, and giving the cell bindings `always` (BND-07) changed nothing. `panel` + `factory` created nothing. So a gate can be used only when the layout reads buttons only as a grid. A router at the very top of the screen gave a different result (COL-47, C-65). `&#123;measured&#125;` (Source: DF)

## 6.8 Rules added from the engine behavior analysis

These were read by analyzing the native library of the Android 1.26.52.3 client (`NB`). The level is `code`.

- **[COL-41]** `factory_variables` is read **only when it is an array** and silently ignored if not. If an item is not a string, it leaves the error `factory_variables should all be strings of json variables created higher up the tree.`. Each name is looked up in the scope of the control that declared the factory, and its value is stored in the factory and received by the created controls (the same as the inference in COL-15). `&#123;code&#125;` (Source: NB-04)
- **[COL-42]** If it is `"type": "factory"` and that control directly has `control_name` or `control_ids`, the factory name is not read separately (the control name is the factory name, COL-25). Other types create a factory only when a `"factory": { … }` object exists, and if its `name` is empty it leaves `The factory name should not be empty!`. `&#123;code&#125;` (Source: NB-05)
- **[COL-43]** A factory reads `control_name` first and reads `control_ids` only when it is empty (COL-28). `insert_location` inserts at the front only when the value is exactly `"front"` and anything else is back (default `back`). `&#123;code&#125;` (Source: NB-06)
- **[COL-44]** When creating a control, **if the parent has a collection component with a collection name**, that control automatically becomes a collection item. `collection_index` is read only then (default -1) and fixes the index. So `collection_index` is meaningful only on a direct child of a collection parent (the same conclusion as COL-02 and COL-38). For a control that is a direct child but must not become an item (a decorative panel, etc.), give `"ignoreCollectionItem": true`. `&#123;code&#125;` (Source: NB-07)
- **[COL-45]** Factory resolution path: if it is `"type": "factory"` and directly has `control_name` or `control_ids`, it resolves without a name, and otherwise, regardless of type, it resolves only when `factory` is **an object** and reads `name` (you may also write a `factory` object on a `type: factory`). Only one factory attaches to one control. `control_name` builds the prototype right away with the declaring control's variable scope at resolution, and `control_ids` stores only the kind and definition string (the COL-29 difference). `max_children_size` is 0 if omitted. `&#123;code&#125;` (Source: NB-13)
- **[COL-46]** `tags_factory_first_hidden_child_index`, `languages_factory_first_hidden_child_index` and `<prefix>_first_hidden_child_index`, which vanilla does not have, are **exclusive to the store detail screen description component.** This integer in the property bag decides from which tag or language to hide or push to the next row, and an array repeating `"tag"` or `"language"` that many times is given as the length binding value. It is not a general factory feature, so it is not used in server form or HUD factories. Who uses this value was not checked. `&#123;code&#125;` (Source: NB-14)

## 6.11 Rules added from the server form test add-on measurement
