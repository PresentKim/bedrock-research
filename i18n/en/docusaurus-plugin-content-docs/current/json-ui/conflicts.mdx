## Concept: how to read the verdict table

JSON UI material has many contradictory claims (wiki typos, game version changes, experiment errors by authors). This table gives each contradiction an ID (C-nn) and writes the two claims, the basis of the verdict, the verdict and the related rules in one line. Verdict priority puts game measurement and the vanilla exhaustive search first, and if the reconstructed engine (`CN`) differs from measurement, measurement is followed. In the **Verdict** column, `resolved` means one side is confirmed right, `partly resolved` means the scope is split and both are right, and `open` means measurement is needed. Example: C-06 was resolved as "do not use" when a community example using the `%` operator ran into the measured `Invalid expression` assert. A.3 below is a list of 28 experiments whose verdicts can be settled if confirmed in game.



All the places where sources disagree are collected. The bases of the verdicts are the exhaustive vanilla 1.26.50.4 search (`VN`), the original text of the bedrock-core measurements (`BC-S*`, `BC-facts`), the recheck of the BedrockAdvancements original (`BA-original`), the Bedrock Wiki documents and their edit history (`BW`), and the Cinnabar code that reconstructs the native client and its run results (`CN`, `CN-run`). If `CN` differs from measurement, follow measurement.
**Verdict** column: `resolved` = one side confirmed right, `partly resolved` = scope split and both right, `open` = measurement needed.

## A.3 Items that need measurement
