The vanilla baseline is bedrock-samples v1.26.50.4 (46ba6ea). There are 389 rules in total.

## Evidence levels

| Level | Meaning |
| --- | --- |
| measured | in-game measurement recorded by a source |
| vanilla | used in vanilla resource pack ui/ |
| working pack | used by a released, working pack |
| code | confirmed by reading source/compiled output |
| inferred | inferred |
| unverified | claimed without evidence |
| conflict | sources disagree; see Appendix A |

## Chapter 1. Files and definitions

| ID | Rule | Level | Source |
| --- | --- | --- | --- |
| FILE-01 | A new UI file loads only if its path is registered in the `ui_defs` array of `ui/_ui_defs.json`. Files at the same path as vanilla (`ui/hud_screen.json` and so on) are already registered by vanilla, so they are not registered again. | vanilla, working pack | VN _ui_defs.json, AP-samples _ui_defs.json, BA, BW-intro |
| FILE-02 | A registered file loads even if its extension is not `.json` (for example `ui/adv/_screen.r4ui`). | working pack | AP 4.9, BW-intro |
| FILE-03 | A UI file is JSON that allows `//` and `/* */` comments. | vanilla, working pack | VN header comments of all files, AP-samples |
| FILE-04 | `ui/_global_variables.json` loads automatically without registration, and the `$variable`s defined in it can be used in all files. Vanilla also does not register this file in `_ui_defs.json`. | vanilla, working pack | VN _ui_defs.json and _global_variables.json, AP, MJ ch. 5, BW-intro |
| FILE-05 | A new file has one `"namespace": "name"`. A merge file at the same path as vanilla works with the vanilla namespace even if it omits the namespace. A checking tool that flags this as an error is giving a false positive. | working pack, inferred | AP-samples hud_screen.json, MJ ch. 5 |
| FILE-06 | `"name@namespace.base": { ... }` inherits `base` to make a new definition and overrides properties. A definition in the same file can also be referenced as `@base` without a namespace. | vanilla | VN throughout |
| FILE-07 | A definition in another file is referenced as `namespace.name`. The location of a definition is decided by the **file** that owns it, so even with the same namespace, the same name in a different file is treated as a different definition. | measured | BC-facts |
| FILE-08 | An entry `{ "childname@ns.definition": { ...properties to override... } }` in a control array is the **instantiation point**. Some properties, such as `collection_index`, are accepted only at the instantiation point (chapter 6). | vanilla, measured | VN, BC-facts |
| FILE-09 | `$name` is a variable. Put it in a definition as `"$x": value` or pass it at the reference point. `"$x\|default": value` is a default used only when the value was not passed from above (the reference point). | vanilla | VN `\|default` 3,419 times |
| FILE-10 | Variable substitution in an ordinary property happens **only when the whole value is a variable**. `"text": "$title"` works, but `"text": "Title: $title"` prints the `$` as is. If a combination is needed, use a variable expression (FILE-11). | measured | BC-facts |
| FILE-11 | A variable value can be a parenthesized expression. Vanilla uses this to assemble binding names, texture paths, and control names. Example: `"$toggle_state_binding_name": "('#' + $dropdown_name)"`. | vanilla, working pack | VN ui_common.json:1126, AP 4.3 and 4.9 |
| FILE-12 | Some variables are supplied in advance by the engine. Examples: `$education_edition`, `$is_ps4`, `$pre_release` (platform and build), `$container_title` on chest screens, and `$actionbar_text` and `$title_fade_in_time` on controls created by HUD factories. | vanilla, measured | VN top values used by ignored, VN hud_screen.json:2158 and 2170, BC-facts |
| FILE-13 | Each entry of the `variables` array applies that entry's variables when `"requires": "<$variable expression>"` is true. Instead of an array it can also be written as a **single object**. | vanilla, working pack | VN 274 arrays and 4 objects, e.g. realms_settings_screen.json:2557, AP 4.6, BW-doc |
| FILE-14 | A control array can also be passed as a variable: `"controls": "$target_control"`. It is a way to make a "child slot" in a template. | vanilla, working pack | VN 14 times, e.g. persona_cast_character_screen.json:14, AP 4.2, BW-intro |
| FILE-15 | `"child@$variable"` can mount the definition the variable points to. Vanilla also uses it 413 times with variables passed at the reference point (for example `content@$button_content`). However, in one configuration of the bedrock-core chest router (referencing a host that declares `$gate\|default` twice with different `$gate`), there is a measurement where nothing was drawn. If mounting fails, write the definition name directly. | vanilla, working pack, conflict | VN 413 times, AP 4.8, BC-facts, Appendix A C-03, BW-intro |
| FILE-16 | If `"ignored": "<$variable expression>"` is true, that control is **not created at all** (no binding or layout cost either). Use only `$variable`s in the expression, and `#binding`s cannot be used. `ignored` is evaluated in the outer (parent) scope, not in the control's own `$` declarations (FILE-34). | vanilla, measured, code | VN 958 times, BC-S8, BW-best, NB-10 |
| FILE-17 | `ignored` is evaluated **once, at the time the control is created**. So splitting creation by runtime data needs a path for the data to enter as a variable. A control created by the HUD title factory receives the title string as `$title_text`, so it can be filtered with `ignored`. Ordinary server form screens have no such path, so factory length is used for per-unit branching (chapter 6). A variable the factory supplies enters the outer scope of the created control, so the top-level `ignored` of that control can read it (FILE-34). | working pack, measured, code, inferred | AP 4.1, BC-S8 and S11, Appendix A C-17, CN |
| FILE-18 | `ignored` can also be attached to an **array element**, such as one entry of `button_mappings`. | vanilla, working pack | VN gameplay_common.json:272, AP 4.3 |
| FILE-19 | In the variable expression of `ignored`/`requires`, `$v > 'a'` was used to tell whether it is a string and `$v > 0` whether it is a number. `ignored` cannot see its own `$` declarations or values received at the reference point (FILE-34), so attach it to a **child** of the control that receives the variable. The example below is the form of the AP original. | working pack, code | AP 4.7, CN, AP-samples _screen.r4ui:321 |
| FILE-20 | Using a **path key** like `"parent/child/grandchild": { ... }` in a file at the same path as vanilla overrides only the properties of a deep vanilla control. Vanilla itself does not use this syntax (0 times). | working pack | BA ch. 2 `main_screen_content/server_form_factory`, AP 4.9 `recipe_unlocked_popup/input_panel/label_panel/horizontal_padding_1`, BW-intro, BW-best |
| FILE-21 | Writing a definition with the same name as vanilla in a file at the same path as vanilla **merges per property** (only the properties written change). Example: specifying only the two properties `force_render_below` and `screen_draws_last` in `in_bed_screen`. When several packs use the same property, the later one in pack order wins. | working pack, inferred | AP-samples in_bed_screen.json and toast_screen.json, BC 6.3-9, BW-best |
| FILE-22 | Redeclaring a vanilla definition in a file with a different name is ignored. A redeclaration is valid only in a file at a path vanilla owns. | measured | BC-facts |
| FILE-23 | `property_bag` holds initial values of `#property`s. It is used for defaults before a binding has written a value, renderer input (`#item_id_aux`), routing dictionaries (chapter 10), and so on. | vanilla, working pack | VN 240 times, AP 4.7, BC 4.1 |
| FILE-24 | `size`, `offset`, and `alpha` values put in `property_bag` are not applied. Only bindings can change these three. | measured | BC-S12 |
| FILE-25 | A path in `_ui_defs.json` is the full path from the resource pack root to the extension. The wiki says folders outside `ui/` (`my_ui/main_menu.json`) also work. Vanilla and this project's working packs all use only paths under `ui/`, so check before using anything outside `ui/`. | unverified | BW-intro |
| FILE-26 | A prefix can reportedly be attached to a namespace (`"namespace": "wiki:main"` -> `"x@wiki:main.element"`). It is for reducing the chance of colliding with vanilla namespaces. There is no usage in vanilla or this project's sources. | unverified | BW-best |
| FILE-27 | If the child that a path key (`"parent/child"`) points to does not exist, a resource pack error is left in the Content Log but the rest of the UI works normally. A path key is the contact point that breaks first when vanilla is reworked, so if the definition itself can be overridden, use that instead. | unverified, inferred | BW-best |
| FILE-28 | When using an engine-supplied variable (`$actionbar_text` and so on) in an expression, receive it once into your own variable (`"$atext": "$actionbar_text"`, `"visible": "(not ($atext = 'x'))"`). The wiki says engine variables cannot be compared directly, and the AP declaration `"$title_text\|default": ""` seems to have the same effect. | unverified, inferred | BW-intro, AP 4.1 |
| FILE-29 | Among the engine-set global platform variables, those that vanilla 1.26.50 UI actually references are 34 including: `$pocket_edition`, `$win10_edition`, `$osx_edition`, `$console_edition`, `$education_edition`, `$is_console`, `$is_desktop`, `$is_ios`, `$is_ps4`, `$xbox_one`, `$touch`, `$pocket_screen`, `$desktop_screen`, `$is_pregame` (screens outside the game), `$is_publish`, `$pre_release`, `$trial`, `$store_disabled`, `$is_holographic`, `$apple_os`, `$google_os`, `$microsoft_os`, `$nx_os`. The other 21 of the wiki's list of 55 (`$game_pad`, `$mouse`, `$fire_tv`, `$gear_vr`, and so on) do not appear in vanilla UI files, so it is unknown whether they are still supplied. | vanilla | BW-doc Global Variables, VN full search |
| FILE-30 | UI files are read with jsoncpp rules. Comments and leading zeros are accepted, but **trailing commas and unquoted keys are errors**. On an error only the definitions read before it are loaded and the rest silently drop out. If the first file at the same path fails, overwrites from later packs are not accepted either. | code | CN |
| FILE-31 | Paths in `_ui_defs.json` are read once each in sorted order. When several files redefine the same definition, the last one in path-name order wins. | code | CN |
| FILE-32 | If a key without `@` has a dot, the part before the dot is read as the namespace (`"spacer_9.5"` -> namespace `spacer_9`, name `5`). Do not use dots in control names. `"@.name"` is the namespace of the same file. | code | CN, CN regression test Lifeboat |
| FILE-33 | `$variable` lookup finds a fixed value first. If a `"$x": value` exists anywhere outside, it beats an inner `"$x\|default"`, and the nearest `\|default` is used only when there is no fixed value. null means unset. | code | CN, CN-run |
| FILE-34 | **`ignored` does not look at that control's own `$` declarations.** Neither the `$x\|default` inside the definition nor the `"$x": true` passed at the reference point reaches its own `ignored`, and it reads only the value in the parent (outer) scope. Pass the gate variable to the parent and attach `ignored` to its child (vanilla `hover_slot` of `focus_border` and the child of AP `category_tab_icon` are this form). The engine evaluates `ignored` before that control's `variables` (FILE-43). | code, vanilla | NB-10, CN and CN-run (`$x\|default` and the reference point value), VN 2 of 146 reference points pass the variable, AP-samples |
| FILE-35 | If the result of `ignored` is a boolean it is used as is, an integer means not created when nonzero, and a string means created. An unset `$variable` is null inside an expression, but as a whole value like `"ignored": "$x"` it remains as the text `$x` and the control is created. | code | CN |
| FILE-36 | A child key can also be a variable: in `{ "$slot": { ...properties to override... } }`, if `$slot` is `"name@ns.definition"`, it is built with that name and definition. Only the instance name can also be a variable, as in `"$name_var@ns.definition"`. | vanilla, code | VN 83 times, e.g. ui_template_tabs.json `base_tab`, CN |
| FILE-37 | In inheritance, a property the derived definition writes replaces the base's **even when it is an object, as a whole**. In contrast, a redeclaration in a file at the same path (FILE-21) merges object values per member. To change only part of a `property_bag`, redeclare; to change all of it, inherit. | code | CN |
| FILE-38 | A `"property": null` in a top-level definition erases the base value, but a `null` in an inline reference inside a control array leaves the base value as is. | code | CN |
| FILE-43 | The engine evaluates **`ignored` first** for each control, and if true it skips the rest of the processing for that control, including applying `variables`. So a value decided by its own `variables` (including conditional variables) does not reach its own `ignored` (FILE-34). Putting a real number, array, or object in `ignored` gives the error `An invalid value was provided for "ignored" field.` `variables` accepts one object or an array of objects, and entries in the array that are not objects are skipped. | code | NB-10 |

## Chapter 2. Modifying vanilla screens

| ID | Rule | Level | Source |
| --- | --- | --- | --- |
| MOD-01 | `modifications` is written with `array_name`, `operation`, `value` (the array of entries to insert), and `where` (the condition that finds the entry to delete). The `operation`s confirmed in this project's sources are `insert_back`, `insert_front`, and `remove`. Vanilla itself never uses `modifications` (a pack-only feature). The engine's operation name table has 11 entries (MOD-23), and the game behavior of the other 8 is not confirmed in this project's sources (MOD-14). | working pack, code, vanilla | AP-samples hud_screen.json, BA ch. 2, BC 4.1, VN 0 times, NB-01 |
| MOD-02 | `modifications` is interpreted **per file path**. Only what is written in a copy at the same path as a vanilla file applies to the vanilla definition, and those from several packs stack in pack order. If written in a file at another path, the pack's own namespace definition is read as a new definition and replaces the original (`Type not specified`, `Unknown property [modifications]`), and the vanilla definition is silently ignored (FILE-22). The Cinnabar reconstruction merges by namespace and name only, without this distinction, but the measurement is followed (Appendix A C-46). | measured | BC-facts, Appendix A C-46 |
| MOD-03 | The arrays `modifications` reached in game were `controls` and `bindings`, and specifying `variables` was ignored. The engine does not filter `array_name` against a fixed list (MOD-25), so other arrays such as `button_mappings` are also interpreted, but the effect was not measured (Appendix A C-64). The engine does read the `target_control` key (MOD-24). | measured, code, conflict | BC-facts, NB-02, NB-03, Appendix A C-10, Appendix A C-64 |
| MOD-04 | Inserting into an **array the target only inherits and does not declare directly** creates a new array and hides the inherited content (the vanilla content disappears entirely). So insert into a definition that declares the array directly. Inserting into a definition that originally has no inherited array (for example `bindings` of `hud_title_text`, which has no bindings) is fine. | measured, working pack | BC-facts, AP-samples hud_screen.json |
| MOD-05 | If you `remove` an **inherited child control** in a derived definition, the whole modification of that file is not applied, with no log. In contrast, specifying a **binding entry** the definition itself holds with `where` and `remove`ing it works. Settings and inventory screens also have required toggles that must not be removed (MOD-16). The Cinnabar reconstruction leaves only a diagnostic and applies the rest, but the measurement is followed (Appendix A C-47). | measured, working pack | BC-facts, AP 4.4, BW-doc, Appendix A C-47 |
| MOD-06 | Do not delete vanilla controls; **hide them with a binding.** Add the hiding condition as a `#visible` view binding, or cover it with the visibility of a wrapping panel. Required toggles on settings and inventory screens cause an assert in development builds if removed, so keep them even if hidden (MOD-16). | measured, working pack | BC 6.3-7, BA ch. 2, AP 4.4, BW-doc |
| MOD-07 | To AND the vanilla `#visible` binding with your own condition, `remove` the original binding (specified with `where`) and then `insert_front` to read the original value and your value again and combine them. | working pack | AP 4.4, AP-samples chat_screen.json |
| MOD-08 | If the definition originally has no `#visible` binding, you can hide it just by adding a view binding with `insert_back` (the way a title prefix check is attached to vanilla `long_form` and `custom_form`). | code | BC 4.1-(1), BW-form, BW-intro |
| MOD-09 | Do not edit the vanilla definition directly; **wrap it.** `"wrapper": { "controls": [ { "long_form@server_form.long_form": {} } ] }` refers to the final merged result even if another UI pack replaces `long_form` entirely, so the visibility condition put on the wrapper survives. BA fixed the problem of "screens mixing together when used with a UI pack" with this structure in 2.0.2, regardless of pack order. | working pack | BA ch. 2 |
| MOD-10 | When adding a feature to a vanilla template, add it as a **slot that defaults to off**. Example: adding `"$show_hover_content\|default": false` and a child wrapped in `ignored` to `common_buttons.focus_border` affects only buttons that turn that variable on. | working pack | AP 4.8 |
| MOD-11 | To replace the content of a screen wholesale, redeclare the screen definition in a file at the same path and change `$screen_content`. Vanilla also builds screens this way, as in `shulker_box_screen@chest.small_chest_screen` and `barrel_screen@chest.small_chest_screen`. | vanilla, measured | VN chest_screen.json:240 and 258, BC 4.3-(2), BC-facts |
| MOD-12 | If you redeclare a screen definition, only one side remains against other packs that redeclare the same screen. Vanilla features such as the ordinary NPC dialog also receive the properties you redeclared (`render_game_behind` and so on). Use it only when necessary, and wrap the vanilla content so the original function keeps working. | working pack, inferred | AP 4.2 |
| MOD-13 | When several add-ons must attach to the same vanilla screen, use **only `modifications` that define nothing**. Writing a definition (including property overrides) in a vanilla file competes in overwriting with the same definition in other packs. | measured, inferred | BC 6.3-9, BC-facts, BW-best |
| MOD-14 | The wiki documents 11 `operation`s: `insert_back`, `insert_front`, `insert_after`, `insert_before`, `move_back`, `move_front`, `move_after`, `move_before`, `swap`, `replace`, `remove`. The reference entry is found with `"control_name": "name"` in `controls` and `"where": { "binding_name": "#x" }` in `bindings`, and `move_after`, `move_before`, and `swap`, which need a second reference, use `"target": { ... }`. `replace` swaps the entry found with `where` for `value`. Only `insert_back`, `insert_front`, and `remove` have confirmed behavior in this project's sources, so check the rest on a test screen before use (DBG-04). The engine's operation name table is also exactly these 11 (MOD-23), and the second reference reads `target_control` first and `target` if absent (MOD-24). The names and keys are confirmed in the engine, but the game behavior of each operation has not been measured yet. | unverified, code | NB-01, NB-02, Appendix A C-39 |
| MOD-15 | Gather the points that attach to a vanilla screen (entry points) into **one place**. If you `insert` into several child controls separately, renaming just one of them breaks part of it and the places to debug multiply. Put your controls inside a wrapper panel inserted at a single entry point. | inferred | BW-best, BW-hud |
| MOD-16 | Settings and inventory screens have toggles the engine assumes exist (the accessibility tab in settings, the construction, equipment, items, and nature tabs in the inventory, and so on). Replacing a screen wholesale while dropping these toggles causes an assert in development builds. Keep them even if hidden (MOD-06). | unverified | BW-doc "HardCoded Toggles" |
| MOD-17 | `modifications` is applied **after** ordinary property merging of the same entry finishes. Within one `modifications`, a later operation can select only original elements, so an element inserted earlier cannot be moved or deleted again in the same list. | code | CN |
| MOD-18 | If `where` is an object, it selects the first element where **even one member is equal** (they need not all be equal). `where: {}` selects nothing, and with no condition the first element is selected. Specify a binding to delete with a unique member (`binding_name`). | code | CN |
| MOD-19 | If a same-path redeclaration writes a **`@base` different from the existing one**, the existing definition (type, factory, bindings) is discarded and it becomes a new definition. When changing only properties of a vanilla definition, do not write `@`. | code | CN |
| MOD-23 | The engine's `operation` name table is exactly the 11 of MOD-14 (numbers 1~11). The names must match exactly and there are no other operations. The game behavior of each operation still needs measurement (MOD-14). | code | NB-01 |
| MOD-24 | The second reference of an operation entry reads **`target_control` (a string) first** and reads `target` only when it is absent. The entry keys the engine reads are `array_name`, `control_name`, `operation`, `where`, `target_control`, `target`, and `value`. The statement in MOD-03 that "`target_control` has no basis" was wrong at the interpretation stage. | code | NB-02 |
| MOD-25 | `array_name` is not compared against a fixed list; the engine finds the **member with the same name** in the definition and uses it as the target if it is an array. If `array_name` is empty and `control_name` is a string it is filled with `"controls"`, so control operations may omit `array_name`. So at the interpretation stage arrays other than `controls` and `bindings` can also be targets, but this disagrees with the measurement that `variables` was ignored (MOD-03), so the effect is unconfirmed. | code, conflict | NB-03, Appendix A C-64 |

## Chapter 3. Controls and layout

| ID | Rule | Level | Source |
| --- | --- | --- | --- |
| LAY-01 | The list of valid types is judged by vanilla usage and not by the official enum. The official enum lacks types vanilla uses, such as `factory`, `collection_panel`, `tooltip_trigger`, and `scroll_track`. `scrollbar_track` in the wiki type table is a typo (vanilla uses `scroll_track`, Appendix A C-34), and the legacy types `tab`, `grid_item`, and `scrollbar` never appear in vanilla. `carousel_label`, which the wiki classifies as legacy, remains once in vanilla. | vanilla | VN, BC-facts official schema section, BW-doc |
| LAY-02 | `scroll_box` is not a type but a **control name** in `ui_common.json`. Do not assemble scrolling by hand; reuse the `common.scrolling_panel` template with variables such as `$scrolling_content`. | vanilla, working pack | VN server_form.json `scrolling_panel@common.scrolling_panel`, BA ch. 5, AP, MJ 4.2-2 |
| LAY-03 | Use the size keywords in the table above. The meaning of `%x`/`%y` as "relative to the other axis" is judged from a vanilla comment (`25%x * 56.25%`) and usage. The meaning of `"default"` differs per type, appearing as 100% for panels and text size for labels (Appendix A C-36). In the Cinnabar reconstruction an omitted size is `100%c` on the main axis of a stack panel, the texture ratio for a ratio image, and the parent size otherwise (LAY-38). In size expressions, write `%c` and similar after the `%` (LAY-36). | vanilla, code, inferred | VN store_search_screen.json:64 comment, VN full search, BW-doc, CN |
| LAY-04 | **A stack panel gives no space to hidden (`#visible` false) children.** Collapsing a conditional row pulls what is below up, and turning power-of-two-size spacers on and off makes their sum the coordinate (chapter 11 recipe 6). | working pack, measured | BA ch. 4, BC-S12 |
| LAY-05 | The position (`offset`) of a static control cannot be bound. To change the position, bind the **size of a spacer placed before it** so the stack pushes the next child. The Cinnabar reconstruction accepts an `[x, y]` binding on `#offset`, but the measurement is followed (Appendix A C-44). | measured, working pack | BC-S12, BA ch. 4, Appendix A C-44 |
| LAY-06 | Build responsiveness with `max_size` and `min_size`. Example: with `"size": [314, "100% - 64px"]` and `"max_size": [314, 236]`, the window height shrinks on small screens. | working pack, vanilla | BA ch. 5, VN max_size 204 times |
| LAY-07 | If a background is put as `"100%sm"` inside a `"100%cm"` box, then when a row inside hides, the box and background shrink together and what is below follows up. | measured | BC-S12 |
| LAY-08 | If a label and a `"100%sm"` button are put in a `"100%cm"` panel, the button hitbox fits the character size exactly in every language. Using `"100%c"` in the same place makes the button drop below the label. | measured | BC-S10 |
| LAY-09 | When putting an icon-only button in a row whose height is decided by its children, give an explicit square size. A percentage height does not decide the row height. | measured | BC-rules |
| LAY-10 | A size binding writes values into `#size_binding_x` and `#size_binding_y`. The value is a **multiplier**, not pixels. There are two interpretations of what it multiplies: the declared size (the interpretation of S12) and the parent size (the Cinnabar reconstruction: a value v becomes `v×100%`, and `#size_binding_x_absolute` and `_y_absolute` are pixels). The S12 observation that putting it inside a `[1, 1]` size frame makes the value equal to pixels matches both interpretations, and Appendix A C-14 leans toward the parent size. Keep the declaration as `["100%", "100%"]`. The earlier record that an out-of-range value draws nothing was likely due to a `[0, 0]` declaration. The only size binding in vanilla (`resizing_xp_bar_with_hotbar`) is used with `use_anchored_offset: true`, and the wiki also says this property is needed (CN does not require it). Until it is reconciled with the S12 record that it works on a static control without it, using the two together is safer (Appendix A C-37, LAY-14 caution). | measured, code, conflict | BC-S6, BC-S12, Appendix A C-14, BW-doc, VN hud_screen.json:319, CN |
| LAY-11 | A size binding must bind **both axes**. Binding only one axis makes the other 0 and looks as if the binding did not work. In the Cinnabar reconstruction an unbound axis keeps its declared value, so if the declaration is `[0, 0]` that axis stays at 0, which is the same phenomenon (Appendix A C-14). | measured, code | BC-S12, CN |
| LAY-12 | What can be bound and where depends on where the control was created. Whether a size binding needs `use_anchored_offset` is unresolved (Appendix A C-37). | measured | BC-S12, BW-doc |
| LAY-13 | A bound `alpha` applies only 0 and 1. If you need translucency, make copies with different literal alphas and show only one. The Cinnabar reconstruction accepts the number of a bound `alpha` as is. If the measuring expression used a literal like `0.5`, that value is integer 0 (EXP-27) and it may have looked like "only 0 and 1", so remeasure with `.5` (Appendix A C-45). | measured, conflict | BC-S12, CN, Appendix A C-45 |
| LAY-14 | The combination of a size binding + `use_anchored_offset` + a collection cell crashed the client twice on a chest screen. Avoid this combination. | measured | BC-S6 |
| LAY-15 | Whether the layout is redone when a size binding value changes while the screen is open was not measured. | unverified | BC-S6, BC ch. 8 |
| LAY-16 | `anchor_from` is the reference point of the parent and `anchor_to` is the control's own reference point. The values are 9: `top_left`, `top_middle`, `top_right`, `left_middle`, `center`, `right_middle`, `bottom_left`, `bottom_middle`, `bottom_right`. | vanilla | VN all 9 used, Appendix B |
| LAY-17 | `offset` is a shift relative to the anchor and uses the same units as size (pixels, `%`, expressions). Example: `"offset": [0, "50%-68px"]`. | vanilla | VN hud_screen.json:2146 |

| ALT-11 | Ore UI screens are hashed, minified JS, CSS, and HTML bundles in the install folder `data/gui/dist/hbui/`. When looking for an Ore UI file (`ui://...`), the engine looks at the pack stack before the install folder, but only at trusted packs (`isTrusted`). Trust is decided by the access strategy used to open the pack, and the UUID and Marketplace signature are not looked at. For plain packs (Zip and Directory strategies) only the built-in packs in the install folder are trusted, so ordinary resource packs and plain server packs cannot change layout, behavior, or CSS. The three encrypted pack strategies are always trusted, so `hbui/<file>` in a pack opened with those strategies changes the HTML, JS, and CSS of the in-game Ore UI page (`gameplay.html`: death, bed, inventory, DDUI, trade, and block screens). There are two ways to open it that way. **(1) Without a server: put an empty 0-byte file `content.zipe` at the root of a local resource pack folder** and the engine opens that pack with `DirectoryPackWithEncryptionAccessStrategy`. The engine only checks whether this file exists and reads the plain files in the pack folder as they are, without a key. When importing as a `.mcpack`, `manifest.json` and `content.zipe` must be directly at the top of the zip (one level deeper makes the import silently fail). A pack that attaches the same fake encryption header to `contents.json` does not change. **(2) A pack the server encrypts with any 32-byte content key and sends with the key** (it was measured that the same pack sent as plain text does not change). The JS of this page reads and writes the vanilla DDUI data store, so you can build a screen that draws according to the layout the server sent and returns presses and input (OL `DDUI-server-guide.md`). The changed `gameplay.html` contains the hashed file names of the vanilla bundle, so match it to the install on every game update. The tool that patches the client install folder directly (OUC) applies only to that client and must be reapplied on every update. | code, measured | OUC ch. 2 and 3, OL ch. 3, 6, 7, 8, and 9 |
| ALT-12 | When Ore UI uses game textures, it requests them with `pack://textures/...png` URLs, and this path also resolves to textures of untrusted server packs (measured with a button texture). So a resource pack that changes textures will probably also be reflected in Ore UI item and block icons (the icons themselves were not checked separately). The bundle's own images (`/hbui/assets/`) and fonts (`gui/dist/hbui/fonts`) are read from the install folder and are not changed by packs. | code, measured, inferred | OUC ch. 3 and 4.6, OL ch. 4 and 6 |
| ALT-13 | There is a facet `vanilla.screenTechStack` (`getTechStackForScreen`, `getPreferredTechStackForScreen`, `selectTechStackForScreen`) that chooses per screen whether to use JSON UI or Ore UI. On screens where both implementations coexist, JSON UI modifications are seen only when the JSON UI side is selected, so if a modification does not show, first check which side that screen opened on. | code, inferred | OUC ch. 0 |
| ALT-14 | Ore UI's data channel is a facet and not a binding (`engine.trigger("facet:request", name)`, then `facet:updated:<name>`). That `vanilla.gameplay.*` facets for in-game screens (furnace progress, container items and size, death info, respawn, bed, a coordinates HUD, and so on) exist is a sign that the screen is moving or has moved to Ore UI. Work that reskins such a screen with JSON UI should take the migration risk into account. | code, inferred | OUC ch. 3 |
| ALT-15 | The engine resolves two JSON UI definitions from the pack stack and passes them with the facet `vanilla.resourcePackOverrides` to the in-game Ore UI (all of `gameplay.html`: death, bed, inventory, DDUI, trade, and so on). It takes `$new_ui_button_texture` (background, including nine-slice), `$text_color` (text color), and `$border_color` (border color) from the child controls `default`, `hover`, `pressed`, and `locked` of `common_buttons.light_text_button`, and `texture` from `common_buttons.focus_border`, and applies them to the default, hover/focus, pressed/selected, and disabled states of primary and secondary buttons. So a pack that changed `$light_button_*_text_color` in `_global_variables.json` or `textures/ui/button_borderless_light*.png` also changes the buttons of the Ore UI death screen (measured with a server pack). Other definitions and properties are not passed over, and the out-of-game menu bundle does not use this facet. | code, measured | OL ch. 4 and 6 |
| ALT-16 | DDUI layouts (`ddui/root/*.json` = `minecraft:ui-root`, `ddui/composition` = `minecraft:ui-composition`) are read from resource pack folders, but the engine reads only packs marked as built-in (first-party) (the same flag as the POI's allow check for the `minecraft:` namespace). Putting `ddui/root/custom_form.json` in a user or server pack probably will not be used.
