| FILE-28 | When using engine-provided variables (`$actionbar_text`, etc.) in an expression, receive them once as your own variable (`"$atext": "$actionbar_text"`, `"visible": "(not ($atext = 'x'))"`). In an unnamed chest, a label with `visible: "($container_title = 'container.chest')"` was hidden and the label with `"not"` added was shown (the direct comparison is false), and a label with `($copy = 'container.chest')` received through `"$copy": "$container_title"` was shown (true). In the code `$container_title` and `$actionbar_text` are not strings but objects with the keys `__string`, `__rawtext` and `value`, while `$title_text` and `$subtitle_text` are plain strings. `$actionbar_text` came out the same: after `/title @s actionbar xyz`, a `($actionbar_text = 'xyz')` label was hidden and the `(not ...)` label was shown, and a `($copy = 'xyz')` label received through `"$copy": "$actionbar_text"` was shown. The reason is in the code: the only place that unwraps the object into its `value` string is the property value resolver, and it unwraps only when the whole property value is a single `$name`. A `$name` inside an expression is looked up by the expression parser as the object itself, so a direct comparison is always false (EXP-34). The `$` keys of a definition and `variables` values go through that resolver into the local scope, so the copy is the unwrapped string (HOST-19, HOST-48). AP's `"$title_text\|default": ""` declaration appears to have the same effect. | measured, code (binary), inferred | Windows 1.26.65.1 | BW-intro, AP 4.1, 2026-11-23 Windows 1.26.65.1, 2026-11-24 Windows 1.26.65.1, 2026-11-24 decompilation |

| FILE-39 | Name siblings in the same `controls` array differently (the name before `@`). There are reports that from a version around April 2025 duplicate names cause JSON UI errors (StarLibV2 1.0.3.3), and none of the 5,084 `controls` arrays of vanilla 1.26.50 has a duplicate. Split a common name like `padding` into `padding_top` and `padding_bottom`. On Windows 1.26.65.1 the reported error does not occur. Two `dup` siblings in one `controls` array and two `re9dup@re9.tl` in the HUD were all created and shown side by side, and the Content Log had no line about that name ([claim measurements](../../design/json-ui-claims.mdx)). The code agrees: building controls walks the `controls` array in order and only appends each child to the parent's child list without comparing names, and the executable has no message reporting a duplicate JSON UI control name. A name lookup picks only the first sibling. So the second sibling of a duplicate name becomes an ordinary control the button does not handle. With two siblings named `default_control` (`CD_A`, `CD_B` in that order) on a button in the HUD and on the chat screen, both are shown with no input; when the mouse is over the chat screen button, only `CD_A`, first in the array, is hidden and the hover control `re9ch` is shown, while `CD_B` stays shown regardless of the button state. | FILE-40 | A `\uXXXX` escape in keys and string values is decoded into the original character when read. The small pack escape tool (JSON-Escape) writes a character outside the BMP as a five-digit escape, which breaks the character. A character outside the BMP must be written as a surrogate pair. Not checked: whether a definition that writes the `"type"` key and the `"label"` value with `\u` escapes works, and whether a label that writes an emoji outside the BMP as a surrogate pair is drawn. | code (source), unverified | - | JEN, SP |
