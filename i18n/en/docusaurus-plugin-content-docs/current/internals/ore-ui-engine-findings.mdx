Ore UI is a React-based web UI that runs on Coherent Gameface. Settings, the world list, loading, the death screen, some in-game screens and script forms (DDUI) are on this side. Unlike JSON UI, its layout cannot be changed with a resource pack's JSON, so "can it really not be changed with a resource pack" has been a long-standing question. This page is the result of reading the client binary to confirm **how a file request looks up packs**, **which packs are trusted**, **the bridge by which JSON UI button definitions pass to Ore UI**, **the DDUI data channel**, and **`geo-item://` icon resolution**.


All verification levels are `code`. It was read from compiled output, so it does not guarantee game behavior, and if it differs from in-game measurement, follow the measurement. The analyzed build is Android 1.26.52.3 arm64. Binary details such as addresses and internal function and class names are not published on the site and are kept separately in the repository's `native-notes/`. The analyzed code is not included, and only the behavior is rewritten in English.

Each finding is paired with a measurement (`OL`, the Ore UI loading survey) made by sending probe packs from a server (Dragonfly) and checking on Windows 1.26.52. The binary answers "why it happens" and the measurement answers "whether it really happens".

:::caution[Blocked from 26.64]
The route that NB-17 and NB-20 describe (encrypted packs and `content.zipe` packs changing Ore UI files) worked up to 26.63. In 26.64 Mojang blocked resource pack access to Ore UI for a security reason (Source: private research). The analysis on this page records an earlier version, and versions after 26.64 were not analyzed.
:::

## 0. At a glance

- An Ore UI file request (`ui://…`) looks at the **pack stack first**, before the install folder, but only at trusted packs. `hbui/…` in ordinary and server resource packs is not used (NB-17).
- Encrypted pack access strategies are **always trusted**. So a pack the server sends encrypted with any content key, or a local pack with only a 0-byte `content.zipe` in its root, replaced Ore UI files (NB-20). This route worked up to 26.63 and is blocked from 26.64.
- The look of in-game Ore UI buttons comes from two JSON UI definitions (`common_buttons.light_text_button`, `common_buttons.focus_border`) through `vanilla.resourcePackOverrides` (NB-18).
- DDUI layouts (`ddui/root`, `ddui/composition`) are read only from packs that carry the built-in pack marker (NB-19).
- The item icon `geo-item://<name>?width=&height=&id=&bag=` accepts the `#item_id_aux` property bag that the JSON UI item renderer uses (NB-22).

## 1. File requests and pack lookup

### NB-17 An Ore UI file request looks at trusted packs first, and opens from the install folder if there is none

The question was "can Ore UI really not be changed with a resource pack" (2026-10-23 analysis). The whole survey, including measurements, is in (`OL`).

- The engine normalizes the request path to `ui://…` and then finds the file. `../` and `..\` are rejected.
- It walks the pack stack and checks whether the file exists only in packs where the access strategy's trust check is true (reading this check as a trust decision is inferred). If there is none, it opens under `gui/dist/` from the app package file system.
- `hbui/routes.json` and `gui/dist/hbui/fonts` are read only from the install folder.
- A `hbui/…css` put in a server pack was not applied (`OL` measurement).


## 2. Pack access strategies and trust

"Whether a pack is trusted" is decided by the **access strategy class** that reads the pack. The pack UUID and manifest are not looked at.

### NB-20 Encrypted pack access strategies are always trusted

The trust check of NB-17 was examined for each kind of access strategy.

- The Zip pack access strategy is true when the pack is inside the app package or one creation flag is set, and the folder pack access strategy is true only when the pack is inside the app package.
- The encrypted file access strategy, the zipped encrypted files access strategy and the encrypted folder pack access strategy return **always true**.
- The pack UUID and manifest are not looked at. A pack the server sends encrypted with any content key is also trusted and replaces Ore UI files (`OL` chapter 7 measurement).
- For a folder pack, pack creation looks for `content.zipe` when a key provider exists, and if it is there opens it with the encrypted folder pack access strategy. A local pack with only a 0-byte `content.zipe` in its root was also trusted and replaced Ore UI files (`OL` chapter 7 measurement). This check appears to look only at whether the file exists. The pack file type decision does not treat anything under 256 bytes as an encrypted file, but an empty file worked (inferred).
- That flag of a Zip pack is set from an argument when the pack is created. All four places that create Zip packs put 0 into this value, so no pack is trusted through this flag.
- The client looks up the content key only from keys sent by the server, entitlements and the built-in table. It does not look at key files next to the pack or the world db.


## 3. Button definitions passing from JSON UI to Ore UI

### NB-18 `vanilla.resourcePackOverrides`: two JSON UI button definitions pass to Ore UI

- The facet outputs `definitions` and `lastUpdated`. A definition is `identifier`, `control`, `propertyData[]` (`name`, `value`) and `textureData[]` (`identifier`, `path`, `sliceSize`, `uvSize`, `uvScale`).
- The definitions the engine resolves are two hardcoded ones: `common_buttons.light_text_button` (texture `$new_ui_button_texture`, properties `$text_color` and `$border_color`) and `common_buttons.focus_border` (texture `texture`).
- The in-game bundle turns this into per-state `border-image` (`pack://<path>.png?filtering=point`), `color` and `filter` of the primary and secondary buttons. It was confirmed that a server pack changes the Ore UI death screen buttons (`OL` measurement).


## 4. DDUI

DDUI (the `CustomForm` family of `@minecraft/server-ui`) is the way Ore UI draws forms made by scripts. The layout loader and the data channel are as follows.

### NB-19 DDUI layouts are read only from built-in packs

- The engine reads `ddui/root` (`minecraft:ui-root`) and `ddui/composition` (`minecraft:ui-composition`) from the pack stack and keeps the pack UUID as `sourcePackId`.
- Only packs where one of two bool markers of the pack object is true are read. The same two markers decide whether the `minecraft:` namespace is allowed in the POI loader (if both are false, `Cannot use minecraft namespace found %s`). So these values are treated as the built-in pack marker (inferred). DDUI layouts of user packs are not read. It was not measured.

### NB-21 The DDUI data channel and the in-game Ore UI switch

- The in-game bundle reads DDUI data with the engine queries `vanilla.ddui.string/number/bool/object/objectArray` (arguments: store, property, path). Writing is the command group `vanillaDduiDataStoreSetCommandGroup` (`setDataStorePathString/Number/Bool`, `dataStoreButtonPress`, `dataStoreCloseButtonPress`). Injected JS can use the same things with `engine.trigger("query:subscribe/<name>", id, …)` and `window.__commands__` (`OL` chapter 9 measurement).
- The binary has types for these queries, the command group, and the client and server sync of the data store. The packet `ClientboundDataStorePacket` is defined as a cereal schema, and its content is one of three kinds: update, change or removal.
- The item icon is `geo-item://<name>?width=&height=` (`OL` chapter 10 measurement). Resolution is in NB-22.
- The property `devOreUIGameplayUI` of `vanilla.screenSpecificOptions` is true when one client option is the integer 1 (1 on, 2 off). The two other places that read this option first check the global settings object and then check whether the option is 1. One of them also checks whether the screen number passed as an argument falls in a bit mask (it appears to be a per-screen-kind allowance table, inferred). The place that registers the option could not be read.
- The feature toggle table registers (number, flighting key, name, default). `mc-enable-sdl-inventory`/`enableSDLInventoryPage` is one of them and is off by default.


## 5. The item icon `geo-item://`

### NB-22 `geo-item://` accepts the property bag of the JSON UI item renderer

- The `geo-item://` scheme is registered together with `https://` and `paperdoll://`, and `geo-item://` and `paperdoll://` share the same handler, told apart by one flag.
- The handler passes the URL string of the request to an item resource resolve step.
- The resolve step takes the URL host as the item name. It reads the query keys `width`, `height`, `id` (integer) and `bag` (a JSON value after URL decoding). The default size is 50.
- The step that creates the item handle finds the name in the item registry and returns an empty handle if there is none. If there is one, it creates an item instance and puts its id and aux value into `#item_id_aux` of the property bag. But **if the property bag already has `#item_id_aux`, it does not put it in**. So the `#item_id_aux` given through `bag` becomes the item to be drawn. Custom items and blocks are drawn too (`OL` chapter 10 measurement).
