# VV settings files

## Concept: settings files and keyframes

Vibrant Visuals sets the mood with the pack's JSON settings files. If texture sets define the surfaces of individual blocks and entities, lighting and effects are defined by per-folder JSON (`atmospherics`, `color_grading`, `lighting`, `fog`, `water` and so on) and keyframes. For values that change with the time of day, use the **keyframe** syntax. The key is a number from 0 (noon) to 1 (the next noon, 24 hours later) representing the time of day, and the value is the parameter value to change by keyframe. When keyframes are given, the engine linearly interpolates between values according to in-game time (Source: ms-learn, Key Frame JSON Syntax).

```json
{
  "format_version": "1.21.40",
  "minecraft:lighting_settings": {
    "description": { "identifier": "my_pack:default_lighting" },
    "directional_lights": {
      "sun": {
        "illuminance": { "0.0": 100000.0, "0.25": 20000.0, "0.35": 400.0, "0.5": 1.0, "0.65": 400.0 },
        "color": [255.0, 255.0, 255.0, 255.0]
      },
      "moon": { "illuminance": 0.27, "color": [255.0, 255.0, 255.0, 255.0] },
      "orbital_offset_degrees": 0.0
    },
    "emissive": { "desaturation": 0.1 },
    "ambient": { "illuminance": 0.02, "color": "#ffffffff" }
  }
}
```

The above is a shortened MS Learn example (noon 0.0, sunset 0.25, midnight 0.5). But the `illuminance` 100000 (lux) in this example is a value reported by the community as a "documentation error", and in practice it accepts only small floats (see the lighting section below). The rules below were gathered from the community research (Source: private research).

## Client biomes and linking settings files

- **Per-biome files**: water, color_grading, atmosphere and lighting settings are biome based. The client biome JSON references the identifiers of the color grading, lighting and atmosphere files. The "default" biome file has no effect, so each biome needs a file (for example `plains.client_biome.json`). To make all biomes look like one you like, change each client biome's identifiers to those settings. A wrong biome identifier gives no error, so check the content log.
- **Overriding global defaults**: Override all-biome defaults with `minecraft:` namespace identifiers (`minecraft:default_water`, `minecraft:default_color_grading`). The lighting default cannot be overridden this way. A pack with only `color_grading/color_grading.json` changed only the tone mapper, so per-biome assignment seemed necessary.
- **Referencing lighting files**: If there is only one lighting json of each kind, you do not need to reference it per biome, and per-dimension files are referenced in `client_biome.json`. There is a case where `orbital_offset_degrees` worked only when every referenced lighting file was complete and consistent.
- **Sun angle reset in the swamp biome**: The vanilla swamp (and mangrove, mesa) has its own lighting identifier and sun position, so it resets the sun angle. Copy that biome's `client_biome` file from the Microsoft samples biomes folder and change its lighting identifier to your settings, and the global angle applies. When testing, restart the whole game.
- **Per-biome items**: Orbital offset and atmospherics can now be set per biome (previously fixed at 0 everywhere). The client biome decides the water surface color and fog decides the underwater color.
- **Samples**: The starting point for atmosphere/lighting/color grading JSON is `deferred_lighting_starter` in microsoft/minecraft-samples (somewhat old), and the default VV settings in the game install folder (`...\MinecraftForWindows\data\resource_packs\1.21.90`) are the real defaults. bedrock-samples has only textures and no VV settings.

## Color grading and tone mapping

- **JSON structure** (format_version 1.21.90, for example identifier `my_pack:default_color_grading`):

```
minecraft:color_grading_settings
  color_grading
    midtones   {contrast, gamma, offset, saturation, gain}   each [r,g,b]
    highlights {highlights_min, enabled, contrast, gain, gamma, offset, saturation}
    shadows    {shadows_max, enabled, contrast, gain, gamma, offset, saturation}
  temperature  {temperature, type: "color_temperature" or "white_balance"}
  tone_mapping {operator: "hable"}
```

One note (2026-01) wrote the keys in camelCase such as `midtonesMax`, `highlightsMin` and `shadowsMax`, and another note (2026-04) wrote `highlights_min` and `shadows_max`. Check the exact spelling in the samples. `conflicting`
- **Recommended values**: `shadows_max` of about 0.3 (0.3~0.4) is suitable, and 0 burns the screen excessively. `highlights_min` of 12~20 (usually about 20, 16 for catgamer) is suitable, and a low value such as 1 or 4 clamps colors hard and causes banding. Saturation 1.2 is oversaturated, so use 1.04~1.1. A washed-out world starts from saturation 0.35. Adjust midtones, highlights and shadows together, and use RGB rather than hex.
- **Sharp boundaries and banding (blue rings and so on)**: Often caused by split grading with `highlights_min` near 1 or `shadows_max` near 1. Raise `highlights_min` and set `shadows_max` to 0.3~0.4, or bisect by pasting in other packs' settings one at a time, or try changing the tone mapper. The asker confirmed the fix. VV is inherently prone to banding. A blue tint in dark corners was fixed by turning off shadow grading.
- **Temperature direction**: With `color_temperature`, the higher the K, the **cooler** (blackbody style; the sentence in the documentation saying "warmer" is wrong), and with `white_balance`, the higher the K, the warmer. 6500 is widely used as neutral, and cold biomes use a cooler temperature. Tested in the 1.21.120/.130 Preview. `confirmed`
- **Global-only items**: To use `color_temperature`, you must turn on temperature grading in the global (default) color grading and set the type to `color_temperature`. Otherwise per-biome settings are ignored and it falls back to the global white_balance. The tone mapping operator and temperature type apply only globally, and the other grading values apply per biome. Temperature cannot be keyframed, so change the sun and sky colors.
- **Value range limits**: Range limits were added to color grading values (for example saturation -9999 is not allowed). This blocked extreme values used for film negative and infrared looks, for reasons of performance and platform stability. Invalid values silently fall back to default grading.
- **VV tone mappers**: There are `generic` (Mojang custom), `reinhard`, `reinhard_luminance`, `reinhard_luma`, `hable` (= uncharted2), `aces` (a simplified ACES Fitted that avoids licensing, not the complete ACES 1.0). There is no AgX, Lottes or Uchimura, and they cannot be forced by a pack (the tone mapper is inside the VV material and modifying it is unofficial). There is a note that the default tone mapper is generic and a note that it is Reinhard. `conflicting`
- **Tone mapper comparison**:
  - ACES: The only operator that does not blow out even if you raise saturation and contrast a lot in color grading. In exchange, bright reds shift to orange and blues to purple, which bloom softens. For the hue shift on bright emissive objects, there was a recommendation to lower the VV emissive value rather than hide it with grading, because the MER emissive values tuned for RTX are too high. Grading tuned for ACES looks bad on other tone mappers.
  - Reinhard/Hable: Raising saturation makes things mushy or blown out (Hable is fine unless you add saturation). Hable is more filmic, has interesting color reproduction, and blows out less. reinhard_luma is similar to reinhard and reinhard_luminance has a bad reputation. reinhard, reinhard_luma and hable look similar to each other.
  - generic: Because of the "anti-hue shift" behavior, sky banding stands out, dull bands appear in very high-luminance pink areas, and it overwrites fog on red and SSS blocks.
  - Popular packs mostly use hable or aces and also use Reinhard Luma. Cat RTX/Cat Visuals changed from ACES to Hable. One member uses a method of raising contrast and saturation on reinhard to imitate AgX, but most disagree.
- **Cause of sky banding**: For mobile performance, VV renders to a low-precision `R11F_G11F_B10F` buffer instead of RGB16F. Fixing it needs Bayer dithering or higher precision. Hable has almost no banding, Reinhard_luma is similar, and ACES blows out and gives a washed-out feel. Banding when Rayleigh strength is below 10 is often a display or phone problem, so also check in a browser.
- **Reproducing other tone mappers (veka.)**: veka.'s WIP tool converts arbitrary shader tone mapping code into VV color grading settings (optimizing the tone mapper and temperature type for minimum error). The shared `.json` settings are AgX default/punchy, Sildur's Vibrant, Lottes (input x0.5, nearly 1:1), Hejl-Burgess-Dawson (x0.2), the Escheridia Lottes variant (x0.5), Uchimura (needs gamma correction), OpenDRT, Complementary Reimagined, Khronos PBR Neutral, and AceX (ACES 2.0 fitted curve). Most were closest with Reinhard-based settings, and generic was the worst. VV's washed-out feel is due more to lighting than to tone mapping. The comparison method was a custom `ColorPostProcessing.material.bin` that applies the custom tone map to half the screen.
- **Order of exposure and tone mapper**: Exposure and auto exposure are applied before tone mapping, so they are independent of the tone mapper choice. The sun geometry brightness is about 30 in luminance units, and the grading optimization used a range up to 10.
- **Other tips**: To make shadows deeper, adjust the grading `gain` and `gamma`. "Total darkness" (almost black with no light source) needs a contrast adjustment, and midtones alone are not enough. Avoid extreme contrast or very deep shadows. Sharp god rays do not need such values either.

## Auto exposure

- **Location**: Auto exposure is controlled by `tone_mapping.json` and `average_luminance.json` in the game's `data/renderer` folder (for example `C:\XboxGames\Minecraft for Windows\Content\data\renderer`). The majority opinion is that it cannot be changed from a resource pack or on mobile and consoles, and it is a common complaint of pack authors. In 2025-12 there was a report that a pack could override `average_luminance.json` and that VV improved greatly when adjusted to keep exposure in bright places while not over-brightening dark places. `conflicting` (the latest report says it is not possible from a pack)
- **Keys**: `min_log_luminance` -3.0, `log_luminance_range` 20.0, `low_percent` 80.0, `high_percent` 100.0, `adaptive_time_coefficient`, `light_adaptation`, `dark_adaptation`. According to quirkyplague's empirical interpretation, the first value is overall exposure (negative, -1.0 darker, -8.0 very bright), the 3rd and 4th are bright/dark area corrections, the last three values are adaptation speeds, and the effect of `log_luminance_range` is unknown. `single report`
- **Status**: The exposure parameters are not public, and Mojang (aajabrams) put publishing tone mapping exposure on the plan board. The rework (after DTP) made auto exposure stronger and dark nights harder to make. "The day looks washed out and the night is too dark" may be because auto exposure does not adapt enough. There is a feedback post requesting a toggle to turn off auto exposure. RTX auto exposure does not include the sky, so the RTX sky is very bright. Auto exposure also ignores fog, so presets with heavy fog (Infectious) blow out to white.

## Lighting settings and keyframes

- **Structure**: `minecraft:lighting_settings` (format 1.21.80): `directional_lights.orbital.sun` and `.moon` (each `illuminance`, `color`), `orbital_offset_degrees`, `directional_lights.flash` (`illuminance`, `color`), `emissive.desaturation`, `ambient` (`illuminance`, `color`), `sky.intensity`. `orbital_offset_degrees` (the sun angle) is in `lighting/global.json`, has a default of 0 and may be omitted. `emissive.desaturation` is a setting that reduces the saturation of emission.
- **Keyframe range**: The time of day is 0.0~1.0, with 0.75~1.0 from sunrise to noon and 0.0~0.25 from noon to sunset. If the value is constant, the keyframe map can be omitted, and if you use keyframes, define at least 0.0 and 1.0. The End has no time so keyframe 0.0 effectively applies. The conversion from time to keyframe is as follows.

```
ang = fract(timeOfDay / 24000.0 - 0.25);
ang = ang + (cos(ang * PI) * -0.5 + 0.5 - ang) / 3.0;
```

Multiplying the result by 360 (degrees) or 2*PI (radians) gives the sun angle. Useful `/time set` values are 0 (6:30), 1000 day, 6000 noon, 11000 sunset transition, 12000/12500 dusk, 13500 night, 18000 midnight.
- **"expected keyframes" error**: An unhelpful message, but it actually means a value was out of range. The orbital `illuminance` accepts only small floats (about 0.0~100.0), not the lux values of the documentation example (120000 and so on) (the documentation error was reported to Mojang on 2025-11-20). A negative offset (-23.5) also gave this error. There is also a guess that lighting.json values below 1 or above 20 cause render-corruption artifacts. `confirmed`
- **sky intensity**: A keyframeable skylight intensity was added to the Preview around 2026-01-08 (for example golden hour at 23500, bright at noon, dark shadows and clouds at night, moon illuminance 1~3). Example: `"sky": {"intensity": {"0.000000":0.85,"0.190000":0.55,"0.215000":0.2,"0.230000":0.1, ..., "0.827000":0.55}}`. The maximum is 1. Below 1, both sky and water reflections decrease and water gets an oily, white feel (solved with `"sky": {"intensity": 1}`). Since the 2026-04-30 Preview there are fog/lighting keyframes, so adjust by time of day. A suggested value is 0.4 (Nether 0.1~0.4), and before keyframes a dark night needed 0.2. It is a trade-off between reflections and a dark night.
- **skylight color and ambient**: The skylight color comes from the client biome's `sky_color`, not the `sky` field of the lighting file. Ambient was deliberately not made keyframeable (caves would darken with time and there is no general cave biome to override). Because ambient skylight is proportional to the sun illuminance, previously you could not darken the night without darkening the day.
- **Dark caves and real darkness**: VV has no brightness control by light level. The only means is the ambient in the lighting folder (intensity and color 0), but the night also gets slightly darker. Java's "hardcore darkness" (black at light level 0) cannot be done with textures.
- **"No global lighting" approximation**: Set the sun and moon colors to a very small nonzero value and raise skylight. Shadows cannot be removed completely, and the sun is imitated with particles.
- **Negative sun angle**: Possible with keyframes but unstable: `"orbital_offset_degrees": {"0.000001": 359, "0.000000": 0.0, "0.215000": 325.0, "0.500000": 325.0, "0.70000": 45.0}`. The sun's tilt is moved with the orbital offset, and rotating the sun texture itself requires baking the rotation into a high-resolution texture. Changing the sun and moon orbits usually does not affect the sky itself.
- **End/Nether**: In the End, `sun_mie_strength` has no visible effect and sun and moon illuminance do not brighten the End sky but do affect the Nether. There is a report (2026-01) that End flash light can be set with `directional_lights.flash`, and a report (2025-12) that in format 1.21.80 the flash luminance and color in `lighting/global.json` did not work and that there is no pack toggle to turn off the End flash. The End skylight seems to be hard-coded as flat white/gray lighting.

## Atmosphere and sky

- **Structure**: `minecraft:atmosphere_settings` (format 1.21.40): `description.identifier`, `sky_zenith_color`, `sky_horizon_color` ([r,g,b] at keyframes "0.0"~"1.0"), `horizon_blend_stops` (`min`, `start`, `mie_start`, `max`), `rayleigh_strength`, `sun_mie_strength`, `moon_mie_strength`, `sun_glare_shape`. The sky color comes from the per-time atmosphere settings and not from the air/fog color. The JSON key is `atmospherics` (not `atmospherics_configuration`). Turn off cloud lighting with `"cloud_lighting_enabled": false`.
- **atmospherics errors**: With no format version in `atmospherics.json` it gave "[Lighting][error] no valid version", and with one it gave "[Rendering][error] Identifier already exists in resource pack" (unresolved).
- **Blown-out white daytime sky**: Lower the Rayleigh strength and keep the atmosphere colors away from white. Experienced creators keep Rayleigh mostly under 1.0 and at most 1.2. A beginner's problem was solved immediately. Desaturating and darkening the sky reveals the yellow sunlight. Any fog fades a saturated blue sky.
- **Sharp straight lines in the sky**: Caused by horizon blending, not the sun and moon angle. `mie_start` is computed relative to `horizon_blend_stops.min`. If mie_start is much lower than min, mie scattering sticks to the sun position, if it is close to min it is fixed toward the horizon, and if it is larger than min it stays at the horizon and then curves up toward the sun. If the values are too close, artifacts appear, and if horizon min/max are too close, the horizon-zenith gradient disappears. Another member found the cause in `moon_mie_strength`. It was visible in Editor mode and disappeared after reloading the world.
- **Fog does not cover the sky**: Make the client biome's `sky_color` the same as the fog color or modify the atmosphere (linked through the client biome component).
- **Custom sky color**: Reference `minecraft:atmosphere_settings` (`sky_zenith_color`, `sky_horizon_color`, `horizon_blend_stops`, `rayleigh_strength`) from the client biome's `minecraft:atmosphere_identifier`. It is VV only, and the non-VV sky color is decided by the fog definition. The problem of a yellow sky looking greenish was fixed with `rayleigh_strength` 1. In 2026-11 there was also an answer that the sky color is changed with a new `atmospherics` file at the pack root or a cubemap (`single report`).
- **Script Atmospherics API**: It exists separately in the server-graphics beta (`Atmospherics.setSkyHorizonColor`). The graphics module lets script change things like the moon color, but it is VV only and runtime texture swapping is not supported. Whether VV is on can be detected from script.
- **Clouds**: VV clouds are hard-coded, thin, do not support transparency, and do not follow the sky color. 3D clouds cannot be made without a custom shader. One creator used a 512x512 Perlin noise cloud texture. If the vanilla VV cloud shadows are too large, blur them with the shadow settings (Gaussian blur).
- **Sun and moon textures**: The default VV sun and moon have a pixelated glow and get an outline. It is solved with a large, soft texture but the resolution must be high. The cause of the "squircle" sun not updating was an old pack left in the regular `resource_packs` folder, so develop in `development_resource_packs`. Even if you empty the sun texture, the vanilla sun glow is an engine shader and remains, so to replace the sun completely you must rebuild the sky with particles.

## Water

- **Water settings**: The water settings file (`biome_water_color_contribution`, Microsoft Learn watercustomization) is on the VV side and the fog file is on the RTX side. The two cannot be merged. The water settings mix the biome water color of client_biome and the VV particle concentration, need a Preview newer than 1.21.120, and have their own `format_version`. Vanilla `water.json` (1.21.120) does not use the biome water color contribution, so it is effectively swimming pool water. Turning on `biome_water_color_contribution` in swamps and mushroom fields made the water black (a bug).
- **Underwater fog density**: It is not set in the fog file but decided by the particle concentration (chlorophyll/CDOM) in the water settings. Even 0 hardly changes it (VV underwater fog is thick by nature). It cannot be lowered with the old parameters and the only way is to turn off fog in the settings. The water fog entry of the fog file changes only the underwater light color. Changes to density, scattering and absorption having no effect is presumed to be a bug. The volumetric block light option removes the milky underwater fog.
- **Waves**: Custom waves require `waves->enabled` to be true in `minecraft:default_water`. The `sample width` parameter was removed (around GDK 1.21.12x), waves became smoother, and wave reflections of flowing water were turned off. Odd waves at biome boundaries come from incomplete blending, so the only fix is to give the same water settings to all biomes in that area (all ocean variants) (confirmed). The new `material.bin` `WaterSimulation` in the 2026-08-06 Preview hints at physically based waves and boundary artifact fixes.
- **Reflections and limits**: The VV water reflectivity is decided by the MER roughness (blue) of the texture set. VV SSR works only on water (ice is matte). VV water uses only a sine wave normal map and has no parallax/POM waves (SDGP had them), refraction, SSAO, AA or weather customization. There is no underwater absorption and attenuation, no water distance fog control, and the sharpness of Snell's window is poor. Caustics render only on the top faces of blocks underwater and are based on the player's viewpoint. Water block shadows were removed long ago, and the white shadow artifact on the water surface is an engine bug about 2 years old. In an aquarium the water becomes nearly transparent.
- **Workarounds for water shading bugs**: Making the client_biome sky color black removes the water shading bug but breaks shadows. Sky reflections are not rendered on water that is not directly under the sky (milky). The problem of render distance fog being affected by the sky lightmap was fixed in 1.21.120. VV water renders behind custom material entities, but on Fancy it does not. Overriding vanilla water with a material works only outside VV.
- **Hiding water inside a boat**: Hiding vanilla water with a material works only on Fancy. Under VV `DisableColorWrite` is broken and water is a separate pass so it is probably impossible. A partial workaround is a transparent material drawn over the water (the water in front of the player remains). There is a report (2026-05) that a blend transparent plane over the boat worked and a test (2026-09) that it did not. `conflicting`
- **Look underwater**: The look underwater is a combination of fog and a blend material water surface, so there is no single material to copy. The 2026-11 complaints about VV water were seeing through fog, broken transparency handling, no biome color, and the Series S reflection not fixed.
- **Thin lines on water (PBR packs)**: A Mojang bug. The workaround is to define the still water flipbook as 3 atlas tiles (`a_still_water_grey_1` to `3` from `textures/blocks/water_still_grey_left`, `water_still_grey`, `water_still_grey_right`, with the first and last being exact copies) in `flipbook_textures.json` (`ticks_per_frame: 2`) and `terrain_texture.json`, or use the vanilla water texture, or adjust the resolution.
- **Lava**: Lava cannot have smooth flow animation like custom VV water (a retexture is needed) and has no default emissive value.

## Shadows

- **Resolution and texel_size**: The VV shadow map is always fixed at 2048 and cannot be raised. The `texel_size` of `minecraft:shadow_settings` (`shadow_style`: `blocky_shadows`/`soft_shadows`) is not the resolution but only the pixel grid that blocky shadows and reflections snap to (maximum 1024) and does not change performance. The claim that a 1024 setting is unstable and 512 is stable was refuted. `confirmed` (the resolution part)
- **Where settings are**: Shadow settings are in game files (`<install>/data/render(er)`, shadow config, LODs, for example PC ultra), so they cannot be changed by a resource pack and can be changed locally on one PC only (Android by extracting the APK, which did not work for one user). Lowering `cascade_pcf_width` to 2~3 makes soft shadows sharper. Lowering the cascade bias reduces peter-panning but creates acne. For shadow acne after an update, a custom `shadow_configuration.pc.json` (Windows, shadow quality Ultra) was shared.
- **Cascade behavior**: Mojang's first cascade is the softest and gets sharper with distance (the opposite of the usual way). Because of the PCF width, "ultra" looks blurrier than "high". Ultra uses 2048 and a wide PCF on all cascades, so it is soft but mushy, and Medium loses quality quickly with distance and has a weak PCF. The shadow range is 128 blocks and there is no PCSS (PCSS gives variable penumbra but costs about 15%, bad for mobile). VV uses a PCF shadow map that smooths uniformly and peter-panning from shadow bias, while RTX uses ray-traced shadows that soften with distance.
- **Maximum shadow distance**: It is in the game file `renderer\platform_config\pc\shadow_configuration.pc.json` and defaults to 128. There is a case where edits reverted to 128 on every launch (unresolved). At render distance 48 chunks, VV shadows are drawn only up to about 8~12 chunks.
- **Pixel-precise geometry**: Vanilla VV does not draw shadows consistently on pixel-precise geometry such as sign posts, so there is advice to round pixel sizes. `single report`
- **Performance**: `soft_shadows` (PCF penumbra) cuts FPS by about 30% when seen through glass (an FPS drop bug when looking at a glass aquarium 2025-12-03). FPS also drops when looking at large water.
- **First-person shadow**: First-person player shadow quality is a VV problem. Custom player geometry with large visible bounds (for example Actions & Stuff) makes the player small in the shadow map and blurs first-person soft shadows (solved by turning off the custom geo).
- **Transparent objects**: Deferred rendering cannot handle transparent objects such as glass, water, ice, leaves and hair properly, so Mojang mixes forward rendering for transparents. A transparent custom block between the sun and the ground hardly makes VV shadows, and only fully opaque textures block VV sunlight. Colored glass shadows are unsupported and unlikely (colored shadows only for water). Alpha test and opaque particles cast shadows.
- **Block shadow and AO limits**: VV lighting behaves like vanilla lighting, so there is no real occlusion shadow cast by blocks. Occlusion shadows need ray tracing or point lights, and SSAO/GTAO are only approximations. Vanilla AO is applied after lighting under VV (treated like albedo) and darkens sunlight at block edges, and it should originally be applied before lighting. VV has no SSAO.
- **Entities and shadows**: Under VV you cannot stop shadows from being cast on entities (possible in non-VV). To turn off an entity's shadow interaction, use a `DisableDepthWrite` material, but the draw order of intersecting geometry can break. Flat vanilla items render no shadow.
- **Light-leak band-aid**: AO and lightmap based skylight attenuation reduced ground skylight too much in the Preview. The shadow distance setting affects shadow artifacts.

## Reflections (SSR, IBL)

- **SSR behavior**: SSR uses a Hi-Z buffer, renders at half resolution, mips, upscales and snaps to a pixel grid (the reason VV reflections look pixelated; "disabled pixelation" only snaps to a 1024 grid). The resolution is about 50% of the screen multiplied by the TAAU scale and gets lower with distance. It is screen space, so reflections vanish at the screen edges (a separate reflection FOV was proposed).
- **Getting smooth reflections back**: Raising `texel_size` in `shadows.json` to about 1024 and using soft shadows makes reflections look high-resolution (Prizma's method). Some users still saw pixel snapping.
- **Roughness ignored**: VV reflections are always mirror-like regardless of roughness (only the specular changes) and support only perfect mirrors. There are no rough reflections because they need denoising, and true mirrors and first-person player reflections are impossible. Planar reflections other than water are expensive and unrealistic. A high-resolution random-direction normal map (192x192) is used to imitate rough reflections.
- **Sky and cloud reflections**: A baked cubemap (IBL) effectively updated only about every 5 seconds, an intentional performance trade-off.
- **Nether metals**: Nether metals reflect the sky even though there is a ceiling. Making the atmosphere sky color black and changing sky intensity did not remove it, and only ambient affected lighting. For the IBL fade, see `start_ibl_fade_light_level` and `end_ibl_fade_light_level` below.
- **Consoles and platforms**: Reflection `linear_search_step_count` needs about 200 (a maximum of 100 on Series S, 200 on PS4, with 250~300 also suggested). Console "ultra" reflections equal PC "medium" and Series S reflections are worse than PS4 (MCPE-230030). Per-platform `reflection_configuration.console_2.<quality>.json` were merged into one. Android has blurry and limited reflections because of hardware and RAM. The color precision setting in the reflection settings json is presumed to affect only IBL (`unverified`).

## deferred_shading_parameters and internal game settings files

- **`deferred_shading_parameters`** (all numbers): `block_light_indirect_contribution_multiplier` (static light brightness), `sky_light_indirect_contribution_multiplier` (ambient sky light), `ibl_indirect_contribution_multiplier` (sky reflection), `volumetric_fog_min_ambient_value` (fog lighting in complete darkness), `emissive_brightness_multiplier` (PBR emissive), `end_portal_emissive_multiplier`, `start_ibl_fade_light_level` (15) and `end_ibl_fade_light_level` (12) (the light levels where sky reflection starts and finishes fading).
- **`transitioning_ambient_scalar`** (2026-09-22 Preview): Scales the indirect and block light contribution while point lights are active. The default is 0.65, and at 0 it behaves as if tinted glass blocks block light. The community prefers 0.3~0.5. According to Mojang, the direct and indirect light terms are separated and change in stages, and existing block light has linear attenuation while point lights have realistic attenuation.
- **Game install folder settings**: In `C:/XboxGames/Minecraft For Windows/Content/data/renderer/` (XboxGames, not WindowsApps). `platform_configs/pc` has quality and performance settings (`render_distance_configuration`, shadows, reflections, volumetric fog, clouds), and materials are in `.../renderer/materials`. Back up the originals. If one comma is missing in a list such as `[2, 4, 6, 8, 64]`, it silently breaks. This editing cannot be done with a resource pack.
- **Other values**: `deferred_lighting_configuration.shared.json` has `optimize_gamma_correction` and local exposure entries (see the next section).

## Cubemaps, HDR, main menu panorama

- **Cubemaps**: Put the VV cubemap JSON in the resource pack's `cubemaps/<name>.json` and reference 6 cubemap PNGs. The VV custom skybox behaves like vanilla (no entity needed) and there are cubemap parameters that affect fog and lighting. HDRIs must be converted to a 6-face cubemap, and the new exposure parameters made HDRIs usable. A custom cubemap covers the sun and weather, and there is no way to draw the sun over it.
- **`.hdr` textures**: Supported everywhere in Bedrock (first added for the VV HDR main menu cubemap; a vanilla example is `textures/ui/panoramahdr_0.hdr` in bedrock-samples). It can hold values above 1.0, so using it as albedo gives a fake glow that reflects more than it received (affects only bloom, not light in the dark). It can cause bloom on entities and attachables (and probably items). It can be exported with Photoshop/GIMP. HDR PNG (cICP/cLLi chunks) is also a valid PNG feature. `.hdr` images are not allowed on the Marketplace.
- **HDR cubemap capture (veka workflow, 2026-06-07)**:
  1. Prepare Python: `pip.exe install numpy pillow` (without commas, in cmd). The script attached to the thread crops to a square, inverse tone maps, optionally downscales, scales the brightness, and outputs a lossless-compressed `.hdr`.
  2. In `C:\XboxGames\Minecraft for Windows\Content\data\renderer\tone_mapping.json`, set `min_luminance` and `max_luminance` to the same value (about 1 at night, about 4 in the day, negative is also possible) and match `LUMINANCE_EV100` in the script.
  3. Turn off bloom, display brightness 100% (reset to default), apply the provided color grading (replace everything in the VV pack), `/effect @s invisibility infinite 1 true`, FOV 90 (`/camera @s fov_set 90`), full screen with no UI.
  4. Start with `/camera @s set minecraft:free pos ~~1.62~ rot 0 0`, take 6 shots at yaw 90, 180, 270, then `rot -90 0` and `rot 90 0`, as `panoramahdr_0` to `5`.
  - Limit: local exposure still affects brightness and 8-bit screenshots get banding.
  - Improvement (2026-09-05): Setting `optimize_gamma_correction` and local exposure to false in `deferred_lighting_configuration.shared.json` and `low_percent` and `high_percent` both to 80.0 in `average_luminance.json` removes the color seams. Panoramas should not break with updates, and a non-VV panorama needs only the same procedure with a square crop. There is a report that custom panoramas broke in v26.52.

## Upscaling, quality, performance

- **Upscaling**: VV has only TAA and bilinear. TAAU became blurrier since 1.21.80 (CAS was requested) and is still blurrier than a few years ago. Bilinear is cheaper than TAAU and sharper for some. Mojang fixed the TAA jitter bug in the 2026-05-12 Preview. There is a case where ReShade FXAA at native resolution was used as an alternative. TAAU creates inverted and stretched artifacts in the End sky and wrong star colors (bilinear is fine).
- **Render scale**: The VV render scale and rescale settings multiply (50% x 0.33 gives a very low internal resolution, and volumetric fog is half of that). Consoles have lower reflection settings than PC and a lower render distance cap, and the resolution slider only shrinks. VV limits the render distance (for example vanilla 96 versus VV 28).
- **VSync**: It is not exposed in VV, so set `gfx_vsync` to 0 in `options.txt` (`%appdata%/minecraftbedrock/users/<id>/games/com.mojang`, also the `minecraftpe` subfolder). There is a case where turning it off improved VV FPS, and VSync greatly lowers performance especially in ray tracing. VV performance is irregular (fluctuating 90~180 FPS).
- **Phone tips**: Hiding the hand, not holding transparent items, bilinear filtering instead of anisotropic, and a render scale of 20~33% were recommended. `single report`
- **Linux**: With wine vkd3d it crashed when the render distance exceeded 40 chunks, and VV high was about 160 fps.
- **Transparency cost**: Deferred rendering is very slow at transparency. In a test, the GPU time of rain particles was 1.6 ms without VV and over 20 ms with VV (5 ms with VV and no rain). Avoid transparent materials and reduce screen size and overlap. For example, halve the particle count and double the opacity, and it is better to use several small particles that are visible one lump at a time than large particles with lots of empty space. Under VV, using **more** small particles can be better.
- **Other bugs**: Around 26.0, the mobile "DX11 fallback" render corruption is fixed by leaving full screen, quitting the game, relaunching, and going full screen. UI and texture corruption in the Preview (no crosshair, wrong textures) was a sync bug mitigated in 26.20.21, and the workaround was a frame limit. On 2026-01-27, raster overlays such as first-person fire changed from linear RGB (banding) to sRGB.
